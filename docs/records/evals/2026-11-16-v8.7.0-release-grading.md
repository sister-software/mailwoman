# v8.7.0 release grading against model 10.8.0

Status: **not eligible**. Release spec v8 returns `fail` for the candidate as staged with the card the run requires
(`requires.anchor.span_mode: "postal"`), on both frozen collections. The cause is serving code rather than the trained
weights: under a `postal` card, the post-decode postcode repair reads the `postal` family of `@mailwoman/postcode`, and
that family widens postcode spans over state codes, country prefixes and locality words (section 2). The same weights
under a `shaped` card pass every spec v8 minimum they have rows for and pass the objective on the development
collection. That arm is a diagnosis. The release candidate is the `postal`-card arm, because the run trained under
`anchor_paint_mode: postal`.

The run: `packages/corpus/data/training-configs/v8.7.0-base-c6-90k-usgs-structures-s42.yaml`, from scratch, 90,000
steps, seed 42, Modal run key `74eaf854986e4211` (exit 0), corpus `v0.8.19-retention-overlay`. The control run is
v8.6.3 seed 42, shipped as 10.8.0. A from-scratch run has no placebo leg. Final validation reported by the run:
val_loss 0.8630, macro F1 0.8808 over 22,210 val rows.

Every number below was produced in the worktree of branch `lane-u-grade-v870` at `origin/main` `9800c749e7`, from its
compiled tree, because the `mwdev_*` worker can't start in the main checkout. Each section states the tool that produced its numbers.

## 2. The cause: the postcode repair under a `postal` card

Observed on `Alameda, CA 94501` with `buildGauntletDeps(...).diagnoseParse`: the anchor features, the per-token model
confidences and the Viterbi path are identical for 10.8.0's weights under a `shaped` card and under a `postal` card.
`CA` decodes as `B-region` in both. The difference is one post-decode pass,
`repairs: [{pass: "postcodeRepair", before: [… "B-region", "B-postcode" …], after: [… "B-postcode", "I-postcode" …]}]`.

`repairPostcodeLabels` (`packages/neural/lib/postcode/repair.ts`) reads `collectPostalMatches` when the card declares
`postal`, which calls `findPostcodeSpans` and `disjointSpans`. For `Alameda, CA 94501` that returns
`{"kind":"postal.so","form":"alnum","start":9,"end":17,"countries":["SO"]}`: Somalia's shape matches `CA 94501`,
because every shape of the family matches either case, and it outranks the five-digit span. The repair applies a
match with no country restriction, and as `alnum` it may add a postcode over admin labels. The frozen table returns
only `94501:numeric` for the same text. For `S(088903)` the frozen table returns `designated`, which may write a
postcode over any label, and the family returns `numeric`, which can only snap an existing one, so SG loses the
postcode the model never labeled.

This is inference code that pull request 3101 introduced for the `postal` span mode, and it isn't the
training-to-serving anchor agreement the handoff measured. That measurement compared anchor spans. The anchor spans
are equal here too. The trained weights don't change it: 10.8.0's weights show the identical 191 board regressions under a
`postal` card.

### 9.1 The cause and the fix

| Input                                                      | Labels before the repair  | `postal` repair before the fix | Mechanism                                                                                        |
| ---------------------------------------------------------- | ------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------ |
