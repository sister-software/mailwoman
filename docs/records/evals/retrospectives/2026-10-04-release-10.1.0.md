# Release 10.1.0: postmortem

## Summary

Release 10.1.0 promoted the v7.2.0 address-system model: an address-system head over 39 systems and a
`locale_hint` graph input, trained from scratch on corpus `v0.7.2-address-systems`. It reached npm and
the demo, but the path from the graded model to a working install took eight PRs, four publish
dispatches and a demo hotfix. The timeline records an uninstallable release from 22:33 until it
resolved by 23:55 UTC, a window of at most 82 minutes between those observations.
`npm install mailwoman` could not resolve: `mailwoman@10.1.0` was live while the
`@mailwoman/neural-weights-en-us@10.1.0` it pins was not.

The publication failures below concern release tooling, the runtime interface for a new graph input,
release documentation, and the demo's caching. The model also shipped accepted regressions, recorded
separately below.

Times are UTC on 2026-10-03 unless marked.

## The decision to ship

**Decided:** the operator accepted an exception to the D-rule, which requires default-on model changes
to preserve tier-1 locale results. `mwdev_arc` on the
1,226-row regression board read 274 improved and 57 regressed against 9.1.0. Subtracting the 57
regressions from the 274 improvements gives a net increase of 217 rows. The self-control differed on
0 of 1,226 rows. The candidate regressed 2 FR, 2 GB and 6 US rows, and the promotion check `v9.0.0-base` missed one floor
(`us.region` 88.9 against 89.4). Russia's held-out test rows went from 682 of 1,963 exact to 1,959 of
1,964. #2439 lists every accepted regression with both parses. The decision is recorded here so the
regressions are not mistaken for a release defect.

**Unknown:** why the Russian held-out comparison has different denominators. A comparison of the
shared rows is needed before attributing the difference entirely to the model. The self-control
establishes reproducibility on this board and comparison path. It does not isolate the address-system
head from the corpus and other training changes in v7.2.0.

## What went wrong

### 1. A new required graph input broke every caller that did not read the model card

**Observed.** The v7.2.0 export added `locale_hint` as a required input. The runtime fed it only when the
classifier carried the card's `address_systems` table, and refused to run when the graph declared the
input and no id was given. Only the two card-reading loaders passed the table. `createScorer`, the
browser loader's warm-up `runner.infer([0])`, the web runner tests and about ten evaluation tools build
the classifier or call the runner directly, and all of them failed. The promotion battery was the first
to show it, as a run that died without grading.

**Cause.** The input had no default the runtime could supply without the card. A first attempt, an ONNX
initializer named `locale_hint` as an overridable default, worked in Python and was silently ignored by
onnxruntime-node, which drops a feed whose name is absent from `inputNames`.

**Change.** The runtime feeds `locale_hint` = −1 when a caller gives none. The exported `Gather` reads −1
as the last row of the hint embedding, which the trainer reserves for "no hint". onnxruntime-node gave
logits identical to id 39, and an export test pins the equality.

### 2. The live-pipeline tests graded the old model until `copy-weights` ran

**Observed.** The gauntlet harness, the conformance suites and the structural-validity test load the
materialized `packages/neural-weights-en-us/model.onnx`. Before `copy-weights`, that file held 9.1.0's
bytes, and the gauntlet's `files_md5` guard refused to run. After it, the same suites graded v7.2.0 and
listed 11 newly invalid board rows, one whitespace variant and one confound row.

**Change.** The runbook now orders `copy-weights` before the root test suite and says to record each
accepted regression in its suite's exemption list with an issue reference.

### 3. The runbook listed 7 of the 18 files the CI weights fetch requires

**Observed.** The Hugging Face upload followed the runbook's file list, and `fetch-hf-weights` then
reported 11 files missing: the de-de, es-es and it-it FSTs, the street-morphology FST, six pair indexes
and the GB postcode table. The Fisher artifact was also missing from the list.

**Change.** The runbook gives the full 10.1.0 set and makes the fetch itself the check:
`yarn mwops release fetch-hf-weights --into <scratch>` must exit 0 before dispatch.

### 4. The first upload shipped gazetteer data no release had published

**Observed.** `copy-weights` materializes FSTs and pair indexes from the data root. The data root held
an FST rebuild from 2026-08-24 and pair indexes 16 bytes longer than 9.1.0's. A size comparison against
`en-us/v9.1.0/` caught it after upload, and the 9.1.0 bytes replaced them before publish.

**Cause.** The runbook said to reuse the previous release's FST. The tooling read the data-root copy
without comparing its contents with the previous release.

**Change at release.** The runbook said to upload the previous release's FSTs and pair indexes and
compare their sizes. The follow-up in #2453 requires content hashes for every reused artifact.
Equal sizes cannot establish that two files contain the same bytes.

### 5. The metadata check was undocumented

**Observed.** `verify-release-metadata` requires the eval ledger, the release matrix and the status page
to name the model version. The runbook named none of them, so the first dry run stopped there.

**Change.** The runbook has a step for the three surfaces and runs `verify-metadata` locally first.

### 6. The dry run never reached the tarball check

**Observed.** The dry run stopped at the metadata check, before packing. After the metadata fix, the
next dispatch was the real one, so `verify-tarball` first ran during the real publish. It refused the
nine Latin weights packages: each carried an `imports` map pointing at `./out/*`, which these data-only
packages never build. #2405 made `verify-tarball` require every `imports` pattern to match a shipped file
after 10.0.0 had published with the same map. The runtime packages had already published, so
`mailwoman@10.1.0` pinned a weights version that did not exist.

**Change at release.** #2446 removed the map. The dry-run preflight already packs and audits every
release workspace. The follow-up in #2453 runs that preflight in real publish mode too, before
creating a tag, a GitHub release or publishing a package. The runbook requires a complete publish
dry run after a correction. A prepare dry run does not establish that the tarballs pass.

**Remaining limitation.** Publication packs the workspaces again. Binding publication to the audited
tarballs and coordinating registry defaults remain follow-up work under #1894.

### 7. npm held five versions for up to an hour after upload

**Observed.** npm accepted every upload with `Your package is being processed and may take a few
minutes to become available.` Five versions stayed at 404 for about an hour: `sentencepiece-wasm` from its
22:33 upload to about 23:35, and the four weights packages from about 22:57 to some time before 23:55.
All five then resolved without intervention. During processing, `npm stage list` returned an empty list and npm refused a re-upload with
E409.

**What I got wrong.** I escalated this as an npm-side fault and proposed contacting support and
publishing 10.1.1. The operator read it correctly as packages going live at a steady pace. The
lesson: distinguish an accepted upload from a retrievable package and a successful clean install.
After an E409 on an accepted upload, check availability again before attempting recovery. These five
uploads do not establish a general one-hour processing threshold. Record upload receipts and later
availability checks; a 404 alone does not establish that another version is needed.

### 8. The demo served the new model to old code

**Observed.** The repoint set R2's `defaultVersion` to v10.1.0. A visitor whose page an earlier service
worker had served kept running its old JavaScript, which fetched the new manifest and loaded the 10.1.0
graph without feeding `locale_hint`. The worker calls `skipWaiting` and `clients.claim`.
The page continued running the JavaScript it had loaded before the worker update.

**Change.** Earth and planetary reload once when a new worker takes control of a page an earlier worker
served. A release entry may declare `requiresRuntime`, and the runtime passes over a default release whose
capabilities it lacks. The v10.1.0 entry declares `["locale_hint"]`.

### 9. The jurisdiction layer shipped without loading in a browser

**Observed.** The address-system fill indexed a literal array of colors, which MapLibre's validator
refuses. The fills drew above the labels and had no legend or hover card. Unit tests and typecheck
passed; the style had not been loaded in a browser before release.

**Change.** A cartographer test runs the layers through `validateStyleMin`. The fix was checked in a
Playwright session against the local Earth build before merge.

### 10. Two readers were out of date with v7.2.0

**Observed.** `readAdmittedCountries` read only the first `CC: weight` pair on a line, and v7.2.0 writes
`country_weights` in flow style, 12 to a line. It returned 18 of 215 admitted countries, which fed
`jurisdiction-coverage.mdx` and `mwdev_coverage`. Training was unaffected: the Python loader parses the
YAML. `scope.config.json` also still named the v4.4.0 config as the en-us graph's. Both were fixed in
#2450.

## What went right

- The self-control on the regression board differed on 0 of 1,226 rows, establishing reproducibility
  for that comparison path.
- The gauntlet's `files_md5` guard refused to grade a stale model.
- The size comparison against the previous release caught the unreleased gazetteer data before publish.
- Two browser tests marked as known failures under 9.1.0 (`Praha 100 00, Czechia` and
  `1502 A Cage Street, Houston, TX 77020`) passed under 10.1.0, and the marker mechanism reported it.

## Product direction and the talk

**Decided:** the building feasibility application in
[#2291](https://github.com/sister-software/mailwoman/issues/2291) and its children will guide the talk's
motivation. The motivating question is what must become true to connect a property, what it might
cost, and which investigation should happen next. Address identity is the first dependency of that
workflow: assigning a record to the wrong building changes every conclusion drawn from its location.

**Proposed:** demonstrate a bounded set of publishable building cases. Follow the issue's sequence:
identity and source inventory (#2285 and #2286), testable investigations and cost assumptions (#2287
and #2288), then the map and dossier (#2289). Keep public-program research (#2290) separately scoped.
Each material conclusion should carry its source, date, spatial resolution and unresolved evidence.

**Unknown:** whether this workflow meets customer needs or reduces decision time. A pilot should
compare it with the participant's current process, with acceptance criteria agreed before measurement.
Report identity errors, missed blockers, cost error where a verified outcome exists, and decision
time with their denominators. Distinguish an implemented result from a proposed investigation.

The release motivates reliable installation and explicit uncertainty because those properties affect
whether another team can reproduce a dossier. It does not establish serviceability, commercial
feasibility or postal deliverability. The next model work remains in #2438 and #2439; a new locale
architecture is not a prerequisite for presenting the application.

## Addendum

The following talk is scheduled for Tuesday, October 13 at FOSS4G:UK 2026. It's included as a guide to the design and deployment of Mailwoman.

### Truth or Consequences, New Mexico: Approximately Correct

Address software includes rule engines, statistical parsers such as
[libpostal](https://github.com/openvenues/libpostal), neural parsers such as
[Deepparse](https://deepparse.org/), and geocoders such as [Pelias](https://github.com/pelias/pelias).
Mailwoman combines a compact neural sequence labeler with reference data from postal registries,
gazetteers and postcode indexes. The model receives that data as soft evidence.

The parser feeds a resolver that matches its output against geographic data. The shared Latin model
uses SentencePiece tokenization and an int8 ONNX graph of about 40 MB; the CJK family uses a separate
character path. Node.js and browser runtimes support local execution, with browser inference over
WebGPU or WASM and resolution through SQLite-WASM. Model size is only part of the deployment cost:
the [product overview](../../../articles/product/overview.mdx) reports a 707 MB Node installation and
a separate 2.88 GB gazetteer. Browser payload and latency require their own measurements.
Mailwoman also exposes Nominatim, Photon and libpostal API shapes, with
[documented compatibility limits](../../../articles/product/drop-in-replacements.mdx).

This talk uses building and broadband feasibility as the motivating application: identify a property,
attach evidence about infrastructure and access, state what remains unknown, and choose the next
investigation. It explains how OpenStreetMap, Overture, Who's On First and national address sources
feed training and resolution, and what the 10.1.0 release taught us about delivering the measured
system to users. The en-GB build illustrates the data, evaluation and runtime work behind a locale.

Attendees will see how to evaluate an address pipeline for this application, how to distinguish a
resolved identity from an unsupported serviceability claim, and what evidence a locale needs before
its coverage can be claimed. The dossier application remains proposed work under #2291; implemented
capabilities and planned steps will be identified separately.
