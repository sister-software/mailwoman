# Status

This page is the authoritative record of what works in Mailwoman now. For the project's direction, including locale tiers, workstreams, and standing invariants, see [Current scope & roadmap](https://github.com/sister-software/mailwoman/blob/main/docs/engineering/SCOPE.mdx). The Archive's plan directory records history. The roadmap lives in the scope document.

:::info[Verified as of 2026-08-11 — model 9.1.0 (npm 9.1.0)]
The current npm release is **9.1.0**, with model **9.1.0**, the suffix-boundary fix (v4.4.0-suffix-boundary-v2, trained from scratch on the anchor-fix recipe). It fixes the absorbed-suffix class at the source (B1 119/128). The package-shaped int8 model passes the whole v9.0.0-base check 17/17 with fp32↔int8 deltas ≤0.3pp. The ship interface (shaped span mode, card-resolved lexicons, GB Code-Point binary) is unchanged.

Prior verification (2026-08-06, model 9.0.0, npm 9.0.0): the npm release was **9.0.0**, with model **9.0.0**, the anchor-fix base (v4.2.0-base-anchor-v2, from scratch). It was the first base whose postcode-anchor channel trained every letter-containing country slot. It shipped with the shaped span-mode interface, card-resolved lexicons (locality-surface v7), and the restored license-clean GB postcode binary (Code-Point Open, 1.75M keys). gb-golden scored 318/318 with the channel fed, GB dependent_locality went 0→205/207 under the base package, and US/FR parity improved.

Prior verification (2026-08-01, model 7.0.0, npm 8.4.0): the npm release was **8.4.0** (`npm view mailwoman version`), with model **7.0.0** unchanged. It was a code-only release: the SP 0.2.2 WASM tokenizer runtime with native offsets, the calibrated B11 fine-tune template, the exotic-venue probe set and per-country gauntlet grading, and the curated-data/placetype reference docs. The model was the **from-scratch base retrain** (v4.0.1-base-60k). That golden master used one recipe and one provenance, was the first model whose locality evidence channel was trained, included the venue-led fix and the retired fr.cedex watch, and shipped with the Fisher consolidation artifact beside the weights.

Earlier releases: 8.1.0 left the model bytes unchanged (**v385**, model version **6.6.4**). It was the static-index release, shipping the per-locale FST gazetteers rebuilt with build-time degenerate-surface curation plus the sealed street-morphology artifact. **8.0.0** before it shipped the decode-time evidence layer default-on (FST distribution + GB/NZ `dependent_locality` pair-index overlays). The model lineage below is unchanged. **7.1.0** promoted the **v385 latam** model (model version **6.6.0**), the first to add new locale coverage: Mexican and Canadian addresses through a dedicated Overture `overture-latam` extract (MX locality +8.7). The earlier **7.0.0** was the package-only rules-parser excision (model unchanged from 6.5.0/v381). 6.5.0 promoted the **v381 punct-fix** model, the first to pass the full Gauntlet clean. 6.4.0 promoted the **v310 fr-fragment** line (the house-number license), and 6.3.0 the **v264 country-softguard** model. 6.0.0 was the breaking, code-only Hono API cutover: all four HTTP surfaces (the native `mailwoman serve` plus the photon/nominatim/libpostal drop-ins) moved to one shared Hono stack, and the express server was deleted without a compatibility shim. See [Releases & capabilities](./releases.mdx) for the rows.

**The current model is the 6.7.0-bundle** (`v3.24.0-bundle-ordinal` step-4000), the Option-A retrieval-augmented evidence bundle. It is a fine-tune off **v385** on v385's own feed that adds two learned input channels (`street_type` + `locality_surface`). The channels are painted at train and inference time from four-law curated, digit-guarded lexicons, and the model was trained under absence and false-evidence curricula with ordinal-street augmentation. The channels feed only in the **fragmented** register (`inputMode`, Decision A) and only when street context is present. The formatted/record register runs the trained absence identity and meets the full v6.0.0-shipped-baseline floor set (17/17).

Its base, v385 (`v3.8.5-latam-8k`, model 6.6.0), was a fine-tune off **v381** with **one** change: a dedicated `overture-latam` extract (CA + MX Overture-Addresses rows) with +CA/+MX in `country_weights`. It was the first model to add new locale coverage (MX locality 74.0→82.7).

Its base, v381 (`v3.8.1-punct-fix-full`), was a two-change fine-tune off v310. It added the `synth-no-fragment` digit-ownership extract and the `augment_punct_drop_prob` delimiter-free augmentation ([#1101](https://github.com/sister-software/mailwoman/issues/1101)). It was the **first model to pass the full Gauntlet clean**, and v385 also passes (33/33). Shipped 6.4.0 fails the metamorphic `comma-drop` invariant: a comma-free `1600 Pennsylvania Ave NW Washington DC` absorbed the locality into the street and lost the rooftop (~2 km, address_point→admin). The punct-drop augmentation fixes it by adding a comma-stripped training copy of each row with re-targeted spans. It had been built and tested but was not enabled in the shipped recipe until this release. The digit-ownership extract teaches the street/number boundary, so a bare `Nordtømmesvegen 178` reads as `house_number` rather than a postcode. On the Norwegian digit board, `bare-street-hn` went **0.693 → 0.733** and `bare-pc` stayed at 1.000. The golden check passes with no tag more than 2 pp below shipped and `us.country_homograph` **+2.3**. The change is weights-only and does not touch the lexicons, inference, or browser code. The tokenizer is unchanged, `v0.9.0-multisplice` (73,143 pieces).

One known failure is still open. The **French** comma-free input without an anchor (`Rue du Chevaleret Paris`, a bare terminal locality without a trailing state or postcode) stays a tracked #1101 xfail. A locality name-index ([#30](https://github.com/sister-software/mailwoman/issues/30)) would fix it. See the [v6.5.0 punct+digit grade](https://github.com/sister-software/mailwoman/blob/main/docs/records/evals/2026-07-17-v650-punct-digit-result.md) for the full write-up.

**The per-tag tables below are frozen at the 2026-07-02 full re-score of the earlier 5.0.0/v4.15.0 line** (the #885 measurement re-anchor). Several model releases have shipped since then without a full re-score (5.1.0 → 5.4.0 → 5.9.0 → 6.1.0 → 6.2.0 → 6.3.0 → 6.4.0 → 6.5.0). Their measured deltas are described release by release on [Releases & capabilities](./releases.mdx), which is the current authoritative per-release record, and are not folded into a new scorecard. Treat the [parity scorecard](https://github.com/sister-software/mailwoman/blob/main/docs/records/evals/competitive-parity/parity-scorecard-2026-07-02.md) below as a historical baseline. It does not report the shipped model's current per-tag numbers.
:::

The trend, in words:

- **Healthy (2026-07-02 re-score):** postcode (95.0/99.3 US/FR, both exactly at their revised check floors), house_number (90.7/98.1), venue-US (89.1), street (82.3 US, its best measured score), and fr.region, which the multi-locale work raised from 16.2 to 48.4.
- **Fixed by the parity campaign:** `unit` 0 → 92.3 on real-OOD designators (the 4.1.0 headline).
- **Shipped by the consolidation (v4.2.0):** locality +12.8, region +10.7, country 0 → 89.8 (gazetteer soft anchor), affixes now emitted (0 → 64.9/48.8 at P≈100), DE 90.9.
- **Closed by the boundary consolidation (v4.4.0):** the scorecard's last empty rows (po_box 0 → 89.1, cedex 0 → 96.1, intersections 0 → 100, real-OOD, P ≥ 95) and the v4.3.0 arena shortfall (perturb 64 → 72, now a conditional floor). The span bridge ships as required decode config. The corpus format cannot label dotted surfaces such as "P.O. Box", and the bridge handles them. The [ship check](https://github.com/sister-software/mailwoman/blob/main/docs/records/evals/model-versions/2026-06-11-v4.4.0-ship-check.md) describes all three test batteries.
- **Closed by the relabel (v4.3.0):** the affix ceiling was never a capacity limit. It came from a 1,039:1 label contradiction in the training mix ([#492](https://github.com/sister-software/mailwoman/issues/492) → [#511](https://github.com/sister-software/mailwoman/issues/511)). Affixes now score 93.6/96.6 (int8, real-OOD), and 92.2/90.3 on the 193-row NAD-native eval where v4.2.0 scored 18.2/8.9. The release also shipped the first conventions-layer increment: the model's locale head is exported and the decoder applies it (fr mask).
- **Formerly "open gaps," now closed:** both rows this section used to flag are resolved. FR venue/region ([#330](https://github.com/sister-software/mailwoman/issues/330)) was a measurement artifact. The model's FR venue F1 is 89.1+ and région 99.6% in-distribution. A synthetic multi-script eval had implied 0% and 19%. The v4.4.0 real-TIGER intersection extract fixed intersections ([#487](https://github.com/sister-software/mailwoman/issues/487)): 0 → 100/100 real, 94.9/96.1 VT golden.

Capability-arena results (whole parse, against the v0 rules system): rules still win on clean, canonical input, the neural parser wins on noisy or degraded input (+21pp), and both are weak on rare edge formats. An [arbitration layer (#478)](https://github.com/sister-software/mailwoman/issues/478) was built to take the better of the two per component. The coordinate check ruled out its promotion ([#685](https://github.com/sister-software/mailwoman/issues/685)). Its +122 arena label wins raised coordinate p50 from 3.3 to 1069 km and dropped the street+house_number geocode precondition from 100% to 48%. It stays merged, default-off, and research-only.

## Confidence

Every node carries a confidence score. Pass a calibrator (isotonic, shipped per locale in the weights bundle as `calibration.json`) so that a score of 0.90 means the label is correct about 90% of the time. See [Confidence calibration](./concepts/confidence-calibration.mdx) for what the numbers mean.

## Browser demo

The live demo at [mailwoman.ai/demo](https://mailwoman.ai/demo) runs the int8 model (37.6 MB, the v264 line). The softened country channel is baked into the same ONNX that the browser country wiring in `@mailwoman/neural-web` 6.2.1 already feeds. The demo also loads a **byte-range global gazetteer**: the "candidate" table without FTS (~530 MB, queried over `sql.js-httpvfs`), where a resolve makes ~12 range fetches regardless of file size. It provides global admin coverage, **US + EU postcode resolution**, and a debounced FST place autocomplete in the search box. US **street-level (rooftop)** resolution works nationwide, in all 50 states plus DC and VI, through per-state situs/interp extracts (124.9M address points, [#735](https://github.com/sister-software/mailwoman/issues/735)). FR rooftops resolve through the hosted BAN situs extract with a street-tier fallback (shipped 5.10.0, see [Releases & capabilities](./releases.mdx)). R2 serves the artifacts with byte-range requests. The demo calls the classifier's argmax path directly, and joint reconcile is not active in the demo.

## Model line (July 2026)

The current shipped weights are the **v381 line** (`v3.8.1-punct-fix-full`, promoted in 6.5.0, [#1101](https://github.com/sister-software/mailwoman/issues/1101)), the first model to pass the full Gauntlet clean. Each model release between the 5.0.0/v4.15.0 line (documented in past versions of this page) and today was judged on the **shipped assembled coordinate or a targeted repro** instead of raw label-F1: v5.1.0
(`v0.6.0-bsplice` tokenizer splice) fixed Slavic diacritic fragmentation — CZ/PL/SK/SI wrong-city
roughly halved, US byte-identical; v5.2.0 (`v0.7.1-nsplice`) extended the splice to Nordic
diacritics (SE resolve 83.8 → 90.2%); v5.3.0 (`v2.2.0-full-family`, from scratch) fixed the FR
street fragmentation the v5.2.0 splice had shipped unconditional (bare 16/40 → 34/40, anchored 13/40 →
37/40); v5.4.0 (`v2.3.0-nl-postcode`, fine-tune) fixed a Dutch digits-first postcode misread that
was pulling `1012 LG Amsterdam` into the US situs tier; v5.9.0 (`v2.4.1-fr-nsplice-ft`, fine-tune)
gave the merged FR diacritic pieces gradient after a training-free vocab splice was falsified for
regressing FR streets, reducing the accent mangle rate 23.5% → 17.7%; v6.1.0/v261
(`v2.6.1-span-boundary-full`, fine-tune off the stable v257 fragment-campaign line) trained a
span-boundary auxiliary head to shrink the region→street boundary-absorption class (US region→street
flips 5→2 vs v257, parity street +13pp vs v241), shipping through a documented cosmetic check
exception on golden country recall ([#1104](https://github.com/sister-software/mailwoman/issues/1104) —
real-postal country recall and precision are unaffected); **v6.2.0/v263**
(`v2.6.3-country-channel`, fine-tune off v261) turned that exception into a fix — a dedicated country
soft-feed channel recovered golden country recall 84.8→89.3% (clearing the 88.6% v241 bar) while the
held-out coordinate held flat on both locales, carrying a coordinate-invisible region per-tag
trade (6.2.1 then wired the channel into the browser runtime); and **v6.3.0/v264**
(`v2.6.4-country-softguard`, fine-tune off v263) softened that channel's homograph guard
(`country_ambiguous_scale` 1.0→0.5, baked into the ONNX) — strictly dominating v263 with no trade:
country-homograph F1 82.6→85.1, golden WOF-admin country recall 89.3→91.1%, aggregate golden
label-fails −3, coordinate pass both locales; **v6.4.0/v310** (`v3.1.0-fr-fragment`, fine-tune off v264)
taught the house-number license with a BAN fragment extract — a street name is a street name without a
house number, so `Rue Montmartre` no longer reads as a locality (FR fragment bare-street 0.215→0.715);
and **v6.5.0/v381** (`v3.8.1-punct-fix-full`, fine-tune off v310) folded the digit-ownership
`synth-no-fragment` extract (Norwegian `bare-street-hn` 0.693→0.733) and the `augment_punct_drop_prob`
delimiter-free augmentation that closes the #1101 comma-free rooftop loss — the first model to pass the
full Gauntlet clean, golden check pass with no tag more than 2 pp below shipped and `us.country_homograph`
+2.3. Full per-release evidence lives on
[Releases & capabilities](./releases.mdx), which this page points to for anything shipped after
the last full re-score. The ordered work queue to the full geocoder is
[epic #488](https://github.com/sister-software/mailwoman/issues/488).

## What is not supported today

- Multi-locale ensemble (en-US + fr-FR weights in the same runtime).
- Korean addresses, because no open data source exists. Japanese addresses **are** supported through the postcode-route resolver (Geographic Rule Engine).

Three items that used to be on this list have shipped and are covered elsewhere on this page:
nationwide US rooftop geocoding (all 50 states + DC + VI, see **Browser demo** above,
[#735](https://github.com/sister-software/mailwoman/issues/735)), reverse geocoding (`mailwoman
reverse`, see the **Runtime pipeline** table above, [#484](https://github.com/sister-software/mailwoman/issues/484)),
and the production-hardened server API (batch, observability, `RemoteResolver`, versioned data
switchover — shipped v4.7.0, [#485](https://github.com/sister-software/mailwoman/issues/485); the
6.0.0 Hono cutover retired the last express-era code path, see
[Releases & capabilities](./releases.mdx)).
