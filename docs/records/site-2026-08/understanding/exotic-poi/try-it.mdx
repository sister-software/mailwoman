# Try it: the POI intent tester

Type a query below to see how Mailwoman handles it. The kind classifier decides whether the query is a POI query or an address. The tester then extracts the subject, which is either a taxonomy category (`hospital`, `drinking fountain`) or a chain brand (`chevron`, `applebee's`). It splits off the location anchor and renders an OverpassQL export you can paste into [Overpass Turbo](https://overpass-turbo.eu/).

Intent detection runs entirely in your browser without a network request. It uses the same `matchPOISubject`, `createKindClassifier`, and OverpassQL emitter that Mailwoman ships as a library in [`@mailwoman/kind-classifier`](https://www.npmjs.com/package/@mailwoman/kind-classifier) and [`@mailwoman/poi-taxonomy`](https://www.npmjs.com/package/@mailwoman/poi-taxonomy). A brand subject resolves to its Wikidata QID from the same brand table the runtime uses. Pressing "Search live" on a category result sends byte-range HTTP requests against the published gazetteer and POI layer. That step uses no server-side code or model weights, but it does need a network connection.

## Reading the result

- **Kind badge.** This badge shows the Stage 2.5 kind classifier's verdict (`poi_query`, `structured_address`, …) with its confidence. Expand it to see the runner-up kinds.
- **Category chip.** When the kind is `poi_query`, this chip shows which taxonomy category the subject phrase matched.
- **Brand chip and QID.** When the subject is a chain brand, this chip shows the brand's canonical name and a linked Wikidata QID (`Q319642` = Chevron). Brands resolve by that QID against the layer's `brand_wikidata` index rather than by category, so they carry neither an OverpassQL export nor an OSM-tag k-ring.
- **build-local badge.** This badge means the category's data lives only in ODbL sources (OpenStreetMap). Mailwoman ships the builder for the local layer rather than the data itself. [Amenity queries](./amenity-queries.mdx) explains why that split exists.
- **anchor.** The anchor is the text left over after the subject phrase is split off (`near Springfield`, `, New York`). The runtime pipeline would hand this text to the address parser to resolve a location constraint.
- **OverpassQL export.** This is a ready-to-run query against the category's OSM tag, scoped to the anchor when one resolved. Overpass is only an export target. Mailwoman prints the query and never runs it for you.
- **Search live.** For a category result with an anchor, this button range-loads the published `poi.db` (13.68M Overture-places rows, US/CA/MX/FR) in your browser via sql.js-httpvfs and shows real, distance-ranked results. It uses no server or model weights. It makes byte-range reads against the same admin gazetteer and POI layer that the CLI's `mailwoman poi` and the `mailwoman_poi_search` MCP tool query. Each click runs a k-ring walk capped a few hundred meters out, covers categories only, and depends on the anchor. An unresolvable place name shows "couldn't place" instead of a silent empty list. A `build-local` category never offers the button, because its data is deliberately unpublished. Live search covers categories only on purpose. A brand-wide fetch by QID has to hydrate every one of a brand's globally scattered rows from the 3.9 GB layer, and byte-range reads make that very slow. Even a 25-row brand costs ~13 s and 60 range requests, and the large brands time out. That lookup belongs on a server. The Node `POILookup` does the same QID fetch in under a millisecond, so brand subjects in this tester stop at intent detection.

## Why "hospital, 350 5th Ave, New York" doesn't become a POI query

Try that preset. The lexicon matches `hospital` as a subject, but the remainder (`350 5th Ave, New York`) leads with a house number. A leading house number signals a venue-led full address ("the hospital located at this specific address") rather than a category search. The classifier's `structured_address` score wins, and the query falls through to the "parses as an address" state instead of an Overpass export. [The parser uses the same check in production](../our-approach/the-staged-pipeline.mdx) to keep full addresses that start with a category word from being routed into the POI branch.

## What isn't here yet

- **Landmark subjects.** The lexicon matches categories (`hospital`, `fire_hydrant`, `drinking_water`, …) and chain brands (`chevron`, `applebee's`, from the QID-keyed brand table). Bare landmark names ("Eiffel Tower") aren't in the phrase table yet. See [Landmark queries](./landmark-queries.mdx) for the target shape. [Franchise queries](./franchise-queries.mdx) covers how the brand path works end to end.
- **Live brand search in the tester.** Brand subjects resolve their QID here without a live search, because the "Search live" step covers categories only. A brand-wide byte-range fetch over the published layer is too slow, as the Search live entry above explains. The CLI and the `mailwoman_poi_search` MCP tool do brand-exact lookups server-side against a built `poi.db` in sub-millisecond time.
- **Free-text (FTS5) name search.** The CLI and MCP tool also expose FTS5 name search against `poi.db`. This browser tester is limited to intent detection and category k-ring search, matching the runbook's multi-hop exclusion for the demo.
