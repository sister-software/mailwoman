# Landmark queries

A landmark query asks for a specific place that is typically unique. The user wants **the** Eiffel Tower, **the** Golden Gate Bridge, or **the** Empire State Building rather than the nearest instance of a category. The geocoder must recognize the landmark name and resolve it to a single coordinate or a small candidate set.

## What landmark queries look like

| Query                  | Type                                                          |
| ---------------------- | ------------------------------------------------------------- |
| Eiffel Tower           | Landmark — globally unique                                    |
| Golden Gate Bridge     | Landmark — unique, but spans a distance                       |
| Empire State Building  | Landmark — unique, has a street address                       |
| Taj Mahal              | Landmark — unique, well-known                                 |
| Sydney Opera House     | Landmark — unique, well-known                                 |
| the White House        | Landmark — unique, politically sensitive                      |
| Wrigley Field          | Venue — unique, has a street address                          |
| Grand Central Terminal | Transit + landmark — unique, transit hub                      |
| Central Park           | Area — large, multiple entrances                              |
| The High Line          | Linear feature — spans a distance                             |
| The Las Vegas Strip    | Area — a polygon rather than a single point                   |
| Stonehenge             | Landmark — remote, well-known                                 |
| Mount Everest          | Natural feature — summit vs base camp are different locations |

In a landmark query, the user knows the name of the place but does not know or care about its address. The geocoder must map the name to a coordinate without the structured components (`street`, `city`, `state`) that address queries provide.

## Landmark taxonomy

### Structures

Buildings, bridges, towers, monuments: Eiffel Tower, Empire State Building, Big Ben, Colosseum, CN Tower. These are the easiest landmarks to geocode because they typically exist in gazetteers (WOF, OSM, GeoNames) with a single name and coordinate.

Some structures, however, share their name with structures in other cities. There are replica Eiffel Towers in Las Vegas, Paris (Texas), and Tokyo. The user searching for "Eiffel Tower" from Paris, France wants the real one. The user in Las Vegas wants the replica. The geocoder needs a **prominence signal**. The original Eiffel Tower is more prominent than the replica, and users searching without a location constraint probably mean the prominent one.

### Natural features

Mountains, rivers, lakes, forests: Mount Everest, the Amazon, Lake Tahoe, Central Park. These are areas or linear features rather than points. A geocode for "Central Park" could be the park's centroid, the main entrance, or the park's visitor center, and each has a different coordinate. A single point for "the Amazon" is meaningless because the Amazon rainforest spans 5.5 million square kilometers across 9 countries.

The geocoder should return the feature's centroid for map display and the most relevant entrance or access point for navigation. Which one to return depends on the use case, and the geocoder cannot know the use case from the query text.

### Venues

Stadiums, theaters, museums, arenas: Wrigley Field, Sydney Opera House, the Louvre, Madison Square Garden. Venues are easier because they are buildings with street addresses, and gazetteers typically have them. A venue may still have multiple entrances (main entrance, box office, VIP entrance, loading dock), and the geocoder's single coordinate is an implicit choice about which entrance matters.

### Areas

Neighborhoods, districts, informal regions: SoHo, Shibuya, the French Quarter, Silicon Valley. These are areas rather than points, with fuzzy boundaries that change over time and vary by who you ask. A geocode for "SoHo" places a pin at an arbitrary point within a neighborhood whose boundaries are contested.

WOF models neighborhoods as `neighbourhood` placetypes with a representative coordinate and a parent chain (Soho → Manhattan → New York City → New York → United States). The coordinate is approximate, and WOF does not model the boundary. That is acceptable for most use cases, such as finding SoHo on a map. It is not acceptable for use cases that need boundary-level precision (delivery zones, real estate searches, neighborhood statistics).

### Linear features

Trails, parkways, pedestrian paths: the High Line, the Appalachian Trail, Route 66, the Las Vegas Strip. These are paths rather than points. A geocode at the midpoint of the High Line places the pin in the middle of the park. That pin is useful for map display and useless for navigation, since the nearest entrance might be a mile away. Linear features need a **point-set representation** (the path as a polyline) and a way to answer "where is the nearest access point?"

## How traditional geocoders handle landmark queries

**Google's Places API** handles landmark queries through its place database. Landmarks are a `type` in the Places taxonomy. Google's results include a `location` (coordinate), `viewport` (bounding box for area landmarks), and `types` (what kind of landmark). Google handles disambiguation through user context. The user searching from Paris gets the real Eiffel Tower, and the user in Las Vegas gets the replica.

**Nominatim** handles landmarks through OSM's tagging. Buildings with a name tag (`building=yes` + `name=Eiffel Tower`), monuments (`historic=monument`), parks (`leisure=park`), and natural features (`natural=peak`) all appear in OSM. Nominatim's search matches the landmark name against OSM's name tags and returns the best match. OSM coverage limits the results. OSM covers well-known landmarks in well-mapped areas and misses lesser-known landmarks in unmapped areas.

**Pelias** indexes WOF venues and landmarks. WOF has good coverage of globally prominent landmarks (Eiffel Tower, Taj Mahal) but spotty coverage of local landmarks (the neighborhood park, the local statue). Pelias's search matches the landmark name against WOF's name fields and returns the best placetype match.

## What Mailwoman does today

Mailwoman's resolver indexes WOF administrative places plus a limited set of WOF venues. Well-known landmarks that exist in WOF as `venue` or `neighbourhood` records are resolvable. Lesser-known landmarks are not.

The parser handles landmark queries as venue queries. A query with a known venue name and without address-format tokens (numbers, street suffixes, or state abbreviations) is classified as `kind=venue` and routed to the venue resolver. The F1 ≈ 0.39 figure once cited here was measured in v0.4.0, three model generations back, and does not describe the current classifier. A venue-fragment retrain is specified but has not run. Until that retrain lands, treat the venue classifier's quality as unmeasured, and rely on neither the old number nor an assumed improvement.

**Landmark queries are partially in scope** and partially overlap with the newer category-query path. A landmark that also matches a POI-taxonomy category (a hospital, a park with a proper name) can resolve through `poi.db` the way [amenity queries](./amenity-queries.mdx) do. Bare landmark names that aren't categories ("Eiffel Tower") still depend on the venue classifier and WOF venue records. Those are limited by data coverage (WOF's venue catalogue is incomplete) and by the unretrained classifier described above.
