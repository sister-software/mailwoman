# How Mailwoman resolves a place

[The parsing page](./how-mailwoman-parses-an-address.mdx) ends with a tree of labeled spans (this text is a locality, this one a postcode) and no coordinates. Resolution is the second half of the job. If you have run Pelias or Nominatim, you already know its inputs: a gazetteer, an admin hierarchy, and population-weighted ranking. Mailwoman uses all three. This page covers what happens around them. The resolver checks the parse tree against the map, lets the map correct the parse, and reports the precision of the coordinate it returns.

As on the parsing page, this page follows one address through the process, with output captured verbatim:

```bash
mailwoman geocode "413 S 8th St, Springfield, IL 62701" --format text
```

```text
input:            413 S 8th St, Springfield, IL 62701
resolution_tier:  address_point
coordinate:       39.797779, -89.645386
uncertainty_m:    1
locality:         Springfield
region:           IL
postcode:         62701
hierarchy:
  locality             Springfield [wof:85940429] (39.7710, -89.6539)
  region               IL [wof:85688697] (40.1242, -89.1486)
```

That coordinate is Abraham Lincoln's house. The rest of this page explains that output: which of America's several Springfields was chosen, why the coordinate is a rooftop rather than a city centroid, and what `uncertainty_m: 1` means.

## What resolution adds

The parse labeled "Springfield" as a locality. Resolution answers the question the parse deliberately left open: which of the existing Springfields is meant? It adds three things:

- **Identity.** Each resolved node gets the winning place's stable [WhosOnFirst](./resolver-and-wof.mdx) ID, so the result works with any other WOF-based tool.
- **A coordinate** from the finest data available. Here that is a rooftop, and elsewhere it may be only a town centroid.
- **Objections.** When the map contradicts the parse, the resolver reports the conflict instead of averaging it away.

`mailwoman parse --resolve` shows these additions on the same tree the parsing page ended with, in the XML projection:

```xml
<address raw="413 S 8th St, Springfield, IL 62701">
	<region start="27" end="29" conf="0.92" src="resolver:region:85688697" lat="40.124199" lon="-89.148632" place="wof:85688697">IL
		<locality start="14" end="25" conf="0.95" src="resolver:locality:85940429" lat="39.770987" lon="-89.653852" place="wof:85940429">Springfield
			<street start="6" end="9" conf="0.94">8th
				<house_number start="0" end="3" conf="0.89">413</house_number>
				<street_prefix start="4" end="5" conf="0.96">S</street_prefix>
				<street_suffix start="10" end="12" conf="0.90">St</street_suffix>
			</street>
			<postcode start="30" end="35" conf="0.90">62701</postcode>
		</locality>
	</region>
</address>
```

The spans, offsets, and confidences are unchanged from the parser. The resolver adds `place=` and the coordinates, and changes the `src=` attribution to `resolver`, keeping the classifier's original label in metadata. Parsing and resolving are deliberately separate jobs. The model handles the grammar, the gazetteer handles geography, and either side can be upgraded without retraining the other. [What Mailwoman is](./what-mailwoman-is.mdx) explains that design in full.

## The atlas on disk

Everything the resolver reads is a read-only SQLite artifact, built ahead of time and stamped with provenance and a release date. The base layer is WhosOnFirst, the open gazetteer Pelias also uses, chosen for its stable IDs and containment hierarchy. The reference build's admin layer holds about 4.1 million places across 244 countries, each with alternate names, population, bounding box, and ancestor chain. Postcode extracts sit beside it: US postcode centroids, Dutch PC6 codes at street-block grain, and a GeoNames-derived international tail. The rooftop layers hold about 125 million US address points from the National Address Database and OpenAddresses, attached per state, and 26 million French points from BAN, the national address register. These artifacts are built or downloaded separately from the packages. The browser demo reads a hosted copy of the same gazetteer over byte-range requests, so the demo and the server return the same results.

## From a span to candidates

The resolver walks the tree top-down. At each node whose tag is a place type (country, region, locality, postcode), it asks the backend which places have this name and type under the current constraints. Lookups are budgeted, by default to ten per tree with five candidates each. The resolver never queries tags without place semantics, such as `house_number` and `unit`.

Retrieval is an exact lookup on normalized name keys, with a trigram index for fuzzy matches. Ranking follows a strict order:

1. **Exact name matches outrank partial matches.** A place named exactly "Springfield" beats every "Springfield Gardens" the index also returns.
2. **Within a tier, prominence decides.** Prominence is capped log-population, plus a proximity term when the caller supplies a map viewport or user location. This is the importance ranking a Pelias user expects, but it only breaks ties _within_ one match-quality tier. Applied across tiers, population would pull "ME" to Missouri (a populous partial match) over Maine (the exact match).
3. **The raw text-match score is the last tiebreak.** Full-text scoring penalizes a famous city's long, alias-heavy index entry, by roughly 15 BM25 points compared with a small namesake's short entry. The text score therefore admits candidates to the pool but does not order them.

Under that ranking, a bare `Springfield` with no other evidence resolves to Springfield, Missouri, the most populous place with that name. That is the right answer when there is no context.

## The tree must agree with the map

Our query has more context than a bare Springfield, because the parse nested it under a region. The walk is top-down, so `IL` resolves first, to Illinois. The locality lookup below it is limited to descendants of Illinois in the gazetteer's containment graph, so the Missouri Springfield never enters the pool. This is how the resolver handles namesakes such as the several Berlins or Warsaws. It applies the same containment logic that [the tree builder](./containment-and-tree-projection.mdx) used to nest the spans, now checked against the map instead of the string.

Scoping assumes that the parent resolved correctly. Several fallback passes cover the cases where it did not, and these passes handle most namesake cases:

- **An empty scope triggers one retry without the parent**, keeping the country constraint. A missing link in a gazetteer's ancestor chain should not turn a resolvable town into a null.
- **A resolved region with a failed child locality** usually means the greedy order picked the wrong region. A bare "ME" can mean Maine or Messina, Italy. A post-walk pass then asks which same-named region candidate has a locality of this name under it. It re-picks both nodes as a pair and records the swap on the node.
- **An explicit country token gets the same joint treatment.** For "Vienna, Austria", the resolver re-picks the locality to the same-named place inside the country the address names. The resolved output is the Austrian capital (48.2085, 16.3721) rather than a populous namesake abroad.
- **A resolved postcode anchors the locality.** Postcodes are unambiguous within a country, and town names are not. If a locality resolves more than 50 km from its sibling postcode, the resolver re-picks the same-named candidate nearest that postcode. If no candidate is close enough, the coordinate falls back to the postcode's area, and the node is flagged `postcode_city_mismatch`. In that case the input, rather than the map, is likely wrong. This pass was added after a measured failure: "06260 Saint-Pierre", one of several French Saint-Pierres, once resolved 617 km from its own postcode.
- **When no rung resolved**, a last-resort pass re-reads the raw text against the gazetteer. The model occasionally splits an accented name such as "Grudziądz" into pieces that no lookup can match. The pass inserts the recovered locality and marks it as recovered rather than parsed.

Every pass records its action in node metadata (`admin_coherence_repicked`, `postcode_city_mismatch`, `span_rescore`, …). Each pass runs only on a failure, so a tree that resolved directly passes through byte-identical. The metadata always shows which reading the resolver chose.

## The precision ladder

Admin resolution ends at centroids. "Springfield" resolves to a point near the middle of town, about 3 km from Lincoln's door for our query. The ladder runs after the admin walk. The resolver consults each rung only when the rung above found no candidate:

1. **Rooftop** (`address_point`) is an exact (street, house number) match in an address-point extract, scoped by postcode or locality. Our example resolves here. The matching row copies its provenance (`source: "overture:NAD"`, `release: "2026-05-20.0"`) into the node's metadata, and `uncertainty_m` reports the 1 m floor. A registered address point is never overwritten by an estimate.
2. **Interpolation** (`interpolated`) applies when there is no exact point but the house number falls within a known range along a street segment (US TIGER data). The estimate carries a calibrated radius: half the segment length times a per-region conformal calibration factor. The factor ranges from 1.44 in dense DC to 3.12 in sprawling Arizona, with 1.95 where unmeasured. It is sized so the stated radius contains the true point about 90% of the time. The uncalibrated radius covered only ~72%.
3. **Street centroid** (`street`) applies to queries without a house number, such as "Place Bellecour, Lyon". It returns the center of the street, with a radius of half the street's extent. The BAN register backs this tier today, so in practice it covers France.
4. **Admin centroid** (`admin`) is the floor wherever the gazetteer has the place. It returns a locality, postcode, or region centroid, with `uncertainty_m: null` because there is no finer estimate to size.

The tier appears first in the output. `resolution_tier` identifies the rung and `uncertainty_m` gives its radius. Whether that is close enough depends on _your_ task: routing a truck needs the rooftop, and assigning a sales territory does not. [How close is close enough?](./how-close-is-close-enough.mdx) covers this in full, with measured accuracy per rung.

## What to trust, and how much

A resolved result includes two kinds of numbers, and they answer different questions. The `conf=` on each span comes from the parser and estimates how likely the text is to be a locality. An [isotonic-calibrated](./confidence-calibration.mdx) version is available, so 0.94 can mean correct about 94% of the time. The resolver does not reduce its result to one score. It reports the tier and radius, plus named flags where evidence conflicted, because its failure modes differ in kind rather than degree:

- **Coverage gaps.** When a region has no rooftop extract, the ladder stops at the admin rung and reports that tier. The coordinate is still the right town, and the output never presents a centroid as a rooftop.
- **Namesakes.** The coherence passes resolve most of them. When the gazetteer's hierarchy cannot decide, the runner-up candidates are attached to the node (`alternatives`), so a consumer can re-rank them with context Mailwoman lacks.
- **Contradictory input.** `postcode_city_mismatch` means the address disagrees with the map, for example through a transposed postcode or an outdated city name. The returned point is the safer of the two readings, and the flag is what the consumer should act on.
- **Stand-in placetypes.** When a region span matched only a broader admin tier (an Italian _regione_ is a `macroregion` in WOF's taxonomy), `resolution_quality: "fallback"` records that a coarser tier was used.

## Where it's strong, where it's thin

Coverage is claimed per locale, and only where a coordinate-graded eval exists. The current tier table is in [the scope declaration](https://github.com/sister-software/mailwoman/blob/main/docs/engineering/SCOPE.mdx). The US and France are first-class and floor-conditional, fourteen more locales are trained and have coordinate panels, and Japan is resolver-route only. Where the rooftop tiers have data, accuracy depends on the data rather than the model, so the main remaining work is coverage. The [demo map](https://mailwoman.ai/demo) has a coverage overlay that shades the places the resolver cannot yet locate precisely. [The coverage-overlay runbook](https://github.com/sister-software/mailwoman/blob/main/docs/engineering/reference/coverage-overlay.mdx) documents its build. For measured results on the resolver ladder, interpolation calibration, the postcode anchor, and per-locale coordinate panels, see [the resolver & geo eval reports](https://github.com/sister-software/mailwoman/blob/main/docs/records/evals/resolver-geo/index.mdx). Each report is dated, so you can tell when each number was measured.
