# Joint decoding — a walkthrough

[The knowledge ladder](../understanding/our-approach/the-knowledge-ladder.mdx) explains _why_ the v0.5.0 pipeline added two information layers: the Stage 2.7 phrase grouper and an expanded Stage 5 reconcile. This article follows one concrete input through the pipeline to show _what they do_.

The input is the operator's hardest test case:

> `NY-NY Steakhouse, Houston, TX`

Every earlier version of Mailwoman parsed this string wrong. On its own, the token `NY` looks exactly like the abbreviation for New York, and a per-token classifier reads it that way. The only reading that makes sense for the whole string is that `NY-NY` is part of a venue name, the city is Houston, and the region is Texas. No single layer can reach that conclusion alone, and joint decoding is the layer that combines their evidence.

Read [The staged pipeline](../understanding/our-approach/the-staged-pipeline.mdx) first. This article assumes you know the six stages by name.

## Stage 1 + 2 + 2.5 (warm-up)

Stage 1 normalizes the bytes. For this input it makes no NFC fixes and expands no abbreviations, so the string passes through unchanged.

Stage 2 is the locale check. For Latin-only input like this, the default is `en-US` with moderate confidence. The downstream resolver weights therefore favor US gazetteer matches.

Stage 2.5 is the kind classifier. It looks at the shape of the string (commas, capitalization, the trailing two-letter token after a final comma) and classifies it as a `structured_address`, rather than a bare postcode or a single locality. The full pipeline runs.

These three stages perform no notable work for this example.

## Stage 2.7 — phrase grouper proposes spans

The phrase grouper is the new layer at the top. It **only discovers boundaries**. It decides which tokens belong together, but not what type each span is. It emits a list of proposals with confidence scores.

For our input it produces these proposals. The scores come from [`phrase-grouper/kryptonite.test.ts`](https://github.com/sister-software/mailwoman/blob/main/phrase-grouper/kryptonite.test.ts):

| Span   | Body               | Hypothesis            | Confidence |
| ------ | ------------------ | --------------------- | ---------- |
| 0..5   | `NY-NY`            | `HYPHENATED_COMPOUND` | 0.85       |
| 0..16  | `NY-NY Steakhouse` | `VENUE_PHRASE`        | 0.85       |
| 18..25 | `Houston`          | `LOCALITY_PHRASE`     | 0.65       |
| 27..29 | `TX`               | `REGION_ABBREVIATION` | 0.95       |

Three details in this output matter:

1. **`NY-NY` and `NY-NY Steakhouse` both appear**, with the same start position. The grouper does not choose between them. It proposes both and leaves the decision to Stage 5. A `HYPHENATED_COMPOUND` is one structural unit, and a `VENUE_PHRASE` ending in a known venue marker (`Steakhouse`) is another. Both are coherent readings of the same prefix.
2. **`Houston` gets a lower confidence (0.65) than `TX` (0.95)**. `TX` sits at the end of the string after a comma, which is a strong structural signal for a region abbreviation. `Houston` is a capitalized word that _could_ be a locality, but the grouper has no dictionary. It only knows that the word has the structure of a `LOCALITY_PHRASE`.
3. **No span covers `,` or whitespace.** The grouper proposes spans only over real input tokens. The character offsets in the span column refer to the original input string.

The grouper does _not_ know that `NY` abbreviates New York, that Houston is in Texas, or that "Steakhouse" suggests a venue. That is world knowledge, and the grouper deliberately avoids it. It supplies only structural priors, which keeps this layer consistent with the [bitter lesson](../understanding/our-approach/the-knowledge-ladder.mdx#why-this-decomposition-is-bitter-lesson-aligned).

## Stage 3 — classifier emits top-k tag sequences

Stage 3 is the neural classifier. Before v0.5.0 it returned a single best tag for each token (the argmax). Since v0.5.0 it returns the **top-k**: a ranked list of plausible interpretations per span, with calibrated scores.

For the spans the phrase grouper proposed, Stage 3 returns:

| Span   | Body               | Tag        | Score            |
| ------ | ------------------ | ---------- | ---------------- |
| 0..5   | `NY-NY`            | `region`   | **0.70** (top-1) |
| 0..5   | `NY-NY`            | `venue`    | 0.60 (top-2)     |
| 0..16  | `NY-NY Steakhouse` | `venue`    | 0.55             |
| 18..25 | `Houston`          | `locality` | 0.85             |
| 27..29 | `TX`               | `region`   | 0.95             |

A pipeline that stopped here would produce the wrong answer. The classifier's **argmax** for `NY-NY` is `region` (score 0.70), because `NY` is overwhelmingly the New York region abbreviation in the training data. The `venue` reading is second (0.60). A pre-v0.5.0 system would emit `region: NY-NY, region: TX`, and the resolver could not make sense of it.

The `venue` interpretation is close behind. The classifier considers a venue plausible and rates region only slightly higher when it sees the span _in isolation_. The top-k output keeps that information for Stage 5.

## Stage 4 — sequence corrector

Stage 4 is the CRF decoder. It enforces the BIO grammar on the tag sequence, which forbids an `I-*` tag without a preceding `B-*`. This example has no orphan BIO labels, so the CRF passes the top-k candidates through unchanged. [CRF decoder](./crf-decoder.mdx) shows a case where Stage 4 _does_ change the output, `Saint Petersburg` → `Petersburg`.

## Stage 5 — reconcile picks the joint-coherent interpretation

The new joint decoder does its work in Stage 5. Stage 5 receives:

- **Phrase proposals from Stage 2.7** (the table from §3 above).
- **Top-k tags from Stage 3** (the table from §4 above).
- **Resolver candidates from Stage 6**, queried per span, as shown below.

Stage 5 picks **one** parse tree that maximizes joint coherence. Instead of taking each span's argmax, it picks the combination that is internally consistent.

### What "joint-coherent" means

Our input has two candidate interpretations.

**Interpretation X** takes every span's argmax:

```
NY-NY     →  region   (0.70 × ?)
Houston   →  locality (0.85 × ?)
TX        →  region   (0.95 × ?)
```

Every Mailwoman version before v0.5.0 returned this reading. It has two regions in one address (`NY` and `TX`) and one locality. The resolver tries to satisfy it and fails, because no `parent_id` chain places Houston in both New York and Texas. The output is incoherent.

**Interpretation Y** takes the `venue` reading for `NY-NY`:

```
NY-NY Steakhouse → venue    (0.55 × ?)
Houston          → locality (0.85 × ?)
TX               → region   (0.95 × ?)
```

This reading has one venue, one locality, and one region. The resolver _can_ satisfy it: `parent_id(Houston) = Texas`. The venue does not need to be in the gazetteer, because venues are user-supplied free text.

Interpretation Y is **joint-coherent**, and Interpretation X is not. The classifier alone cannot tell them apart, because it scores each span in isolation. Stage 5 sees all the spans together.

### How the scoring works

Stage 5 runs a beam search over `(span × tag × resolver candidate)` and scores each combination with:

```
score = phrase_confidence × classifier_confidence × resolver_score × concordance_bonus
```

The `concordance_bonus` is the new factor. For each candidate parse tree, Stage 5 looks up the `parent_id` chain in the Who's On First gazetteer (see [Resolver and WOF](./resolver-and-wof.mdx)) and checks whether the chain agrees with the tags:

- Interpretation X says `region: NY` and `locality: Houston`. WOF records `Houston → Texas`, not `Houston → New York`, so the chain disagrees. The bonus drops to ~0, which nearly eliminates the interpretation.
- Interpretation Y says `venue: NY-NY Steakhouse, locality: Houston, region: TX`. The chain `Houston → Texas → United States` is intact, so the bonus is ~1.0.

The product favors Y by a wide margin, even though its individual span scores are lower. The consistency check dominates because downstream consumers cannot use an incoherent parse.

### The empty-parse trap

The first version of the reconciler used a purely multiplicative score. In testing, the score was _maximized_ by emitting **no spans**. Every factor is in `[0, 1]`, so fewer factors produce a higher product, and the empty parse won every comparison. Stage 5 fixes this by adding a fixed log-bonus for each accepted slot, which makes accepting a high-confidence span a net gain. See [`reconcile-empty-parse-bonus.md`](./reconcile-empty-parse-bonus.mdx) for the full failure. This bonus is the only non-obvious setting in the joint decoder.

## Stage 6 — resolver looks up coordinates

Stage 6 takes the winning parse tree from Stage 5 and matches each typed span to a place row in WOF. For Interpretation Y:

| Span               | Tag      | WOF lookup                            | Result                                 |
| ------------------ | -------- | ------------------------------------- | -------------------------------------- |
| `NY-NY Steakhouse` | venue    | (no lookup — venues are pass-through) | preserved as venue text                |
| `Houston`          | locality | locality + region:TX hint             | Houston, Texas (lat 29.76, lon -95.37) |
| `TX`               | region   | region in US                          | Texas (lat 31, lon -100)               |

The country is inferred from the region's parent chain (`Texas → United States`).

## Output

The full v0.5.0 output for `NY-NY Steakhouse, Houston, TX` is:

```json
{
	"venue": "NY-NY Steakhouse",
	"locality": "Houston",
	"region": "TX",
	"country": "US",
	"coordinates": [29.76, -95.37],
	"confidence": 0.42
}
```

The confidence is the product of the winning interpretation's per-stage scores. It is modest (0.42) because the underlying signals are modest. For example, `Houston` got only 0.65 from the phrase grouper, and the venue tag was the classifier's second choice. The parse is still _correct_, which was the v0.5.0 goal for this input.

## Why this was impossible before v0.5.0

The previous pipeline (v0.4.0 and earlier) had three limits:

- It had no phrase grouper, so Stage 3 had to infer boundaries _and_ types at once from BIO labels.
- The classifier returned only the argmax, without top-k.
- Stage 5 only sorted spans by position and emitted them in order.

With those limits, `NY-NY Steakhouse, Houston, TX` returned `region: NY, locality: Houston, region: TX`, and downstream code crashed on the two regions. The fix had to go in the reconciler, because by design each upstream stage sees only its own part of the input.

This example illustrates the [knowledge-ladder](../understanding/our-approach/the-knowledge-ladder.mdx) argument. Each stage contributes one kind of information, and the joint decoder combines them. Without a joint decoder, geocoders fail on adversarial inputs like this one. Adding it was most of the v0.5.0 work.
