# Input robustness — absorbing the mess users type

Addresses in a test fixture are clean, and the addresses a geocoder receives are often messy. They arrive in all caps from a compliance export, with commas squeezed together from a spreadsheet paste, missing a letter from fast typing, or with `Ave` where the fixture said `Avenue`. A parser that works only on clean input is not usable in production.

The useful test is whether `1600 PENNSYLVANIA AVE NW,WASHINGTON DC` resolves to the same rooftop as `1600 Pennsylvania Avenue NW, Washington, DC 20500`. This page describes how Mailwoman handles that input. Three layers remove surface noise before it can move the coordinate, and three checks verify each layer.

## The absorption stack

The three layers are ordered from the cheapest and most certain transforms to the most learned. Each layer handles variation that the layer before it should leave alone.

### Layer 1 — deterministic normalization

The first pass is plain code without a model, in [`@mailwoman/normalize`](https://github.com/sister-software/mailwoman/blob/main/docs/engineering/reference/STAGES.mdx). It applies only transforms that have a single correct answer:

- Unicode NFC, so a composed `é` and a decomposed `é` become the same string.
- Punctuation folding.
- Whitespace collapse, which reduces a run of spaces to one and trims a trailing `.`/`,`/`;`/`:` (`normalize/whitespace.ts`).

The trailing-punctuation trim fixed a real failure. A stray period attached to the final token (`…Washington DC.`) used to drop the street tier from `address_point` to `admin`, and trimming it costs nothing.

Every transform is offset-mapped. The normalized string carries a map back to the raw character positions, so a span the model finds in the clean text still points at the right bytes of the user's input. A normalization that corrupted the offsets would do more harm than good.

This layer deliberately does **not** expand abbreviations at runtime. `normalize/abbreviations.ts` can turn `Rd` into `Road` and `Ave` into `Avenue`, and it is fully built. It is opt-in, and the runtime pipeline leaves it off (`normalize/compute.ts`). Abbreviation handling belongs to the model. A hard-coded `Ave → Avenue` rule in front of the parser would take a decision away from the model, and the model could not correct the rule if it proved wrong for a locale. See [What Mailwoman is](./what-mailwoman-is.mdx) for why hand-written knowledge stays out of the model's input path.

### Layer 2 — model-side case normalization

Some noise is too locale-sensitive for Layer 1 but too systematic to leave to the corpus. Casing is the main example. A model trained on mixed-case text is partly out of domain on an all-caps compliance record, where it drops tokens and sets wrong span boundaries. For example, `214 JONES RD, ELKHART, TX 75839` produced a locality of `ALESTINE`. `neural/case-normalize.ts` therefore title-cases an all-caps input before the model sees it (#690), and it restores the trained mixed-case form of an all-lowercase input (#829). Both are on by default.

The detection is deliberately strict. Only an input that is entirely uppercase or entirely lowercase qualifies, so ordinary mixed-case text passes through with an identical byte path. The transform must also keep offsets stable. It handles only pure-ASCII input, because title-casing accented or non-Latin text can change length (`ß`→`SS`, the Turkish dotted and dotless I) and break the offset mapping that Layer 1 preserves. Measured on TX HHSC data, locality recall went from 90.1% to 99.7%.

### Layer 3 — trained-in variation

The last layer is the training corpus rather than a pass. The parser learns to handle surface variation because the training data contains it. The corpus includes casing permutations (`corpus/src/extract-recipes/intersection.ts`, `locale.ts`) and abbreviation variants in both directions (`street-affix.ts`, the `unit.ts` designators from #454, `fr-bare-street.ts`). This layer teaches the model that `Ave` and `Avenue` are the same street. No rule rewrites one into the other. The model saw both forms in training and learned that they refer to the same place.

Layer 3 is what makes it safe for Layer 1 to skip abbreviation expansion. Because the model trains on both forms, `normalize/` can leave abbreviations alone. The three layers divide the work. Deterministic code handles transforms with one right answer, the corpus handles variation whose meaning depends on context, and case normalization covers the systematic casing gap between them.

## The checks

Each layer needs a measurement to show that it works. Three checks cover these layers, and each grades something different.

### Metamorphic INV/DIR/BAND — the un-gameable layer

The most important check is `mailwoman eval gauntlet --layer metamorphic` (`mailwoman/eval-harness/gauntlet/metamorphic.ts`), layer 2 of [the Gauntlet](./eval-discipline.mdx). It asserts _relations_ between outputs instead of comparing against stored expected values. A curated corpus therefore cannot inflate its results. It also grades the **assembled geocode**, meaning the coordinate and tier rather than parse F1. A robustness bug that leaves the tags intact but moves the coordinate still returns a wrong answer.

The check has three relation families, separated by how much a perturbation may change the answer:

- **INV (invariance, ≤1m).** A label-preserving perturbation of a base address must not move the coordinate more than a meter (`INV_EPSILON_KM = 0.001`) or change the resolution tier. The perturbations are lowercasing, uppercasing, doubling the spaces, appending a stray dot, removing the space after a comma, and replacing an expanded suffix with its abbreviation. The `abbrev` case inverts the `normalize/` abbreviation table (`Avenue`→`Ave`). It passes because the model trains on both forms.
- **DIR (directional, ≤5km).** With the postcode removed, the result must still land within 5km of the result with the postcode. This keeps the #251 failure class, where the parser failed as soon as a user omitted the ZIP, as a permanent check.
- **BAND (tolerance, ≤5km).** A _corrupting_ perturbation may change the parse, so requiring byte-identical output would be the wrong test. These perturbations are a single-character transposition or substitution, or a spelled-out ordinal or house number. The result must still land within a tolerance band of the clean coordinate. This family catches classes of input the pipeline never trained on.

When a perturbation fails deterministically, it goes in `KNOWN_INV_XFAIL` or `KNOWN_BAND_XFAIL` with a tracking note. The failure stays visible without blocking the build, so the check fails only on _new_ regressions. An xfail that starts passing is flagged for removal. This prevents the list from growing stale the way Pelias's pass-list did, which this design was built to avoid.

Casing and spacing pass. The two normalizer changes above (#829's lowercase restore and the trailing-punctuation trim) fixed them without retraining. The EN suffix abbreviations also pass. The tracked xfails cover the rest:

- The FR `Boulevard`→`Bd` swap drops from rooftop to admin tier. The street gazetteer stores the expanded type, so the abbreviation misses the point-tier name match. The gap is in the resolver rather than the model.
- House-number spelling falls outside the band.
- A single-character typo in a locality or street can lose the coordinate.

The typo cases are measured with the anchor and gazetteer channels off, which is the harness default. In the shipped configuration, the gazetteer soft-feed is the mechanism that would recover a misspelled `Amsterdam`. Read these results as the anchor-off baseline. They do not measure production behavior.

### Golden `graceful/*` sets — labeled adversarial cases

The golden set (`data/eval/golden/v0.1.2`) includes a small hand-labeled adversarial track under `graceful/*`. It covers typos (`Pensylvania`, `Portlnad`, `Fransisco`), incorrect casing, incorrect punctuation, and irregular whitespace. Around ten of these are single-character typo cases. The track is a stress test with expected components. It does not check coordinates. The parse should still succeed at lower confidence, and the labels define the expected result.

### `perturb-golden.ts` — the one-off arena

`packages/mailwoman/lib/dev-tools/perturb-golden.run.ts` takes golden rows and applies perturbations designed to break rule-based parsers, such as stripping the delimiters, lowercasing everything, or joining the region to the postcode as `OR97214`. It keeps the component labels intact. Its purpose is to show that a contextual model degrades more gracefully than a rule parser that depends on delimiters. It is a generator you run on demand. No standing check runs it.

## The coverage matrix

The table maps each perturbation class to the layers that handle it and the check that covers it, including the gaps.

| Class                                        | `normalize/` (runtime)                     | Trained (corpus aug) | Conditional                                                                                               |
| -------------------------------------------- | ------------------------------------------ | -------------------- | --------------------------------------------------------------------------------------------------------- |
| Casing                                       | yes (case-normalize #690/#829, model-side) | yes                  | INV[lower/upper] green                                                                                    |
| Spacing                                      | yes (whitespace.ts)                        | incidental           | INV[ws], INV[comma-tight] green                                                                           |
| Abbreviation swap (Road↔Rd)                  | capable but off at runtime (deliberate)    | yes                  | INV[abbrev]: EN suffixes green; FR `Bd` tracked-xfail (resolver name-match gap)                           |
| Number spelling (5th↔Fifth, 100↔One Hundred) | no                                         | no                   | BAND[num-ordinal] green; BAND[num-house] tracked-xfail (untrained)                                        |
| Typos (single-char edit)                     | no                                         | no                   | BAND[typo-sub]: most bases green; tracked-xfail where a typo'd locality/street loses the pin (anchor-off) |
| Transpositions                               | no                                         | no                   | BAND[transpose]: same anchor-off gaps as typo-sub                                                         |

Casing and spacing are resolved. The runtime handles them, the corpus reinforces them, and a standing invariant passes on them. The bottom four rows used to be untested. They now run through the metamorphic check, and several of them already pass. The EN suffix abbreviations pass the strict one-meter invariant. Ordinal street spelling (`5th`↔`Fifth`) stays inside the tolerance band even though no training data covers it. The gaps were smaller than expected, and the xfail maps list each one:

- a French street-type abbreviation that the resolver cannot match at rooftop tier
- house-number spelling
- single-character typos that lose a locality or street when the anchor and gazetteer channels are off

Each gap is a tracked line item that the check reports on every run.
