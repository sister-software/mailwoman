# Choosing the dedup yardstick — why org-name rather than NPI

"How good is the matcher at deduplication?" sounds like a question with one
number for an answer. The answer depends on which ruler you measure against.
On the NPPES provider registry, the ruler you reach for first gives a misleading
answer.

The **NPI** (National Provider Identifier) looks like clean held-out truth. It
is a stable, government-issued key, assigned once per registration. You can run
[the matcher](./geocode-first-record-matching.mdx) blind to the NPI and then grade its clusters against it. Two records
that share an NPI _should_ land together, a cluster fusing two NPIs is an
over-merge, and an NPI split across clusters is an under-merge. This approach
needs no labels or adjudication, only counting. On this registry, it is wrong
by construction.

## One organization, several NPIs

The NPI is a registration key rather than an organization key. A single hospital system
holds a **separate NPI for every billing subpart** — each clinic, each
department, sometimes each location — plus legal-form variants, state qualifiers,
and the occasional typo'd re-registration. `Baylor College of Medicine` appears
four times at one address (`1504 Taub Loop`); `WAL-MART STORES TEXAS LLC` and
`… LP` are the same Walmart pharmacy under two corporate names. Each group is one
organization with several registration numbers.

When the matcher correctly recognizes that four co-located `Baylor` records are
one place, NPI-as-truth scores all six of those within-org pairs as
**over-merges**. The matcher is penalized for being correct, so a lower measured
precision may indicate that it is working better.

## Four rulers, one set of clusters

The fix is a better ruler rather than a better model. We grade the **identical**
matcher output against four entity-truths, ordered from over-segmenting to
tightest:

- **NPI** — one entity per registration. Over-segments every multi-subpart org.
- **site** — collapse NPPES-flagged subparts back into their parent, then split
  an NPI's distinct addresses (mailing vs practice). Closer, but the
  subpart flag is conservative: it misses the 37% of same-org pairs that aren't
  flagged.
- **org-name** — the gold-set-validated truth: same NPI implies same entity
  (recall preserved), **plus** collapse co-located NPIs whose primary
  organization names agree (token Jaccard ≥ 0.7), with no reliance on the subpart
  flag. Co-location here is the address _string_ key — so it still misses
  same-building records whose text drifts.
- **org-name (coord)** — the same rule, but co-location is keyed on the geocoded
  **building** (within 50 m) rather than the address string. `1504 Taub Loop` and `1504
Taub Lp Ste 100` key apart as strings yet geocode to one point, so this collapses
  the same-building same-org pairs the string key leaves split. It is the
  geocode-first key, and the tightest ruler of the four.

The same 2757-record sample carries **1000 NPI** classes → **1456 site** → **956
org-name** → **928 org-name (coord)**. The class count first _expands_ (site splits
multi-address NPIs) and then _contracts_ below the NPI count (org-name fuses the
co-located subparts, and the coordinate key fuses a few more). That pattern shows
over-segmentation being corrected.

Grade the shipped GBT scorer's clusters against each ruler and the F1 climbs
**53.6% (NPI) → 55.3% (site) → 60.7% (org-name) → 68.1% (coordinate)** — a
**+14.5pp** swing with the clusters held _identical_. The over-merge count falls
(109 → 76) and precision rises (43.7% → 64.6%) for the same reason: the ruler stops
counting correct same-org merges as errors, and the geocode-first building key
catches the most of them. The climb comes from a more precise yardstick, and the
model does not change.

## Why we trust the org-name ruler

A ruler invented to raise a score is worthless unless it is _right_, so the
org-name collapse was validated against a frozen gold set: the hardest
stratum — co-located, name-similar, **distinct** NPIs that are **not** flagged
subparts — adjudicated one pair at a time. The verdict was unanimous:
[**120 of 120**](https://github.com/sister-software/mailwoman/blob/main/docs/records/evals/matcher-dedup/2026-06-16-dedup-gold-set-tx120.md) were the same
real-world organization; **zero** were two unrelated companies wrongly fused.
Every hard pair the matcher merges at a shared address is a correct merge that
NPI-truth was scoring as an error.

That result also settled the model question. An earlier experiment added
"corroboration" features aimed at reducing over-merges, and precision did not
move. The gold set explains why: there was almost no over-merge to reduce.
Optimizing the scorer for precision here targets errors that do not exist. The
ruler was the thing that needed to change.

## The discipline

Report the number that matches the entity you are resolving. For NPPES
organization dedup that is the **org-name F1 — ~60.7% by the address-string key,
~68.1% by the geocode-first building key** — not the NPI-level 53.6%, which mostly
measures NPI over-segmentation, a property of the registry rather than of the matcher.
State the ruler next to the number every time. A dedup F1 without a named
truth-grain cannot be interpreted.

The rest of the system follows the same principle: [grade the pipeline against
the right target rather than a convenient proxy](./eval-discipline.mdx). The remaining
org-name over-merge (76 clusters at the coordinate grain) is the remaining work. It is small and
approaching the [irreducible ceiling](https://github.com/sister-software/mailwoman/blob/main/docs/records/evals/matcher-dedup/2026-06-16-dedup-ceiling.md) of co-located
distinct organizations that no address-based signal can separate.

A closing note on framing: NPI-as-truth is _conservative_ in the direction that
matters. A cluster fusing two NPIs is a candidate "same entity, two registrations"
**surfaced for review** rather than an adjudicated error; an NPI split across distant
addresses is geocode-first behaving correctly. We resolve and report the join;
what it _means_ is the consumer's call.
