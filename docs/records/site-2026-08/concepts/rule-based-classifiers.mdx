# Rule-based classifiers

A rule classifier is a small piece of hand-written code that labels tokens. Pelias and Mailwoman v1 are built almost entirely on rule classifiers. Mailwoman v2 keeps them and runs the neural classifier beside them. [How it works now](../understanding/our-approach/how-it-works-now.mdx) describes the hybrid.

This article describes how rule classifiers are structured and where they work well and poorly.

## One classifier per component

Mailwoman has one rule classifier per address component type, and they all run in parallel. The classifier interface looks roughly like this:

```ts
interface RuleClassifier {
	id: string // 'postcode', 'house_number', …
	component: ComponentTag
	classify(tokens: Token[], context: Context): ClassificationProposal[]
}
```

Each classifier:

- Reads the full token sequence, so it can use the next or previous token as context.
- Returns zero or more proposals. Each proposal states something like "tokens i..j are a `postcode` with confidence 0.95".
- Runs independently of every other classifier. The solver merges their proposals.

## A worked example — the postcode classifier

The postcode classifier is probably the simplest. Postcode detection is a regex problem. It does not need machine learning.

```ts
const US_POSTCODE = /^\d{5}(-\d{4})?$/  // 10118 or 10118-1234
const FR_POSTCODE = /^\d{5}$/            // 75008
const UK_POSTCODE = /^[A-Z]{1,2}\d[A-Z\d]? ?\d[A-Z]{2}$/i  // SW1A 1AA

classify(tokens: Token[], context: Context): ClassificationProposal[] {
	const out: ClassificationProposal[] = []
	for (const token of tokens) {
		if (US_POSTCODE.test(token.text)) {
			out.push({
				span: token.span,
				component: "postcode",
				confidence: 0.95,
				source: "rule",
				source_id: "rule:postcode:us",
				penalty: 0,
				metadata: { country_hint: "US" },
			})
		}
		// FR + UK regexes similarly
	}
	return out
}
```

Three details matter:

1. **Confidence is below 1.0** even when the regex matches. A 5-digit number could also be a house number (rare) or a year. The solver sees the high score and can still reject the proposal if the other classifiers support a better interpretation.
2. **The country hint goes in metadata.** The classifier sets `country_hint: "US"` when the US pattern matches. The solver can use the hint to bias the country classification.
3. **Several patterns can match.** If the same token matches both the US and UK regexes, the classifier emits two proposals, and the solver chooses between them.

## A harder example — the locality classifier

The locality classifier is harder because no regex can tell whether a word is a city name. The Mailwoman v1 locality classifier looks up each token, and short n-grams of consecutive tokens, in a [Who's On First](https://whosonfirst.org/) dictionary file. Pseudo-code:

```ts
const WOF_LOCALITIES: Set<string> = loadDictionary("wof/locality.txt")

classify(tokens: Token[], context: Context): ClassificationProposal[] {
	const out: ClassificationProposal[] = []
	for (let i = 0; i < tokens.length; i++) {
		// Try 1-, 2-, and 3-token spans
		for (let len = 1; len <= 3; len++) {
			const candidate = tokens.slice(i, i + len)
			const text = candidate.map((t) => t.text).join(" ")
			if (WOF_LOCALITIES.has(text)) {
				out.push({
					span: { start: candidate[0].span.start, end: candidate.at(-1)!.span.end },
					component: "locality",
					confidence: 0.6,
					source: "rule",
					source_id: "rule:whos_on_first:locality",
					penalty: 0,
				})
			}
		}
	}
	return out
}
```

Notes:

- **Confidence is moderate** (0.6) because dictionary matches can be misleading. "New" starts several city names, so a 1-token match on "New" is weaker evidence than a 3-token match on "New York City".
- **An n-gram sweep** handles multi-word cities. The classifier tries spans of length 1, 2, and 3 and emits a proposal for each match.
- **The classifier does not exclude overlapping matches.** If "New York" matches as a locality and "New" matches as a different component, both proposals are emitted. The solver picks one self-consistent combination.

## What rule classifiers are good at

- **Determinism.** The same input always produces the same output, without retraining or random initialization.
- **Easy fixes.** A regex bug takes a one-line fix, while a bug in a neural model takes a retraining run.
- **No training data.** A rule classifier ships in code. The dictionary classifiers ship a few MB of dictionaries rather than a multi-GB model.
- **Speed.** Pattern matching takes microseconds per address, and the whole parse runs in milliseconds.
- **Explainability.** Every proposal carries a `source_id`. A consumer that sees `rule:postcode:us` on a wrong proposal knows exactly where to look.

## What rule classifiers are bad at

- **The long tail.** Real-world inputs do not follow predictable patterns. Every regex misses some inputs.
- **Context.** A regex sees one token at a time. "Lincoln" might be a city, a person, or a venue, and a regex cannot tell which.
- **Languages.** Every locale needs its own hand-written rules from someone who knows that language.
- **Multi-word components.** N-gram sweeps work for 2- and 3-token cases. "Saint Petersburg, FL" works, and "Mt Tabor Forest Preserve" (a 4-token venue) is harder.
- **Negative evidence.** A rule can say "this looks like X". It cannot easily say "this looks like X only when Y is absent".

These weaknesses motivated the neural classifier. See [How the model reasons](./how-the-model-reasons.mdx).

## How rule classifiers and the neural classifier coexist

In Mailwoman v2, both kinds of classifier produce `ClassificationProposal`s in the same shape. The **policy registry** decides whose proposal wins for each component:

```ts
const policy: ClassifierPolicy[] = [
	{ component: "postcode", mode: "rule_only" }, // regex wins, model not even consulted
	{ component: "country", mode: "rule_preferred" }, // rule wins unless rule confidence is very low
	{ component: "venue", mode: "neural_only" }, // rules can't classify venues at all
	{ component: "house_number", mode: "neural_preferred" }, // model is stronger here in v3.0.0
]
```

The neural classifier takes over one component at a time, after it proves itself on that component. If a neural model regresses, switching the component back to `rule_only` takes one line of config.

## Where this lives in the code

- `core/classifiers/` (in the v1 tree): every rule classifier
- `core/policy/`: the per-component policy registry
- `core/solver/`: the merger that picks self-consistent combinations
