# Switching from Photon

[Photon](https://photon.komoot.io) is a type-ahead geocoder that searches as you type and returns GeoJSON. It runs on an Elasticsearch cluster, which must load a Photon import before it can answer queries. Mailwoman serves the same `/api` interface from a SQLite file, so your autocomplete keeps working without the cluster.

**Try it first.** We host a live instance at [photon.mailwoman.ai](https://photon.mailwoman.ai), so you can test it without installing anything or waiting for an import. Open [`/api?q=berlin&limit=3`](https://photon.mailwoman.ai/api?q=berlin&limit=3) in a browser, or point your existing Photon client at the host, and check the GeoJSON it returns. When the results look right, the command below runs the same service on your own machine.

## One command

```bash
npx @mailwoman/photon serve --port 2322
```

```bash
curl "http://localhost:2322/api?q=berlin&limit=5&lat=52.5&lon=13.4"
curl "http://localhost:2322/reverse?lat=52.52&lon=13.405"
```

## Endpoint map

| Photon         | Mailwoman      | Parameters honored             |
| -------------- | -------------- | ------------------------------ |
| `GET /api`     | `GET /api`     | `q`, `limit`, `lat`/`lon` bias |
| `GET /reverse` | `GET /reverse` | `lat` / `lon`                  |

`limit` returns the top-N ranked matches, so an ambiguous name like `Springfield` returns each instance. `lat`/`lon` is a proximity bias: the same query near different map centers ranks results closer to the viewport higher. `lang` and `osm_tag` are accepted for wire compatibility but not yet applied. `lang` has no effect because the model ships a single (en-US) locale, and `osm_tag` layer filtering is on the roadmap.

Both endpoints return a GeoJSON `FeatureCollection` of `Point` features with `properties` (`name`, `street`, `postcode`, `city`, `county`, `state`, `country`, `countrycode`, `osm_key`, `osm_value`, `type`, …). Photon clients already parse this shape.

## What's different

- **It does not use Elasticsearch.** Resolution runs over the same SQLite gazetteer as the rest of Mailwoman, and `/api` uses the FST autocomplete tier plus the neural parser.
- **Properties** come from the Who's On First / Overture placetype chain, mapped to Photon's key names, rather than from raw OSM tags.

## What's missing

- **Prefix ranking** is a separate problem. Today Mailwoman's `/api` resolves the query through the geocoder. A dedicated prefix-first FST front end is the planned change to match Photon's tuned type-ahead ordering.
- **Coverage** follows the gazetteer. It is strong in the US and improving across the EU.

## Photon in the wild

[Cartes](https://cartes.app), an open-source French web map we admire, shows Photon in production. It runs its own Photon instance and adds France's [BAN](https://adresse.data.gouv.fr) address API for house-number queries. The combination works well for them. A parser-first geocoder does not need that kind of per-country addition. Mailwoman reads the house number in the query and resolves it directly against the same BAN rooftop data.

See [how Mailwoman compares](./how-mailwoman-compares.mdx#what-about-the-map-apps) for the full capability matrix and a longer note on Cartes. For structured lookup (the Nominatim shape) instead of autocomplete, see [Switching from Nominatim](./switching-from-nominatim.mdx).
