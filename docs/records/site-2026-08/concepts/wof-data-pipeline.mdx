# WOF data pipeline — sync, prepare, resolve

Who's On First (WOF) is the gazetteer behind Mailwoman's Stage 6 resolver. It provides place IDs, parent-child chains, placetypes, and multilingual name variants for every admin boundary on Earth. This article documents how the Mailwoman codebase ingests, normalizes, and serves that data, one layer at a time, from raw GeoJSON to queryable SQLite artifacts.

[Resolver and Who's On First](./resolver-and-wof.mdx) covers the runtime. This article covers the build: how the data gets from raw GeoJSON on GitHub into a queryable per-placetype SQLite DB.

## The end-to-end flow (as designed)

```
WOF GitHub repos                     Per-placetype SQLite DBs
(100K+ .geojson files)               (<placetype>/<lang>.db)
         │                                     ▲
         │ git clone / pull                    │ upsert
         ▼                                     │
┌─────────────────┐     ┌──────────────────┐   │
│ commands/wof/   │     │ commands/wof/    │   │
│   sync.tsx      │────▶│   prepare/       │───┘
│                 │     │   index.tsx       │
│ • gh repo list  │     │   _app_worker    │
│ • git clone     │     │                  │
│ • Placetype     │     │ • glob *.geojson │
│   .prepare()    │     │ • Piscina batch  │
└─────────────────┘     │ • pluckSpec      │
                        │ • write to DB    │
                        └──────────────────┘
```

**Status (updated 2026-07-14):** every stage below has shipped. The [`mailwoman gazetteer` CLI](https://github.com/sister-software/mailwoman/tree/main/mailwoman/commands/gazetteer) now builds, verifies, and seals the unified admin gazetteer in one command: `gazetteer build admin` runs WOF ingest → Overture divisions → GeoNames folds → enrich → FTS → verify check → seal. It replaced the standalone `build-unified-wof` and `build-importance` scripts that earlier versions of this article described.

## Layer by layer

### `commands/wof/sync.tsx` — repo cloning

`sync` finds WOF data repos with `gh repo list whosonfirst-data --no-archived`, optionally filtered by `--repos` (a comma-separated allow-list). It clones or pulls each repo into a local directory. After all repos sync, it calls `Placetype.prepare()` to load the placetype hierarchy from `whosonfirst-placetypes`.

The `--repos` filter exists because the corpus build needs only a few repos (admin-us, admin-fr, postalcode-us, postalcode-fr). Cloning all ~100 WOF repos would download 2.9 GB of git data that the build never uses.

### `commands/wof/mermaid.tsx` — render the placetype hierarchy

After `sync` has populated the local clone of `whosonfirst-placetypes`, `wof mermaid` renders the hierarchy, or any subtree of it, as a Mermaid flowchart. Output goes to stdout by default, or to a file with `--output`. The `--roles` flag filters descendants by `common`, `common_optional`, and/or `optional`, which keeps charts readable when the optional part of the tree is large.

```bash
# Full tree from the root, piped to a file
node mailwoman/out/cli.js wof mermaid <localRepoDir> planet > planet.mmd

# Common-only subtree rooted at "country"
node mailwoman/out/cli.js wof mermaid <localRepoDir> country \
  --roles common,common_optional --output country.mmd

# Swap the color palette for any d3-scale-chromatic sequential interpolator
node mailwoman/out/cli.js wof mermaid <localRepoDir> planet --interpolator viridis
```

Edges are colored by their depth from the root, so lineage paths (`planet → continent → country → …`) follow a smooth gradient down the chart. The default gradient is `interpolateViridis`, which is perceptually uniform and colorblind-friendly. Pass `--interpolator <name>` to use any other `d3-scale-chromatic` `interpolate*` function (`turbo`, `plasma`, `cool`, `magma`, etc.). Node fills always use the hand-tuned blue/green/yellow role palette. Hand-tuned colors distinguish the three categorical roles better than sampled gradient colors, so the gradient applies only to edges. Cyclic interpolators (`rainbow`, `sinebow`) also work, but they produce similar colors at both ends of the gradient.

The renderer is `generateMermaidMarkup` in `core/resources/whosonfirst/placetypes/mermaid.ts`. It runs on whatever `Placetype.find(<name>)` returns from the static cache that `Placetype.prepare()` loads. It traverses with a recursive `findChildren` walk, the same one [`wof tree`](#commandswoftreetsx--emit-a-nested-json-tree) uses. Every emitted edge is a direct parent → child relationship colored by the child's role. ELK therefore lays out a clean DAG instead of a tangle of star edges from the root to every descendant. Leaf children of the root (e.g. `custom`, `ocean`, `timezone` under `planet`) sit next to their real siblings instead of at the edge of the chart. Long `classDef` / `linkStyle` lines are written directly to stdout, bypassing Ink's `<Text>` renderer, so the output stays valid Mermaid when redirected.

### `commands/wof/tree.tsx` — emit a nested JSON tree

`wof tree` takes the same inputs as `wof mermaid` (`<localRepoDir> <placetype>`, optional `--roles`, optional `--output`). It produces a recursive `PlacetypeTreeNode` (`{ name, id, role, children }`) for consumers that expect a nested tree, such as `d3-hierarchy`. `--compact` turns off pretty-printing.

```bash
# Pretty tree from "country" filtered to common roles
node mailwoman/out/cli.js wof tree <localRepoDir> country --roles common

# Compact, written to file
node mailwoman/out/cli.js wof tree <localRepoDir> locality --compact --output locality-tree.json
```

The renderer is `generatePlacetypeTree` in `core/resources/whosonfirst/placetypes/tree.ts`, a recursive `findChildren(roles)` walk. **Note:** WOF placetypes form a DAG in which many descendants are shared. For example, `installation` is a leaf reachable from several parents. A tree projection duplicates every shared subtree under every parent path. For shallow or sparse roots like `country` or `locality` the tree is small, and for `planet` it grows to ~174 MB. Use [`wof graph`](#commandswofgraphtsx--emit-a-node-link-json-graph) for large roots.

### `commands/wof/graph.tsx` — emit a node-link JSON graph

`wof graph` is the flat counterpart to `wof tree`. It emits `{ root, nodes: [...], links: [{ source, target }] }`, in which each node and each parent→child edge appears exactly once, regardless of DAG topology. `planet` is 9.4 KB in this shape, compared with 174 MB nested. Field names follow d3-force / react-flow / cytoscape conventions, so common HTML graph viewers can load the output directly.

```bash
# Full planet graph, compact JSON, ~9 KB
node mailwoman/out/cli.js wof graph <localRepoDir> planet --compact --output planet-graph.json

# Common-only subgraph rooted at "country"
node mailwoman/out/cli.js wof graph <localRepoDir> country --roles common
```

The renderer is `generatePlacetypeGraph` in `core/resources/whosonfirst/placetypes/graph.ts`. It uses the same recursive `findChildren(roles)` walk, but it records visited nodes and emitted (parent, child) pairs in sets, so nothing is emitted twice. It stays O(nodes + edges) for any root.

### `commands/wof/prepare/index.tsx` — batch GeoJSON processing

`prepare` does most of the ingest work. It is designed to process 100K+ individual `.geojson` files, one per WOF feature, with Piscina worker threads.

**Architecture:**

- The main thread globs `**/*.geojson` from the admin directory with `fast-glob` streaming.
- `takeAsync(matchStream, BATCH_SIZE)` groups the files into arrays of filenames, one per available CPU core.
- `asyncParallelIterator(fileNames, BATCH_SIZE, delegateInsertion)` dispatches each batch to workers.
- Workers run `_app_worker.mts::insertRecord(filePath)`, which reads the file, parses the GeoJSON, and calls `pluckPlacetypeSpec` to extract structured fields.

**What `pluckPlacetypeSpec` produces:**

```ts
interface ParsedWOFPlacetype {
	id: number
	parent_id: number
	name: string
	src: string
	placetype: WhosOnFirstPlacetype
	localizedPropMap: Map<Alpha3bLanguageCode, Map<WOFNameKind, string>>
}
```

The `localizedPropMap` holds the multilingual name variants. For each language code (ISO 639-3b), it carries the `preferred`, `variant`, `colloquial`, `abbr`, and `short` forms, which match the columns of `PlacetypeDataSource.records`.

The worker writes to `PlacetypeDataSource`, a set of small per-placetype SQLite DBs. An earlier version wrote to Redis, and v0.5.0 replaced it.

### The incomplete "send batches of filenames" design

The original design was more efficient than the current per-file dispatch:

1. The main thread globs a batch of N filenames (N = `availableParallelism()`).
2. It sends the entire batch to one worker, instead of one filename per Piscina task.
3. The worker processes the batch sequentially and builds an in-memory table of results. File reads are fast once the files are cached.
4. The worker returns the batch results to the main thread, or writes them to an in-memory SQLite DB and then flushes it.

This design needs one IPC round-trip per batch instead of one per file. It also lets the worker keep a DB connection open across the batch instead of opening and closing one per row. The per-file dispatch in the current code was the first version, and batched filenames were the planned next step.

### The in-memory-SQLite-then-consolidate idea

A related design was never built. In it, each Piscina worker holds its own `:memory:` SQLite database during the batch and inserts all processed records into it, without disk I/O during processing. At the end of the batch, the worker dumps the in-memory DB to a temporary file and signals the main thread. The main thread then merges the N temporary DB files into the final per-placetype/per-language DBs on disk with `ATTACH DATABASE` + `INSERT INTO ... SELECT FROM ...`.

The reasons for writing to memory first:

- It avoids disk contention during processing. 100K individual writes to the same few DB files from N concurrent workers would serialize on SQLite's WAL writer.
- Workers are fully independent, without shared file handles or lock contention during processing.
- Consolidation is a single bulk operation after all workers finish, and SQLite handles it efficiently with `ATTACH`.

This design never went past the design stage. The Redis target was good enough for prototyping. By the time it was clear that Redis would not be used in production, other work (the neural classifier, corpus pipeline, and resolver integration) took priority.

### `PlacetypeDataSource` — the target schema

Per-placetype, per-language SQLite DB files at `<dataDir>/<placetype>/<lang>.db`. Schema:

```sql
CREATE TABLE records (
  'id'        INTEGER NOT NULL,
  'src'       TEXT NOT NULL,
  'name'      TEXT NOT NULL,
  'preferred' TEXT,
  'variant'   TEXT,
  'colloquial' TEXT,
  'abbr'      TEXT,
  'short'     TEXT,
  'parent_id' INTEGER,
  PRIMARY KEY ('id', 'src', 'name')
);
```

- `id`: WOF Brooklyn Integers ID.
- `parent_id`: the hierarchy chain for concordance scoring.
- `name` and the variant columns: the aliases the reconciler matches against. "Saint Petersburg", "St. Petersburg", and "St Petersburg" are the `name`, `variant`, and `short` values for the same ID.
- `src`: provenance (whosonfirst, quattroshapes, etc.).

`DataSourceCache` manages a pool of open `PlacetypeDataSource` handles, keyed by `(placetype, languageCode)`. It opens each handle on first access, and the handles are disposable.

### `Placetype` — the hierarchy cache

`Placetype` is an in-memory hierarchy built from the `whosonfirst-placetypes` codex, a JSON spec that defines the parent/child/sibling graph of all WOF placetypes. `Placetype.prepare()` reads the JSON files from the cloned repo and populates static maps (`#byID`, `#byName`, `#childrenOfParentName`).

This is the **placetype-level** hierarchy (country → region → county → locality → neighborhood), not the per-record parent_id chain. The per-record `parent_id` chain lives in `PlacetypeDataSource`.

To inspect this hierarchy, use [`wof mermaid`](#commandswofmermaidtsx--render-the-placetype-hierarchy) for a flowchart, [`wof graph`](#commandswofgraphtsx--emit-a-node-link-json-graph) for flat node-link JSON, or [`wof tree`](#commandswoftreetsx--emit-a-nested-json-tree) for a nested form (small subtrees only). All three read the same in-memory cache.

### `WOFPlacenameCache` + `loader.ts` — the GeoJSON-direct index

This separate path builds a normalized placename→languages index directly from the GeoJSON source files with `fast-glob` + `TextSpliterator`. The rule-based classifiers (locality/region dictionaries) use it to check whether a string is a known placename in any language, without going through SQLite.

This path works today. It reads raw GeoJSON and builds Map-based indexes in memory, without `PlacetypeDataSource`. The two paths were always meant to coexist: `WOFPlacenameCache` serves the rule classifiers, and `PlacetypeDataSource` serves the resolver and reconciler. They have different query patterns and different storage tradeoffs.

## Where Spliterator fits

The `spliterator` package, published separately as `@sister-software/spliterator`, was written for this pipeline:

- **`TextSpliterator`** iterates line by line over file streams without loading entire files into memory. `loader.ts` uses it to read the large WOF GeoJSON bundles.
- **`AsyncSpliterator.asMany(source, delimiter, concurrency)`** splits a single large file into N concurrent byte-range iterators for parallel processing. It is designed for WOF data that arrives as a single NDJSON dump (e.g. from data.geocode.earth) rather than 100K individual files. It is marked `@internal` and has never run at scale, because the individual-file path was sufficient for the repos we use.
- **`asyncParallelIterator` / `takeAsync`** are the batching primitives that `commands/wof/prepare` uses to dispatch work to Piscina workers.

Spliterator handles **read** parallelism by splitting a file into chunks. Piscina handles **compute** parallelism by processing parsed records across CPU cores. `PlacetypeDataSource` handles the **write** to structured storage. The pipeline needs all three layers, and today only the first two are connected.

## How this connects to the reconciler

The Stage 5 joint decoder (`reconcileSpans` in `core/pipeline/reconcile.ts`) needs three inputs per span:

1. **Phrase proposals** from the phrase grouper (shipped and working).
2. **Classifier top-k** from per-span logit aggregation (PR in progress).
3. **Resolver candidates + parent chains** from `PlacetypeDataSource`.

This pipeline produces item 3. Specifically:

- **Name lookup**: given a span body like "Houston", find all `PlacetypeRecord` rows where `name = 'Houston'` OR `variant = 'Houston'` OR `abbr = 'Houston'` etc. Filter by `placetype`, for example only `locality` candidates for a span the classifier tagged as locality.
- **Disambiguation**: when there are multiple candidates (WOF US admin has 13 "Houston" entries), filter by `parent_id`. The classifier's region tag for the same input narrows the candidate set.
- **Parent-chain walk**: for concordance scoring, walk `parent_id` up the hierarchy to `country`. The chain `Houston (id=3) → Texas (id=2) → United States (id=0)` tells the reconciler that `locality=Houston, region=TX` is coherent.

The WOF spot-check (2026-05-24) found the raw `spr` table's parent_id chains reliable (18/20 correct). It also found two problems that the prepare pipeline needs to address:

1. **Name aliasing**: a bare `name` lookup does not find "Saint Petersburg", because WOF stores it as "St. Petersburg". This is [a known WOF failure mode](./whosonfirst-gotchas.mdx). The `variant`/`short` columns in `PlacetypeDataSource` are designed for this case, and they still need to be populated.
2. **Disambiguation**: a bare-name lookup without `parent_id` filtering picks the wrong record. A Nebraska village named "New York" outranks NYC because of alphabetical ID ordering. The `find` query needs a `parent_id` filter or population-weighted ranking.

Completing the prepare pipeline populates the variant columns and fixes the first problem. Calling `PlacetypeDataSource.find` with criteria that filter by parent_id or placetype fixes the second.

## What needs to happen next

In priority order:

1. **Migrate the worker target from Redis to SQLite.** In the recommended design, each worker opens `PlacetypeDataSource` per (placetype, language) on demand and batch-inserts in a wrapped transaction, with 1000 rows per COMMIT for throughput. Workers write to separate DB files, so they need no cross-process locking.

2. **Send filenames to workers in batches** instead of one at a time, to reduce IPC overhead. Each Piscina task gets an array of file paths, and the worker processes them sequentially over one open DB connection.

3. **Connect `PlacetypeDataSource` to the reconciler** as the `ResolverCandidatesLookup` + `ParentChainLookup` implementation. This replaces the mocked resolver in the reconciler's current tests with real data.

4. **(Stretch) Use the in-memory-then-consolidate design** for maximum throughput. Workers write to `:memory:` during processing and dump to temp files at the end of each batch, and the main thread merges the files with `ATTACH`. This is worth doing only if steps 1 and 2 are too slow for the full WOF dataset (~120K features × 5-10 languages = 600K-1.2M rows).
