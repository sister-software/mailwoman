## The overlay `link-dev-weights.ts` copy-paste template

The locale overlay packages (`neural-weights-de-de`, `-es-es`, `-it-it`, `-en-in`, …) each carry their
own `scripts/link-dev-weights.ts`. The small ones are ~117 lines and were cloned from one another, so
a new locale is added by copying a sibling. Copying reliably localizes the code and leaves the prose
behind. `es-es` and `it-it` both shipped `de-de`'s docstring. It told the reader that the script exists so
`resolveWeights({locale: "de-de"})` resolves, and that the index is inert without the `de` entries
because "German addresses write 50733 Köln". The code was right in both packages, but everything a
reader would use to verify it pointed at the wrong country. No check catches this, because the script works.

If you add a locale overlay, rewrite the docstring for the locale you are adding as well as the paths.
If you are adding several, extract the shared implementation first (the freshness guard, the md5-with-
sidecar compare, the force-link, the index spawn) so a new overlay is a manifest plus a call. At the
number of locales the project is heading toward, copying the template will keep producing defects.

A related list is easy to "fix" wrongly. `LEADING_POSTCODE_COUNTRIES` in `packages/neural/lib/placetype-pair-prior.ts`
lists `fr, de, es, it`. A country's absence there is not always a gap. `en-IN` is absent on purpose.
The PIN goes last, so the trailing-postcode strip already folds its parent segment correctly, and its
docstring says so. Membership is earned by a codex postcode shape plus a confound board.

## A workspace missing from the release list — `neural-weights-en-au` at 9.0.0

`.release-it.json`'s workspaces list is both the publish set and the bump set. A workspace outside it
is also never version-bumped. release-it does not rewrite its `version`, so the workspace keeps the
number it had when it dropped out, in the repo and on npm, while every sibling moves on. Nothing
fails. `yarn release` reports success, because from its side there was nothing to do.

`@mailwoman/neural-weights-en-au` was the worked example. It is now in the list, so read this section
for the mechanism rather than as a live defect. It sat outside the list while public and already on
npm. Its siblings reached 9.1.0, en-au held 9.0.0 in `package.json` and on npm, and nothing failed.
The actual cost differed from the apparent one, and it was measured rather than reasoned out. `npm
view @mailwoman/neural-weights-en-au@9.0.0 dependencies` answered `{"@mailwoman/neural-weights-en-us":
"9.1.0"}`, which is the correct base. `yarn pack` freezes `workspace:*` to whatever version the
sibling has at pack time, and the hand-publish happened after the 9.1.0 bump. The real cost was a
version number that no longer meant anything (9.0.0 shipping against a 9.1.0 base) and a workspace
that shipped only when someone remembered to publish it by hand. The remaining hazard is ordering,
and it applies beyond this instance. If you pack a package before a release bump, the same mechanism
pins a base that the overlay is behind.

A `private: true` flag is checkable, but membership in a JSON array is not. Check the difference
whenever you add or move a workspace:

```bash
node -e "const w=require('./package.json').workspaces,r=require('./.release-it.json').plugins['@release-it-plugins/workspaces'].workspaces;console.log(w.filter(x=>!r.includes(x)))"
```

Every name it prints needs a reason you can state. `scripts/scaffold-weights-overlay.ts` registers a
new overlay in both lists for this reason. A locale added by hand skips that step.

A new workspace joins six registers, and only the first one fails loudly. `yarn install` reads the
root `workspaces` array, so a missing entry there breaks immediately. The other five fail without an error:

- The release list above, or `SANCTIONED_RELEASE_ABSENCES` in `scripts/release-stage.ts` when the
  workspace is held out. That constant records "a reason you can state" as data.
  `checkReleaseListIdentity` refuses a workspace that is in neither list and reports its name rather
  than a count. Its `publishCount` pin in `scripts/release-stage.test.ts` changes with either edit.
- Both root `tsconfig.json` reference entries: `./packages/<name>` and
  `./packages/<name>/tsconfig.test.json`.
- `scripts/smoke-clean-install.ts`'s pack set. It enumerates the workspaces the clean-install smoke
  packs and silently skips any workspace it does not list.

A brand-new npm name has a seventh obligation before it may enter the release list: the
`bless-package` first publish. An unblessed name fails the whole release at that workspace with a
bare `E404` (see the pitfall below). If you skip the tsconfig pair, `tsc -b` never builds the
workspace, so `out/` stays empty. Every test-project reference to it then fails with `TS6305:
Output file has not been built from source file`. That error reads as a broken test rather than an
unregistered project, and a local run hides it completely if you happened to build that workspace
by hand.

## Moving a workspace — the 2026-08-14 regroup

`tsc -b`, `yarn lint` and `yarn typecheck:tests` all pass over a half-moved tree. The paths that break
are strings, and the compiler never reads them. Regrouping the workspaces under `packages/` left ~40
cwd-relative literals behind. None of them failed a build, and that is why they matter. Each one is
read at runtime by code that treats a missing path as a negative answer rather than an error.

- `.husky/pre-commit` matched staged files against `^mailwoman/(commands|cli-kit)/`, so the
  CLI-reference freshness guard stopped firing entirely. That guard exists because the docs CI
  check failed four times in one day.
- `promotion-check.ts`'s recompile-before-eval guard probed `existsSync("core/out")`. The probe
  returned false, so a stale core would have been graded without a warning.
- `api-engine.test.ts` and `v1-parse-check.test.ts` run only when
  `realpathSync("neural-weights-en-us/model.onnx")` resolves. The call threw, so both suites were
  skipped. Repairing the path took the slow leg from 109 to 110 files and from 60 to 57 skips, all passing.
- `publish.yml` read the model card inside two `node -e` strings and ran the pair-index parity test
  from `neural/test/`. The prose and the `::error::` remediation string beside them had already been
  updated by hand, but the executable one-liners had not.

After a move, search for quoted literals whose first path segment is a workspace name. Imports do
not need this search because the compiler checks them. These literals usually sit in `.husky/`,
`run:` blocks, CLI flag defaults, and test skip-guards. Two shapes look stale and are not. One is a
data-root-relative path (`data-bundles.ts`'s `localPath`, paired with a `remotePath`). The other is a
package specifier: `import("mailwoman/gazetteer-pipeline")` is the `mailwoman` package's subpath
export rather than a directory, and prefixing it with `packages/` breaks it.

CodeQL reacts to a bulk rename by re-raising every existing alert at its new path, and dismissals do
not follow the file. The regroup PR reported "17 new alerts, 17 high severity". Thirteen were already
open on `main` and four had been dismissed as false positives, at identical rules and line numbers. The
check's own caveat says the changes were too large to attribute. Re-dismiss the alerts after merge.
Do not read the count as a regression, and do not let it block the merge, because the ruleset
requires only the `test` context.

## Shared constants are not a shared function — #861

**When two copies must agree, share the function. Shared constants do not keep the logic in
agreement.** The #861 server↔demo parity matched four literals and a "keep them in lockstep" comment
in both files. The literals stayed matched for the interface's whole life. The code diverged anyway,
at two points a constant cannot express:

- Which field the population term reads. The server read `prominence ?? score` and the browser read
  raw `score`, so the demo let population lift a demoted cross-country alias back over a primary.
- Whether the combined value is written back into `prominence`. The server wrote it and the browser
  did not, so the resolver walk's own `prominence ?? score` sort discarded the demo's ordering.

A reviewer comparing the constants, as the comments instructed, would have found them identical
every time. Extract the function into a platform-free module and have both sides call it.
`primary-preference.ts` and `proximity-rerank.ts` are now shared this way.

## Seven CSV splitters in `extract-recipes/`

**A duplicate often indicates a defect in the shared tool.** The seven copies of a hand-rolled CSV splitter in `packages/corpus/lib/extract-recipes/` were the worked example. `CSVSpliterator` was already a dependency of every one of those workspaces, so the authors knew about it. They tried it, hit 207 seconds on a whole-buffer parse, and wrote a fast splitter that could not see quotes. The duplication was a rational local response to a real upstream defect (a quadratic `searchMatches`, fixed in spliterator 5.0.0). Seven independent authors worked around the same defect without reporting it. When you find a duplicate, ask **"what was wrong with the shared tool?"** instead of asking why the author did not know about it. Sometimes nothing was wrong. Often the shared tool was too slow, async against a sync caller, or shaped for a different call site. If you fix that problem, the duplicates can be removed. If you delete them without fixing it, they come back.

## Partial-result readers — the 2026-08-23 model arc

**A reader that can return a partial result must report what it got, or throw.** The 2026-08-23
model arc produced seven bugs of one shape. Each returned a well-formed wrong answer that nobody would
have questioned:

- `Array.isArray` on a nested Arrow column. Corpus `labels` arrives as `{list:[{element:…}]}` in some
  corpus files and as a plain array in others. The check is false for the first form, so every label
  count reads zero. This produced "GB has no street data".
- `getCursor(["country","labels"])` silently drops `labels` in the corpus files that one writer era
  produced. It raises no error, and the column is absent from the result. On one GB corpus file, the
  unprojected read found 1,519/2,000 street rows and the projected read found 0/2,000. This produced
  "only 4 countries have street data", and the real figure is 29.
- `flattenTreeNodes` projected away `source`, and later the whole resolver payload. Both times the
  affected spans reported as `unchanged`.
- An `EngineConfig` key typo (`weightsCacheRoot` for `weights_cache`). A plain object drops the unknown
  key without a warning, so both arms ran the same weights. The comparison reported "0 of 6 differ",
  which reads as "the candidate is identical" but means "the change never ran".
- Two artifact resolvers sorted by name. `v0.9.9` beats `v0.26.0` lexically and `v8-jp-full` beats both
  numerically, so a coverage report silently described a corpus nine versions old.

In each case the failure is indistinguishable from a real absence. Absence is usually what the
question was about, so the wrong answer looks like a discovery. Three rules follow. Prefer a reader
that errors on a requested-but-missing column over one that omits it. When a projection drops a
field, the consumer that needed it gets `unchanged` rather than a type error, so carry the whole
payload or record what you dropped. Finally, `?? 0`, optional chaining, and a bare `.filter()` all
convert _"I could not read this"_ into _"there is none of it"_. At a measurement boundary that
conversion produces a false result. Before reporting a surprising absence, re-measure it by a second
path. Reading one corpus file two ways caught two of the seven bugs in sixty seconds.

## A right answer under the wrong TYPE — the UAE's 178,171 postcodes

**A check that asks whether an answer is supported will pass an answer that is supported and
mislabelled.** Three mechanisms in this repository refuse to produce a well-formed answer they cannot
back. `createStreetLocaleRegistry` throws for an unregistered country rather than falling back to a
neighbour. `coarserAnswerMarker` returns null rather than an empty marker. `declared_ambiguity`
reports its margin rather than presenting a narrow win as a clear one. None of the three would have
caught this defect.

The widened GeoNames postal tail took 178,171 rows for AE. That is more than RU, RO and KR combined,
and the largest single country in the tail. Every row is a `NNNNN NNNNN` pair at Dubai-area
coordinates (lat 24.63–25.32, lon 54.91–56.20). The rows are Makani **building** geocodes. The United
Arab Emirates has no postcode system, and mail is addressed to PO boxes.

The lookup works, which is why nothing would have reported it. The #920 name law strips
non-alphanumerics so a stored name matches what `sanitizeFTSQuery` makes of a query token, turning
`28119 95762` into `2811995762` on both sides. A user typing a Makani number gets the right building,
at the right coordinate, through the right key. Only the placetype is false, and the tier above reads
`placetype = 'postalcode'` as an interface. A country census would have ranked the UAE the third
best-covered postcode locale in the artifact, and every coverage figure drawn from that tier would
have included these rows.

There are therefore three distinct failure modes rather than two. **Under-claiming** is abstention.
**Over-claiming confidence** presents a result as clear when it is not, and `declared_ambiguity`
exists to report that. **Claiming the wrong kind** is this case, and neither of the other mechanisms
can see it. The answer is fully backed and correctly retrieved, but it describes a different kind of
thing than it says. The answer itself never shows the error. The evidence is whether the category
exists in that country at all.

The defect was found by drawing real rows out of the built artifact to set up a before/after
measurement. Reading the country list would not have found it, because a list of ISO codes looks
fine. The two receipts below make the same point about method: an aggregate that agrees with itself
is not evidence, and a row you can read is.

## A short read is a small file — the GeoNames quote-handling loss

This defect is the inverse of the quote-blind splitter below, and the same rule applies from the
other side. `TSVSpliterator` defaults `enableQuoteHandling` to true. A GeoNames dump is unquoted TSV
in which `"` is an ordinary character in a place name (`Ovrag Kyzylak"on`). A quote-aware reader over
an unquoted source does not fail. It joins every line between one `"` and the next into a single
record. **7,411,412 rows went in and 6,504,155 records came out, losing 907,257 across 16
countries.** The losses included Finland 84.4%, Azerbaijan 94.7%, Vietnam 88.3%, and Russia 43.7%. The
alias fold's founding measurement was taken on Finland.

Nothing downstream could see the loss. The fold reports places written, so a country that was read
short reports a smaller number. The coverage pre-flight compares one fold against the previous fold,
so once both sides are short it agrees with itself. **A short read and a small file produce the same
number at every later boundary.** The fix is therefore a reader that compares its record count
against the source's own line count (`readUnquotedTSVChecked`), not a list of sources to distrust. 69
dumps contain a quote and only 16 lose rows, because a pair that opens and closes inside one line
never crosses a row boundary.

Two facts about how the defect was found matter more than the fix:

**The dismissal.** The symptom was seen and explained away first. A rebuilt fold held 49,229 fewer
places than its predecessor, and the reasoning was _"this diff cannot touch place ingestion"_. That
was true of the diff, but the missing places were a measurement. A claim about code was allowed to
outrank a count. The rule that covers this was already written one section above: re-measure a
surprising absence by a second path.

**The scoping error.** The first census reported 540,259 rows across 9 countries, because it counted
over `DEFAULT_GEONAMES_COUNTRIES`, the alias fold's own list of 161. That list belongs to one consumer
and does not bound the defect. The currency backfill, the label-point anchor adjudication, and the
corpus adapters each read the same dumps for their own country sets. Re-measuring over every dump on
disk also found Russia, Vietnam, Iraq, Iran, Kazakhstan, Belarus and Jordan. **A count inherits the
scope of the list you chose.** Here that list was one of three country lists in the same file, and
none of them bounds the defect.

A single graded row surfaced the defect. A 982-row board comparison came back with one regression:
`Turkmenabat` answered a Tajik namesake 468 km away, and Türkmenabat has a population of 230,861. An
aggregate that moves by one row is still worth opening.

## A count taken at the wrong unit — the 2026-09-14 script measurement

This error is related to the scoping error above. That census counted over the wrong population.
This one counted the right population at the wrong unit. The sign of it is an exact integer ratio
between the wrong number and the right one.

Three counts entered [#2282](https://github.com/sister-software/mailwoman/issues/2282)'s task list from
an earlier comment, and re-deriving them against the files gave:

| Source                                              | Claimed |  Measured |
| --------------------------------------------------- | ------: | --------: |
| `data/eval/external/jp-overture-gold.jsonl`         |  11,946 | **3,982** |
| …of those, kana-containing                          |     356 |   **178** |
| `corpus-python/…/countries/kr-build-reference.json` |      37 |    **20** |
| `…/gauntlet/cases/cn/organizational-units.jsonl`    |      59 |    **21** |

11,946 is 3,982 × 3 exactly, and 356 is 178 × 2 exactly. The first count had walked `text`, `muni` and
`pref` as three rows each, and kana appears in two of those three fields on a kana-containing row.
Neither number came from a typo or a stale file. Both counted the right file at the wrong unit, and
the integer ratio shows it.

**The conclusion from the rate still holds, but its denominator was wrong.** Kana decides Japanese
on 4.5% of rows (178 of 3,982) rather than 3.0% of fields (356 of 11,946). Either way, kana is too
rare in this set to decide the language, so a script rule must abstain rather than guess. Because
the conclusion did not change, nothing caught the error. A number can be wrong by 3× and still
support the same conclusion.

The rule behind this is already written: count at the unit the model reads. This receipt adds a
detector. **When a re-derived count differs from the old one by a small exact integer factor, the
unit changed rather than the data.** A stale file gives an irregular difference. A changed unit
gives 2×, 3×, or the reciprocal of one.

## The `node_modules` reach-around census — 2026-08-06

**The rule does not forbid `node:path`.** The 2026-08-06 triage counted **1,095 `join`/`resolve` call sites across 244 files**. The breakdown is the useful part: 20 node_modules reach-arounds, 48 data-root assembly, 25 module-relative, and **1,002 legitimate**. The legitimate sites are `mkdtemp` scratch dirs (127), test fixtures (420), and dynamic filesystem work (455), such as CLI `--out` flags, walking a user-supplied tree, or composing under a root that a caller passed in. Banning the import would flag 1,075 correct lines to catch 20. Two shapes look like violations and are not. The first is a local root alias derived once from `dataRootPath()` and composed from afterward (`scripts/copy-weights.ts`). The concern is re-deriving the root, not composing from it, and that file's contrast between `resolve(repoRoot, …)` and `resolve(dataRoot, …)` is required. The second is a probe that reads a foreign project's install layout on purpose (`scripts/smoke-clean-install.ts`). `import.meta.resolve` would answer from the monorepo's graph, which a clean-install smoke must not consult.

## Defects in the input tail — the 2026-08-02 audit

**The defects that survive review occur on uncommon inputs.** Every correctness bug the 2026-08-02 audit found was in code that worked on every input anyone had tried. The bugs were a ReDoS that needs tab characters, an `expandH3Cell` that drops a leading zero only for base cells 0–7 (7 of 122), a quote-blind CSV splitter against sources where 6 of 8 carry no embedded newline, a quadratic scan whose existing callers all happened to be chunk-bounded, and a freshness guard that compared zero checksums. Reading the code tells you what it does on the inputs you are imagining, and those are the inputs that already work. When a change rests on a claim about data or scale, such as _this source has no quoted newlines_, _this path is fast enough now_, or _this artifact is stale_, run the one command that determines the result. Measurement found all five of those bugs. Each of the four audit findings that turned out wrong had been reached by reasoning instead, and someone implementing the fix disproved it.

## Acronym casing — the #875 deferral list, closed 2026-08-03

**Known gaps (#875), closed 2026-08-03.** The old checker held eighteen public renames behind a `DEFERRED` map: `@mailwoman/codex/nz`'s `NZ*` family, `@mailwoman/nuts-lookup`'s `NUTS*`, `@mailwoman/neural/weights`'s `CRFTransitions`/`readCRFTransitions`, `@mailwoman/annotations`'s `NUTS`, and `@mailwoman/registry`'s `createGBTScorer`. They landed in the v9 major (#1432), and the same commit deleted `scripts/lint-acronym-casing.ts` along with the map. **The deferral list and its script no longer exist.** Enforcement comes entirely from the `acronymCasing` block in `oxlint.config.ts`, which drives `sister-software/no-title-case-acronym` and runs under `yarn lint:oxlint`. CI requires that command. The check is therefore stricter than any sweep was. A new violation gets renamed in the commit that introduced it, and the only exceptions are the two that the AGENTS.md rule describes: a scoped disable comment, or an `ignoreNames` entry when the casing is not ours to choose. Local (non-exported) identifiers stay out of scope, because renaming one costs nothing at any time and flagging them adds noise. **Correction to the pre-2026-08-03 text:** `outJsonl`/`outJson` were listed here as "residual internal cosmetic" without a caller/def split. They are members of exported options interfaces (`packages/registry/lib/tools/gold-set-sample.ts`'s `outJsonl?: string`), so a consumer constructing the options object types the name. They are caller-visible and were renamed with the rest. `ID` is enforced too: the house form is `ID`, never `Id`.

## A threshold fitted to a failing population — the 2026-09-14 span-rescore arc

**A rule fitted to the rows that are failing measures the defect that produces the failures instead
of the quantity the rule names.** The span-rescore audit of #2266 counted 34 of 453 frozen rows decided from
a proper sub-span and found what looked like a clean separation. Sorted by the share of the query
the recovered span covers, **every row under 57% was wrong and every row at or above was correct**,
with two exceptions. A coverage floor was the obvious rule, and it was one edit away from being
registered.

The rule would have been wrong. The low-coverage rows had low coverage **because of the defect the
same issue was fixing**. They recovered a two-character region code (`WA`, `ENG`, `CA`, `OK`)
instead of the nine-character locality beside it. The span comparator sorted by token count, and
both spans are one token. With the comparator corrected, those rows recover the locality and land
at 67% to 82%. After the fix, 26 of 28 sub-span recoveries were correct, and the two failures read
**67% and 100% of the recoverable range**. Those are the lowest and highest values the metric can
produce. No threshold on either denominator separates them from the 26.

If the floor had shipped first, every one of its wins would have come from an ordering defect. The
floor would then have stayed in the code with nothing left to do and a plausible docstring
explaining why it was there.

The general form is the D-rule's argument: a mechanism earns a default only from evidence that still
holds after the other defects are fixed. Three tests, each costing minutes, would have caught this
case. **Fix the cheapest candidate cause first and re-measure.** **Check whether that cause produces
the separating quantity.** **Read the failures the rule would newly refuse.** Here those are `13 Kobe`
and `ENG Bootle`, at the same 67% as the row the rule was built to catch.

Two more findings from the same arc have the same shape. A "pocket of random countries" appeared:
CN, JP and KR seemed to be the only places where a locality's same-name `localadmin` is absent from
its ancestry chain. The pattern disappeared when all 241 countries were measured. The depth-1 parent
is `region` in 136, `county` in 56, and `localadmin` in only 15, so CN at 98% `county` sits with
India at 100%. Separately, a withheld-gold benchmark stratum removed every `gn:id`-concorded id but
left the `localadmin` twin answerable for 10.6% of populated localities. As a result, three correct
answers (`Langfang` 2.8 km, `Matsusaka` 1.3 km, `Troyes` 0.6 km) were published as examples of
confident failure.

The coverage rule's withdrawal is on https://github.com/sister-software/mailwoman/issues/2266.
