# Deployment options

Every shape below runs the same engine. The shapes differ in what has to be resident on the machine
and what you give up to get it there. Choose by the constraint you cannot change.

## As a library

Run `npm install` and call a function. This shape has the fewest moving parts, and every other shape
is built on it. It opens no port, needs no supervised process, and makes no network calls that a parse
could fail on.

Choose it when Mailwoman runs inside an application you already deploy. You operate no second service,
and the call pays no serialization cost.

[Library API](../developers/reference/library-api.mdx)

## As a self-hosted server

`mailwoman serve` gives you `/v1/parse`, `/v1/geocode`, `/v1/batch`, `/v1/resolve` and `/v1/format`
over HTTP, with an OpenAPI document the server emits itself. Run it in a container and mount the
gazetteer read-only.

Choose it when several services need addresses and you would rather run one geocoder than embed one
in each. Check two constraints before you commit. The published image is `linux/amd64` only, because
`onnxruntime-node` has no musl prebuild and arm64 has not been verified. The `:latest` tag also lags
the npm releases, so pin a digest instead of assuming the tag is current.

[Run the API server](../developers/tutorials/run-the-api-server.mdx)

## On a serverless runtime

The engine fits on a serverless runtime after trimming. On the host the guide measured,
`node_modules` installed at 746 MB. Of that, 500 MB was ONNX Runtime builds for hardware the machine
did not have, and deleting them reduced the install to 303 MB. A cold start on that host took about
1.1 s, and the one-time model load accounted for 70% of it.

Those two numbers differ from the 707 MB and 523 MB that
[Footprints](../developers/reference/footprints.mdx) and [Overview](./overview.mdx) report because
the hosts differ. The serverless guide measured a different machine, and npm selected different
runtime builds for its platform and Node version. Both figures are `du` on a real install. They show
that most of the install is runtime binaries you do not execute. Re-measure your own target before
you size a bundle to either number.

Choose it for spiky traffic that does not justify keeping a machine warm. The install size is the
main constraint. At 303 MB before weights, the install exceeds AWS Lambda's 250 MB unzipped limit, so
Lambda requires a container image or a layer. The data root must also be a real filesystem, because
SQLite needs `pread` on a local file descriptor.

[Deploy on a serverless runtime](../developers/how-to/deploy-serverless.mdx)

## In the browser

`@mailwoman/neural`'s browser runtime parses in the tab, with the query text never leaving the page. The load is
about 50.4 MB of model files plus one `onnxruntime-web` build between 12.5 MB and 25.4 MB, and a cold
load measured 1.7 s from `127.0.0.1`.

Choose it for form autofill and validation while someone types. Two constraints decide whether it
suits you. First, **you host the weights yourself**. `public.mailwoman.ai` answers cross-origin
requests only for the demo's own domain, so a page on your domain receives no
`Access-Control-Allow-Origin` header and the fetch fails. Second, the browser runtime parses but does
not resolve. To geocode in the tab, you need either a slim database built for your own coverage or a
server call with the parsed components.

[Parse in the browser](../developers/tutorials/parse-in-the-browser.mdx)

## As an MCP server

`@mailwoman/mcp` exposes nine tools to a coding agent over stdio — parse, geocode, POI search and the
layer readers among them. It opens no port and needs no deployment.

Choose it when the consumer is an agent rather than an application. The server communicates over
stdio only, so a client that cannot launch a subprocess cannot use it. It loads only the `en-US`
weights.

[Use the MCP server from an agent](../developers/how-to/use-the-mcp-server.mdx)

## What every shape shares

A worker runs one parse at a time. Inference blocks the JavaScript thread in all five shapes, so a
single process serves one request at a time regardless of queue depth. Concurrency comes from running
more instances, containers or processes.
