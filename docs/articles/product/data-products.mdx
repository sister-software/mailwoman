# Data products

The model travels with the npm package. The reference data does not, because the smallest useful
gazetteer is <BundleSize name="candidate" /> and a registry tarball that size would be paid for by
every consumer who wanted the parser alone. So the data is a separate download, pulled once and kept.

`mailwoman data pull` fetches it. The table below is the whole published set, read from the command's
own registry when this page is built, and the command exits with an error and lists the same names if
you name anything else.

## What you build yourself

Everything else on the shelf is a local build, and three cases are worth naming because people ask
for them by name.

**The full WOF distribution reverse geocoding needs.** Not a published bundle, and not the
`candidate` gazetteer above — a separate build carrying the `place_bbox` R\*Tree. It is hours of work
and tens of gigabytes of source data.

**Timezone, NUTS and UN/LOCODE lookups.** `@mailwoman/timezone-lookup`, `@mailwoman/nuts-lookup` and
`@mailwoman/un-locode-lookup` publish code to npm and build their own databases locally. No bundle in
the bucket serves them.

**OpenStreetMap rooftop databases.** Built, and deliberately unpublished — ODbL is share-alike on a
derived database, and no file goes to npm or the bucket until counsel has reviewed how that applies
to serving a coordinate from one. Build one and the obligation is yours.

## Where the data came from

Every source is recorded with its license at the point it enters the pipeline, and each built
artifact carries an `ATTRIBUTION.json` naming the source, release and license behind it. Two items
matter to a review and are stated in full on the compliance page. The OpenStreetMap **rooftop**
extracts in `@mailwoman/osm` reach no published artifact. The served `candidate` gazetteer does carry
a Northern Ireland postcode fold derived from OpenStreetMap under ODbL, 4,757 places measured
2026-09-27, and what ODbL asks of that is with counsel. And one source's license is recorded
inconsistently in our own files, so attribute Who's On First until that is settled.

[Data provenance](../about/security-and-compliance.mdx#data-provenance) on the compliance page, and
the
[provenance record](https://github.com/sister-software/mailwoman/blob/main/docs/records/site-2026-08/licensing/data-provenance.md)
that carries the measurement.

## When it changes

No cadence is committed. Artifacts are rebuilt when coverage changes or an ingest bug is fixed,
rather than on a schedule, and this is the one to plan against: do not build a pipeline that assumes
a weekly or a monthly artifact.

What you get instead is that each artifact is sealed and dated, and the vintage travels in the remote
path, so you can always tell which build you are running without downloading anything. A new build is
a new path, which arrives in a new release of the `mailwoman` package.
