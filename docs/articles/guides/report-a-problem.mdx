# Report a parsing or geocoding problem

You'll have a reproducible report with the exact input, expected and observed results, the first visible mismatch, package and data versions, and a safe submission route.

## Prerequisites

- Node.js 24 LTS or later.
- A Mailwoman installation that reproduces the result. The commands below were checked with published `mailwoman@11.0.0` on Linux x64.
- Use an address you may publish. The parser trace includes the full input. If the only reproducer contains a private address, keep its trace local and email [teffen@sister.software](mailto:teffen@sister.software) to arrange a private report.
- If the behavior could be exploited as a security vulnerability, use the [private security route](#report-a-security-issue) before preparing a public issue.

## 1. Write the expected and observed results

Copy the input exactly, including its script, spaces, punctuation, and casing. State the expected component or coordinate beside the observed value. For a wrong coordinate, say whether the parsed components were correct. An expected result should come from a source you can identify, such as the address as supplied by its owner or a published reference record.

The example used throughout this page is fictional. It demonstrates the report format. The invented place names have no authoritative expected parse.

| Input                                      | Expected for this exercise                       | Observed with `mailwoman@11.0.0`                             |
| ------------------------------------------ | ------------------------------------------------ | ------------------------------------------------------------ |
| `17 Imaginary Lane, Exampletown, ZZ 00000` | `Exampletown` as `locality` and `ZZ` as `region` | `Exampletown` as `dependent_locality` and `ZZ` as `locality` |

## 2. Save the parser output

Set `ADDRESS` to the exact input. Run the installed CLI with the locale you used when the problem appeared. The following command keeps the full JSON trace and standard-error diagnostics in separate local files:

```bash
ADDRESS='17 Imaginary Lane, Exampletown, ZZ 00000'
npx --no-install mailwoman parse --locale en-US --debug "$ADDRESS" > trace.json 2> parse.stderr
```

Inspect `trace.json` for `input`, `normalized`, `locale`, `kind`, `path`, and `tree`. Keep `parse.stderr` because a missing optional artifact or another runtime warning can affect interpretation. The command above exited successfully in the verification run. Its `parse.stderr` reported that no postcode-prefix index was available, so the anchor-region prior was off.

If the problem is a geocoding result, also capture the exact `mailwoman geocode` command, its complete response or error, and the data bundle used. A parse command returns labeled components. A coordinate requires a resolver and a geographic database. The example on this page tests parsing only.

## 3. Identify the first visible mismatch

Compare the stages in order. Start with `normalized.normalized`, then `locale` and `kind`, then the labels and spans in `tree`. For geocoding, compare the parse tree before the resolver's candidates, selected coordinate, and `resolution_tier`. Use [the schema reference](../reference/schema.mdx) to identify each field.

In the fictional example, `normalized.normalized` preserves the input and `kind.kind` is `structured_address`. The first visible mismatch is in `tree`: the returned top-level node tags `ZZ` as `locality`, and its child tags `Exampletown` as `dependent_locality`. The CLI trace doesn't establish whether classification, decoding, or a repair caused that label choice. Select **Unknown** for the issue form's **First stage that diverges** field and explain the visible tree difference under **Evidence and scope**. Choose a specific stage only when the captured evidence identifies it.

## 4. Record the environment

Run these commands in the same installation:

```bash
node --version
node -p "require('mailwoman/package.json').version"
npx --no-install mailwoman doctor --json > doctor.json 2> doctor.stderr
```

For the verification run, `node --version` returned `v24.22.1`, the package version command returned `11.0.0`, and `doctor.json` reported the en-US weights package as available and the admin gazetteer as missing. The missing gazetteer prevents this installation from verifying a coordinate. It doesn't explain the fictional parse's node labels. Record the model or weights version, configured locale, operating system, relevant data bundle and its vintage, and any runtime flags that affect the call. Review `doctor.json` and the trace before sharing them because they can contain local paths, configuration details, and the input address.

## 5. Fill the bug-report form

Open the [Mailwoman issue chooser](https://github.com/sister-software/mailwoman/issues/new/choose) and select **Bug report**. The form requires **Failing input**, **Expected result**, **Observed result**, **First stage that diverges**, **Evidence and scope**, **Artifacts under test**, and **Reproduction**. Its **Why chain** field asks for only the causal steps the evidence supports. It also requires the submission checkboxes.

The fictional example fills the core fields as follows. Paste the complete `trace.json` under **Observed result** or attach it to the issue after reviewing it for private data.

| Form field                | Dry-run entry                                                                                                                                                                                     |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Area                      | `locality`                                                                                                                                                                                        |
| `Failing input`           | `17 Imaginary Lane, Exampletown, ZZ 00000`                                                                                                                                                        |
| Expected result           | For this exercise, `Exampletown` is `locality` and `ZZ` is `region`. These are fixture expectations for invented names.                                                                           |
| Observed result           | `tree.roots[0]` has `tag: "locality", value: "ZZ"`. Its child has `tag: "dependent_locality", value: "Exampletown"`. Include the full trace.                                                      |
| First stage that diverges | `Unknown`. The tree is the first visible mismatch. The trace doesn't isolate the model or decoder.                                                                                                |
| Evidence and scope        | The input, normalized text, and `structured_address` kind appear in the trace. The tree differs from the exercise expectation. This is one synthetic reproduction, with no accuracy rate claimed. |
| Artifacts under test      | `mailwoman@11.0.0`, `@mailwoman/neural-weights-en-us@11.0.0`, Node.js `v24.22.1`, Linux x64, `--locale en-US`. `doctor.json` reports the admin gazetteer missing.                                 |
| Reproduction              | `npx --no-install mailwoman parse --locale en-US --debug '17 Imaginary Lane, Exampletown, ZZ 00000'`                                                                                              |
| Why chain                 | `1. Observed: the returned tree assigns ZZ to locality. 2. Unknown: this trace does not identify the model or decode decision that produced the tag.`                                             |

Check the form's required boxes against your actual report. Put each measured number beside its denominator and comparison when you make a performance or accuracy claim. The fictional example makes no such claim. Submit the issue only after the input and attached output are safe to publish.

## Report a security issue

Email [teffen@sister.software](mailto:teffen@sister.software) privately with the impact, reproduction steps or proof of concept, and affected version or commit. The repository's [security policy](https://github.com/sister-software/mailwoman/blob/main/SECURITY.md) directs vulnerability reports to that address. Keep exploit details out of a public GitHub issue.

## Verify

Before submitting a public bug report, confirm that the issue contains the verbatim input, expected and observed results, the earliest mismatch the evidence supports, package and data versions, and a command another person can run. Confirm that every attached trace is safe to publish. In the dry run above, the exact command reproduced the displayed tree and the `doctor --json` command identified the missing gazetteer.

## Limits

- The parser trace shows the final component tree and pipeline decisions. If the cause of a node label is still unknown, include that uncertainty in the issue. A model trace or maintainer investigation can separate classification from later repair.
- The example uses invented place names and supplies an exercise expectation. For a real report, identify the source of the expected address or coordinate.
- A private input belongs in a private message until a public synthetic input reproduces the same result. A security vulnerability follows the security route above.
