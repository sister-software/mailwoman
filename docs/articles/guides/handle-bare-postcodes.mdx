# Require country context for a bare postcode

Use this guide when a user enters only a postcode and your application needs to decide whether it has enough context to attempt a geographic lookup. Keep the country supplied by your application or user beside the original input. A postcode's shape can match several national formats, so the postcode's country needs context beyond its shape.

## Prerequisites

<CommonPrerequisites />

Start by installing the required packages:

```sh npm2yarn
npm install mailwoman
```

This exercise parses text and reads no geographic database. Save the following file as `route-postcodes.ts`.

## Keep caller country separate from the parse

```ts
import { createParser, decodeAsJSON, flattenTreeNodes } from "mailwoman"

await using parser = await createParser({ locale: "en-US", machinePreferences: "none" })

const cases: Array<{ input: string; applicationCountry: string | null }> = [
	{ input: "10118", applicationCountry: null },
	{ input: "10118", applicationCountry: "US" },
	{ input: "10118-1234", applicationCountry: null },
]

for (const example of cases) {
	const result = await parser.parse(example.input)
	const { postcode } = decodeAsJSON(result.tree)

	const route =
		result.faults.length || result.kind.kind !== "postcode_only" || !postcode
			? "review-parse"
			: example.applicationCountry
				? "country-scoped-lookup-pending-data"
				: "request-country"

	const formats = result.queryShape.knownFormats.map((match) => match.format).join(", ")

	console.log(
		`${example.input} (application country: ${example.applicationCountry ?? "none"})\n` +
			`path: ${result.path}, kind: ${result.kind.kind}, formats: ${formats || "none"}, route: ${route}`
	)
	console.table(flattenTreeNodes(result.tree), ["tag", "value", "start", "end"])
}
```

The application owns `applicationCountry`. The parser reads the same input in the first two cases. The policy reads the application field directly and marks a future country-scoped lookup as pending data. It requests a country when that field is absent, even when one format name looks specific to a country. Supply the country as a resolver preference when you perform the later lookup.

Both `10118` runs returned kind `postcode_only` and the same `postcode` node. Both listed `us_zip`, `fr_postcode`, and `de_postcode` as format matches. The country `US` came from the application record, and the parser left the choice between those three shapes open. Even for `10118-1234`, which matched only `us_zip4` and took the fast path, this policy requests a country from the application.

The coordinate and deliverability of all three records stay unknown, because this exercise ran neither a geographic lookup nor a postal-authority check. With a [verified data bundle](../reference/data-and-locales.mdx), run the country-scoped lookup and inspect its candidate evidence, `resolution_tier`, and `epistemic_status`. A country preference narrows the lookup and supplies no coordinate itself. When a later lookup returns `lat` and `lon` as `null`, store them as `null` in your record. The [result schema](../reference/schema.mdx) defines the fields, and the [confidence and limits explanation](../explanation/confidence-and-limits.mdx) separates format, place, and coordinate evidence.
