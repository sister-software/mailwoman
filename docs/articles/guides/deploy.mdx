# Deploy the server in a container

Use this procedure to run the native Mailwoman HTTP server in a container. You build an image that installs the published 11.0.0 packages, and you mount the geographic data into it read-only. The model weights install with the packages, so the image needs no other model download.

The container registry image `ghcr.io/sister-software/mailwoman` has only the tags `7.3.0` and `latest`, both from the 7.3.0 release. This guide builds its own 11.0.0 image instead. The commands were run with Podman. Docker accepts the same `Dockerfile` and the same `build` and `run` arguments.

## Prerequisites

- Podman or Docker on `linux/amd64`. The `onnxruntime-node` dependency installs prebuilt glibc binaries, so the image uses a Debian-based Node.js image rather than Alpine.
- A data root populated with `mailwoman data pull`. [Install, check, roll back and prune local data](./operate-data.mdx) covers the pull. The example mounts the global place candidates and the Washington, DC address points.

## 1. Write the Dockerfile

Save this file as `Dockerfile` in an empty directory:

```dockerfile
FROM node:24.22.1-slim

# onnxruntime-node links the OpenMP runtime for threaded inference.
RUN apt-get update \
	&& apt-get install -y --no-install-recommends libgomp1 \
	&& rm -rf /var/lib/apt/lists/*

WORKDIR /app
RUN npm init -y > /dev/null \
	&& npm install --omit=dev --no-audit --no-fund \
		mailwoman@11.0.0 @mailwoman/neural@11.0.0 @mailwoman/neural-weights-en-us@11.0.0 \
	&& npm cache clean --force

ENV MAILWOMAN_DATA_ROOT=/data
USER node
EXPOSE 3000

HEALTHCHECK --interval=30s --timeout=5s --start-period=60s --retries=3 \
	CMD ["node", "-e", "fetch('http://127.0.0.1:3000/health').then((r) => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"]

CMD ["node", "node_modules/mailwoman/out/cli/main.js", "serve", "--port", "3000", "--host", "0.0.0.0", "--cpus", "1"]
```

The three Mailwoman package versions are pinned. Their dependencies resolve when the image is built, because the Dockerfile installs without a lockfile. The server runs as the image's unprivileged `node` user, with one worker process. `--cpus 1` keeps one container to one worker. Run more containers for more throughput.

## 2. Build the image

```bash
podman build -t mailwoman:11.0.0 .
```

The build installed 318 packages, and the image measured 1.09 GB. Podman's default OCI image format ignores `HEALTHCHECK` and prints a warning. Build with `--format docker` to keep it, or define the check in your orchestrator, as step 4 shows.

## 3. Run the container with read-only data

The server exits with status 1 when it finds no gazetteer, so a container started without data stops immediately. Its log shows the reason:

```text
✗ no gazetteer data found — the endpoint needs a resolver database to answer queries.
```

Mount the data root read-only at `/data`:

```bash
podman run -d --name mailwoman -p 127.0.0.1:3000:3000 \
	-v "$MAILWOMAN_DATA_ROOT":/data:ro \
	mailwoman:11.0.0
```

The tested run mounted the DC address points from a pulled data root, and mounted the candidate database from a separate path with `-v <candidate.db>:/candidate/candidate.db:ro -e MAILWOMAN_CANDIDATE_DB=/candidate/candidate.db`. When `candidate` is pulled into the same data root, the server should find it without that variable, but that layout wasn't tested in a container. A symbolic link inside the mounted directory must point to a path that also exists inside the container. A link to a host path appears missing inside the container.

`:ro` works with the published data files. The published DC and US Virgin Islands address-point files use SQLite's rollback journal, and the server opened them read-only. A database in write-ahead-log (WAL) mode needs its `-shm` file to be read from a read-only mount. On the host used for this page, a locally built DC file in WAL mode answered at the `admin` tier instead of `address_point`, with no error. If you build your own data, check that each file uses a rollback journal before mounting it read-only.

## 4. Check readiness

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3000/health
```

```text
200
```

A 200 from `/health` means the server answered. It doesn't prove that geocoding reaches address points, so send one known address after each deployment:

```bash
curl -s -X POST http://127.0.0.1:3000/v1/geocode -H "content-type: application/json" -d '{"address":"1600 Pennsylvania Ave NW, Washington, DC 20500"}'
```

The container returned `"resolution_tier":"address_point"` with `"coordinate_source":{"source":"overture:NAD","release":"2026-05-20.0"}`. A result at the `admin` tier for an address your data covers means the server didn't read the address points. [Run the Mailwoman HTTP server](../tutorials/run-a-server.mdx) shows complete responses.

## 5. Size the container

After one geocode, `podman stats` reported 452.5 MB of memory for the running container. On the same host, a server run outside a container measured about 607 MB across its manager and worker processes. Each is one measurement on one Linux host, so allow headroom and measure under your own load. Data files are read from the mount rather than copied, so disk use inside the container stays at the image size.
