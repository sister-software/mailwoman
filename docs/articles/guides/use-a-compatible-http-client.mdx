# Point a Nominatim, Photon or libpostal client at Mailwoman

Use this procedure to switch an existing Nominatim, Photon or libpostal REST client to a Mailwoman compatibility server with as few changes as possible. Each compatibility package runs its own server with that service's routes. Change the client's base URL, then compare the fields your client reads with the responses on this page.

## Prerequisites

- <NodeRequirement />.

Install the compatibility package that matches your client. Nominatim and Photon also use the `mailwoman` command to install geographic data:

```sh npm2yarn
npm install mailwoman @mailwoman/nominatim
```

For a Photon client, use:

```sh npm2yarn
npm install mailwoman @mailwoman/photon
```

For a libpostal client, use:

```sh npm2yarn
npm install @mailwoman/libpostal
```

The Nominatim and Photon servers geocode, so they need the global place candidates, plus address points for the places your client queries. If you chose either of those servers, install their data before starting them. The examples query Washington, DC:

```sh
export MAILWOMAN_DATA_ROOT="$HOME/mailwoman-data"

npx mailwoman data pull candidate
npx mailwoman data pull us --only us-dc
```

The Nominatim and Photon responses below were captured with local builds and an earlier data root. Their coordinate and response-field examples haven't been rerun against published 11.3.0 and the rebuilt geographic data. The libpostal responses were checked against the published 11.3.0 package without a geographic database.

## Nominatim clients

If your client uses Nominatim routes, start this server on the port it will call:

```sh
npx nominatim serve --port 7803 --host 127.0.0.1 --candidate-db "$MAILWOMAN_DATA_ROOT/db/wof/candidate.db"
```

It prints the routes it serves: `GET /search`, `GET /reverse`, `GET /lookup`, `GET /status` and `GET /openapi.json`. Point the client's base URL at `http://127.0.0.1:7803`.

A free-text search with `format=jsonv2` and `addressdetails=1`:

```sh
curl --get http://127.0.0.1:7803/search --data-urlencode "q=1600 Pennsylvania Ave NW, Washington, DC 20500" --data-urlencode "format=jsonv2" --data-urlencode "addressdetails=1"
```

Check these differences against your client:

`/lookup` isn't implemented and returns status 501:

```sh
curl -i "http://127.0.0.1:7803/lookup?osm_ids=W5013364"
```

```http
HTTP/1.1 501 Not Implemented
content-type: application/json

{"error":"this engine does not implement lookup"}
```

Only the status line, content type and body of that response are shown. `/reverse` needs a Who's On First admin gazetteer. You build that gazetteer separately from the data bundles. [Reverse-geocode a coordinate](./reverse-geocode.mdx) describes how to build one. Without it, `/reverse` returns status 200 with the body `null`:

```sh
curl "http://127.0.0.1:7803/reverse?lat=38.8977&lon=-77.0365&format=jsonv2"
```

```json
null
```

The compatible servers look for the admin gazetteer among the data root's Who's On First databases, where its conventional path is `db/wof/admin-global-priority.db`. They don't read `MAILWOMAN_WOF_ADMIN_DB`, the variable the `mailwoman reverse` command reads. With an admin gazetteer in the data root, the same request returned `"display_name":"White House Grounds, Northwest Washington, Washington, District of Columbia, District of Columbia, United States"` and no `address` object. `/status?format=json` returns `"status":0,"message":"OK"` with a `mailwoman.artifacts` list that identifies each database the server opened.

## Photon clients

If your client uses Photon routes, start this server and point the client at it:

```sh
npx photon serve --port 7804 --host 127.0.0.1 --candidate-db "$MAILWOMAN_DATA_ROOT/db/wof/candidate.db"
```

It serves `GET /api`, `GET /reverse` and `GET /openapi.json`. A search:

```sh
curl --get http://127.0.0.1:7804/api --data-urlencode "q=1600 Pennsylvania Ave NW, Washington, DC 20500" --data-urlencode "limit=1"
```

```json
{
	"type": "FeatureCollection",
	"features": [
		{
			"type": "Feature",
			"geometry": { "type": "Point", "coordinates": [-77.03654697024702, 38.89767510742324] },
			"properties": {
				"osm_key": "place",
				"osm_value": "house",
				"type": "house",
				"city": "Washington",
				"state": "District of Columbia",
				"postcode": "20500",
				"country": "United States",
				"countrycode": "us",
				"housenumber": "1600",
				"street": "Pennsylvania Ave NW",
				"mailwoman": { "coordinate_source": { "source": "overture:NAD", "release": "2026-05-20.0" } }
			}
		}
	],
	"engine": {
		"name": "mailwoman",
		"version": "11.0.0",
		"license": "AGPL-3.0-only",
		"license_url": "https://mailwoman.post/license",
		"notice": "mailwoman is licensed AGPL-3.0-only: modified or network-served copies must offer their source. A commercial license waives that obligation."
	}
}
```

Check these differences against your client:

- Feature `properties` have `osm_key`, `osm_value`, `type`, the address fields, `country` and `countrycode`. They have no `osm_id`, `osm_type` or `extent`. A house result has no `name`.
- `state` holds the full name, `District of Columbia`, unlike the Nominatim server's `DC`.
- `limit` is honored. A search for `Springfield` with `limit=3` returned three <Country code="US" /> cities called Springfield.

Without an admin gazetteer, `/reverse` returns an empty feature collection with status 200:

```json
{
	"type": "FeatureCollection",
	"features": [],
	"engine": {
		"name": "mailwoman",
		"version": "11.0.0",
		"license": "AGPL-3.0-only",
		"license_url": "https://mailwoman.post/license",
		"notice": "mailwoman is licensed AGPL-3.0-only: modified or network-served copies must offer their source. A commercial license waives that obligation."
	}
}
```

## libpostal clients

If your client uses libpostal REST routes, start this server. Published `@mailwoman/libpostal@11.3.0` parsed and expanded text without geographic data:

```sh
npx libpostal serve --port 7805 --host 127.0.0.1
```

It serves `GET` and `POST` on `/parse` and `/expand`, and `GET /openapi.json`. A parse:

```sh
curl -X POST http://127.0.0.1:7805/parse -H "content-type: application/json" -d '{"query":"781 Franklin Ave Crown Heights Brooklyn NYC NY 11216 USA"}'
```

```json
[
	{ "label": "house_number", "value": "781" },
	{ "label": "road", "value": "Franklin Ave Heights" },
	{ "label": "city", "value": "Crown" },
	{ "label": "city", "value": "Brooklyn NYC" },
	{ "label": "state", "value": "NY" },
	{ "label": "postcode", "value": "11216" },
	{ "label": "country", "value": "USA" }
]
```

The response is an ordered array of `label` and `value` pairs. Values keep the input's casing. In this 11.3.0 run, the parser included `Heights` in `road` and returned two `city` entries. A client that stores one road and one city must decide how to handle those values before switching its base URL. The two services may assign different labels to the same input even when their routes and response fields match.

An expansion:

```sh
curl -X POST http://127.0.0.1:7805/expand -H "content-type: application/json" -d '{"address":"781 Franklin Ave Brooklyn NY"}'
```

```json
{ "expansions": ["781 Franklin Ave Brooklyn NY", "781 Franklin Avenue Brooklyn NY"] }
```

## Check your client before switching

1. Send representative requests to both your current service and the Mailwoman server in a test environment.
2. List the response fields your client reads, and confirm each one is present in the Mailwoman response.
3. For libpostal clients, check repeated labels and the values assigned to each label against your application's expectations.
4. For Nominatim or Photon clients, handle the empty results described above: `null` from Nominatim `/reverse`, an empty feature collection from Photon `/reverse`, and status 501 from Nominatim `/lookup`.

Each server also serves `GET /openapi.json`, its machine-readable route description. The [HTTP reference](../reference/http.mdx) lists every compatibility route and its declared status codes.
