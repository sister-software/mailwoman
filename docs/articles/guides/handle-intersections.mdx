# Route intersection descriptions for review

Use this guide when a location-intake workflow receives a possible street intersection and needs the two street descriptions before a person checks the location. When you finish, the script sends a parse with both crossing streets to location review and asks for clarification when an intersection parse lacks either street. The parser identifies text spans and leaves the crossing coordinate unknown.

## Prerequisites

<CommonPrerequisites />

Start by installing the required packages:

```sh npm2yarn
npm install mailwoman
```

This exercise parses text and reads no geographic database. Save the following file as `route-intersection.ts`.

## Check the two street components

```ts
import { createParser, decodeAsJSON, flattenTreeNodes } from "mailwoman"

await using parser = await createParser()

for (const input of ["5th Avenue and Main Street, Springfield, IL", "5th and Main"]) {
	const result = await parser.parse(input)
	const { intersection_a: first, intersection_b: second } = decodeAsJSON(result.tree)

	const route = result.faults.length
		? "review-stage-fault"
		: first && second
			? "crossing-description-review"
			: result.kind.kind === "intersection"
				? "request-clarification"
				: "other-address-flow"

	const alternatives = result.kind.alternatives.map((alternative) => alternative.kind).join(", ")

	console.log(`${input}\nkind: ${result.kind.kind} (alternatives: ${alternatives || "none"}), route: ${route}`)
	console.table(flattenTreeNodes(result.tree), ["tag", "value", "start", "end"])
}
```

This application rule requires both `intersection_a` and `intersection_b` nodes and an empty `faults` list. It records the query kind and alternatives for diagnosis. When the top kind is `intersection` and the tree lacks either crossing-street component, it asks for clarification. The rule decides the route from the component tree and leaves the coordinate unknown.

For `5th Avenue and Main Street, Springfield, IL`, the returned kind is `structured_address`, and the tree contains `intersection_a: "5th Avenue"` and `intersection_b: "Main Street"`. The application sends those two strings for crossing-description review. For `5th and Main`, the returned kind is `intersection`, and the tree contains only `venue: "5th and Main"`. The application asks for clarification.

Give the reviewer the original input and both returned street spans for `crossing-description-review`. Ask the sender to name both streets and the locality for `request-clarification`. Send `other-address-flow` to the ordinary address intake, and investigate `review-stage-fault` before using any returned spans. The route identifies the application's next action. It doesn't verify that the streets cross.

The script ran no geographic lookup, so the crossing coordinate stays unknown for both results. A locality and a pair of street names describe a crossing. A verified crossing point needs a supported geographic source, a tested lookup for the exact input, and evidence that the point represents the crossing. Check the [data prerequisites](../reference/data-and-locales.mdx), [result schema](../reference/schema.mdx), and the [confidence and limits explanation](../explanation/confidence-and-limits.mdx) before adding that workflow.
