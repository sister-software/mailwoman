# Route parse results to review

Use this procedure when a <Country code="US" /> street-address intake needs a consistent rule for sending parser output to a review queue. Define what your downstream workflow requires first. This example requires a `structured_address` kind, an empty `faults` array, and nodes tagged `house_number`, `street`, `locality`, `region`, and `postcode`. A row meeting those conditions moves to a separate validation step. Whether the address exists or receives mail needs postal or geographic evidence beyond this rule.

## Prerequisites

- Node.js 24 LTS or later.
- An ECMAScript module project, with `"type": "module"` in its `package.json`.

Install the published parser packages:

```sh
npm install --save-exact mailwoman@11.0.0 @mailwoman/neural@11.0.0 @mailwoman/neural-weights-en-us@11.0.0
```

The seven labels in the script below are illustrative application decisions stated before this rule is evaluated. The first three complete street-address strings are labeled `ready`. The PO box, intersection, isolated unit, and row with an unsupported region string are labeled `review`. These labels describe this intake's desired routing, as opposed to a postal authority's judgment or a verified location. The example reads no geographic database.

## Apply the row rule

Save the following file as `review-parses.ts`:

```ts
import { createRuntimePipeline } from "mailwoman"
import { NeuralAddressClassifier } from "@mailwoman/neural"

const classifier = await NeuralAddressClassifier.loadFromWeights({ locale: "en-US" })
const parse = createRuntimePipeline({ classifier })

type TreeNode = Awaited<ReturnType<typeof parse>>["tree"]["roots"][number]
type Route = "ready" | "review"

const examples: Array<[id: string, expected: Route, input: string]> = [
	["A1", "ready", "1600 Pennsylvania Avenue NW, Washington, DC 20500"],
	["A2", "ready", "350 5th Ave, New York, NY 10118"],
	["A3", "ready", "11 W 53rd St, New York, NY 10019"],
	["R1", "review", "PO Box 1234, Springfield, IL 62701"],
	["R2", "review", "5th and Main"],
	["R3", "review", "Suite 400"],
	["R4", "review", "42 Nonexistent Ln, Zzyzx Falls, ZZ, 00000"],
]
const required = ["house_number", "street", "locality", "region", "postcode"]
let readyCorrect = 0
let reviewCorrect = 0

for (const [id, expected, input] of examples) {
	const result = await parse(input)
	const nodes: TreeNode[] = []
	function visit(node: TreeNode): void {
		nodes.push(node)
		for (const child of node.children) visit(child)
	}
	for (const root of result.tree.roots) visit(root)
	const missing = required.filter((tag) => !nodes.some((node) => node.tag === tag))
	const route: Route =
		result.faults.length || result.kind.kind !== "structured_address" || missing.length ? "review" : "ready"
	const weakest = nodes.reduce<TreeNode | null>((a, b) => (!a || b.confidence < a.confidence ? b : a), null)
	if (expected === "ready" && route === "ready") readyCorrect++
	if (expected === "review" && route === "review") reviewCorrect++
	console.log(
		JSON.stringify({
			id,
			input,
			expected,
			route,
			kind: result.kind.kind,
			missing,
			weakest: weakest ? `${weakest.tag}:${weakest.confidence.toFixed(3)}` : null,
		})
	)
}
const readyTotal = examples.filter((example) => example[1] === "ready").length
const reviewTotal = examples.filter((example) => example[1] === "review").length
console.log(`Labeled ready routed ready: ${readyCorrect}/${readyTotal}`)
console.log(`Labeled review routed review: ${reviewCorrect}/${reviewTotal}`)
```

The rule checks the kind and component tags across the whole tree. It prints the weakest returned node score for diagnosis. The route depends on the kind, tags and faults. A stage fault sends a row to review, even when the tree still contains nodes.

## Inspect the decisions

Run `node review-parses.ts`. Published 11.0.0 returned this complete output:


The rule sent the three rows labeled `ready` to downstream validation and the four rows labeled `review` to review. This is an executed result for seven selected example strings, without a production accuracy estimate or a confidence cutoff. For `42 Nonexistent Ln, Zzyzx Falls, ZZ, 00000`, the observed reason is the missing `region` tag. The parser reads the text and leaves the question of whether that address exists to a later check.

The PO box row's weakest node score is `0.914`, the same rounded value as the first ready row. A cutoff chosen from these seven scores would mix different query kinds and score origins. The bundled calibration metadata identifies a model version older than the published 10.8.0 English model, so these raw values have no established probability interpretation. The [confidence and limits explanation](../explanation/confidence-and-limits.mdx) gives the version evidence. Use a separate, representative labeled set to evaluate any score-based policy for your model, locale, and application costs.

For production intake, label records that cover your actual input sources before evaluating this rule. Count false ready decisions and unnecessary reviews with denominators, inspect the exact failed inputs, then change the condition that caused each error. Send rows marked ready through a separate [record validation policy](./validate-records.mdx). The [result schema](../reference/schema.mdx) defines the kind, fault, tag, and score fields used here.
