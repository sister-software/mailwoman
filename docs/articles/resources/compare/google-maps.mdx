# Google Maps Platform

## The question

You can start geocoding this afternoon with an API key and a fetch call. Alternatively, you can
install a package, download a gazetteer, and geocode in a process you already run. Both approaches
work. They are built for different situations, and they differ mainly in where the data lives and who
operates it.

## What Google Maps Platform is

The Geocoding API is a hosted HTTP service. Its own documentation, read on **2026-08-04**, defines it
as:

> "The Geocoding API is a service that accepts a place as an address, latitude and longitude
> coordinates, or Place ID. It converts the address into latitude and longitude coordinates and a
> Place ID, or converts latitude and longitude coordinates or a Place ID into an address."
>
> — [Geocoding API overview](https://developers.google.com/maps/documentation/geocoding/overview)

The same page describes forward geocoding, reverse geocoding, and geocoding by Place ID, plus an
Address Descriptors feature. It notes that developers in the European Economic Area are covered by
different terms with effect from 8 July 2025.

Understand the Place ID before you compare anything else, because the service is designed around it.
A Place ID is a stable identifier into Google's own place graph. Once your records carry Place IDs,
they hold keys that resolve only in Google's system. That link is useful, because it keeps the
geocoder, the Places data and the map rendering consistent. It also means the IDs cannot be used
with another provider.

For what the service costs and what the terms permit, read
[Google's pricing](https://developers.google.com/maps/billing-and-pricing/pricing) and
[terms](https://cloud.google.com/maps-platform/terms). Those pages change and depend on your usage.
A copy quoted in another project's documentation can go stale, so read the originals.

## What each one is built to do

|                      | Google Maps Platform                | Mailwoman                                                  |
| -------------------- | ----------------------------------- | ---------------------------------------------------------- |
| Shape                | Hosted HTTP service                 | npm package, in-process; HTTP servers optional             |
| Where the query goes | Google's infrastructure             | Your process                                               |
| Coverage             | Global and uniform, without setup   | Per-locale, measured where claimed; a download per country |
| Reference data       | Google's, maintained by Google      | Public registers on your disk, refreshed by you            |
| Identifier           | Place ID into Google's place graph  | A component decomposition, plus an address key you compute |
| Non-address queries  | Landmarks, business names, partials | Not the design; the parser needs an address                |
| What arrives         | A matched place                     | Labeled spans with offsets, plus a coordinate and a tier   |
| Operating cost       | Per request                         | Infrastructure and disk                                    |

Two rows account for most of the decision.

**"Where the query goes"** can settle an evaluation early, in either direction. If your addresses
are patient records, employee home addresses, or other data your compliance team regulates, an
in-process library keeps the data inside your systems, so the compliance question does not arise. If
they are public business addresses, compliance is not a concern and this row does not matter.

**"What arrives"** decides how much of your own code you write. A hosted geocoder returns a matched
place. If you need to know which characters of your input were the street, you must work that out
downstream. A label-then-look-up parser returns the decomposition as its primary output, and
deduplication, validation, formatting and record matching all need that decomposition. If you need
only a coordinate, this row makes no difference.

## When to choose Google Maps Platform

In the situations below, a hosted geocoder is the correct engineering decision, and installing
Mailwoman would be a mistake.

- **Your queries are not addresses.** Examples include "Starbucks near Union Station", a business name
  without a street, or a half-typed landmark. These are place-search problems over a business graph,
  and a parser has no field to label. Mailwoman will still parse the input, and the result will be
  wrong.
- **You need uniform global coverage today.** A hosted API covers every country the day you sign up.
  Mailwoman covers the locales where a coordinate-graded evaluation exists, and results elsewhere are
  unverified. See [Locales and tiers](../../developers/reference/locales-and-tiers.mdx). If your file
  spans 40 countries and you cannot wait for tiers, choose the hosted service.
- **You already use the Google ecosystem.** If you render Google maps, use Places, and store Place
  IDs, a second geocoder gives you two place graphs to reconcile. Consistency within one system is
  worth more than the marginal benefits of another one.
- **Your volume is low and engineering time is scarce.** Below the volume where per-request pricing
  becomes a material cost, sourcing and refreshing reference data is ongoing work that gains you no benefit.
- **You have no place to put 1.65 GB.** The gazetteer needs a disk. A serverless function with a
  small bundle limit and no attached volume is a poor host for this design.
  [Deploy serverless](../../developers/how-to/deploy-serverless.mdx) describes the shapes that work.

## When to choose Mailwoman

- **The addresses cannot leave your systems.** Mailwoman sends no query data out of your process, and
  the other benefits follow from that.
- **You need fields rather than only a point.** Mailwoman returns spans with offsets into your
  original string, which deduplication and validation can use.
- **The volume makes per-request pricing your largest line item.** Mailwoman replaces that cost with
  infrastructure and disk, which grow differently with volume.
- **You want to store the results indefinitely.** Reference data on your disk carries whatever the
  source license permits, and you read that license instead of a service agreement.
- **You need to inspect or override a wrong answer.** Every resolved span identifies the gazetteer record
  it landed on, so you can trace a bad result to the stage that produced it.

## Run it yourself

You can check both claims above on your own file. Our published numbers come from two panels, and
their scripts are public:

```bash
curl -fsSLO https://mailwoman.ai/benchmarks/be-panel.mjs
curl -fsSLO https://mailwoman.ai/benchmarks/be-panel.json
mailwoman data pull candidate
node be-panel.mjs --data-root <DATA_ROOT>
```

[Benchmarks](../benchmarks/index.mdx) has the results and the method. To test _your_ addresses,
replace the panel file with your own rows, and `be-panel.mjs` grades them.
