# Belgium — 30 addresses, three configurations

## What ran

On **2026-08-04** we ran 30 Belgian address lines through a local install three times, changing one
thing each time. We chose Belgium because it is an unmeasured locale. No Belgian rooftop register
ships, no `nl-BE` or `fr-BE` weights package exists, and the global candidate gazetteer is the only
artifact that answers. This panel reports the results you get from that setup.

Belgium also suits a bilingual test. Five Brussels streets appear twice, once in Dutch and once in
French, such as `Wetstraat` and `Rue de la Loi` or `Grote Markt` and `Grand-Place`. Each pair tests
whether two surface forms of one street reach the same place.

The main result is that six of the 30 rows do not land in Belgium with default settings. Setting one
option fixes all six.

## Method

The panel is [`be-panel.json`](/benchmarks/be-panel.json): thirty address lines built from public
street names, each paired with the postcode and commune it belongs to. Ten lines are the five
bilingual Brussels pairs. Nine are in Flanders, nine are in Wallonia, and two are in the
German-speaking Community. No Belgian rooftop register ships, so the pipeline parses the house number
but never looks it up. The panel does not depend on any particular number existing on these streets.

The run has three arms, each named for the question a reader is likely to ask:

| Arm              | Weights | Configured             | Question                                       |
| ---------------- | ------- | ---------------------- | ---------------------------------------------- |
| `base`           | `en-US` | no overrides           | What does an install plus a gazetteer give me? |
| `fr-overlay`     | `fr-FR` | no overrides           | Does the nearest measured locale help?         |
| `country-pinned` | `en-US` | `defaultCountry: "BE"` | What if I tell it the file is Belgian?         |

The first two arms leave the country unpinned, because the panel measures country routing. Belgian
place names collide with Dutch, French and Slovenian ones, and the panel is designed to catch
cross-border misses.

The panel grades four measures, and none of them uses a ground-truth coordinate set. Belgium has no
public rooftop register to grade distances against, so this page claims no distance to a true
building.

- **Resolution:** whether a coordinate came back, and at which tier.
- **Country routing:** whether the coordinate falls inside a bounding box drawn around Belgium's
  extremes, and whether the result reports `BE`. A coordinate outside the box did not land in
  Belgium. A coordinate inside the box is not necessarily correct.
- **Locality**, split three ways, because each of the two obvious versions is misleading on its own.
  `parsed` reads the span the model labeled, which is nearly circular because the commune appears in
  the input string. `name matched` reads only the nodes the resolver decorated. It shows that the
  gazetteer returned an accepted spelling but not where that place is. `resolved` combines the name
  match with the bounding-box check, and it is the measure to read. Place names repeat across
  countries, and this panel exists to catch cases where the wrong place won.
- **Bilingual agreement:** for each pair, the distance between the two language forms. This measure
  needs no ground truth. Both rows refer to one street, so any distance between them means the
  pipeline disagrees with itself.

## Numbers

Thirty rows per arm, from [`be-results.json`](/benchmarks/be-results.json):

| Measure                         | `base` | `fr-overlay` | `country-pinned` |
| ------------------------------- | ------ | ------------ | ---------------- |
| Returned a coordinate           | 27     | 27           | 30               |
| Inside the Belgium bounding box | 24     | 24           | 30               |
| Result names `BE`               | 24     | 24           | 30               |
| Locality — parsed               | 29     | 29           | 30               |
| Locality — name matched         | 26     | 26           | 30               |
| Locality — resolved, in Belgium | 24     | 24           | 30               |
| Bilingual pairs declared        | 5      | 5            | 5                |
| Bilingual pairs comparable      | 4      | 4            | 5                |
| Bilingual pairs agreeing        | 4      | 4            | 5                |
| Worst pair separation           | 0 km   | 0 km         | 0 km             |
| Answered at `admin`             | 27     | 27           | 30               |
| Answered at no tier             | 3      | 3            | 0                |

The three findings below are ordered by how much they change what you would do.

**Every row that answered did so at `admin`**, which is a commune centroid. No result on this panel
is street-grade, because no Belgian artifact exists that could provide street-grade results. A
perfect score here means "resolved to the right commune", and a commune is kilometers wide. Three
rows in the first two arms returned no coordinate. They are counted as `none` rather than included
in the `admin` row.

**The last locality row applies a check to the one above it.** A name match shows that the gazetteer
returned a place with an accepted spelling. It does not show that the place is in Belgium. On this
panel, that gap is two rows in each of the first two arms: one Belgian commune name matched a place
in the Netherlands, and one matched a place in France. The last of the two rows is the locality
measure to read.

**The French overlay leaves every measure unchanged.** The `fr-overlay` arm is identical to `base` on every measure
and on all thirty per-row records. The per-arm `weights` entry in the result file shows why. The
single `versions.model` run stamp does not. Both arms record the same `weights.model`, `model.onnx`,
but their `weights.source` values differ: `package:@mailwoman/neural-weights-en-us` against
`package:@mailwoman/neural-weights-fr-fr+base`. The `+base` suffix means the loader resolved the
French package _through_ to the base package. The French package is a data-only overlay. It ships
no `model.onnx`, only French postcode, pair-index and FST siblings, and the pipeline consults none of
them for a Belgian postcode. Belgium has no tier, and choosing the nearest tier does not give it one.

**Pinning the country fixes every failure.** `country-pinned` scores 30 out of 30 on all six
resolution measures. That result comes from one option in the call, and the next section describes
the failures it repairs.

## Losses

Six rows fail in the `base` arm. Five share one defect, and the sixth has a different one.

| Address                             | Where it landed                  | Named |
| ----------------------------------- | -------------------------------- | ----- |
| `Grote Markt 1, 1000 Brussel`       | no coordinate                    | —     |
| `Rathausplatz 1, 4700 Eupen`        | no coordinate                    | —     |
| `Hauptstrasse 1, 4780 Sankt Vith`   | no coordinate                    | —     |
| `Oude Markt 1, 3000 Leuven`         | 51.844, 5.094 — the Netherlands  | `NL`  |
| `Place Saint-Lambert 1, 4000 Liège` | 47.229, 1.110 — Le Liège, France | `FR`  |
| `Rue Léopold 1, 4000 Liège`         | 46.243, 14.364 — Slovenia        | `SI`  |

The gazetteer contains the right answers. A direct probe of `candidate.db` for the names in these
rows returns:

```
leuven      → Leuven/BE pop=102275  |  Leuven/BE pop=101032  |  Leuven/NL pop=0
liege       → Liège/BE pop=197013   |  Liège/BE pop=195278   |  … |  Le Liège/FR pop=238
eupen       → Eupen/BE pop=19254
sankt vith  → Sankt Vith/BE pop=9481
```

The Belgian answer is present and ranked first in each case. A 102,275-person Belgian city loses to a
zero-population Dutch hamlet of the same name, and a 197,013-person Belgian city loses to a
238-person French commune. Ranking did not decide these rows.

The country prior decided them. The six failures were re-run with the country filter disabled, using
the same weights, gazetteer and input strings:

```
default                  hardPlaceCountry: false
─────────────────────    ────────────────────────
(none)             →     BE  50.850, 4.349   Grote Markt 1, 1000 Brussel
(none)             →     BE  50.631, 6.031   Rathausplatz 1, 4700 Eupen
(none)             →     BE  50.280, 6.126   Hauptstrasse 1, 4780 Sankt Vith
NL 51.844, 5.094   →     BE  50.879, 4.701   Oude Markt 1, 3000 Leuven
FR 47.229, 1.110   →     BE  50.645, 5.574   Place Saint-Lambert 1, 4000 Liège
SI 46.243, 14.364  →     SI  46.243, 14.364  Rue Léopold 1, 4000 Liège
```

Five of the six recover. A confident whole-string country guess is promoted from a ranking bias to a
filter. When the guess is wrong, the filter removes the correct candidates before ranking runs. This
also explains why three of the six returned no coordinate instead of a wrong answer. The filter removed
every Belgian candidate, so no candidate was left to rank.

**The sixth row is a parse failure, and no configuration fixes it.** `Rue Léopold 1, 4000 Liège`
parses as street `Rue Léopold 1`, postcode `4000 Liège`, and house number `null`. The parser absorbs
the number into the street span and the commune into the postcode span. Slovenia's postcode 4000 is
Kranj, and a query with `4000` and no readable commune routes there. Under `country-pinned`, this row
returns the right coordinate, but its parse is still wrong: house number `null`, street
`Rue Léopold 1`, postcode `4000 Liège`. **The 30-out-of-30 above includes a row whose parse is
broken.** A high resolve rate can hide a broken parse in this way, so this page reports the parsed
and resolved locality counts as separate rows.

**Two of the six were scored as locality hits until the metric was fixed.** `Oude Markt 1, 3000
Leuven` resolves to a hierarchy reading `["Leuven"]`, and `Place Saint-Lambert 1, 4000 Liège`
resolves to `["Le Liège", "Liège"]`. Both are accepted spellings, and both places are in the wrong
country. On a panel that tests cross-border misrouting, a name match does not count as a correct
resolution. The published metric therefore combines the name match with the bounding-box check, and
the page reports both rows separately.

**One bilingual pair could not be measured.** `Grote Markt 1, 1000 Brussel` returned no coordinate in
the `base` and `fr-overlay` arms, so its French twin had no result to compare against. The pairs
row reads `4 comparable of 5 declared` rather than `4 of 4`. An early version of the script dropped
the unmeasurable pair from its denominator and reported that every pair agreed. Every pair that could
be compared agreed to within the reporting precision, in every arm.

## Caveats

**Belgium is an unmeasured locale, and this panel does not change that.** Mailwoman has no Belgian
eval set, training tier, or rooftop data. All results above come from 30
addresses run through a global gazetteer.
[Locales and tiers](../../developers/reference/locales-and-tiers.mdx) lists the measured locales,
and Belgium is outside that list.

**Every number is a commune-grade number.** All 84 answering row-runs answered at `admin`. Read
`30 of 30` as "the right commune centroid" and not as street accuracy. The error is bounded by the
size of the commune, and this panel does not measure it.

**The bounding-box check is coarse in one direction only.** A coordinate outside the box definitely
missed Belgium. A coordinate inside it could still be the wrong commune, and the locality row covers
that case.

**We wrote the locality expectations.** Each row has a committed list of accepted commune spellings
in `be-panel.json`, covering the Dutch, French and English forms a gazetteer may hold. The spellings
are public facts that anyone can check, but we chose which ones to include.

**n = 30, and the rows are civic addresses on well-known streets.** That population is easier than a
delivery manifest. A harder panel would likely score worse, and we have not run one.

## What to do with this

Pin the country when you know it. For a file you already know is Belgian, `defaultCountry: "BE"` took
this panel from 24 correct to 30. The change is one line in the library, the CLI and the server. The
country prior exists to help an input that arrives without context. A file that _has_ context should
state it instead of letting the prior guess.

## Reproduce

The script is [`be-panel.mjs`](/benchmarks/be-panel.mjs), the panel is
[`be-panel.json`](/benchmarks/be-panel.json), and the output above is
[`be-results.json`](/benchmarks/be-results.json) verbatim, including a per-row record for all thirty
addresses in each of the three arms.

That file's `versions` block records what this run used: Mailwoman 8.7.0, `model.onnx` from
`neural-weights-en-us@7.0.0`, and `candidate-global-1026.db`. Each arm additionally carries its own
`weights` entry, which is how the identical `base` and `fr-overlay` columns are traceable to one ONNX
file behind two package names. The block has no data-release field, because no Belgian register
ships.

```bash
npm install mailwoman @mailwoman/neural @mailwoman/neural-weights-en-us \
            @mailwoman/neural-weights-fr-fr @mailwoman/resolver \
            @mailwoman/resolver-wof-sqlite @mailwoman/spatial
mailwoman data pull candidate
node be-panel.mjs --data-root <DATA_ROOT> --out be-results.json
```

The run needs one 1.65 GB bundle and no rooftop database, which is the condition the panel tests. The
three arms took 4,273 ms together, excluding model load.
