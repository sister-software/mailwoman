# Supported languages and countries

Each row below is a support promise. It states the country an address is in, the language and script you type it in, and the deepest component Mailwoman guarantees for it.

Inside that depth, a wrong parse or a missed result is a bug we fix. Below it, Mailwoman returns the deeper components as unresolved and leaves them unguessed. For example, the United States row for Japanese text guarantees cities: `ニューヨーク` resolves to New York City. A street typed in katakana, such as `ブロードウェイ`, can come back unresolved.

## The support field in a response

Every result from `POST /v1/geocode` and every geocoded row from `POST /v1/batch` includes a `support` field. It holds the row above that the query falls inside, matched on the resolved country and the script the query is written in, or `null` when no row covers it. A `null` value means the result sits outside every guarantee. The result may still be right. `POST /v1/parse` returns no `support` field, because a parse resolves no country to match on.

## How a row is kept true

The table is generated from `packages/codex/lib/support/promises.json`, which ships in `@mailwoman/codex` as `@mailwoman/codex/support`. Every code in it is checked against the IANA Language Subtag Registry through `@mailwoman/registry`.

A row stays only while the regression suite holds a passing case in that country, written in that script. The repository check `support-promises` refuses a row without one, and it reports each failing case inside a row as an open bug.

Text in a script the table doesn't list may still parse and resolve, but no row guarantees it.
