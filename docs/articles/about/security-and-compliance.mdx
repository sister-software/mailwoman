# Security and compliance

Mailwoman runs inside your infrastructure. The addresses you process stay there, because no step in
a parse or a geocode sends them anywhere else. This page describes that behavior precisely enough for
you to check it, and links the artifacts a security review asks for.

## What the library sends over the network

A parse or a geocode sends no request over the network. Those calls read model weights and gazetteer
files from local disk and return. No published package contains telemetry, analytics, crash
reporting, a version check or a usage ping. Mailwoman's install runs no lifecycle scripts:
`npm install` fetches tarballs and stops.

The network behavior has four boundaries:

- **`RemoteResolver` is opt-in, and you own the endpoint.** It separates parser nodes from a
  gazetteer service inside your own network. It throws unless you construct it with an endpoint URL.
  It is never a default, and we do not operate the service.
- **The dataset build commands download datasets.** `mailwoman gazetteer build` and related commands fetch
  from the US Census, Geofabrik, `adresse.data.gouv.fr` and the FCC. You run these commands
  deliberately, at build time, separately from parsing.
- **The data pull command downloads reference data.** `mailwoman data pull` fetches prebuilt
  gazetteer, POI and locale bundles from `public.mailwoman.ai`. A HEAD request checks the remote
  size, and then a GET streams the file to disk. The command runs only when you invoke it.
  [Your first ten minutes](../developers/get-started/ten-minute-trial.mdx#5-geocode-it) shows the
  exchange line by line.
- **The browser runtime downloads its model.** `@mailwoman/neural/web-loader` fetches model and data
  artifacts once, from a URL your application supplies. The query text stays in the page. Our hosted
  [Earth](https://earth.mailwoman.ai/) demo is a deployment of that runtime. It serves those
  artifacts from `public.mailwoman.ai` and calls `tiles.mailwoman.ai` for coarse map centring. The
  demo makes both of those requests. The library you install makes neither.

## How it is licensed

One codebase is available under two licenses:

- **AGPL-3.0-only.** The full text and the dual-license header are in
  [`LICENSE.md`](https://github.com/sister-software/mailwoman/blob/main/LICENSE.md). The license has
  one condition. If you distribute software built on Mailwoman, or run it as a network service that
  others use, those users are entitled to your corresponding source under the same license.
- **A commercial license**, which releases you from that condition. The reference terms are in
  [`COMMERCIAL-LICENSE.md`](https://github.com/sister-software/mailwoman/blob/main/COMMERCIAL-LICENSE.md).
  That document is a template and grants no rights. Only the executed agreement is binding. Rates are on
  [Pricing](../pricing.mdx).

The code license and the data license are separate. Our license covers the code. Data provenance,
below, describes the terms that the reference data carries.

## Software bill of materials

We publish an SBOM for the `mailwoman` package in two open standards: SPDX 2.3 and CycloneDX 1.5.
The built-in `npm sbom` command generates both, without third-party tooling in the trust path. It
runs against the published tarball instead of the working tree, so the SBOMs describe what a consumer
installs and exclude development-only dependencies.

The files are served under
[`/sbom/`](https://mailwoman.ai/sbom/mailwoman-9.4.0.cdx.json) and committed to the
repository. Generation is a release-time step that runs on demand instead of in CI, so the newest
published SBOM can lag behind the newest release. Check the version in the filename before you scan
it.

npm Trusted Publishing uses GitHub OIDC and removes the need for a long-lived registry token that
could leak. Packages do not currently carry a sigstore provenance attestation.

## Data provenance

The pipeline records each source with its license at the point the source enters. The legal notices
ship as
[`THIRD_PARTY_NOTICES.md`](https://github.com/sister-software/mailwoman/blob/main/THIRD_PARTY_NOTICES.md)
in the source distribution. Each built data artifact carries its own `ATTRIBUTION.json`, which
records the source, release and license it was built from. The catalog of sources and their terms is
[data licensing and provenance](https://github.com/sister-software/mailwoman/blob/main/docs/records/site-2026-08/licensing/data-provenance.md).

Two items on that page matter to a review, and we would rather you heard them from us:

- **The OpenStreetMap rooftop tier reaches no published artifact.** The rooftop extracts in
  `@mailwoman/osm` are built and deliberately unpublished, on npm and in the demo alike, because OSM
  data is share-alike and enabling that tier is waiting on legal review. The served `candidate`
  gazetteer does carry a Northern Ireland postcode fold derived from OpenStreetMap under ODbL: 4,757
  places, measured 2026-09-27 by downloading `gazetteer/2026-08-25b/candidate.db` in full and
  counting the rows in that fold's id range. What ODbL asks of that is with counsel, and this page
  states no conclusion about it. The
  [data products](../product/data-products.mdx#as-served) page shows what each published bundle's
  own manifest records.
- **One source's license is recorded inconsistently in our own files.** Who's On First appears as
  CC0 in the provenance catalog and as CC-BY 4.0 in the resolver package's own notes. Until that is
  settled, attribute Who's On First.

## Report a vulnerability

Report vulnerabilities privately by email instead of in a public issue. The policy, the scope and
what to include are in
[`SECURITY.md`](https://github.com/sister-software/mailwoman/blob/main/SECURITY.md).
