# What a confidence score can tell you

Can a high `confidence` value tell you that an address is valid? It describes how a component label was selected. A correctly labeled `locality` can still name several places, and a correctly labeled `house_number` can still lead to a coordinate for a whole street. Those questions need separate evidence.

## The score belongs to a label decision

The parser assigns a score to each returned node in its `AddressTree`. On the neural path, the tree builder averages the selected pieces' label scores across the span. Label repairs can change those scores before the average. A postcode or locality fast path instead uses the query-shape or kind classifier's confidence. A provisional phrase-grouper node uses a scaled proposal score. The pipeline `path` and a node's `source`, when present, help identify which mechanism produced a node.

These scores have different origins. One threshold across them would mix different measurements. The [parse inspection tutorial](../tutorials/inspect-a-parse.mdx) shows scores for `apt 4b 350 5th ave new york ny 10118` in a published 11.0.0 run. That one result gives no error rate for other addresses.

A calibration table can map raw scores to observed label frequencies for a specified model and evaluation population. The default runtime parse doesn't apply such a table. The published `@mailwoman/neural-weights-en-us@11.0.0` package names model `10.8.0`, while its bundled `calibration.json` names model `5.3.0`. The table therefore doesn't establish an accuracy mapping for the published model. A decision threshold needs an evaluation of the exact model, locale, input population, and cost of an incorrect decision. [What supports a model-quality claim?](./data-and-model-quality.mdx) explains that evaluation.

## Place identity has its own alternatives

The parser can label `New York` as a `locality` before a resolver identifies a geographic record. A geocode result can list several `candidates` for that span. Their scores rank places within the span. They have no common unit across separate spans or answers. A `null` score comes with `scoreUnmeasured`, which explains why no score was recorded.

For some bare place-name queries, `declared_ambiguity` marks a result when two distinct places are rankable and the leading candidate fails a dominance test. The selected candidate remains in the result. An absent marker doesn't establish a unique place. The check may lack rankable alternatives, or the query may take another path. Inspect the candidates when the place identity matters.

## A coordinate needs geographic evidence

`resolution_tier` identifies whether the selected point came from an address point, interpolation, street, postcode, or administrative place. `coordinate_source` records a source stamp for selected rows that supply one, and `epistemic_status` describes the claim supported by the coordinate evidence. A reported `uncertainty_m` is a radius in meters; `null` means no radius was reported. None of these fields turns a parse-node score into a measured distance from the destination. [Why a geocode coordinate has a precision tier](./geocoding.mdx) explains the selection mechanism.

When no coordinate is selected, the geocode result can return `lat: null`, `lon: null`, and `epistemic_status: unresolved`. A selected coordinate can still have an ambiguity or coarse-answer advisory. An application can accept a result only after it states which identity, tier, source, and error evidence its task requires. The [result schema](../reference/schema.mdx) defines the fields. The [provenance review guide](../guides/review-geocode-evidence.mdx) shows how to inspect them.
