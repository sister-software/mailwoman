# What confidence and ambiguity can tell you

A parse node can have a high `confidence` while a place name still resolves to several locations. A geocode can return coordinates at a coarse tier even when every component was labeled correctly. Which result tells you whether to use the answer?

A node score describes a component label. Resolver candidates describe possible places for a parsed name. A coordinate tier and its provenance describe how the selected point was obtained. The application decides whether that evidence meets its use case.

## Parse labels and place identities

Consider a line containing a street, a place name, and a postcode. A reader can identify which words are the street and which are the place while remaining unsure which real place the name identifies. A map can then provide a point for that place at city scale without locating the building. Mailwoman exposes those judgments through different results so the caller can preserve the remaining uncertainty.

The parser's `AddressTree` contains labeled spans and their `confidence` values. A resolver can attach place identities and alternatives to those spans. The separate `GeocodeResult` contains the selected coordinate, its `resolution_tier`, `epistemic_status`, and any reported `uncertainty_m`. The [result schema](../reference/schema.mdx) defines the fields.

## Where node scores come from

For a node built from the neural classifier, the tree builder averages the selected pieces' label scores over the span. Word-consistency repair can replace a piece's score with the repair vote's mean before that average. The value describes the returned label for that span. It doesn't measure address existence, delivery, or coordinate accuracy.

Other paths produce node scores differently. A postcode or locality fast path uses the query-shape or kind classifier's confidence. A provisional node added by the phrase-grouper audit uses a scaled proposal score. These origins can be inspected through the pipeline `path` and a node's `source` when present. A single threshold applied across all such nodes would mix scores from different mechanisms.

The [parse inspection tutorial](../tutorials/inspect-a-parse.mdx) prints node scores for `apt 4b 350 5th ave new york ny 10118` using the published 11.0.0 en-US packages. Those observed numbers describe that one run. They're not a measured error rate over other addresses.

## Calibration of node scores

`createCalibrator` can map a raw span score through an isotonic lookup table when a caller supplies the table to a direct classifier parse. The default runtime parse doesn't pass a calibration table. A mapping fitted on held-out labels can support a frequency interpretation only for a model and population where the mapping has been evaluated.

The published `@mailwoman/neural-weights-en-us@11.0.0` package identifies its model as version `10.8.0`. Its bundled `calibration.json` identifies `model_version` as `5.3.0`. The bundled table was therefore fitted to an older model, and calibration for the 10.8.0 model is unknown. The model card records calibration figures from that earlier fit. Those figures describe the 5.3.0 model. Treat the default node score as a model output whose current accuracy mapping is unknown. A decision threshold needs an independently checked calibration or outcome study for the exact model, locale, input population, and cost of an incorrect acceptance.

## Place candidates and ambiguity markers

A correctly labeled `locality` span can still refer to several places. A geocode result can list ranked `candidates`, with the selected place first. A candidate's `score` ranks places within that answer. Candidate scores have no shared unit across separate answers. A `null` candidate score means the resolver recorded no score for that candidate.

For some bare place-name queries, the geocoder emits a `declared_ambiguity` intent marker when at least two distinct places can be ranked and the leading candidate doesn't meet its dominance test. The marker reports ambiguity while leaving the top-ranked answer in place. Its absence isn't a statement that the place is unique: the check can lack enough rankable candidates or the query can take another path. When the place identity matters, read the alternatives and the evidence behind the winner rather than interpreting the parse node's confidence as a place-match score.

## Coordinate tier, status, source, and radius

`resolution_tier` identifies how the point was produced: for example, `address_point`, `interpolated`, `street`, `postcode`, or `admin`. A building-level task needs evidence at a finer grain than a locality or administrative centroid supplies. The `house_number` text can remain in a geocode result even when the selected coordinate comes from a coarser tier, because the field records what was parsed and the tier records what was located.

`epistemic_status` describes what the coordinate's evidence permits the caller to claim. It varies independently of the tier. A coordinate from an authority-designated register and one from a crowdsourced observation can occupy the same `address_point` tier while having different statuses. `coordinate_source` identifies the register row behind an address-point or interpolated coordinate when available. `uncertainty_m` is a reported radius in meters when the tier supplies one. A `null` value means the result provides no radius. A reported radius doesn't establish how frequently coordinates fall within that radius for the current data and conditions.

## Unresolved results and abstention

The parser returns a tree and records caught stage failures in `faults`. A classifier failure can leave that tree empty. The parser doesn't provide a general address-validity verdict. The geocoder can return `lat: null`, `lon: null`, and `epistemic_status: unresolved` when it has no coordinate. It can also return a coordinate with an ambiguity or coarser-answer advisory. These states report different conditions, and an advisory doesn't automatically suppress the coordinate.

An application should define the evidence it needs before accepting a result. A routing task may require an address-point coordinate from an acceptable source. A regional count may accept an administrative result. If the result has unresolved coordinates, unresolved identity, or an evidence tier below the application's requirement, the application can request more input or send the record for review.
