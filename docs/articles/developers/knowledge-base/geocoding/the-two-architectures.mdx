# The two architectures

## The question

Two geocoders answer the same question: you type an address, and they return a point. One of them
recommends 128 GB of memory before you start. The other is an npm install and a file on disk. They do
different amounts of work, and code quality does not explain the difference. There are two ways to
build a geocoder, and they do the work in different places.

This page describes those two designs: how each works, what each is good at, and what you get when you
pick one.

## The analog

You are at the front desk of a large building and want to find someone. You can ask in two ways.

In the first, you give the receptionist everything you know, such as a half-remembered name, a floor
and the word "accounts". The receptionist searches every directory in the building for anything
resembling any of it and reads you the best matches in order. This works well even when half of what
you said was wrong, when you gave a nickname, or when you wanted a room instead of a person. The cost is
that the receptionist must keep every directory in the building open at once and must rank well,
because everything matches a little.

In the second, the receptionist reads your note, works out that "accounts" is the department and the
rest is a person's name, goes to the accounts department's own list, and looks up the name there. Fewer
pages get opened. The answer comes with its reasoning: you know it came from the accounts list, so you
know what it means. The cost is that someone must understand your note first. If they read "accounts"
as a surname, they go to the wrong list and come back with nothing at all. You do not even get an approximate answer.

Every geocoder works like one of those two receptionists.

## Architecture one: search engine with a map

This design takes every known place (countries, regions, towns, neighborhoods, streets, address points,
points of interest) and turns each one into a document in a full-text search index. Each document gets
its name, its alternate names in every language, its parents, and its coordinate. At query time, the
engine sends the user's whole string to the index and ranks the results.

This design deliberately does not label your string before the lookup. Some engines do run a query
parser first. Pelias shapes its queries with libpostal, which accounts for the 4 GB in its row below.
That parse shapes the query without deciding the answer, and the ranking still runs against one index
over everything. The system never decides that `Springfield` is a locality. It finds documents that
score well against the token `springfield` and ranks them. The system does not resolve ambiguity. It
returns the candidates as a result list. Adding a country means adding documents. Adding a language
means adding name variants to existing documents. Neither requires writing a grammar.

Nominatim, Photon and Pelias use this architecture, and so does the tantivy-based
[Airmail](https://github.com/ellenhp/airmail). The storage engines differ (a relational database with
spatial extensions in one case, OpenSearch in another), but the design is the same: one index over
everything, queried as text.

**What it is good at.** These strengths are real advantages:

- **Fuzzy recall over a huge corpus.** For a misspelled name, half an address, or a landmark instead
  of a street, the index still returns a ranked result, because scoring is continuous. A design that
  parses first has nothing to look up when the parse fails.
- **Inputs that are not addresses.** "The station", "castle museum", or a venue name containing a
  place name are documents in the index like any other. They are not addresses, and a parser has no
  label for them.
- **Every script, immediately.** The index stores text. A Korean place name and a Polish one are the
  same kind of document, and neither needs a locale rule.
- **A ranked list suits autocomplete.** A search box needs five plausible completions instead of
  one confident answer, and this architecture always produces a ranked list.

**What it costs.** Ranking runs against the whole corpus at query time, so the corpus needs to be in
memory, and the ranking function must be tuned against all of it at once. A change that improves one
country's recall can reduce another's precision without any warning, and you find out only from the
aggregate scores. The answer is also a matched document without a breakdown of your input. You learn which
record matched, but you do not learn which part of your string matched what. If you need to know whether `Ave` was a
street suffix or part of a venue name, this architecture never determines that.

## Architecture two: understand, then look up

This design labels the string first. It decides that one span is a house number, another a street,
another a locality and another a postcode, without consulting any place database, because that decision
depends on how the words are _used_ instead of on which places exist. It then runs one constrained lookup per
labeled span against a gazetteer. Instead of asking "what matches this string", each lookup asks "which
locality has this name, inside this region".

The lookups are cheap because they are constrained. A locality lookup scoped to a resolved region never
considers the rest of the planet, so it performs a small indexed read instead of a ranked scan. This is
why the data can stay on disk: the query reads a handful of pages instead of the whole corpus.

Mailwoman uses this architecture. Any pipeline built on libpostal uses part of it. libpostal provides
the labeling half without the lookup half, which is why it is a parser and not a geocoder.

**What it is good at:**

- **A breakdown of the input as well as a match.** The result says which piece of the input was the
  street and which was the town, with offsets into your original string. Any downstream task that needs
  fields instead of a point (deduplication, validation, formatting, record matching) needs exactly
  this.
- **Answers that record their source.** Each resolved span identifies the gazetteer record it matched,
  so you can trace a wrong answer to the span that caused it.
- **A small memory footprint.** The model is a file, and the gazetteer is a sealed read-only database
  read from disk.
- **You choose the scope of the data.** Coverage is a set of downloads that you choose separately
  from the install, so a US-only deployment stores only US-sized files.

**What it costs.** Someone must train the labeler on a labeled corpus for each locale. Where that corpus
is thin, the labels are wrong, and no amount of gazetteer data repairs them. When labeling goes wrong,
the result is empty and nothing flags the error. A span labeled `street` that was really a locality is
looked up in the street index, matches nothing, and returns an empty result instead of an approximate
one. The search architecture would have returned something. A query that is not an address at all has
no useful labeling, so it has no useful lookup.

Each project publishes what it recommends you provision. The figures below are quoted from each

| Pelias          | Elasticsearch                             | The published requirements document covers software dependencies rather than hardware. Keep four points in mind before you draw a conclusion from that table.

**The rows measure different things.** Nominatim's and Photon's figures are for a planet-scale install
and are recommendations for smooth operation under load. Mailwoman's figures are measured install and
download sizes. The Footprints page states that runtime memory is measured per workload on other pages
and is not re-measured there. A missing number is not a small number.

**Addok combines traits of both categories**, which is why it is in the table. It uses a search-style
index (Redis and ranked matching, without a parser), and it has no memory problem, because it indexes one
country's address register instead of the whole planet. When the corpus is scoped down, the
architectural cost of the search design mostly disappears. If all your addresses are in one country
and that country publishes a register, Addok is a strong option, and nothing on this page argues
against it.

**Disk space also costs something.** Mailwoman's US rooftop tier is 41.3 GB if you download all of
it. The difference is that the large part is optional, split by state, and unused until queried.

**Both designs pay for the same thing in different ways.** Geocoding needs the world's places stored
somewhere it can reach them. The search design reaches them by ranking, which needs them in memory. The
label-then-look-up design reaches them by constrained lookups, which lets them stay on disk. It pays
for that with a model and a labeled corpus per locale. That cost is paid before you run a single query,
and no hardware page lists it.

## Where the verdict lands

The choice depends on what your input looks like. The hardware table does not decide it.

If your queries are exploratory (search boxes, partial strings, landmarks, "the thing near the
station"), the search architecture fits the job, and a parser is the wrong tool because such a query can
contain nothing to parse. If your queries are addresses from a form, a CRM export or a delivery manifest, and
you need fields as well as a point, the labeling architecture fits the job. A ranked document list
would have to be post-processed into fields anyway.

The two designs can also be combined. A pipeline can label first, use the constrained lookup when it
succeeds, and fall back to a ranked full-text search over the raw string when the labeling produces
nothing usable. That design is workable, and it carries both sets of costs.
