# Training and the corpus

## The question

The model assigns one of 33 labels to each piece of your input, and it learned to do so from
examples. This page explains what those examples are, where they come from, who labeled them, and what
prevents a run that improved one thing and broke another from shipping.

## The analog

In a rule-based parser you write the rules, and the rules are the specification. Anyone can read them
and predict the parser's behavior on a new input, because the rules fully determine the behavior.

In a learned parser you write the examples, and the examples are the specification. Everything the
parser does on unseen input is an extrapolation from its examples, including extrapolations nobody
intended. A corpus that is three-quarters one country teaches that country's ordering as a general
fact about addresses. A corpus where the locality is nearly always the first token teaches the model
to label the first token as a locality without reading it.

Each approach has a cost. Rules are auditable and bounded: you can read them, and you can see where
they stop applying. Examples generalize beyond what anyone listed, but you cannot audit them the same
way. The only way to learn what a corpus taught is to test the model on data it did not see.

The rest of this page follows from that tradeoff.

## Where labeled rows come from

Nobody hand-labels address text at the scale a model needs, so the labels are derived. A large amount
of open address data already has two parts: a structured record with the components in separate
fields, and the address as a line of text (either published alongside the record or reconstructible
from it).

National address registers publish data in this form. So do census street files, open gazetteers, and
collaborative address projects. Mailwoman's published attribution list includes several of them:
France's Base Adresse Nationale, Great Britain's Price Paid Data, New Zealand data derived from LINZ,
OpenAddresses extracts for several European countries, Overture's addresses theme, and Who's On First
for administrative names. Every row carries the license of its source, so the list serves as an
attribution list and not only an inventory.

The **alignment** step turns a structured record into a training row, and it fails in several common
cases. It takes the record's components, finds each one in the text line, and marks the
first piece a component covers `B-<tag>` and the rest `I-<tag>`. Sometimes a component cannot be
located: the record says the region is `California` and the line says `CA`, a diacritic differs, or
the source's fields disagree with its own address string. In those cases the row is **quarantined**
instead of guessed at. It is written to a separate file with the reason, and it is not used for
training.

The quarantined rows are a useful signal. If a source's quarantine rate jumps, its schema has likely
changed, and the quarantine rate shows this before the model's scores do.

## The multiplier, and the reason for it

Real users do not type addresses the way registers store them. They abbreviate the street type, drop
the commas, type in a single case, and leave the accents off. A corpus built only from register text
teaches only the register's formatting.

For that reason, each row is expanded into surface variants before alignment runs: all uppercase and
all lowercase, with and without commas, the state name and its abbreviation, `Avenue` and `Ave`, `Apt`
and `Apartment`. The set of variants is chosen per country. Accent stripping is a French default, for
example, and has no useful effect on United States rows. Each variant is aligned from scratch instead
of copying labels onto it, because changing the surface text moves the boundaries. A variant that
fails to align is quarantined like any other row.

This is why case handling appears twice in the design. Case restoration at parse time handles the
lowercase input the model was not trained on, and case variants at training time reduce how much such
input there is. Neither one alone covers the way users type.

## What a run optimizes

A training run optimizes one objective: for each piece, put as much score as possible on the correct
label. That objective is per-position cross-entropy, and it is the whole loss. The loss has no
sequence-level term. It neither rewards a well-formed reading nor penalizes an impossible transition,
because the decoder enforces those constraints instead. See
[Decoding and the best path](./decoding-and-viterbi.mdx#why-the-transition-scores-are-constraints-rather-than-weights)
for the alternatives that were tried and why they did not ship.

Two changes shape what that loss rewards in practice.

**Source weighting.** Sources differ in size by orders of magnitude, so training on the raw mixture
lets the largest source define what an address looks like. Weighting lets the trainer sample an
under-represented source at a higher rate than its row count would suggest. It prevents a positional
failure: a corpus dominated by one source's field order teaches that order instead of the components.

**Labels for pieces that had none.** A sequence labeler learns a tag partly by learning where it
stops, so adding a new tag sharpens the tags next to it. Before `unit` was a category, the model had
to assign `Apt 456` some other label, and it assigned `street`. As a result, `street` absorbed
everything on the road line and had no reliable end. Giving those pieces their own label moved them
off `street`, and `street` became more precise as a side effect. Adding a category has a cost in
general, because two categories that overlap in the data trade one confusion for another. When the
old label was absorbing a distinct kind of text, the cost is close to zero.

## Held-out means held-out

The evaluation portion of the corpus consists of whole regions instead of a random sample of rows. The
regions were chosen for low data density and removed from training entirely: Vermont, Wyoming and
North Dakota for the United States, Corse, Lozère and Creuse for France, Saarland and
Mecklenburg-Vorpommern for Germany. Rows from those regions are divided between validation and test by
hashing each row's source identifier, and all other rows are used for training.

A random split would inflate the scores, because addresses on the same street share most of their text. If
`13 Main St, Springfield, IL` is in training and `15 Main St, Springfield, IL` is in evaluation, the
model can score well by recalling `Springfield` instead of reading the address. A model could appear
to generalize while only memorizing place names. Holding out whole regions prevents this. The
measurement then answers the question that matters for most deployed input: how the model performs
on a place it has never seen.

One rule keeps the holdout valid over time. A holdout added after a corpus was built is not a holdout.
Every corpus version records its split in a committed manifest, so a rerun reproduces the same
division, and nobody can decide after the fact which regions were meant to be unseen.

## Why an evaluation stands between a run and a release

A training run produces a checkpoint and a number. Neither is a reason to ship.

The evaluation reports results per tag and per locale instead of as one aggregate. An aggregate score
moves when one large category moves, and it barely changes when a small category collapses. Shipping
on an aggregate therefore means shipping without checking the categories that make it up. First-class
locales have per-tag floors that block a release when a tag falls below them. Other locales are
measured, recorded and discussed, but they do not block a release.
[Locales and tiers](../../reference/locales-and-tiers.mdx) lists which locales are in which tier and
what each tier means. The key distinction is that a locale counts as supported only when a graded
evaluation covers it. Training data alone is not enough.

Two practices accompany the evaluation.

**Every shipped model carries its own numbers.** The model card inside the weights package publishes
the label set, the architecture, the calibration measurements, the data attribution, and per-tag
scores by locale. It ships to the registry with the model, so the published scores always match the
model they describe. You can read the measurements for the model you installed from the package you
installed.

**Numbers are recorded per version instead of overwritten.** A regression is detectable only with a
per-version ledger. Without the previous version's numbers, measured the same way, there is no baseline
to compare against.

## What it costs

**The corpus determines what the model can do, and coverage is uneven.** Coverage follows open data,
which follows national policy, which has no relation to where your users are. The model reads
addresses well in countries that publish an address register. In a country without one, accuracy
stays low no matter how much compute goes into training.

**A source's bias becomes a prior.** Every register encodes conventions: which fields are populated,
how the region is spelled, and whether the postcode comes first or last. The model then expects those
conventions in inputs that do not follow them.

**Improvement is not monotonic.** Adding a locale can interfere with an existing one, and adding a
category can trade one confusion for another. For this reason, the evaluation reports per tag and per
locale instead of a single score with a threshold. A run that improves the headline number can still
be the wrong one to ship.

**A small evaluation set cannot distinguish a small regression from noise.** Human-labeled evaluation
data has its own annotation errors, so a shift of a point or two is within the noise. Inspect such a
shift case by case instead of reading it off the table.
