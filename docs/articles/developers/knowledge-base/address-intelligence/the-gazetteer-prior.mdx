# The gazetteer prior

## The question

You have a list of every place name in the world, with a type attached to each. Why does the parser
not read the input, check each token against the list, and label the hits?

The list knows which strings can be place names, but it does not know which strings are used as place
names in a given input. This page explains how Mailwoman uses a place list with that limitation. The
parser keeps the list and consults it on every parse, but the list does not decide the labels.

## The analog

Most people start with a gazetteer lookup. They tokenize the input, probe a table of place names with
each token, and label every token found in the table as a place.

This approach works on a large fraction of real input, but it fails on common cases. In
`Park Avenue`, `Park` is a place name somewhere, so the lookup labels the street as a town. In
`Paris, TX`, the lookup has no reason to prefer the Texas Paris over the French one, because the table
contains nothing about the `TX` next to it. In `Buffalo Health Clinic, Buffalo`, it finds `Buffalo`
twice and cannot tell which one is the business and which is the town.

All of these failures have the same cause. The lookup answers "is this string ever a place name", but
the parser needs to know "is this string used as a place name here". The first question is about the
world, and the second is about the sentence. The table can only answer the first.

A better table would not fix this. The fix is to treat the table's answer as one piece of evidence and
combine it with evidence about the sentence, which the per-piece scores already provide.

## The mechanism

Before the model runs, the parser walks the input against a place index and collects every match.
For each match it produces a small set of adjustments to the per-piece scores:

- **A bonus on the matching component labels.** A locality match adds to `B-locality` and
  `I-locality` on the pieces it covers.
- **A penalty on the competing labels.** The same match subtracts from street, house number and
  venue on those same pieces. A span that matches a known town is evidence against those readings as
  well as evidence for its own.

The parser adds those adjustments to the model's scores, and the decoder reads the sum. This technique
is called shallow fusion. It comes from speech recognition, where a language model's scores are added
to an acoustic model's scores at decode time instead of replacing them. Adding the scores keeps both
sources of evidence. The model contributes what the sentence looks like, the index contributes what
the world contains, and the parser consults both on every input.

The bonus is scaled by how prominent the matched place is and capped at three points of score. The cap
keeps the index from overriding a confident model. When the model's top two readings are far apart,
three points does not close the gap, and the model's reading wins. When they are close, three points
decides the result. The index therefore has the most influence where the model is least certain.

Three details explain behavior you can observe.

**Match length changes the size of the penalty and leaves the bonus unchanged.** Length is counted in
words. A one-word match is weak evidence, because surnames, common words and street heads are place
names somewhere. A match spanning several words is stronger, because a coincidental match becomes less
likely with each word. By default, the parser discounts the penalty on competing readings for a short
match and keeps the bonus at full strength. A bare `Hollywood` is a one-word match, and the full bonus
is what makes it come back as a locality. Discounting the bonus would remove the index's most
important effect. A wrong one-word match does its damage through the penalty, so the penalty is the
part that is reduced.

**A match in a street-like context gets no bonus.** When a matched name is in a street-name position,
with a street-type word beside it or a house number to its left, the runtime pipeline withholds the
positive bonus and keeps only the penalty. The index therefore does not pull a street named after a
town toward the town. `800 Washington Ave, Portland, OR` and `123 Madison Ave, New York, NY 10016`
parse identically with and without the index. The penalty is never withheld, because the index
provides evidence for a reading and against its competitors. It never penalizes a reading it has no
information about.

**One span can match several kinds of place at once**, and the index does not choose between them.
`New York` is both a city and a state, and both entries apply. Each adds a bonus to its own component
labels on the same pieces, and the decoder decides which one wins by reading the rest of the line.

## What it can and cannot do

**It cannot resolve.** The index reports that a span could be a place of some type. It does not choose
which place, and it produces no coordinate. The resolver does that after the parse.
[Gazetteers](../geocoding/gazetteers.mdx) describes the database, and
[The two architectures](../geocoding/the-two-architectures.mdx) describes where the two jobs sit.

**It covers four component types.** A match becomes a bonus only when its place type has a model
label: country, region, locality or postcode. The index holds more types than that. Querying `Boston`
returns neighborhood entries as well as the locality. Entries outside those four types contribute
nothing, because there is no label to apply the bonus to.

**It contains administrative names only, without streets or venues.** A gazetteer of specific street names
would add several million entries, and the package does not ship one. A separate, much smaller
vocabulary of generic street-type words (`avenue`, `rue`, `straße`) exists, but it is a different
mechanism with its own wiring status. Venue names are open-ended and are not in any index. This matters
because the hardest ambiguity in address parsing is a venue named after a place, and the index has
the least information about that case.

**It cannot override a confident model.** The bonus is capped, and the model's scores are not. If the
parse is wrong in a way that a place-name lookup would fix, the index will not fix it.

**It is a prior instead of a stage, so a missing index produces no error.** The runtime pipeline loads the
index from the weights package on its first call and passes it to every parse. A classifier you
construct and call directly receives no index. The parse still succeeds, but it is less accurate on
the inputs the index is meant for, and nothing reports the difference. A bare `Hollywood` comes back
as a street without the index and as a locality with it.
[Library API](../../reference/library-api.mdx#wiring-the-gazetteer-index-on-a-bare-call) has the
wiring and the measured difference.

## What it costs

**The index is the second-largest file in the weights package, after the model itself.** It is
21.8 MB, against 39.4 MB for the model. [Footprints](../../reference/footprints.mdx) lists it with the
other files. The design spends build time to save query time. Every place name is compiled into a
walkable structure once, offline, and a parse only walks that structure. Because of this, the same
index can ship to a browser instead of running behind a lookup service.

**A correction from the index does not raise the reported confidence.** The score on each span is the
model's own score for the chosen label, computed before the index adjustments are added. When the index
changes a reading from wrong to right, the corrected span shows the score the model gave that reading
on its own. That score is low, because the model preferred another label. On a bare `Hollywood`, the
score is 0.691 as a street without the index and 0.264 as a locality with it. The label improved, and
the score fell. If you threshold on confidence, your threshold will send this kind of correct answer to
review. [Calibration and confidence](./calibration-and-confidence.mdx) covers how to handle it.

**The index covers only what the gazetteer covers.** The prior cannot help with a town that is missing
from the open data. That failure looks like an uncertain model instead of a missing record.

**The index does not fix the venue-versus-place case, which the parser still gets wrong.**
`Riverside Garden Center, Boston` comes back with two locality spans through the pipeline. The business
name is labeled a locality across characters 0 to 22, and `Boston` is correctly read at 0.784. The town
is labeled correctly. The parser fails to decide that the leading phrase is a venue instead of a
second place name. The output is identical with and without the index, both through the pipeline and through
a bare classifier call. `Riverside` and `Boston` are both in the index, but neither match changes that
decision. Separating a business name from the town after it requires judging how the words are used,
and the index has no entries for business names. A prior that supplies world knowledge without sentence
structure will produce this kind of failure.
