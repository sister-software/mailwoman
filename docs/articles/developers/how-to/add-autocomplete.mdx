# Add place autocomplete

**Outcome.** A search box returns ranked place completions as the user types. The completions come
from a file you already have, and this page measures the cost of each keystroke.

This autocomplete completes **place names** (localities, boroughs, counties, neighborhoods) from a
finite-state transducer built over the gazetteer. It does not complete street addresses or house
numbers, and it uses a different index from forward geocoding.

## Prerequisites

- The library install from
  [Install and first parse](../get-started/install-and-first-parse.mdx). The FST ships inside
  `@mailwoman/neural-weights-en-us` as `fst-en-us.bin` (21.8 MB), so you already have it.
- `@mailwoman/resolver-wof-sqlite`, if you call autocomplete from code. The autocomplete functions
  are on deep subpaths of that package instead of its root. Step 2 shows the imports.
- You do not need a gazetteer database. The FST is self-contained.

## 1. Try it from the command line

Tell the CLI where the FST is. Its built-in default is a staging path that will not exist on your
machine, so pass `--fst` or set `$MAILWOMAN_FST_BIN`:

```bash
export MAILWOMAN_FST_BIN="$PWD/node_modules/@mailwoman/neural-weights-en-us/fst-en-us.bin"
npx mailwoman autocomplete "san franc" --limit 5
```

```
 1. San Francisco [+francisco]  (locality, wof:85922583, imp:0.6901)
 2. San Francisco [+francisco]  (county, wof:102087579, imp:0.6901)
 3. San Francisco Township [+francisco]  (localadmin, wof:404511703, imp:0.0641)
 4. San Francisco [+francisco]  (locality, wof:1125799349, imp:0.0000)
 5. San Francisco Plaza [+francisco plaza]  (locality, wof:1226462397, imp:0.0000)
```

`[+francisco]` is the completion the FST supplied for the partial token you typed. `imp` is the place's
importance score. Results are sorted by importance, highest first.

`--json` emits the same list as an array of `{ name, placetype, wofID, importance, completionTokens }`.
Build a dropdown from that shape.

The tool's error text is wrong in one place. If the FST is missing, it tells you to run
`mailwoman fst build`, but that command does not exist. The builder is `mailwoman gazetteer build fst`,
and you should not need it, because the shipped file is the same artifact.

## 2. Wire it into a search box

The code uses three functions from deep subpaths of `@mailwoman/resolver-wof-sqlite`. The package root
does not re-export them, so import them by subpath:

```js
import { readFile } from "node:fs/promises"

import { resolveWeights } from "@mailwoman/neural/weights"
import { autocomplete } from "@mailwoman/resolver-wof-sqlite/fst-autocomplete"
import { deserializeFST } from "@mailwoman/resolver-wof-sqlite/fst-serialize"

// resolveWeights finds the installed weights package, so you never hard-code a node_modules path.
const { fstPath } = await resolveWeights({ locale: "en-US" })

// fstPath is optional: it is only set when the index file is actually present in the resolved
// package, so a weights bundle without one gives you `undefined` rather than an error.
if (!fstPath) throw new Error("no FST index in the resolved weights package — autocomplete is unavailable")

// Deserialize once, at startup. The returned object IS the matcher — do not wrap it.
const fst = deserializeFST(await readFile(fstPath))

export function suggest(query) {
	return autocomplete(fst, query, { maxSuggestions: 10, dedupeByName: true }).suggestions
}
```

`deserializeFST` returns the matcher directly. Wrapping its result in `new FSTMatcher(...)` produces an
object that answers every query with zero suggestions and raises no error, which is hard to debug.

A dropdown needs `dedupeByName: true`, which is off by default. It collapses places with the
same name to the one with the highest importance:

```
dedupeByName: false
  Brooklyn (borough, imp 0.806)
  Brookline (locality, imp 0.431)
  Brookline (localadmin, imp 0.429)
  Brooklyn (neighbourhood, imp 0.364)
  Brooklyn Center (locality, imp 0.359)
dedupeByName: true
  Brooklyn (borough, imp 0.806)
  Brookline (locality, imp 0.431)
  Brooklyn Center (locality, imp 0.359)
  Brooklyn Heights (neighbourhood, imp 0.318)
  Brookleigh (neighbourhood, imp 0.297)
```

Without deduplication, five slots show three distinct places. With it, they show five. The CLI leaves
deduplication off because a person auditing the gazetteer wants to see that New York is both a city
and a county.

## 3. Measure the keystroke cost

Loading happens once and is cheap. Query cost varies, and the most expensive keystroke costs about
three orders of magnitude more than the cheapest. Measure it before you decide whether to debounce:

```bash
node autocomplete-bench.mjs
```

```
load 0.26 s   rss 265 MB
keystroke shape        n     p50 µs   p95 µs
complete token         760          8        67
partial first token    680       8370     10512
partial later token    400          6        19
```

Measured on an AMD Ryzen 9 8945HS, 16 logical cores, Node.js 26.2.0, `mailwoman` 8.7.0, over every
keystroke of four typed queries (`san francisco`, `brooklyn`, `washington dc`, `cambridge ma`), 40
samples per prefix, after a warm-up pass. The machine was shared, so treat the absolute values as one
host's figures. Your numbers will differ, but the ratios below should carry over. Resident memory
after load ranged from 241 MB to 293 MB across runs, so treat that figure as an order of magnitude.

The three keystroke shapes behave differently, and the partial first token dominates the cost:

- **Complete token**: the input is a whole word the index knows (`san`, `brook`). The walk reaches a
  state and reads its entries. 8 µs.
- **Partial later token**: a complete first word plus a fragment (`san fr`, `washington d`). The full
  walk fails, so the code walks the complete prefix and filters that state's continuation edges by
  prefix. That state has 100 edges. 6 µs.
- **Partial first token**: a fragment and nothing else (`sa`, `br`, `brookl`). The same prefix filter
  runs, but on the root state, which has 53,904 continuation edges. The code scans every one of them.
  8.4 ms.

The expensive keystrokes are therefore the first few characters of the first word. The cost drops as
soon as the user types a space.

Compare these costs with a parse instead of with a clock, because the ratio carries over to other
machines. `classifier.parse` over the same twenty addresses, on the same host in the same session,
measured p50 6,086 µs. A complete-token completion is **roughly three orders of magnitude cheaper
than one parse**, and a partial-first-token completion **costs about as much as one parse**. The
index is nearly free to query except at the root, where one query costs about as much as a model
call.

The ratio has two consequences for the front end. First, debounce input instead of querying on every
keydown, because a fast typist generates mostly root-scan keystrokes. Second, keep the query off the
main thread of a browser tab. On this host 8.4 ms is longer than a frame at 60 Hz, and a slower host
exceeds the frame budget by more.

## Verify

```bash
npx mailwoman autocomplete "brookl" --limit 3 --json
```

```

    "name": "Brooklyn",
    "placetype": "borough",
    "wofID": 421205765,
    "importance": 0.8064998388290405,
    "completionTokens": [
      "brooklyn"
    ]
  },
  {
    "name": "Brookline",
    "placetype": "locality",
    "wofID": 85950817,
    "importance": 0.4307776987552643,
    "completionTokens": [
      "brookline"
    ]
  },
  {
    "name": "Brookline",
    "placetype": "localadmin",
    "wofID": 404476429,
    "importance": 0.42851021885871887,
    "completionTokens": [
      "brookline"
    ]
  }

```

Every suggestion carries a `wofID`, the Who's On First identifier. Your code can resolve a selected
suggestion to coordinates and a hierarchy without a second text query. That is the reason to build
the dropdown on this index instead of on repeated geocodes.

## Limits

- **It completes places only.** It does not complete streets, house numbers or points of interest. A
  user typing `1275 Pennsylv` gets nothing useful from this index.
- **Each file covers one locale.** `fst-en-us.bin` ships with the en-US weights, and
  `@mailwoman/neural-weights-fr-fr` carries its own file. The library does not merge locales, so a
  search box that serves several markets loads several files and merges the result lists itself.
- **Resident memory is a few hundred megabytes after load** (241 MB to 293 MB across the runs above).
  The file is read fully into memory instead of being memory-mapped. Plan for that cost once per locale per process.
- **Ranking uses importance and ignores proximity.** There is no `near` parameter. A user in Boston typing
  `brookl` gets Brooklyn first because Brooklyn has higher importance, even though Brookline is
  closer. Re-rank on your side with the coordinates that the `wofID` resolves to.
- **The CLI's default FST path is a staging directory.** Set `$MAILWOMAN_FST_BIN` in any environment
  where you rely on the command.
