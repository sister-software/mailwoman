# Deploy with Docker

**Outcome.** You have a geocoding endpoint running in a container, with the gazetteer mounted read-only
from outside the image, and you know when to build your own image instead of pulling the published one.

The image installs the published `@mailwoman/*` packages from npm and includes the model weights. The
gazetteer is kept out of the image because it is 1.65 GB or larger and changes on a different schedule
from the code. It mounts read-only at `/data`. Parsing works without any volume.

**How this page was verified.** Docker is not installed on the machine these docs are written on, so no
container was built or run for this page. Every command below comes from the repository files that
produce the published image: the repo-root `Dockerfile`, `docker/package.json`,
`docker/docker-compose.yml` and `docker/README.md`. The registry facts in step 1 come from the GHCR API.
The [example server](/examples/mailwoman-server.mjs) in step 4 _was_ executed outside a container, in
both states the image can start in: with a gazetteer on disk, and with an empty data root, which matches
a first run without a volume. Those transcripts are real output. The `docker run` lines were not
executed.

## Prerequisites

- Docker, on `linux/amd64`. The image is amd64 only, because `onnxruntime-node` ships glibc x64
  prebuilds and arm64 has not been verified.
- Disk for a gazetteer if you want coordinates. [Your first ten minutes](../get-started/ten-minute-trial.mdx)
  covers what the `candidate` bundle is.

## 1. Run the published image

```bash
docker run --rm -p 3000:3000 ghcr.io/sister-software/mailwoman:latest

curl -s -X POST localhost:3000/v1/parse \
  -H 'content-type: application/json' \
  -d '{"address":"350 5th Ave, New York, NY 10118"}'
```

Parsing answers immediately because the weights are in the image. `/v1/geocode` and `/v1/batch` return a
`503` with `{"error":"geocoder not available"}` instead of crashing, so a first run needs no data.

**Check the tag before you depend on it.** As of 2026-08-04 the GHCR tag list is `7.3.0` and `latest`,
and both point at the same digest. `:latest` is therefore the 7.3.0 build, while npm is on the 8.x line.
The publish workflow (`.github/workflows/docker-publish.yml`) has a `release: published` trigger, but its
run history shows one manual dispatch and no release-triggered rebuild. Pin a digest and re-check the
tag instead of assuming that `:latest` tracks the current package line.

## 2. Mount the gazetteer read-only

```bash
docker run --rm -p 3000:3000 \
  -v /path/to/mailwoman-data:/data:ro \
  ghcr.io/sister-software/mailwoman:latest
```

The mount is the only configuration needed. The image sets `$MAILWOMAN_DATA_ROOT=/data`, and since
`8.7.0` the resolver falls back to `<data root>/db/wof/candidate.db`. A gazetteer at that path inside
the volume is found without an `-e` flag. Earlier versions of this page passed
`-e MAILWOMAN_CANDIDATE_DB=/data/db/wof/candidate.db`, which is now redundant.

`:ro` is correct for both resolver backends. Every runtime lookup opens SQLite read-only. The only
writable open is an explicit FTS index build, and the servers never run one.

Two mount details decide whether this works on the first try.

- **A symlinked `db/wof/candidate.db` is broken inside the container.** Host-side symlinks point at
  host paths, and discovery follows the link. A broken link looks like a missing file, so the container
  boots with geocoding off instead of reporting a broken path. Mount the real file, or set
  `-e MAILWOMAN_CANDIDATE_DB=` to its real filename inside the mount.
- **Per-state rooftop databases use WAL mode.** Their `-wal` and `-shm` sibling files must be in the
  same mount. If a sibling file is missing, the address falls back to a coarser resolution tier and the
  request still succeeds. This failure produces no error, so check for it.

If you have no gazetteer yet, the image can fetch one, so your host still needs no Node toolchain:

```bash
mkdir -p mailwoman-data
docker run --rm -v "$(pwd)/mailwoman-data:/data" \
  ghcr.io/sister-software/mailwoman:latest \
  node node_modules/mailwoman/out/cli.js data pull candidate
```

This one run needs a writable volume, so omit `:ro`. The image's `$MAILWOMAN_DATA_ROOT` is `/data`,
so the file is saved at `/data/db/wof/candidate.db`, which is where the read-only run above expects it.

## 3. Run a drop-in instead of the native API

The same image includes the three compatible servers. Override the command:

```bash
# Nominatim-compatible — /search /reverse /status, port 8080
docker run --rm -p 8080:8080 -v /path/to/data:/data:ro \
  ghcr.io/sister-software/mailwoman:latest \
  node node_modules/@mailwoman/nominatim/out/cli.js serve
```

The image's built-in health check targets `:3000/health`. If you override the command without
overriding the health check, the container stays unhealthy. `docker/docker-compose.yml` sets a health
check for each service for this reason. Copy that approach instead of removing the check.

## 4. Build your own image when the published one does not fit

Build your own image if you want pinned versions instead of `latest`, a smaller dependency set than the
full set of drop-in servers, or your own entrypoint.

[mailwoman.Dockerfile](/examples/mailwoman.Dockerfile) builds such an image. It differs from the
published Dockerfile in three ways and is otherwise the same:

```dockerfile
RUN npm init -y >/dev/null \
	&& npm install --omit=dev --no-audit --no-fund --loglevel=error \
		mailwoman@8.7.0 \
		@mailwoman/neural@8.7.0 \
		@mailwoman/neural-weights-en-us@8.7.0 \
		@mailwoman/resolver@8.7.0 \
		@mailwoman/resolver-wof-sqlite@8.7.0 \
	&& npm cache clean --force

RUN rm -rf node_modules/onnxruntime-node/bin/napi-v6/win32 \
		node_modules/onnxruntime-node/bin/napi-v6/darwin \
	&& rm -f node_modules/onnxruntime-node/bin/napi-v6/linux/x64/libonnxruntime_providers_cuda.so \
		node_modules/onnxruntime-node/bin/napi-v6/linux/x64/libonnxruntime_providers_tensorrt.so
```

The binary trim is the change most worth copying. `onnxruntime-node` installs 500 MB, most of it for
the other two platforms and for the CUDA and TensorRT execution providers. On this host, removing them
reduced `node_modules` from 746 MB to 303 MB. CPU inference is unaffected, because it loads only
`libonnxruntime.so.1` and `onnxruntime_binding.node`.
[Deploy on a serverless runtime](./deploy-serverless.mdx) has the full measurement.

The entrypoint is [mailwoman-server.mjs](/examples/mailwoman-server.mjs). It uses `node:http` without a
framework, serves three routes, and builds every expensive object once at module scope. It was run
outside a container against a real gazetteer:

```bash
PORT=13783 MAILWOMAN_DATA_ROOT=/tmp/mw-fresh-demo node mailwoman-server.mjs
curl -s "http://127.0.0.1:13783/health"
curl -s "http://127.0.0.1:13783/geocode?address=1600+Pennsylvania+Ave+NW,+Washington,+DC+20500"
```

```
listening on http://0.0.0.0:13783 (geocoder: ready)
{"ok":true,"geocoder":true}
{"lat":38.904831,"lon":-77.016216,"resolution_tier":"admin","epistemic_status":"observed","locality":"Washington"}
```

That command does not pass a candidate-database path. `/tmp/mw-fresh-demo` is a data root holding one
file, `db/wof/candidate.db`, which matches the layout of the mounted volume above. One line in the
server makes that layout sufficient, and the same line lets the server boot when the volume is missing:

```js
// Check on the gazetteer being THERE rather than on anything being configured.
const candidateDB = resolveCandidateDBPath()
```

`resolveCandidateDBPath` from `mailwoman/resolver-backend` tries an explicit path, then
`$MAILWOMAN_CANDIDATE_DB`, then `<data root>/db/wof/candidate.db`, and returns no path unless one of them
is on disk. The data-root fallback makes the `-e` flag unnecessary. The existence check keeps a run
without a volume alive. A server that trusted a configured path would try to open a missing file and
exit at import with `SQLITE_ERROR: unable to open database file`, before binding a port. The published
image's entrypoint uses the same check.

You can verify this without Docker. Point the data root at a directory without a gazetteer, which
matches the container's first-run state, and run the server under plain node:

```bash
PORT=13782 MAILWOMAN_DATA_ROOT=/tmp/mw-verify-trial node mailwoman-server.mjs
curl -s "http://127.0.0.1:13782/health"
curl -s "http://127.0.0.1:13782/geocode?address=1600+Pennsylvania+Ave+NW"
curl -s -o /dev/null -w 'parse status %{http_code}\n' "http://127.0.0.1:13782/parse?address=1600+Pennsylvania+Ave+NW,+Washington+DC"
```

```
listening on http://0.0.0.0:13782 (geocoder: off)
{"ok":true,"geocoder":false}
{"error":"no gazetteer found — mount one at <data-root>/db/wof/candidate.db"}
parse status 200
```

The process stays up, parsing returns 200, and geocoding reports 503. This output demonstrates the
claim from step 1 that parsing works without a volume.

One behavior contradicts what the fallback suggests. If `$MAILWOMAN_CANDIDATE_DB` points to a file that
does not exist, discovery does **not** fall through to the default path. It stops at the first position
that is set and reports that no gazetteer was found. A stale `-e` flag therefore turns a correctly mounted
volume into a container with geocoding off. This was measured with the same server on `8.7.0`. Setting
the variable to `/data/db/wof/candidate.db` without a volume produces the transcript above, even when
`/tmp/mw-fresh-demo/db/wof/candidate.db` exists.

To build the image, save the two example files side by side under the filenames the docs site uses:

```bash
curl -O https://mailwoman.ai/examples/mailwoman.Dockerfile
curl -O https://mailwoman.ai/examples/mailwoman-server.mjs
docker build -f mailwoman.Dockerfile -t my-mailwoman .
```

The `COPY` and `CMD` lines refer to `mailwoman-server.mjs`, so a directory holding those two downloads
builds without renaming anything.

## Verify

If you built [your own image](#4-build-your-own-image-when-the-published-one-does-not-fit) in step 4,
note that its pins were ahead of npm when this page was written. `mailwoman.Dockerfile` pins 8.7.0,
while `npm view mailwoman version` reports 8.6.0, so the build fails at `npm install` until 8.7.0 is
published. Check the published version before you build, and lower the pins to match it if needed.

The health route is the image's own health-check target, so a healthy status and a successful curl
confirm the same thing:

```bash
docker run -d --name mw -p 3000:3000 \
  -v /path/to/mailwoman-data:/data:ro \
  ghcr.io/sister-software/mailwoman:latest

docker inspect --format '{{.State.Health.Status}}' mw
curl -s localhost:3000/health
```

Allow for the start period. The built-in health check waits 60 s before it starts counting failures,
because loading the model is the slow part of startup.

## Limits

- **The image is `linux/amd64` only.** An arm64 image requires verifying the arm64 ONNX Runtime
  prebuild first. On Apple silicon the image runs slowly under emulation.
- **The image cannot use an Alpine base.** `onnxruntime-node` has no musl prebuild. `node:24-slim` is
  Debian, and the image installs `libgomp1` on top of it for threaded inference.
- **The container listens on 3000, and the published image does not let you change the port.** Remap
  it on the host side with `-p <host>:3000`.
- **One container is one CPU-bound worker.** Inference blocks the JavaScript thread, so add replicas
  for concurrency.
  [Geocode a large file at volume](./batch-geocode-at-volume.mdx) has the measurements.
- **The published image's dependencies resolve to `latest` at build time.** This is deliberate,
  because each rebuild integration-tests the current published packages. It also means two builds of
  the same Dockerfile can differ. Pin a digest for a deployment.
