# Build the planet

"Planet coverage" for a geocoder is two claims, and they come apart. One is that every place on Earth
resolves to a coordinate. A single gazetteer answers that one globally. The other is that a house
number resolves to a building. That one is answered country by country, and today it is answered for two
countries. By the end of this page you'll have built street-level coverage for one region of France twice
— once from the French government's address register, once from OpenStreetMap — geocoded the same address
against both, and seen which answers it. About twenty minutes of work plus a 2.88 GB download.

You will also know which countries you could repeat it for and which have no path at all. The
[status page](../status.mdx) answers that question in terms of parser locales. This page answers it in
terms of data.

## Prerequisites

**This page forks partway through, and it is a packaging fork rather than a preference.** Steps 1 and 2
run entirely from npm. Step 3 does not: `@mailwoman/osm` is not published to npm, so that section needs a
repository checkout. Each requirement below states which half it belongs to.

- **About 3 GB of free disk** for the path below: 2.88 GB of gazetteer and under 100 MB of everything
  else. France's whole national register adds 6.95 GB instead of the three départements; the US
  is 41.3 GB. Check the number for the country you want before you start it.
- **Steps 1–2, from npm.** The CLI, plus the French register's builder:

  ```bash
  npm install mailwoman @mailwoman/neural @mailwoman/neural-weights-en-us
  npm install @mailwoman/resolver @mailwoman/resolver-wof-sqlite @mailwoman/ban
  ```

- **Step 3, from a checkout.** `@mailwoman/osm` has no npm package, so `npm install @mailwoman/osm`
  answers `E404`. Step 3 restates this where you hit it, along with the clone and build it needs.
- **GDAL on your `PATH`**, for step 3 only — `ogr2ogr --version` should answer. Steps 1 and 2 do not
  touch it.
- **A data root**, and the willingness to keep it:

  ```bash
  export MAILWOMAN_DATA_ROOT=/tmp/mw-planet
  mkdir -p "$MAILWOMAN_DATA_ROOT"
  ```

The US tier differs from every build below because the US is the one country with
both a rooftop register and a national street-segment file. It has its own page:
[Build the US address dataset](./build-the-us-dataset.mdx).

## What "the planet" is here

One layer is global and the rest are per country. That split makes "planet" two claims instead
of one.

| Layer                  | Scope                       | Published today                                             |
| ---------------------- | --------------------------- | ----------------------------------------------------------- |
| Candidate gazetteer    | 244 countries, one database | `candidate.db`, 2.88 GB                                     |
| Rooftop address points | Per country                 | US (30.3 GB, 52 databases) and France (6.95 GB, 1 database) |
| Street interpolation   | Per country                 | US only (11.0 GB, 51 databases)                             |
| POI                    | Per country                 | US, Canada, Mexico, France in one 3.89 GB layer             |

That is the complete published set — `mailwoman data pull` offers four bundles and no others. Everything
else on this page you build yourself.

The 244 comes from the three source lists the gazetteer build unions, and you can read them off the
defaults it ships with: 12 countries served from Who's On First repositories, 85 from Overture divisions,
161 from GeoNames, and 244 distinct countries between them. Coverage at that layer means the country,
region and locality resolve — not that a street does.

## 1. Get the global gazetteer

```bash
npx mailwoman data pull candidate
```

```
▸ pull https://public.mailwoman.ai/mailwoman/gazetteer/2026-07-07a/candidate.db (~1652.9 MB) → /tmp/mw-planet/wof/candidate.db

export MAILWOMAN_CANDIDATE_DB=/tmp/mw-planet/wof/candidate.db
✓ candidate: gazetteer/2026-07-07a/candidate.db: content-length verified (1652.9 MB) → /tmp/mw-planet/wof/candidate.db
PASS (1/1 checks)
```

Four minutes for the 1.65 GB `2026-07-07a` build shown in this transcript. The current `2026-08-25b`
build is 2.88 GB, so your download will be larger. The `export` line is a leftover the pull still prints. The file landed at
`<data root>/db/wof/candidate.db` and is found there without it. Take the download unless you have a reason
not to, because the build behind it is the heaviest thing in this repository, and this page does not run
it. These are its steps. The disk each one needs follows the block:

```bash
# 1. Clone the Who's On First data repositories into <data-root>/src/wof-repos.
#    `--countries` takes ISO-2 codes and pulls each country's admin + postalcode
#    repositories; `--repos` names them individually. One of the two is required —
#    the org holds 823 non-archived repositories, several hundred GB checked out.
npx mailwoman gazetteer inspect sync --countries fr

# 2. Build the admin database. Reads the repos above, streams Overture divisions
#    from S3, folds GeoNames dumps you have already downloaded.
npx mailwoman gazetteer build admin

# 3. Derive the query-time gazetteer from it.
npx mailwoman gazetteer build candidate
```

Step 2 runs nine stages in order — `ingest-wof`, `fold-overture`, `fold-geonames`, `freeze`, `enrich`,
`VACUUM INTO`, `fts`, `verify`, `seal` — and a failed `verify` throws and leaves the artifact unsealed
instead of shipping it. Step 3 folds the GeoNames alias tail in and compresses the result into the
byte-range-friendly candidate table.

Budget disk for two databases rather than one, because step 3 reads what step 2 wrote. The sizes are from the
maintainer build host rather than from a run on this page: the admin database there, built 2026-08-02,
measures 5,275,287,552 bytes. The published candidate database is 1,652,916,224 bytes, a little
under a third of it.

Two things about the sync command before you run it. It shells out to `gh repo list`, so the GitHub CLI
has to be installed and authenticated. And size the sync against what you asked for: GitHub reports 54.3
GB for the 823 non-archived repositories, but that is their packed size, and these repositories unpack to
millions of small GeoJSON files — 145 of them measured 65 GB checked out. The command refuses an
unfiltered sync for that reason, so narrow it with `--countries` or `--repos` unless you pass `--all`.

## 2. Add a country with a national register

France publishes the Base Adresse Nationale — 26 million addresses under the Licence Ouverte 2.0. That license
asks for attribution and imposes no share-alike. That makes it the same licensing shape as the permissive
core, and it is why France is the one non-US country with a published rooftop database.

Take three départements rather than the whole country, so the step finishes while you watch:

```bash
mkdir -p "$MAILWOMAN_DATA_ROOT/db/ban/sources"
for d in 48 2A 05; do
  curl -sL -o "$MAILWOMAN_DATA_ROOT/db/ban/sources/adresses-$d.csv.gz" \
    "https://adresse.data.gouv.fr/data/ban/adresses/latest/csv/adresses-$d.csv.gz"
done
```

7.3 MB of gzipped CSV. Then build:

```bash
node node_modules/@mailwoman/ban/out/scripts/build/address-point-database.js \
  --csv-dir "$MAILWOMAN_DATA_ROOT/db/ban/sources" --depts 48,2A,05 \
  --release 2026-08-03 --out "$MAILWOMAN_DATA_ROOT/db/ban/address-points-fr-sample.db"
```

```

[ban]   dept 05: 81,258 cumulative
[ban]   dept 2A: 138,573 cumulative
[ban]   dept 48: 200,406 cumulative
[ban] indexing…
[ban] DONE /tmp/mw-planet/ban/address-points-fr-sample.db
      départements                     : 3
      total source rows                : 200,406
      written points                   : 200,406
      skipped (no street/number)       : 0
```

6.84 s, 200,406 points, and **zero rows skipped**: every row in these three départements has both a
street and a number. A government register provides that, and step 3 does not have it. The build
streams the CSV instead of loading it, so the national set is the same command with a longer file list —
26 million rows, and 6.95 GB in the published database.

Two things about that invocation. It is a script inside the installed package rather than a `mailwoman`
subcommand. There is no `mailwoman ban` group, the fetch is a `curl` against a documented URL pattern,
and the build is the script above. And the path is a `node_modules` path because `@mailwoman/ban` is on
npm. If you are working from a checkout instead, the same file is at
`packages/ban/out/tools/build/address-point-database.js` after `yarn compile`.

## 3. Build the same ground from OpenStreetMap

For a country with no open register, OpenStreetMap is the fallback.

**The license.** OpenStreetMap data is published under the Open Database License 1.0 (ODbL), and the
database you build here is an OpenStreetMap Derivative Database. Mailwoman publishes no OpenStreetMap
rooftop database to npm, the bucket or the demo. The builder, `@mailwoman/osm`, is on npm as code with no
OpenStreetMap data in it, and it builds the database on your machine. The ODbL applies to the file you
build: credit OpenStreetMap where its data is shown, and when you publicly use the database, or a
database derived from it, offer that database under ODbL to its recipients. The
[OpenStreetMap attribution page](../../resources/osm/attribution.mdx) states the terms in full.

Five countries have a registered street-normalization locale for this path: `de`, `fr`, `gb`, `nl` and
`nz`. A build that adds another means registering the country and writing its branch in the street
normalizer in the same commit. That is why the list grows one considered country at a time.

Install the builder and download an extract. The fetch tool dates the file name from the server's
`Last-Modified` header and writes a receipt beside it with the URL and the SHA-256, which the builder
records in the database's manifest. The Corsica extract is 34 MB, small enough to finish in seconds:

```bash
npm install @mailwoman/osm
OSM="$(npm root)/@mailwoman/osm/out/tools"

node "$OSM/fetch/extract.js" --region europe/france/corse

node "$OSM/build-rooftop-database.js" \
  --country fr --slug corse --release 261017 \
  --created-at 2026-10-17T00:00:00.000Z --build-sha "@mailwoman/osm@10.6.0" \
  --pbf "$MAILWOMAN_DATA_ROOT/db/osm/geofabrik/corse-261017.osm.pbf"
```

`$MAILWOMAN_DATA_ROOT`. The six license lines the builder prints before and after the build are shown once:

## 4. See which one answers

You now hold two databases over overlapping ground. Ask both for the same address — `--address-points-db`
points the geocoder at an explicit file instead of the per-state US convention:

```bash
npx mailwoman geocode "12 Cours Napoléon, 20000 Ajaccio" --default-country FR \
  --address-points-db "$MAILWOMAN_DATA_ROOT/db/ban/address-points-fr-sample.db" --format text
```

```
input:            12 Cours Napoléon, 20000 Ajaccio
resolution_tier:  address_point
coordinate:       41.919826, 8.737100
uncertainty_m:    1
locality:         Ajaccio
postcode:         20000
hierarchy:
  locality             Ajaccio [wof:404376035] (41.9346, 8.7005)
```

```bash
npx mailwoman geocode "12 Cours Napoléon, 20000 Ajaccio" --default-country FR \
  --address-points-db "$MAILWOMAN_DATA_ROOT/db/osm/address-points-fr-corse.db" --format text
```

```
input:            12 Cours Napoléon, 20000 Ajaccio
resolution_tier:  admin
coordinate:       41.934571, 8.700510
locality:         Ajaccio
postcode:         20000
```

Rooftop from the register, city centroid from OpenStreetMap, on the same street in the same town. Point
density explains the difference: the register holds 57,315 points for Corse-du-Sud by itself against
14,714 for all of Corsica in OSM, after recovery. This is why the resolver consults a national register
ahead of the OSM tier when both are present, and why the ordering is not a preference you tune.

It does not run one way every time. Swap the address for `20 Boulevard Tino Rossi, 20000 Ajaccio`, in the
same town, and the two swap places:

```
# register:  resolution_tier: admin
# OSM:       resolution_tier: address_point   coordinate: 41.908027, 8.679581
```

The register files that quay as `Quai Port Plaisance Tino Rossi`, so the query misses it and falls to the
city. Neither source contains the other. If you install both, install them as tiers with the register first
rather than merging them into one file.

## 5. What has no path today

Absence is a claim, so this section states the absences directly.

**Great Britain has no open address source in this stack.** Overture's addresses theme has no GB rows
at all. You can confirm that in about two minutes. Pass a release that is currently in Overture's bucket
rather than the CLI's built-in default, because the default has aged out of it. The
[release pin section](./build-the-us-dataset.mdx#the-overture-release-pin-before-it-bites-you) on the US
page has the one-line command that lists what is live. `2026-06-17.0` was live on 2026-08-03:

```bash
npx mailwoman gazetteer overture-ingest --countries GB --release 2026-06-17.0
```

```
[ingest] GB -> /tmp/mw-planet/overture/2026-06-17.0/addresses-gb.parquet (138s)
[probe] GB: no rows found — check the country code or release
✓ overture ingest: /tmp/mw-planet/overture/2026-06-17.0
  release 2026-06-17.0 · GB · 0 probed
```

The command succeeds and writes a 532-byte parquet: a valid file holding the schema and no rows. That is
the shape of a real absence, and it is a different fact from a failed download. Royal Mail's Postcode
Address File is not open, so the GB street tier is a licensing gap rather than a build anyone can run.
Postcode-level resolution for GB still works, out of the gazetteer.

**Korea has no adopted open data path**. The cause is a data-licensing constraint rather than an
engineering one. **Australia's G-NAF** is in the repository, but as a training-corpus adapter
(`mailwoman gnaf assemble` emits labeled JSONL) rather than a rooftop-database builder — there is no
`address-points-au` to build today. **New Hampshire** is a hole inside the country that does have a tier:
its published rooftop database is 20,480 bytes and holds zero rows, because the state appears in neither
Overture nor the OpenAddresses set the build falls back to.

Two closing notes on the word "coverage". A missing row is not a measured zero, and newer mailwoman
artifacts make that distinction structural: the spatial-layer interface the POI layer follows stores
per-cell survey completeness beside the data, so a consumer can tell "surveyed and empty" from "never
surveyed". The address databases on this page predate it and have no such table. That is why the New
Hampshire case above has to be stated in prose. And a locale claim on the [status page](../status.mdx) is
a claim about parsing rather than about street-level coordinates: France and the US are tier 1 for both, and every
other claimed locale parses against a coordinate panel while resolving at the admin tier.

## What you have now

Two rooftop databases over Corsica built from different sources under different licenses, a global gazetteer
under both of them, and a row count for what each source holds instead of an assumption about it.
The same two commands, given a country code the normalizer knows and an extract or a register dump,
produce the next one.
