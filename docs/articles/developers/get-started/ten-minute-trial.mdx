# Your first ten minutes

Mailwoman has two halves, and they become available at different times. Parsing works as soon as
`npm install` finishes, because the model ships inside a package. Geocoding needs reference data that
is too large to ship on npm, so it requires a separate download. By the end of this page you will
have run both checks, pulled that reference data, and geocoded a US address and a French one. The
steps take about ten minutes, plus the time for the one-time gazetteer download.

## Prerequisites

- Node.js 24.18.0 or later, and roughly 750 MB of free disk for the install.
  [Install and first parse](./install-and-first-parse.mdx#prerequisites) explains both numbers.
- About 1.65 GB more disk and a few minutes of download time when you reach
  [Geocode it](#5-geocode-it) below. That space holds the gazetteer database, which you pull once and
  keep for every later geocode.
- `mailwoman data pull`, the command the gazetteer step runs, ships in `8.7.0`. Check
  `npm view mailwoman version` first. If it still prints `8.6.0`, steps 1 through 4 work, and step 5
  needs the next npm release.

## 1. Install

```bash
npm install mailwoman @mailwoman/neural @mailwoman/neural-weights-en-us
```

## 2. Ask it what it has

Run `doctor` before you debug anything else. It runs seven checks, and for each missing piece it
prints the command that installs it. Point it at a data root. The rest of this page reuses the same
data root.

```bash
export MAILWOMAN_DATA_ROOT=/tmp/mw-trial/mailwoman-data
npx mailwoman doctor
```

On a fresh install with no address data on disk, that reads:

```
mailwoman doctor

✓ Model weights (en-us): package:@mailwoman/neural-weights-en-us · model.onnx 39.4 MB, tokenizer.model 1.6 MB
✓ Node runtime: node v26.2.0 (engines: >=24.18.0)
✓ ONNX runtime: onnxruntime-node loadable
✗ Data root: /tmp/mw-trial/mailwoman-data ($MAILWOMAN_DATA_ROOT) does not exist (optional)
    fix: mkdir -p /tmp/mw-trial/mailwoman-data   (or set $MAILWOMAN_DATA_ROOT to an existing dir)
✗ Admin gazetteer: no candidate.db or WOF extract found (probed 5 paths) (optional)
    fix: mailwoman data pull candidate
✗ POI layer: /tmp/mw-trial/mailwoman-data/poi/poi.db not found (optional)
    fix: mailwoman gazetteer build poi   (or: mailwoman data pull poi)
✗ Locale overlay (fr-fr): @mailwoman/neural-weights-fr-fr not installed (optional — only needed for fr-fr parsing) (optional)
    fix: npm install @mailwoman/neural-weights-fr-fr

PASS — core checks ok (weights + runtime); parse is ready
```

The output shows four failed checks, and the command still exits `0`. This is intended. The exit code
reflects only the two core checks, weights and runtime. Everything marked `(optional)` is a data
layer that parsing does not need, so `doctor` reports a missing layer and its fix instead of failing.
The paths in your own output use your `$MAILWOMAN_DATA_ROOT`.

## 3. Parse something

Parsing is ready now. Follow [Install and first parse](./install-and-first-parse.mdx) for a
ten-line script that turns `apt 4b 350 5th ave new york ny 10118` into a labeled tree, or check it
from the shell:

```bash
npx mailwoman parse "350 5th Ave, New York, NY 10118"
```

```json
{
	"region": "NY",
	"locality": "New York",
	"street": "5th",
	"house_number": "350",
	"street_suffix": "Ave",
	"postcode": "10118"
}
```

The output has components and no coordinates, because the parser has its model but not its
gazetteer.

## 4. Know which half you have

**Parsing works out of the box.** It takes free text and returns tagged components: house number,
street, unit, locality, region, postcode, and the rest. The model file ships inside
`@mailwoman/neural-weights-en-us`, so there is nothing more to fetch or configure. French support
needs one more package (`@mailwoman/neural-weights-fr-fr`) and no other change.

**Geocoding needs the resolver database.** Turning `New York` into a latitude and longitude requires a
lookup in the gazetteer, which is a file you download once and keep. At the `2026-07-07a` build, the
candidate gazetteer `candidate.db` is 1.65 GB. Your `doctor` output prints the exact one-line command
that fetches it. The CLI generates that command from the build it knows about, so prefer it over a
command copied from a web page. Run it next.

Point-of-interest search ("coffee near Honolulu") is a third layer with its own database. It is also
optional, and `doctor` also reports it.

## 5. Geocode it

Run the fix line that `doctor` printed above. Use the same shell so that `$MAILWOMAN_DATA_ROOT` is
still set:

```bash
npx mailwoman data pull candidate
```

```
▸ pull https://public.mailwoman.ai/mailwoman/gazetteer/2026-07-07a/candidate.db (~1652.9 MB) → /tmp/mw-trial/mailwoman-data/wof/candidate.db
[DEBUG] (mailwoman data): HEAD: https://public.mailwoman.ai/mailwoman/gazetteer/2026-07-07a/candidate.db
[DEBUG] (mailwoman data): 200 (uncached) HEAD: https://public.mailwoman.ai/mailwoman/gazetteer/2026-07-07a/candidate.db

export MAILWOMAN_CANDIDATE_DB=/tmp/mw-trial/mailwoman-data/wof/candidate.db
✓ candidate: gazetteer/2026-07-07a/candidate.db: content-length verified (1652.9 MB) → /tmp/mw-trial/mailwoman-data/wof/candidate.db
PASS (1/1 checks)
```

The download took about four minutes on the connection used for this page. The two `[DEBUG]` lines
show the download client checking the remote file's size before it starts. They do not indicate a
problem.

Ignore the `export` line. The file is saved at `<data-root>/db/wof/candidate.db`, which is the
default path every entry point checks, so the download completes the setup. The CLI still prints the
line from a time when the variable was required. Setting it changes nothing here.
[Runtime flags](../reference/runtime-flags.mdx#environment-variables) describes what the variable is
still used for: pointing at a copy stored elsewhere, or `none` to pin the older backend.

Geocode a US address:

download (`mailwoman data pull us` or `mailwoman data pull fr`), which this page does not cover.

The result has the right country and the right city, and no flag was needed. This behavior is recent.
The file you downloaded became the default backend in `8.7.0`. Before that release, it was opt-in
behind the variable you were told to ignore above.

You can still run the older backend. `--candidate-db none` pins it. It needs a full admin database,
which is a separate, locally built file that `data pull` does not publish. You can read the
comparison below, but you cannot reproduce it with the downloads on this page. Same input, same
machine:

```json
{
	"lat": 33.668553,
	"lon": -95.54435,
	"countryCode": "US",
	"placeID": "wof:101725293"
}
```

The older backend returns Paris, Texas. The ranking does not cause this. The **country filter**
does. `--locale` defaults to `en-US`, `en-US` implies `--default-country US`, and the older backend
applies that filter while the candidate backend does not. Testing each backend with and without the
filter separates the two effects (measured 2026-08-04, with this gazetteer and this model):

| backend             | country filter US                      | no country filter |
| ------------------- | -------------------------------------- | ----------------- |
| candidate.db        | `Paris Township`, TX (32.960, −96.838) | **Paris, France** |
| full admin (`none`) | `Paris`, TX (33.669, −95.544)          | **Paris, France** |

Both backends return Paris, France without the US filter, and both return a Texas result with it.
This page therefore makes a narrow claim. `candidate.db` is the default, and the default does not
apply a country filter, so the French address geocoded correctly without any configuration. To
compare the two backends yourself, use `--country-scope locale|none` (on `parse` and `geocode`) to
set the filter the same way for both.

## What you have now

You have a parser and a geocoder, both reading from your own disk. `mailwoman parse` (or
`createRuntimePipeline`) returns tagged components. `mailwoman geocode` returns a coordinate once
`candidate.db` is on disk at `<data-root>/db/wof/candidate.db`. After any change to your install,
`mailwoman doctor` shows again which halves are available.
