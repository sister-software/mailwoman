# What Mailwoman is

## The question

You have addresses from a signup form, a CRM export, or a spreadsheet that a field crew filled in on
a phone. You need them split into fields, and you need coordinates. Most tools that do this require
an account first. This page explains what Mailwoman is and where it runs.

## The analog

A sorting clerk reading an envelope does two jobs in order. First the clerk reads it and identifies
the house number, the town and the postcode. Then the clerk looks up where that town is.

Mailwoman keeps those two jobs separate. `npm install mailwoman` gives you the reading job: a
function that takes `apt 4b 350 5th ave new york ny 10118` and returns a tree of tagged components,
each with a confidence score. The lookup job is a second pass that walks that tree and attaches
coordinates from a gazetteer, which is a database of places and their locations.

The reading pass runs a sequence labeler. This is a small model that assigns one tag to each piece
of the input, the way a spam filter assigns one label to a message. This page needs no other model
vocabulary.

## Where it runs

Mailwoman runs inside your process and requires Node 24.18.0 or later. The English model is a
39.4 MB file distributed as the npm package `@mailwoman/neural-weights-en-us`, and loading it is a
file read. A browser build runs the same stages through `@mailwoman/neural/web-loader`.

This design has three consequences:

- **There is no service to go down.** Parsing has no upstream dependency. If your process is
  running, the parser is running. A network outage cannot affect a parse, because a parse makes no
  network connection to us.
- **There is no meter.** You are not billed per address. Re-parsing the same string a thousand times
  because a user kept editing a form field costs a thousand function calls and no billed request.
- **The addresses stay where they are.** A parse call opens no network socket, so customer addresses
  never reach our infrastructure, and your compliance review does not need to cover that transfer.
  [Security and compliance](../../about/security-and-compliance.mdx) gives the details, including
  the one opt-in code path that does make a request.

## What it is not

**It is not a hosted service you sign up for.** It has no API key, dashboard or quota. If you want
an HTTP endpoint, you run one yourself. `@mailwoman/api` and the Nominatim-, Photon- and
libpostal-compatible drop-ins are servers you deploy on your own hardware against your own data.

**It is not a substitute for a postal authority's address file.** Royal Mail's PAF, Ordnance
Survey's AddressBase and the USPS address products answer a question that Mailwoman does not: does
this delivery point exist, and will mail arrive there? Those products are licensed, authoritative
registers of real letterboxes. Mailwoman reads the string you give it and matches what it can
against open data. It can tell you that a string looks like `350 5th Ave, New York, NY 10118` and
where that address is. It cannot tell you that somebody lives there.

## What it costs

You store the data. The model file sits on your disk, and geocoding needs a gazetteer database that
you download once and keep. Running without a server means you manage those files instead of us.

Coverage matches what open data covers, and it varies by country.
[What ships today](../status.mdx) gives the per-locale details, including the locales with weak
coverage.

The two jobs also become available separately. Parsing works as soon as `npm install` finishes.
Geocoding works only after the gazetteer is on disk.
