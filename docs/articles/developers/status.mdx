# What ships today

:::info[Verified as of release 10.0.0, model 9.1.0]

Every figure on this page was re-measured on 2026-09-14 against the published artifacts. The release
process refuses to publish while this box names a model older than the one the release ships.

:::

## Scope

This page records what the current release contains: the version, the packages a consumer installs,
the model artifacts and their measured sizes, the locales that carry a claim, and the limits. It
does not record per-tag accuracy. Those numbers live in the eval ledger
([`evals/scores-by-version.json`](https://github.com/sister-software/mailwoman/blob/main/evals/scores-by-version.json))
and in the dated eval reports beside it.

Every artifact size below was measured on 2026-09-14 against the files this release publishes.

## Version

Every published workspace releases in lockstep on one version number, the model bundles included. A
weights package version therefore tracks the release, not the model's own lineage.

| Fact                | Value                                                                 |
| ------------------- | --------------------------------------------------------------------- |
| Release             | `10.0.0`                                                              |
| Model version       | `9.1.0` — the Latin base, unchanged since release `9.1.0`             |
| Node floor          | `>=24.18.0` (the `engines` field on the `mailwoman` entry package)    |
| Module format       | ESM only                                                              |
| License             | `AGPL-3.0-only OR LicenseRef-Commercial`                              |
| What npm serves now | `npm view mailwoman version`. Check it rather than trusting this page |

## Model artifacts

`@mailwoman/neural-weights-en-us` publishes 15 files totalling 75,120,759 bytes (75.1 MB). That
figure is the published tarball, not the working tree, and it is reproducible:

```bash
npm view @mailwoman/neural-weights-en-us dist.unpackedSize dist.fileCount
```

The seven files that account for the size:

| File                               | Bytes      | Size    | What it is                           |
| ---------------------------------- | ---------- | ------- | ------------------------------------ |
| `model.onnx`                       | 39,419,629 | 39.4 MB | The int8-quantized model, opset 17   |
| `fst-en-us.bin`                    | 21,757,160 | 21.8 MB | The gazetteer prior index            |
| `locality-surface-lexicon-v7.json` | 8,633,963  | 8.6 MB  | Locality surface forms               |
| `postcode-us.bin`                  | 1,904,322  | 1.9 MB  | The US postcode anchor table         |
| `tokenizer.model`                  | 1,632,289  | 1.6 MB  | The SentencePiece model              |
| `pair-index-us.bin`                | 1,341,264  | 1.3 MB  | The locality/region pair index       |
| `fst-street-morphology.bin`        | 327,516    | 0.3 MB  | The street-morphology emission prior |

The remaining eight files — the model card, the four soft-feed lexicons, two calibration tables and
the manifest — total 104,616 bytes between them.

Structure of the model itself, from its model card:

| Property                | Value                                   |
| ----------------------- | --------------------------------------- |
| Encoder                 | 6 layers, 384 hidden, 6 attention heads |
| Maximum sequence length | 128 tokens                              |
| Tokenizer vocabulary    | 73,143 SentencePiece pieces             |
| Output labels           | 33 BIO labels over 16 component tags    |
| Quantization            | int8 dynamic, quantized from fp32       |

The gazetteer is a separate download and is not part of any npm package. The published build is
`gazetteer/2026-08-25b/candidate.db` at 2,880,921,600 bytes (2.88 GB), covering 244 countries. Run
`mailwoman doctor` for the current URL rather than copying one from a page.

## Locales

The tiers below are reproduced from
[`docs/engineering/SCOPE.mdx`](https://github.com/sister-software/mailwoman/blob/main/docs/engineering/SCOPE.mdx),
which is where they are maintained. A locale is claimed only where a coordinate-graded evaluation
exists for it, so trained exposure and a claim are different things.

| Tier | Locales                                                | What the tier means                                                                |
| ---- | ------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| 1    | US, FR                                                 | First-class. Per-tag floors the release process enforces, plus real-world slices   |
| 2    | IT, PT, PL, AT, CZ, DE, AU, BE, ES, NL, CH, HR, DK, FI | Trained, with a per-locale coordinate panel behind the claim                       |
| 3    | NO, SE                                                 | Trained exposure, thinly measured. Claims beyond the panel are unverified          |
| 4    | CZ, PL, SK, SI                                         | Covered by the diacritic tokenizer splice shipped in `5.1.0`                       |
| 5    | JP, KR, CN                                             | The character path, published in `9.3.0`. See the note below for what each carries |

Tier 5 is one 49-label character-path head serving all three, and the three do not carry equal
claims. Japanese has a 20,000-row coordinate board. Korean has a 20,000-row board over 27 held-out
시군구 and resolves to the 시군구 through the candidate table's Korean names; nothing finer than the
county exists for Korean today. Chinese has 126 labeled rows in total, which is a number rather than
a claim.

Queued behind an external constraint rather than an engineering one: GB, IE, SE, HU and RO corpora
via OpenStreetMap, which is waiting on the share-alike review.

## Limits

Cross-locale input is part of the current parser and resolver work, with a precise boundary. The
parser preserves and labels the text it receives; the gazetteer can connect multilingual aliases and
established transliterations to one place identity. Mailwoman does not currently translate arbitrary
address strings. See [Cross-locale queries](./knowledge-base/localization/cross-locale-queries.mdx) for
the behavior of English-written Japanese addresses, kana-written US addresses, and unsupported
scripts.

Each row states the limit and the next step. Where a limit is a default rather than an absence, the
next step turns it on.

| Limit                                                                                      | Next step                                                                                                          |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| Geocoding requires the gazetteer database. Parsing does not.                               | Download it once: `mailwoman data pull candidate`. `mailwoman doctor` prints that command and the variable to set. |
| Confidence scores are uncalibrated by default. The shipped model is under-confident.       | Wire `createCalibrator` from `@mailwoman/core/decoder` with the bundled `calibration.json`.                        |
| The resolver stage has no default. `createRuntimePipeline` parses only until you pass one. | Pass `resolver:` a `createWOFResolver` instance backed by `@mailwoman/resolver-wof-sqlite`.                        |
| One classifier instance loads one locale.                                                  | Construct one `NeuralAddressClassifier` per locale you serve.                                                      |
| Korean resolves no finer than the 시군구. No sub-county register has been adopted.         | None today. The constraint is data coverage, not engineering.                                                      |
| The locale hint reports a single BCP-47 tag, so Han-script input is labeled `ja-JP`.       | Read the resolved country rather than the hint's locale when the input is Han-script.                              |
| Cross-language resolution requires a recorded gazetteer alias or transliteration.          | Supply the expected locale and keep unresolved results visible; arbitrary translation is not performed.            |

## Rationale

Lockstep versioning means one number answers "which release do I have" across every package at once,
including the weights. The cost is that the release number says nothing about the model: most
releases are code-only, so `10.0.0`, `9.4.0` and `9.2.0` all carry the same model `9.1.0`. The model
card inside each weights package carries the lineage.

The gazetteer stays outside npm because it is 2.88 GB. A registry tarball of that size would be paid
for by every consumer who wanted only the parser.
