This is a follow-up to [yesterday's post about the v0.5.0 C-train failures](/research/v0-5-0-c-train-bisect). Yesterday we ran four attempts and ruled out three suspects. Today we ran a fifth and ruled out a fourth, which leaves one hypothesis. The method we used carries over directly from software debugging, so this post is written for engineers who haven't run a training campaign before.

If you've ever bisected a software regression, you already understand the method. That includes running `git bisect`, narrowing a test failure by reverting changes one at a time, or comparing a known-good build with a known-broken build to find which change caused the breakage. The rest is vocabulary.

## The setup, in software terms

Last week we shipped a "v0.4.0" model. A model contains millions of internal numbers (weights). We tune them for hours by feeding the model labeled examples and adjusting the weights according to how wrong each guess is. The output of that tuning is a single file (~50MB) that we copy to production.

v0.4.0 worked. We then changed several things in parallel to ship v0.5.0:

1. New **tokenizer**. The tokenizer splits input strings into model-readable units. We built a bigger one because the old one fell back to raw bytes on non-Latin scripts.
2. New **corpus**. We added synthetic adversarial examples and transliteration pairs to the training data.
3. New **input layer**. "Phrase priors" are pre-computed hints about where each meaningful span starts and ends, fed into the model alongside the raw tokens.
4. Bigger **hidden size**. The hidden size is the internal width of the model, and a bigger one adds capacity in principle.
5. New code around the model: top-k inference, joint decoding, and a new reconcile stage.

Item 5 is new code outside training, so it is not a suspect. Items 1-4 are the suspects, and any combination of them could be what breaks training. This is a multi-variable regression.

## The failure mode

Training is a long loop of ~50,000 iterations, during which we watch a number called "loss" go down. The loss went down smoothly for the first ~1000 iterations and then climbed catastrophically. By the time we noticed, the model had unlearned everything useful and was producing garbage.

In software terms, imagine a process that runs fine for the first hour and then enters cascading state corruption that slowly destroys its in-memory data, even though no individual operation looks wrong. No operation segfaults or throws an exception. The numbers slowly drift from useful to useless.

This pattern has a recognizable shape:

```
descent through warmup  →  brief plateau at a low loss  →  sharp climb back to nonsense
```

Every run so far has shown this shape at slightly different points. The depth of the plateau and the step where the climb starts both vary, but every run climbs.

## Bisecting by elimination

We have made five attempts, each varying one knob from the previous one:

| Run                   | What changed                            | Best loss before climb | When the climb started |
| --------------------- | --------------------------------------- | ---------------------- | ---------------------- |
| v1                    | (all v0.5.0 changes ON)                 | 0.61                   | step 700               |
| v2                    | lowered LR (1.5e-4 → 1e-4)              | 0.51                   | step 1000              |
| v3                    | turned off two loss-side knobs (§1, §3) | 0.41                   | step 800               |
| **bisect-h256**       | reverted hidden-size bump               | 0.31                   | step 1050              |
| **bisect-phrase-off** | reverted phrase-prior input layer       | 0.38                   | step 1050              |

The bisect-phrase-off run is today's new run. The previous post covered v1 through bisect-h256.

In every bisect attempt, **the model learns something useful for several hundred iterations**: the loss decreases and validation accuracy climbs. **Then the loss climbs sharply.** The model can fit the data, so it isn't fundamentally broken, but it cannot _stay_ fit. Something pushes it off that fit.

Each bisect tested a different hypothesis about the cause:

- **v2 tested whether the learning rate was too high.** It was not. Lowering LR delayed the climb but didn't stop it.
- **v3 tested whether the new loss-side weighting knobs were destabilising training.** They were not. v0.4.0's known-stable loss settings still produced the climb.
- **bisect-h256 tested whether the bigger model was the problem.** It was not. We reverted the hidden size to v0.4.0's value and got the cleanest training so far, including the best validation macro-F1 we've ever measured, and the climb still happened.
- **bisect-phrase-off (today) tested whether the phrase-prior input layer was the problem.** It was not. We turned off the phrase-prior feature concatenation entirely, and the climb still appears in the same shape at almost the same step.

Five attempts produced the same loss curve and eliminated four hypotheses. **Exactly one architectural change from the known-stable v0.4.0 setup is still in play**: the tokenizer + corpus pair.

## What's left, and why it's interesting

The two remaining variables are linked:

- **A1 tokenizer**: a new vocabulary of 48,000 sub-pieces that the model uses to split input strings into atomic units. It was trained on the v0.4.0 corpus, including the new transliteration data. As a result, it covers CJK, Cyrillic, Hangul, Han, and Armenian script. The old tokenizer gave up on non-Latin scripts and emitted raw bytes.
- **corpus-v0.4.0**: the old corpus plus ~78,000 new rows generated by an LLM, consisting of adversarial "trick" addresses and transliteration pairs in non-Latin scripts.

These two are bundled, because A1's vocabulary was constructed _from_ v0.4.0's content. The model sees new tokens (vocab change) and new data (corpus change) for the first time together, and we can't fully separate them without retraining one or the other.

One cheap experiment gets us most of the way there. We hold the tokenizer constant (keep A1) and swap the corpus back to v0.3.0, the old data without the transliteration mass. That tests whether the transliteration data is the destabiliser while keeping the tokenizer improvement.

This is the next bisect. If it trains without diverging, we'll know that the synthetic data, specifically B2's transliteration mass, is breaking training. That answer would lead to three follow-ups:

- **Downweight transliteration in the training mix.** The corpus has per-source weights, so we can turn down the new data. This loses some of the new data's value but is cheap.
- **Investigate why the transliteration data destabilises training.** Our working hypothesis is that the LLM-generated rows have systematically different gradient signatures from human-validated address data. They might be _too_ structured, or have repetitive patterns that the model overfits to before diverging. Our `corpus-audit` tooling can quantify this.
- **Ship A1 (the tokenizer improvement) with the proven-stable corpus-v0.3.0 model** for v0.5.0, and defer transliteration training to v0.5.1.

If the corpus-revert bisect also fails, the A1 tokenizer itself is the remaining destabiliser. That would be a stranger answer, because tokenizer training is mostly independent of classifier training, but it is possible. New vocabulary means a fresh embedding table the model has never seen; unusual sub-piece frequencies could in principle produce unusual gradient norms.

## What we'd tell a software engineer reading this

Three things about ML debugging that don't translate directly from regular software:

1. **There's no stack trace.** Loss is the only signal you get, and you can't step into the model to see what's wrong. You change one knob, run the experiment for hours, and interpret the resulting curve. This makes ML feel unscientific, but if you change one knob at a time, record each result, and save the artifacts, the workflow is the same bisect-by-elimination as `git bisect`.
2. **Iterations are expensive.** Each check for the bug costs hours of GPU time. You can't make 100 tries and look at the distribution. You make 5-10 tries, and you design each one carefully to maximise what it tells you. That is why ML researchers put so much effort into ablation studies. They serve the purpose of unit tests, but each one costs $5 of compute.
3. **The "obvious" suspect is frequently wrong.** When v0.5.0 started failing, we assumed the bigger model was at fault, since making it bigger added parameters that could break. The h256 bisect ruled that out. We then assumed it was the new input layer, and the phrase-off bisect ruled that out too. The remaining suspect, the tokenizer + corpus pair, was our least-favourite hypothesis going in, because the tokenizer produced the largest measured improvement in v0.5.0. The data does not care about those preferences. You keep bisecting by elimination until you find the answer the data supports.

## Where we go next

The corpus-revert bisect is the next experiment. It's a 25-30 hour training run on the lab's GPU, so we'll start it tonight and check on it tomorrow morning. If it trains without diverging, v0.5.0 is shippable, with a v0.5.1 follow-up to investigate why the transliteration data destabilises training. If it doesn't, we'll have strong evidence that the tokenizer change itself interacts badly with classifier training, which would be a more interesting problem to write about.

Either way, few steps remain. After five experiments, one hypothesis is left, and the next experiment tests it. ML debugging is frustrating because each iteration takes so long, and it is satisfying because systematic elimination eventually finds the cause.
