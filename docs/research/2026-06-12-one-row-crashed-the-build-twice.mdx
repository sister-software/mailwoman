Our training corpus is built from source. The build combines hundreds of millions of address
rows from eleven raw data sources and writes them to disk over a long unattended night. Last
night's build ran for two and a half hours and then failed on a single row. This post answers
three questions. How does one row out of nearly 700 million stop hours of compute? Why, after
we fixed the first failure, did the build crash again on the _exact same row_? What should
change once you know that a correct assertion can still be an unsafe one?

## দক্ষিণ কোরিয়া

The build failed with a clear error that identified the row: a Who's On First record for the
`name:ben` variant of South Korea, `দক্ষিণ কোরিয়া`, which is the country's name written in
Bengali. We carry localized name variants on purpose. "Saint Petersburg", "St. Petersburg", and
the Bengali rendering of South Korea are all rows we _want_, because a parser that knows only
the Latin spelling of a place fails on most of the world's scripts.

The row failed an assertion we had written deliberately. During alignment, the code checks that
a row's raw text is already in Unicode's NFC normalization form and throws an error if it is
not. This Bengali string was not in NFC. The assertion threw, and a two-and-a-half-hour build
stopped because one record out of nearly 700 million arrived in the wrong normalization form.

## The assertion was right

The assertion is correct, and we would write it again.

Our labels are character offsets. When the corpus says the postcode is at `[10, 15)`, it means
code units 10 through 15 of the raw string. Those numbers are unambiguous only if every stage
agrees on how the string is encoded, and Unicode allows the same visible text to be encoded more
than one way. The letter `é` can be one code unit (NFC, precomposed) or two (NFD, a bare `e`
followed by a combining acute accent). A span of `[10, 15)` lands in a different place depending
on which encoding the string uses. If the offsets are computed over one form and the raw text is
stored in another, every label is shifted by the number of combining marks before it. No stage
reports an error, and the model trains on misaligned labels.

The assertion therefore checks a real requirement: character-offset labels are meaningful only
under a single normalization form. The bug is in how it fails. An assertion that stops the entire
build on the first row that violates it treats a correctness check as a reason to discard all
the work done so far.

The fix for the first crash replaced the assertion with normalization. Where alignment used to
throw, it now normalizes the raw text _and_ every component value to NFC, computes the spans over
the normalized text, and stores the normalized text on the row. Offsets and text still share one
form, and the multi-locale row stays in the corpus. DeepSeek, which we use as an independent
reviewer for decisions like this, agreed that the offsets and the stored text still used one normalization form after the
change. We shipped it
and re-ran.

## Then it crashed again, on the same character

The build passed the NFC check, ran a few seconds, and failed on the same row, South Korea in
Bengali, with a different error:

```
span out of bounds: country@[0,14) over raw of length 13
```

The `country` component here _is_ the whole raw string, the same 13 code units. The span should
have been `[0, 13)`. Our span-locating code returned `[0, 14)`, one code unit past the end of the
string that should contain it. The overrun was exactly one code unit, on a string made almost
entirely of combining marks.

Combining marks are a common source of bugs in character-offset code. A grapheme like the Bengali
`ক্ষ` is several code units. The boundary logic that keeps a short component from matching inside
a longer component's word behaves correctly on Latin script. On this string it stepped one code
unit too far across the combining sequence and returned an impossible offset. The span-invariant
check caught it and threw, which is how we found it.

We had validated the build on nine of the eleven sources, covering every Latin-script shape we
could think of, and they passed. The two sources we had not fully rehearsed were the WOF adapters,
which carry almost all of the non-Latin name variants. The failing rows were in the part of the
data we had not tested.

## Stop trusting the row

The obvious fix is the off-by-one itself. A proper fix teaches the boundary logic about combining
marks and _keeps_ every one of those non-Latin rows. We filed it as issue #555 and will do it
properly. Writing that fix at 3 a.m., during recovery, to unblock a multi-hour build would risk
introducing a worse bug.

The recovery fix was smaller: no single row can crash hours of work. It has two parts. First, an
out-of-bounds span (one that cannot be a valid character offset) quarantines the row with a named
reason instead of throwing. Second, a `try`/`catch` wraps the per-row alignment in the build loop,
so _any_ unforeseen exception on _any_ one row sends that row to quarantine and the build
continues.

The build already handled every other kind of failure this way. A component missing from the raw
text, or a row with empty text, has always produced a quarantine line with a reason, a count, and
no crash. The NFC assertion was the one place in the pipeline that threw instead. We made it
consistent with the rest of the system: a multi-hour unattended build treats each row as suspect
until it aligns, and a row that fails costs a line in a quarantine file rather than the whole
process.

This run quarantined tens of thousands of non-Latin name variants, under two hundredths of one
percent of the corpus. Every one is logged with the reason `span-out-of-bounds`, so the count
appears in the manifest. The loss is small, visible, and on the list to recover.

## The two and a half hours we didn't lose

A third change made the crash much cheaper to recover from.

By the time the build crashed, it had already finished the slow, expensive half of its job:
reading all eleven sources and writing 36 gigabytes of canonical rows to disk. That took two and
a half hours of I/O. The crash was in the _next_ phase, alignment, which reads those canonical
files back and turns them into labeled rows.

The build as written kept no state between runs. Re-running it meant re-emitting all 36 gigabytes
from scratch, which would take another two and a half hours to return to the failing row. That
re-run cost is larger than the cost of the original bug.

The recovery therefore also shipped resume. Each adapter writes its canonical file and then, only
after that file is completely flushed, writes a manifest beside it. A manifest therefore exists
only when its file is complete. Resume checks for that pair and, if both exist, reuses them and
skips the emit. Resume is opt-in. The default still re-emits, because a clean run should produce
the authoritative record instead of reusing a previous run's output. With the flag set, the
re-run reused every gigabyte already written and went straight to alignment. Without the emit,
the align phase turned out to be fast. We had budgeted twenty-two hours for the build, and it
will likely finish in under ten, because the original estimate included an emit phase the
recovery did not repeat.

## Build like it's going to crash

One row produced three fixes, and each is ordinary: normalize instead of throwing, quarantine
instead of crashing, and resume instead of restarting. Together they let the build finish
overnight without someone awake to restart it.

All three reflect the same point: a check that is correct in principle can still be unsafe in
production. The failures come from rows nobody anticipated, such as a combining mark, the one
record in 690 million in the wrong normalization form, or a boundary check that is correct on
every tested script and one code unit wrong on an untested one. That tail is too long to
enumerate, and much of it is in scripts the team cannot read. What you _can_ do is decide in
advance that the tail cannot stop the whole build. A malformed row becomes a quarantine line, a
crash becomes resumable, and an assertion that is right about your data still fails in a way
that preserves completed work.

The proper fix is still pending. The span locator needs to return correct offsets for a few tens
of thousands of non-Latin names, and issue #555 tracks that work. The build that failed twice on
South Korea finished overnight. In the next long build, one bad row will cost a line in a log
instead of a restart.

Make your long jobs survive a bad row, and make them resumable.
