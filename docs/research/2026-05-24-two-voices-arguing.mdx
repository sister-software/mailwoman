## What we're building, in one paragraph

Mailwoman is a piece of software that reads address strings (`"350 5th Avenue, New York, NY 10118"`) and turns them into structured place information ("this is in Manhattan, here are the coordinates, here's the postcode, etc."). It uses a small AI model to do the parsing. The model is small by AI standards, with about 9 million numbers inside it. For comparison, GPT-4 is rumoured to have over a trillion.

We don't need a giant model because the task is narrow. Addresses follow patterns, and we only need to identify which parts of a string are which (`350` is a house number, `5th Avenue` is a street, etc.).

## What "training a model" looks like

Mechanically, training a model works like this:

1. You have a model with millions of numbers inside it (call them "weights"). At the start they're random.
2. You have a pile of example data: addresses labeled with the correct answers.
3. You show the model an address, and it guesses what each part is.
4. You compare the guess to the correct answer. The difference is a number called **loss**. Low loss means a good guess, and high loss means a bad guess.
5. The training algorithm then adjusts the millions of internal numbers to make the loss a little smaller next time.
6. You repeat this thousands or millions of times.

What the model learns is a large set of patterns, refined over 50,000 rounds. In each round, the algorithm finds a mistake such as labeling a postcode as a street name and nudges specific numbers slightly so the model guesses better next time.

If you've ever debugged a function by running it, looking at the wrong output, and tweaking one parameter at a time until the output got right, you've done a single iteration of model training by hand.

## The "loss curve" you keep hearing about

People who train models watch a chart called the loss curve. A healthy one looks like this:

```
loss
 ^
 |   X
 |    X
 |     X
 |      XX
 |        XXX
 |           XXXXX
 |                XXXXXXXXXX
 +----------------------------> step
   0      500      1000     1500
```

Each X is one round of training. Loss starts high while the model guesses randomly and decreases as the model learns. A good training run descends until it plateaus.

Here is our actual loss curve from one of nine training runs we did this month:

```
loss
 ^                                  XXXX
 |                                 X    X
 |                                X      XX
 |                               X         XX
 |    X                         X            XX
 |     X                       X                X
 |      X                    XX                  X
 |       XX                 X                     ...
 |         XXX             X
 |            XXXXX       X
 |                 XXXXXXX
 +----------------------------> step
   0     500     800     1100
```

The model descends steadily for 500 steps (warmup), stays at a low loss for a while, and then climbs back up. By the end, it's worse than when it started. We trained it on 50,000 examples, and it got _worse_.

This curve means something is wrong, and the model gives no indication of what. There is no stack trace or exception, only a chart showing that the model learned and then unlearned.

We saw this exact shape in nine different runs, with different learning speeds, model sizes, and feature combinations. Every run descended steadily and then climbed catastrophically.

## The clue we'd been missing

To find a bug in a program, you typically narrow it down by ruling out parts of the code one at a time. ML debugging works the same way: you change one thing, retrain, and look at the curve. Each retrain, however, takes hours and costs real money on a rented GPU, so you choose experiments carefully.

For weeks we'd been ruling out hypotheses:

- Is the learning rate too high? No. Lowering it only delayed the climb.
- Is the model too small? No. We made it bigger, and the same thing happened.
- Is a new feature we added destabilising it? No. We turned it off, and the problem remained.
- Does the data have a bug? We couldn't rule this out, because it was expensive to check.

Then somebody pointed out something we hadn't questioned: **we were training the model with two different goals at once.**

The model has two scoring systems. We'll call them Voice A and Voice B.

- **Voice A** says: "How good are your guesses for each individual word? Did you tag '350' correctly as a house number? Did you tag 'NY' correctly as a region?"
- **Voice B** says: "How sensible is your overall pattern? Is your sequence of tags structurally valid? Does it look like a real address?"

Both voices are useful, because a working geocoder needs both per-word accuracy _and_ sensible patterns. We'd been adding their feedback together, with Voice B's contribution scaled down to 5%, and using that combined signal to train the model.

We had never asked whether **Voice A and Voice B were telling the model to do the same thing.**

## The five-minute diagnostic

The technique we used is simple enough to explain to a curious teenager.

When you train a model, every weight inside it gets nudged in a particular direction based on the combined loss. That nudge is called a **gradient**. If a gradient is big, the weight moves a lot per step, and if it is small, the weight moves a little.

Each voice contributes its own gradient. The two are added together, with Voice B at 5%, to produce the final nudge.

We asked **which voice contributes most of the gradient** at the step before the model starts unlearning. We took a saved snapshot of the model from that moment, fed it a few example addresses, and measured the size of each voice's contribution to the gradient separately.

We expected Voice A's gradient to be about 20× larger than Voice B's. That would have meant Voice B contributed almost nothing and the 5% scaling was appropriate.

Instead, **Voice B's raw gradient was 16× larger than Voice A's.**

Voice B was supposed to be scaled to 5%, but its raw gradient was 16× larger than Voice A's. 5% of 16× is 80%, so Voice B's effective contribution to training was 80% of Voice A's. We had set the scaling knob so that Voice B would contribute lightly, but it contributed nearly as much as Voice A.

## The cooperative-vs-conflict picture

An analogy helps explain the result.

Imagine a hiker on a foggy hill, trying to walk to the lowest point in the landscape. The hiker can't see far and carries two GPS devices that each point downhill.

- **At the top of the hill (high loss),** every direction is downhill, so both devices point roughly the same way. The hiker makes progress, and loss decreases.
- **Lower down in a specific valley (lower loss),** the landscape has more detail, and the two devices start to disagree. Voice A points left toward the valley floor, and Voice B points right.

When the devices disagree, the hiker mostly follows **whichever device gives the larger signal**. With Voice B's signal 16× larger than Voice A's, the hiker follows Voice B even though Voice A was pointing at the valley floor. The hiker climbs out of the valley toward a different point that Voice B prefers, and Voice A's loss (the per-word accuracy) gets worse.

That is what happened to our model. Above loss 0.41, both voices agreed, and the model descended steadily. Below 0.41, they started to disagree, and Voice B's larger gradient pulled the model away from the basin Voice A had been guiding it toward. The model's per-word accuracy kept dropping, which we saw as the loss climbing back up.

## The fix

The fix follows directly: **remove Voice B from training**, so it contributes nothing to the gradient.

Voice B still encodes useful structural rules, such as forbidding orphan tags and invalid BIO sequences. We therefore keep Voice B for **inference**, when we use the trained model to parse an address, and leave it out of training.

The code change is one line: when Voice B's weight is 0, the loop skips computing it. Training then runs purely on Voice A's gradient, which had behaved well throughout.

## What we tell ourselves we learned

1. **Adding two weighted losses together sounds simple, but it can fail badly.** Two loss functions can have very different gradient magnitudes even when their loss _values_ look comparable. Scaling a loss by a constant does not balance its contribution to the optimiser. Watching the loss values misled us for nine training runs.
2. **The five-minute diagnostic was more valuable than the previous month of retraining experiments.** Each experiment that changed a knob and retrained cost hours. The gradient-norm probe cost five minutes and gave a sharper answer than any of them, because it measured what the model was responding to instead of the end result.
3. **ML debugging is more like programming debugging than the field admits.** Once you have words for what's happening, the techniques are familiar: bisect, isolate, instrument, hypothesise, test. The hard part is finding words for _what's happening inside the model_. After that, the bug is typically findable.
4. **Run cheap experiments first.** A 5-minute probe should always run before a 25-hour retrain. We didn't run the probe earlier because we didn't know about it.

## Update — it worked

We wrote this post while the CE-only experiment was still running, and the experiment passed. The model trained past step 2000, where every prior run had diverged, without any loss climb. Its final validation accuracy was 0.444, the best number any run in this project has produced. The full 50,000-step training run is now in progress.

Without Voice B's gradient, the model reached a lower loss than any prior run reached before diverging.
