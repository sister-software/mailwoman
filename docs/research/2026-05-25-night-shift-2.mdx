The second night shift ran from roughly 2am to 2pm UTC on May 25th, 2026. It started with a GPU that kept crashing and ended with a trained model, an ONNX export, and a full evaluation report. This post describes how moving training to cloud compute worked around the hardware problem.

## The hardware wall

The lab runs on a small form factor desktop with an AMD Radeon 780M integrated GPU. For short bursts (a 2-minute smoke test, a 10-minute diagnostic probe), it works fine. For sustained multi-hour training at 98% GPU utilization, it overheats. The firmware detects thermal stress and resets the GPU, killing whatever process was running on it.

During this session, the GPU hit 22 resets before we stopped counting. Every 60-90 minutes of training, the hardware would fault. A watchdog script would wait 15 minutes for the chassis to cool, then restart from the last checkpoint. Net progress: about 8,800 training steps out of a target 50,000.

At that rate (90 minutes of compute, 15 minutes of cooldown, and 500 steps lost per restart), the full training run would take roughly 38 hours of wall-clock time. That schedule is acceptable for a research prototype, but it does not fit in a night shift.

## The pivot to Modal

[Modal](https://modal.com) is a cloud compute platform where you write a Python function, decorate it with `@app.function(gpu="A100")`, and it runs in a datacenter with a proper GPU. The user does not manage SSH, Docker, or instances.

The pivot took about an hour:

1. **Upload the corpus to Cloudflare R2.** We synced 30 GB of training data with rclone in about 15 minutes. The data was already on a fast local drive, so upload bandwidth set the pace.

2. **Write a Modal wrapper.** The wrapper adds 20 lines around the existing training script. It pulls the corpus from R2 into a Modal Volume (a persistent disk), runs the training, and writes checkpoints back.

3. **Debug three small issues.** The Modal worker needed the R2 credentials passed as secrets (the first attempt used empty env vars), the training config was missing from the volume, and the ONNX export needed `onnxscript` added to the image.

4. **Run the training.** The run completed 50,000 steps on an NVIDIA A100-SXM4-40GB in 2 hours without hangs, resets, or watchdog restarts. It trained at 6.9 steps per second, compared with 0.56 on the local iGPU.

Total cost: about $5, covered entirely by Modal's $30/month free credits for new accounts.

## The results

The CE-only model (which drops the problematic CRF loss term that caused nine previous runs to diverge) trained to completion:

- **val_macro_f1: 0.605** (final), 0.621 (peak at step 35K)
- **Train loss: 0.068** (final)
- **Zero divergence** across all 50,000 steps
- **ONNX export: 66 MB** (full-precision training artifact; the shipped weights are quantized to ~25 MB for the npm package, and smaller still for the browser demo)

For context: v0.4.0 shipped at macro_f1 = 0.36. This is a 68% relative improvement on the same evaluation set.

## The eval matrix

After the model shipped, we ran the full product-level evaluation, which compares four pipeline modes on 4,535 hand-curated golden addresses:

| Mode                      | Exact Match | Macro F1 | Empty Parse | Overconf Wrong |
| ------------------------- | ----------- | -------- | ----------- | -------------- |
| Rule-only                 | **30.8%**   | 22.0%    | 6.3%        | 2.4%           |
| Neural                    | 0.1%        | 7.3%     | 0.3%        | **54.5%**      |
| Hybrid                    | 0.1%        | 7.3%     | 0.3%        | 54.5%          |
| Hybrid-joint (reconciler) | 6.0%        | 16.6%    | **0.0%**    | **0.1%**       |

The table shows four findings:

**The neural model predicts components that are absent.** On the golden set, it predicted a `dependent_locality` (a sub-city neighborhood) 956 times where none existed. Calibration does not explain this, because these predictions come out at high confidence. Decoding does not explain it either, because Viterbi with the structural mask is already running. That leaves training. Cross-entropy weights every mislabeling equally, so the model never learned that `dependent_locality` is rare. Class-weighted CE makes mislabeling a rare tag cost more. It was blocked in v0.4.0 because it destabilized the dual-loss training. CE-only training has now run stably, so class weighting can be tried.

**Hybrid mode shows identical numbers to neural alone.** The hybrid mode fuses rule classifications with neural output. In this iteration the raw neural decoder's overconfidence outweighs the rules, so the numbers match the neural row. The reconciler (hybrid-joint) is the mode that checks the merged result.

**The reconciler reduces overconfident errors.** It drops overconfident-wrong from 54.5% to 0.1% by checking whether parsed components form a coherent real-world hierarchy. It also eliminates empty parses (0.0% compared with 6.3% for rules), because it always produces some output, even a conservative one.

**The rules have little room to improve, and the neural model has a lot.** Rule-only at 30.8% exact match is a mature system, hand-tuned over years. Each additional percentage point costs engineering time. The neural model scores 6.0% (hybrid-joint) after one stable training run. It learns from data, so each new training run can improve every component and every locale at once. The 68% improvement from v0.4.0 to v0.5.0 is the trend that matters.

## The infrastructure lesson

The session started with a GPU that crashed every 90 minutes, a 50,000-step training target, and 12 hours of wall-clock time. Four choices made the run possible:

- **Corpus on R2** means any GPU provider can pull it at datacenter speed. We upload it once and can train on any provider.
- **Modal's per-second billing** means we paid $0 for data upload, $0 for debugging, and ~$5 for the actual GPU compute.
- **Checkpoints every 500 steps** on the Modal Volume means even if a Modal preemption happened (it didn't), we'd lose at most 7 minutes of work.
- **The same training script** ran locally (for smoke tests) and remotely (for the full run) without modification. The config points at `/data/`, which is either the local mount or the Modal Volume.

The local iGPU still runs smoke tests, gradient probes, and quick 50-step experiments. The expensive runs go to the cloud. We settled on this split once we accepted that the thermal limit was real and not worth engineering around.

## What's next

Now that we have cloud GPU access at $5 per full training run, several decisions we made for the local hardware no longer apply. The v0.5.0 model was trained with constraints that made sense on a thermal-limited iGPU but don't make sense on an A100:

- **Hidden size 256.** We wanted 384 but fell back when it failed to train locally. The A100 has 40 GB of VRAM, which fits 384 or 512 easily.
- **Effective batch 128 via gradient accumulation** (batch=16, accumulate 8 steps). This was a workaround for limited GPU memory. The A100 can run batch 128 directly, which changes the gradient noise and may change the training dynamics.
- **50,000 steps.** This was sized for what was affordable locally. At 6.9 steps/second on the A100, 100K steps costs $10. The model may be undertrained.
- **Phrase-prior conditioning disabled.** It was turned off during debugging and never turned back on, although the architecture was designed around it.
- **Class-weighted cross-entropy disabled.** This v0.4.0 recipe change addresses the 956 false-positive `dependent_locality` predictions, and it is now safe to use.

The next iteration removes all of these constraints at once: h384, direct large-batch, phrase priors on, class weights on, and a longer schedule. It keeps the same corpus, tokenizer, and CE-only stability fix. We expect one A100 run of a few hours, covered by free credits.
