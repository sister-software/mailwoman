You've got a hundred thousand addresses to reconcile. Two databases, the same clinics and providers scattered across both, each one spelled a dozen ways: abbreviated here, reordered there, a postcode dropped, a suite number glued to the street. You run them through a geocoder, match on the resolved coordinate, and most rows match. Some fraction land on the wrong building, the wrong block, the wrong town, and the geocoder won't tell you which fraction, because it hands back a pin for every row and no confidence for any of them.

That's the gap we set out to close. Every geocoder chases accuracy, and so do we. Few geocoders also hand you a number on each answer that tells you _which_ ones to trust, so you can keep the good ones and send the rest to a human.

## The forecaster's interface

Think about a weather forecaster. A good one who forecasts "70% chance of rain" is right on about seven of every ten days they forecast it. The forecast is useful because the number means what it states. A neural model makes the same promise implicitly every time it hands you a softmax probability, and for a long while ours broke it, confident in some bands and timid in others, with no single number you could lean on.

We fixed that part first (it's [its own story](https://github.com/sister-software/mailwoman/blob/main/docs/records/site-2026-08/concepts/confidence-calibration.mdx)). A small post-hoc correction maps the model's raw confidence onto a calibrated one, so when a parsed span reads `conf="0.94"` it's right about 94% of the time, measured on addresses the fit never saw. When the model reports high confidence, you can now believe it.

A calibrated number per _span_ still isn't a number you can act on per _answer_, though. So we extended it the last step, to the resolved coordinate.

## Set a precision threshold

mailwoman returns a coordinate and a confidence you can put a threshold on. Set a bar (call it τ) and accept only the answers the model is at least that sure about. Route everything below it to review.

On a deliberately messy held-out set (lowercased, abbreviated, postcodes stripped, the real-world soup), graded by whether the resolved point lands within 25 km of the truth, the dial does what you'd want:

| accept above…  | right-place @25km | share of rows answered |
| -------------- | ----------------: | ---------------------: |
| anything (τ=0) |               84% |                    67% |
| 0.80           |               92% |                    49% |
| 0.94           |               97% |                    16% |

Raise the bar and the precision of what you keep climbs from 84% to 97%. The price is coverage: you answer fewer rows, and you pay it knowingly, because the table shows the price at each threshold. A search index returns one best guess and one confidence. That leaves no threshold to set.

The curve also holds on data it wasn't fitted on. Split the messy set in half, fit no new parameters, and the high-confidence answers still beat the low-confidence ones out-of-sample by fourteen points. The model's confidence is lowest in the locales whose coverage we're still building.

## Auto-accept above the threshold, review below it

Go back to the hundred thousand records. With a threshold you can finally split them in two: the answers the model stands behind and the ones it's hedging on. You auto-accept the first group and move past it. A person looks at the second. The threshold means what you set it to. Set it at 0.95 and your auto-accepted set is right at about that rate, a rate you can put in a report and defend rather than a hope you re-check by hand.

Crank the threshold and you hand more rows to humans. That's the cost, and it's yours to set against your own tolerance for a wrong match. The calibration puts a real number on both sides of that trade.

It's live now in `mailwoman@4.14.0`. Pass a calibrator to the parser, read the `conf=` off the resolved tree, pick your bar.
