# Postcode decode as encoded intent

**Status: design note (2026-08-22), UPDATED the same night after the implementation run. Every number
below is reproducible from the scripts named in the appendix.**

Four of the questions this note left open have since been answered, and one of its recommendations
was measured wrong. See [What the implementation run settled](#what-the-implementation-run-settled)
before acting on anything above it.

Related: [#1773](https://github.com/sister-software/mailwoman/issues/1773) (the grader bug that
started this), `packages/neural/postcode-prefix-index.ts` (PFX1, the artifact), `pfx1.ksy` (its
normative layout).

## The claim

A postal code is not an opaque key. It is **compressed, locale-specific information about where it
is**, and much of it is readable without asking a gazetteer anything.

This matters exactly where retrieval helps least. `800 E Monroe St, Springfield, IL 62701` is
over-specified: retrieval disambiguates and any decode is redundant. Strip it to
`800 E Monroe St 62701` and the ZIP is the **only** evidence of place in the string — and it is
evidence a decoder can read with no database.

Pelias penalizes numeric spans positionally: is this five-digit run a house number or a postcode,
given where it sits? That is a prior on the SPAN. Nothing asks whether the code's own content
**corroborates** the neighbouring spans, or lets that corroboration move confidence.

## What already exists

Most of the implementation is built. The gap is narrower than it looks.

| Piece                                        | Where                                | State                                         |
| -------------------------------------------- | ------------------------------------ | --------------------------------------------- |
| shape → country                              | `core/resolver/postcode-format.ts`   | **default-ON**                                |
| shape → candidate address systems            | `codex/postcode-systems.ts`          | shipped, overlap-aware                        |
| granularity tier, by measurement             | `codex/postcode-systems.ts`          | NL PC6 + GB unit only                         |
| prefix → asserted ancestry + measured radius | `resolver/postcode-prefix.ts` (PFX1) | built, **default-OFF**, GB only               |
| coordinate-based consistency                 | `resolver/resolve.ts`                | default-ON, **needs the postcode to resolve** |
| generic prefix-walk trie                     | `@mailwoman/ancestrie`               | shipped, unused for postcodes                 |

`candidateSystemsForPostcode` is already overlap-aware: `62701` is accepted by the US, DE and FR
shapes, and it returns all three. Resolving that ambiguity by picking one locale up front is the
failure to avoid — the caller's country scope is what narrows it.

## The granularity spectrum is the design constraint

One `postalcode` placetype covers systems that are not comparable:

| System                      | What a full code means                    | Grade              |
| --------------------------- | ----------------------------------------- | ------------------ |
| Australia, US 5-digit ZIP   | a delivery area / locality                | **area**           |
| Canada LDU, UK unit, NL PC6 | a street segment or small address cluster | **street segment** |
| Singapore                   | one building or house                     | **delivery point** |
| Ireland Eircode             | one postal address                        | **address**        |

`PLACETYPE_SPECIFICITY` assigns `postalcode: 9`, above `locality: 4`, and that single number is right
for GB and wrong for FR, where a five-digit zone is coarser than the commune inside it. This is the
root of #1773 and is worth stating as a rule: **a global placetype scale cannot answer a
per-address-system question.**

The rule turned out to have a second edge, sharper than the first. The _ladder_ is per-address-system
too, and it was holding one arm as a global default — see
[finding 6](#6-the-ladders-locality-first-arm-is-a-per-country-claim).

The US is the awkward case because it straddles three levels at once — 5-digit ZIP (area), Unique ZIP
(one organization), ZIP+4 (one side of a street).

## Five findings, measured — the first pass

### 1. There is no postcode parentage to consult

The natural fix for #1773 — ask the hierarchy whether this postcode is finer than this locality — has
no data behind it:

```
postalcode-gb-codepoint.db     1,746,976 rows   parent_id set on 0.0%
postalcode-geonames-intl.db      446,914 rows   parent_id set on 0.0%
admin-global-priority.db               0 postalcode rows
ancestor edges whose CHILD is a postalcode:  0
```

Postcodes live in separate shards, outside the admin hierarchy. A containment relation does exist,
purpose-built, in `postcode-locality-intl.db` — `is_containing` and `distance_km` per pair, 7.6M
pairs for GB — and nothing in either grader consults it.

### 2. WOF parentage is a contaminated instrument for US ZIPs

The ZIP numbering plan is an independent witness: a `5xxxx` code cannot be in New York whatever a
gazetteer parent says.

```
ZIPs with both a numbering band and a resolvable WOF state: 38,816
agree:        35,533 (91.54%)
CONTRADICTED:  3,283  (8.46%)
```

PFX1's own header independently records 7.9%, arrived at by a different method. The two agree.

### 3. The contamination has a computable signature

USPS **Unique ZIPs** — assigned to an organization by mail volume, `00501` is the IRS, `12345` is
General Electric, `10118` is the Empire State Building — describe a mail route, not an area. Their
gazetteer parentage is whatever the source could attach them to.

The detectable signature is not the unique-ness but the **placeholder coordinate**: a coordinate
shared by codes from different SCFs.

```
agreeing ZIPs on a shared coordinate:    1,594/35,533 (4.5%)
DISAGREEING ZIPs on a shared coordinate: 2,153/3,283 (65.6%)
```

A 14.5× enrichment. `38.8933,-77.0146` carries 133 codes across five SCFs; `40.1604,-75.4090` carries
48 codes across **29 unrelated** SCFs.

### 4. Ranked state shares do NOT separate signal from artifact

The first proposal was to return `Array<[state, share]>` and let a threshold decide. Measured, it
fails:

```
cut     kept   plausible   implausible   precision
0.00     749        195           554      26.0%
0.10     249         77           172      30.9%
0.30      76         36            40      47.4%
```

**554 of 749 minority state entries (74%) are flatly contradicted by the numbering plan**, and the
plausible and implausible share distributions overlap (medians 6.9% and 5.1%). A weighted array would
ship mostly noise with a number attached, which is worse than shipping nothing because it looks
calibrated.

### 5. Point-in-polygon beats parentage by 12×, and needs no licence

PIP depends on neither parentage nor a USPS database — only the code's own coordinate and a state
boundary, both of which we already ship under permissive licences.

|                                         | WOF parentage | **point-in-polygon** |
| --------------------------------------- | ------------: | -------------------: |
| ZIPs contradicted by the numbering plan |         8.46% |            **0.69%** |
| SCFs sitting in one state               |         36.6% |            **97.2%** |
| dominant state plausible                |         97.0% |            **99.7%** |

And PIP's residual error is inherited, not produced: 264 of its 286 remaining contradictions sit on a
placeholder coordinate. On clean input it is wrong 22 times in 41,905 — about 0.05%.

The same pass reaches down the admin ladder, degrading by **coverage** rather than by silent
wrongness:

| Level      | polygons |    ZIPs placed | `62701`          |
| ---------- | -------: | -------------: | ---------------- |
| locality   |   45,113 | 25,798 (61.6%) | **Springfield**  |
| localadmin |   23,343 | 17,565 (41.9%) | Capital Township |
| county     |    3,142 | 41,658 (99.4%) | Sangamon         |
| region     |       51 | 41,671 (99.4%) | Illinois         |

Whole run: 2.4 seconds. The 38% locality miss is a polygon gap — only 45,113 of 160,077 US localities
carry geometry — not a PIP failure. `localadmin` returning _Capital Township_ confirms locality is the
rung to aim at, with county as the honest fallback.

## What the implementation run settled

Everything above this line is the note as first written. Below is what building it found, including
the place where the note above is wrong.

### 6. The ladder's locality-first arm is a per-country claim

The note framed the granularity spectrum as a problem for `PLACETYPE_SPECIFICITY`. It is also a
problem for the ladder, which had two arms and was using one of them as a global default. Whether a
postal zone is coarser than its locality is a fact about a country's **administrative** geography, and
code length does not predict it — FR and DE are both 5-digit and disagree.

Coordinate p50, locality-first against the postcode point, OpenAddresses panels through the
production result assembly:

| panel |  rows | locality-first | postcode point | verdict                                         |
| ----- | ----: | -------------: | -------------: | ----------------------------------------------- |
| DE    | 2,997 |        5.84 km |    **1.24 km** | postcode, on **every** percentile incl. p99     |
| FR    | 3,000 |    **0.97 km** |        2.64 km | locality, closer on 77.5% of rows               |
| IT    | 2,833 |    **1.34 km** |        3.05 km | locality, closer on 66.4%                       |
| ES    | 2,929 |    **0.68 km** |        0.97 km | locality, but 46.1% of rows prefer the postcode |
| US    |   577 |    **2.28 km** |        4.15 km | locality — see below                            |

DE shipped as `AREA_POSTCODE_FINER_THAN_LOCALITY` (#1780). Its within-5-km population doubles,
45.1% → 90.4%.

### 7. The US row is 577 and not 10,000, and that difference nearly flipped a locale

The US rooftop cascade is US-only **by construction** — `selectAddressPointsDB` composes
`address-points-us-<slug>.db` — and it serves 94.2% of US queries:

```
result tier:  address_point 8,434   interpolated 989   admin 577
```

So only 577 panel rows reach an admin decision at all, and they are the rows no rooftop or
interpolation shard could place: rural, sparsely covered, exactly where a locality centroid sits close
and a ZIP zone is wide. Graded over all 10,000 the US reads as a postcode-first country (2.41 vs
3.63 km) — **a selection effect, measured on a population production never sends to the ladder.**

Read finding 5 with this in mind. The SCF tier is real and the PIP result stands, but the US is the
locale where an admin-tier measurement describes the smallest slice of what users get.

### 8. Canada is two systems, and the code says which

The note listed CA as an open question — _"The blocker is one number."_ It was two. Measured on 879
graded rows of the CA rooftop panel through the candidate backend:

| population    | arm            |       p50 |         p90 |     ≤1 km | postcode closer on |
| ------------- | -------------- | --------: | ----------: | --------: | -----------------: |
| **732 urban** | locality-first |   2.51 km |     9.53 km |     26.4% |                    |
|               | postcode-first |  **78 m** |   **373 m** | **94.7%** |          **90.4%** |
| **114 rural** | locality-first | **929 m** | **5.73 km** | **53.5%** |                    |
|               | postcode-first |   2.08 km |     8.11 km |     25.4% |              26.3% |

Urban CA is GB's tier — 78 m against GB's 38 m — on a sample fifty times larger than the fifteen rows
GB was admitted on. Rural CA is a delivery route, not a block face.

Canada Post puts a `0` in the **second position** of a rural forward sortation area, so the code
carries the answer: `T0H 1M0` is rural, `M1J 1A8` is not. The urban half shipped into
`UNIT_GRADE_POSTCODE`; the rural half is excluded by that one character.

**The pooled number would have been a trap.** Across both populations CA reads 0.10 km p50, which
looks like a uniform win and is not one. Gating on the character beats promoting the country
_measurably_ — the shipped result now beats blanket postcode-first on every percentile (p90 1.88 km
vs 3.26, ≤1 km 86.2% vs 82.3%), because rural keeps the locality.

### 9. `0,0` is a shard population, not an edge case

144,715 rows across four shipped shards sit on null island — **48,216 of 142,604 JP postcodes, one in
three** — and `decorateNode` was copying that onto the node, where every `lat != null` guard
downstream accepts it. Thirteen hand-written `(lat !== 0 || lon !== 0)` comparisons existed to work
around it, including one three lines above the assignment. Fixed at the seam (#1786): the place still
resolves and identifies itself, and states that it cannot say where it is.

No shipped CLI path produced a `0,0` answer — the cascade's country-bbox check rejects it — so this
was a latent hazard with a live mechanism. Where it did cost something is evals: two DE panel rows
graded **5,776 km** from their own address, moving the panel mean by 3.85 km on both arms.

### 10. A shard named `postcode-*.db` cannot serve `postalcode` queries

`deriveSchemaName` yields `postcode_ca_overture`; the routing tests `startsWith("postalcode_")`.
"postcode" ≠ "postalcode", so seventeen shards holding 877,397 codes silently return zero hits, and
`postalcode-geonames-intl.db` — which routes, being spelled right, but carries only `spr` — throws
mid-query instead. Neither is live (these are build inputs, and the candidate table has all 843,739 CA
codes at placetype 11), but the first CA measurement of this run reported _"974 of 1,000 rows resolve
no postcode node"_, which reads as a coverage catastrophe and was a shard-selection artifact. #1791.

### 11. The currency flags are not empty, they are CONSTANT

The note recorded ZIP currency as unanswerable. It is, but the reason matters: the columns that would
answer it are not missing and not sparse — they are **constants written by the builder**, and they
look exactly like data.

Across all 42,319 rows of `postalcode-us.db`:

```
is_current      1 → 42,319        is_superseded    0 → 42,319
is_deprecated   0 → 42,319        is_superseding   0 → 42,319
is_ceased       1 → 42,319
```

Every one is single-valued, so every one carries zero bits. `is_ceased = 1` on every row is the tell
— read literally it says every US ZIP has ceased.

**The proof that these are builder artifacts rather than data is the disagreement between shards:**

| shard                        |      rows | `is_current` | `is_deprecated` | `is_ceased` |
| ---------------------------- | --------: | -----------: | --------------: | ----------: |
| `postalcode-us.db`           |    42,319 |        all 1 |           all 0 |   **all 1** |
| `postalcode-intl.db`         |   444,727 |      444,708 |          **19** |   **all 1** |
| `postalcode-gb-codepoint.db` | 1,746,976 |        all 1 |           all 0 |   **all 0** |
| `postalcode-nl-pc6.db`       |   464,964 |        all 1 |           all 0 |   **all 0** |

`is_ceased` is 1 everywhere in two shards and 0 everywhere in the other two. The value tells you which
builder wrote the file, not anything about the code. Nineteen `is_deprecated` rows in the intl shard
are the only postal-currency information in any of them.

So `10048` — the World Trade Center ZIP, retired in 2001 — sits at `0,0` flagged `is_current = 1`, and
is indistinguishable from `00501` (the IRS at Holtsville, live) and `12345` (General Electric, live),
which carry the same three flags and differ only in having a coordinate.

**The one real signal is `lastmodified`**, which is genuinely varied — 6,665 distinct values. But it
answers a different question (when the upstream record was last touched) and it stops at
**2021-01-21**, so the shard's provenance is four and a half years old.

#### Why the obvious free substitute does not work

Census ZCTAs are the free, permissive approximation of ZIP areas, and the shard already carries a
`centroid_source` table with **979 rows stamped `census-zcta-2024`** — so someone has already reached
for exactly that. Two facts kill it as a currency source:

- Every one of those 979 is a **territory** code (969xx Guam and neighbours). The enrichment was
  scoped to the places WOF could not place, not to currency.
- **Zero of the 414 null-island ZIPs were enriched by it.** Those 414 spread across 210 sectional
  centres with no concentration — 100xx (Manhattan PO boxes) is the densest at twelve — which is the
  signature of PO-box-only and organisation codes. ZCTAs are built from populated address blocks and
  **exclude PO-box-only ZIPs by design**, so a ZCTA join is structurally blind to exactly the
  population whose currency is most in doubt.

#### What this means for a consumer

The honest posture is the one the artifact already takes elsewhere: **do not claim what the source
cannot say.** Concretely —

1. **Never read these five columns for US postcodes.** A filter on `is_current` selects everything and
   reads as though it selected something, which is worse than no filter at all.
2. **A retired code answers like a live one.** Treat a US ZIP hit as "this code existed in a 2021-era
   register", not as "this code is deliverable today".
3. **The absent coordinate is the closest thing to a signal we hold** — the 414 unplaceable codes are
   enriched in PO-box-only and organisation codes, the class where retirement concentrates. It is a
   correlate, not an answer, and #1786 now makes that absence visible rather than a Gulf-of-Guinea
   coordinate.

Answering it properly needs a source with a retirement date. USPS publishes one and licenses it;
HUD's quarterly USPS crosswalk is free and covers active codes; neither has been evaluated here.

## What the artifact should assert

**Built 2026-08-22 (#1784)** — 915 nodes, 42,313 units, 906 carrying a centroid, median
`radiusP95Km` 53.56 km, 25,773 bytes. Leave-one-out against the arm a caller otherwise gets, 40,004
units: SCF centroid p50 **29.9 km** against the region centroid's **154.6 km**, closer on 94.9%. It
does not meet the GB ≥60%-within-10 km bar (17.7%) and should not — that bar is calibrated for outward
codes with a 3.24 km median p95 radius.

- **US SCF coordinate + `radiusP95Km`**: buildable now. Median p95 radius **53.7 km** on placed codes
  (p90 110 km), against GB outward's 3.24 km and the US 1-digit band's 662 km. A real tier, and one
  neither existing consumer was designed around — which is exactly why PFX1 makes the radius
  mandatory beside a coordinate.
- **US SCF → state**: from PIP, single-state for 877 of 902 SCFs. Not an array.
- **US SCF → locality**: from PIP where a polygon exists, county where it does not, and **nothing**
  where neither does. PFX1 already treats empty ancestry as a legitimate answer.

## Two decisions that block the NEXT artifact

Neither blocked the US SCF index, which shipped as a PFX1 instance rather than a new format. Both
still stand for whatever comes after it.

### Decision 1 — id width

`PostcodePrefixAncestor.wofID` is an `f64` because WOF ids exceed 2^32; the NI shard's synthetic
postcode ids start at 9.8e12. `AncestrieRecord.id` is a `u32`. **These cannot both be right if the
postcode appliance returns WOF ancestry through ancestrie.**

| Option                       | Cost                                                                 | Notes                                                          |
| ---------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------- |
| widen ancestrie ids to `u64` | +4 bytes × (entry + id index + parent tables), ~12 MB per 1M entries | `BigInt64Array` reads are slower                               |
| **dense ordinal mapping**    | ~0                                                                   | build-time WOF id → `u32` ordinal; the real id becomes payload |
| `f64`, as PFX1 does          | +4 bytes, exact to 2^53                                              | ids stop being integers to the type system                     |

**Recommendation: dense ordinals.** It is the technique the format already uses for tokens — intern
the wide thing, reference an ordinal — applied one level up. Hot tables stay `u32`, and an external
identifier belongs in the payload.

### Decision 2 — a seventh hand-rolled format, or a shared header

Six formats exist: `PCN1`, `PCB1`, `PIX1`, `PFX1`, `ANCT`, and the FST. Each carries a per-file
"this file owns BOTH ends" discipline and no shared code. That has held — but the conventions have
already forked:

- header: `u32 headerLen` + UTF-8 JSON (`PCN1`/`PIX1`/`PFX1`) vs a fixed 48-byte binary (`ANCT`);
- ids: `f64` (PFX1) vs `u32` (ancestrie).

**Recommendation: extract a shared header module at the seventh format, not the eighth** — magic,
version, section table, source-md5 stamp. The per-file discipline stays for the payload.

## What it resembles, for orientation

- **Ancestrie** is a Lucene FST + impact-ordered postings + a nested-set index, packaged like
  PMTiles. The pre/post interval labels give O(1) containment both ways and make descendant
  enumeration a contiguous range scan; the usual objection (relabelling on update) is void because
  the artifact is sealed and rebuilt whole.
- **PFX1** is a Parquet dictionary-encoded column group, flattened row-wise.
- **Protobuf** is the wrong tool for the index itself: varints mean you cannot seek, so no mmap and
  no binary search. It is a fine container for pre-sorted opaque blobs.
- **Parquet/GeoParquet** fit bulk analytical postcode work — row groups are byte-range addressable —
  but need a WASM decoder and have poor point-query latency.
- **Entropy coding (Huffman)** buys little here: postcodes share prefixes _and_ suffixes, so the
  FST/DAWG already exploits the redundancy that matters, and a decode cost on every read is the wrong
  trade at these sizes.

## Open questions

- ~~**ZIP currency is unanswerable from the shipped shard.**~~ **ANSWERED, and the answer is worse than
  "unrecorded" — see [finding 11](#11-the-currency-flags-are-not-empty-they-are-constant).**
- **The numbering plan is a first-digit witness**, so it catches only cross-band errors. The 0.69%
  PIP disagreement is a floor on the error, not the error.
- ~~**234 ZIPs (0.56%) fall outside every state polygon.**~~ **ANSWERED — not coastal precision.**
  Measured by distance to the nearest state boundary vertex: median **1,635 km**, and only 14 of the
  234 are within 100 km of any boundary at all.

  **220 of 234 carry a territory prefix** — PR, USVI, Guam, American Samoa, the Northern Marianas —
  which the ZIP numbering plan gives no state band. `96916` sits at `13.2659,144.6892`, 5,036 km from
  the nearest US state polygon, which is Alaska's. The #1784 build is right to withhold a region for
  them, and right for the reason it does so rather than by accident.

  The 14 that carry a mainland band split again, and only four are boundary precision: `78565` is
  0.50 km outside TX on the Rio Grande and `55725` 1.30 km outside MN on the Canadian border. The
  rest sit in the Pacific — `94157` and `94165`–`94168` share `37.7597,-122.6940`, 9.5 km due west of
  San Francisco, which is the placeholder-coordinate signature of finding 3 rather than a
  simplification artifact.

  So a boundary buffer would recover four rows and mislocate two hundred and twenty. Reproduce with
  `us-zip-outside-states.ts`.

- ~~**Canada.**~~ **ANSWERED** — see [finding 8](#8-canada-is-two-systems-and-the-code-says-which).
  It was two numbers, not one: urban 78 m, rural 2.08 km. The urban half shipped into the unit tier.
  FSA/LDU still maps onto PFX1 unchanged — FSA is the prefix tier (~1,650 nodes, analogous to GB
  outward), LDU the unit tier — and no FSA index has been built.
- **Feeding the decode back into span confidence.** `postcode_prefix_ancestors` records what a prefix
  asserts, as metadata on a resolved node. Nothing lets it raise or lower confidence that a
  neighbouring span is really a locality. This is the piece that genuinely does not exist, and it is
  what the Pelias observation is actually about.
