# Artifact and rights inventory

This page records what each published package ships, which party grants rights to it, and where the
record is incomplete. It was observed on `main` on 2026-09-20 by reading manifests, model cards and
rights documents in the checkout.

The page keeps three records separate throughout. Mixing them would turn a corpus measurement into a
claim about a released model:

1. **Current corpus composition**: what the corpus on the training volume contains today.
2. **Historical training inputs**: which records trained a particular released checkpoint.
3. **Runtime datasets and dependencies**: what an operator downloads separately.

This page measures only the first. The second is unresolved for every published package, and this
document says so explicitly.

The licensor and the services operator are different parties, and the repository states both
consistently. Nirrus LLC appears in the website Terms and Privacy Policy and in no rights document.
Operating the services does not make it the copyright holder.

Two commercial documents exist and each says which it is. `COMMERCIAL-LICENSE.md` opens with a
template notice stating it does not execute. `commercial-2026-10.mdx` states that acceptance is
recorded by Stripe Checkout when a buyer ticks the box, and that the page is not edited after
publication.

**Repaired on the page.** `docs/src/pages/license.mdx` said `COMMERCIAL-LICENSE.md` "carries the same
terms in the repository". The two differ in execution mechanism, so the page overstated their
relationship. The page now names `commercial-2026-10` as the agreement that binds and describes
`COMMERCIAL-LICENSE.md` as the reference template its own opening notice says it is. Neither
agreement was edited.

**Repaired in the template.** `COMMERCIAL-LICENSE.md` section 4 waived attribution without saying whose: "Attribution
is not required in end-user-facing software unless mutually agreed in writing." Section 2 of the same document says
third-party obligations continue to apply, so the two are consistent read together and section 4 is not read alone. The
template now scopes the waiver to the licensor's own attribution and states that the licensor has no power to waive an
upstream one. The checkout agreement records acceptance and is never edited after publication, so it is unchanged.

**Already correct, and now propagated:** `COMMERCIAL-LICENSE.md` line 31 limits the grant's scope.

> This grant covers only the code and model artifacts authored by Licensor. It does not extend to
> third-party components bundled with Mailwoman … Any attribution, share-alike, or other obligations
> attaching to those third-party components continue to apply and are not waived or relicensed by
> this Agreement.

The public license page carried no equivalent sentence. It now carries a section stating that the
commercial grant covers the code and model artifacts Sister Software authors, that third-party
components stay under their own licenses, that attribution and share-alike obligations attaching to
them continue to apply, and that separately downloaded reference data carries the terms of whoever
published it.

### Four packages omit the commercial branch

`es-es`, `it-it`, `ja-jp` and `zh-cn` declare `AGPL-3.0`. The other nine, and every other workspace
in the repository including `@mailwoman/core` and `@mailwoman/codex`, declare
`AGPL-3.0-only OR LicenseRef-Commercial`.

The field has two defects. `AGPL-3.0` is a deprecated SPDX identifier, superseded by
`AGPL-3.0-only` and `AGPL-3.0-or-later`, so it does not say which of the two applies. In addition,
`docs/src/pages/license.mdx` line 11 says "every release ships under both", which those four
manifests contradict.

The repository's own admissibility function already refuses the identifier. On this tree,
`assertAdmissibleLicenseExpression("AGPL-3.0")` throws, and `summarizeLicense("AGPL-3.0")` returns
`recognized: false` with `unrecognized: ["AGPL-3.0"]` and an empty obligation list. That function
guarded spatial-layer manifests, and nothing had applied it to a package manifest.

**Repaired.** The four fields now read `AGPL-3.0-only OR LicenseRef-Commercial`, `docs/package.json`
gained the field it lacked, and the `package-license` repository check refuses a workspace manifest
that declares no license, declares an identifier the obligations table does not know, or declares an
expression other than the root's. The four packages have not been republished, so the versions on npm
still carry the old field.

### Twelve model cards carry a version their manifest does not, and the card says which series it is

Every published package's model-card version differs from its manifest version, `fr-fr` most widely
at 6.5.0 against 10.0.0.

**Correcting an earlier reading in this document.** The first version of this section called all
twelve a release-engineering defect. For the graph packages, that reading is wrong. Two version
series exist by design, and `docs/records/site-2026-08/releases.mdx` documents them. Its current row
reads `**10.0.0** (current) · model 9.1.0 (unchanged)`, which describes a code-only release over
unchanged model bytes.
`mwops release verify-metadata` keys its three surface checks off the card version rather than the npm
version for exactly that reason, and `fetch-hf-weights` names the Hugging Face directory
`<family>/v<card version>/`. Forcing the numbers equal would break both.

What the cards did not state is which series a given number belongs to. Two packages ship a model
graph: `en-us` at card 9.1.0 and `cjk` at card 0.0.3. Ten are data-only overlays declaring
`mailwoman.baseWeights`, and an overlay's card version names that overlay's own artifacts while the
graph its rows decode through is the base package's. Nothing in a published tarball said which of the
two a reader was holding.

**Repaired.** Each published package's generated `PROVENANCE.json` carries `version_series`, derived
from `mailwoman.baseWeights` rather than asserted, together with a sentence stating what that series
means and how it relates to `package_version`. The numbers are left free to differ.

`en-us` records four in `files_md5` — `model.onnx`, `tokenizer.model`,

of its two. The remaining ten packages record none of their 48. Summing the table's data-artifact
column gives 62, and 6 of 62 is 9.7%.

`en-us` ships artifacts with separate lineages, and one `data_attribution` list covered all of them.

**Repaired.** Each package's `PROVENANCE.json` now carries a role per artifact, derived from the

calibration tables, a US postcode binary, a placetype-pair index, two gazetteer FST binaries and four
lexicons. A model graph derives from the corpus a training run read. A tokenizer derives from the text
it was fitted on. A pair index and a postcode binary are each built from one named register. Each
of these has its own provenance, and the record no longer covers them with one list.

### Two packages carry training attribution, under two different keys

`en-us` has ten entries at `training.data_attribution`. `cjk` has six at a top-level `attribution`.
Those are the two packages that ship a model graph. The ten overlays record none, which is consistent
with inheriting a graph and says nothing about the artifacts each overlay ships itself.

The table above counted `en-us` alone, because the first reading of these cards looked at
`training.data_attribution` and stopped. Reading one spelling reports the other package as recording

One of those ten entries attributes an artifact that ships in a different package. Entry 1 names
`pair-index-gb.bin` in `neural-weights-en-gb`, attributing it to HM Land Registry Price Paid Data
under OGL v3.0 with Crown copyright and attribution required. `neural-weights-en-gb`'s own card has no

No package shipped a `LICENSE.md`.

**Repaired.** Every published weights package now carries two generated files, written by
`mwops release write-rights-files` and held current by the `weights-rights` repository check.
`LICENSE.md` states the terms this repository grants, that the commercial grant covers only the code
and model artifacts Sister Software authors, and that third-party obligations continue to apply.

entry with the license it names or `null`, and an `unresolved` list. A package whose card records no

attribute. The cross-package case above appears in `en-gb`'s record under
`attribution_recorded_in_another_package`, found by matching each package's artifact filenames against

Generating the files does not satisfy the obligation. `pair-index-gb.bin`'s attribution is still
recorded in another package's card. The fix is to move the entry to the package that ships the
artifact.

found `geonames` records using the same pattern, against the on-disk form `"src:geom":"frgov"`.

These four bundles do not support the Who's On First half of that sentence. The Overture half is a

**Lineage is recoverable.** `source_id` is `wof-<adapter>-<wof_id>-<slot>-<variant>`, so every

name, placetype, country and name variants, which is where the provenance properties stop travelling.

**What the adapters assert.** `packages/corpus/lib/adapters/wof/admin/json/adapter.ts` and

modification of existing open data, that some of those projects do require attribution, and that
"linking back to this License is required". Whether the emitted strings fall inside the original-work
part is a reading this document does not make.

**Scope.** Only the US and FR bundles are in the local data root. GB and DE, the two locales whose
corpus rows are most `wof-*`, are not measured here.

## Publication control

`packages/corpus/lib/utils/license.ts` states the posture:

> exclusion is a deliberate act rather than a silent default. The build includes every row an
> adapter yields … Nothing is dropped on a license string unless the operator named it.

`build.ts` line 238 is `const excludeLicenses = opts.excludeLicenses ?? []`, and no caller in the
repository passes it. `--exclude-share-alike` is an opt-in build flag.

The flag is neither necessary nor sufficient as evidence about a released model. It does not record
which sources contributed, and passing it does not establish that an indirectly included or
misclassified source was caught. A release control needs a reproducible source manifest and an
explicit eligibility decision per input, including inherited checkpoints and auxiliary artifacts.

**Repaired, in three parts.**

A permission is decided per operation. `SourceOperation` names the seven acts this repository
performs on a source — fetch, extract, transform, train, redistribute-data, redistribute-model,
commercial-sublicense — and an elected grant carries a reading per act with the clause it rests on.
An act the grant does not name reads `unreviewed`, never `permitted`, so electing terms establishes
which grant applies rather than that everything under it is allowed.

A corpus build declares what it is for. `BuildProfile.Exploratory` includes every row an adapter
yields, which is what the build always did. `BuildProfile.ReleaseEligible` admits a row only when the
register reports no problem for its source across the four acts ingest performs, and it refuses a
source the register never names. The check runs before augmentation, so a refused source cannot
re-enter as the ancestor of a synthetic row.

A build freezes what contributed. `TRAINING_SOURCES.json` records per source the rows that survived
both refusals, the license stamped on them, and the register's decision as the build read it,
under a digest over itself. `sourcesNotPermitting` is what a publish path asks, and it separates the
three ways a source fails to permit an act. No released model was built from a corpus carrying one.

### Two scope limits kept `data-provenance` from finding it, and one is unstated

The check reads every `data/` directory **that already carries a `PROVENANCE.md`** and reports each
artifact the file omits. `packages/core/data/` had no such file until now, so the directory was
outside the check by construction, as the check's own header states. Four other packages carry
one: `activity-lexicon`, `corpus`, `geographic-model` and `poi-taxonomy`.

The check is also **non-recursive**, which its header does not say: it collects files whose directory
equals the `data/` directory itself. Every artifact in `packages/core/data/` is a level down, in
`libpostal/`, `chromium-i18n/`, `internal/` or `coarse-placer/`. The new record brings the
directory into scope, but the check finds zero artifacts to list and passes. The record itself
states this limit for readers. Making the check recursive requires a separate change to the check.

The Who's On First path was also wrong. Both notice copies sent a reader to a `whosonfirst`
directory directly under `data/`, which holds **0 files** in the tarball. The dictionaries are three
levels in, at `packages/core/data/internal/dictionaries/whosonfirst/`. A consumer following the
notice to find the material found nothing. Both copies are corrected.

reads version `2026-07-22.0` against a published path of `poi/2026-07-20a/`. This page therefore
makes no claim about those bundles from a local read.

Retrieving the National Address Database's disclaimer found a second omission. The page states the
data carries no copyright under 17 U.S.C. § 105 and is available for re-use without limitation, and
it also states that the data "is not intended for use as a mailing list and is subject to individual
state statutes that prohibit it's use as a mailing list". That restriction does not arise from
copyright, so a record stating the copyright status alone loses it, and a postal-address product is
what such a use is about.

### One grant addresses a trained model in its own text

Every other question in this document about whether an obligation reaches a model has to be argued
from what a derived work is. CDLA-Permissive-2.0, the Overture Places grant behind the `poi` bundle,
answers it in two sentences:

> 3.1. This agreement does not impose any restriction or obligations with respect to the use,
> modification, or sharing of Results.

> 5.4. "Results" means any outcome obtained by computational analysis of Data, including for example
> machine learning models and models' insights.

These clauses apply to this agreement only. They do not cover the sources Overture itself drew each
row from, which remain an open question, and they settle nothing for Who's On First, GeoNames,
TIGER/Line, OpenAddresses or Base Adresse Nationale. They show that a grant can answer the model
question in writing. The question stays open for the other sources because their grants do not
address it, and one publisher has answered it.

The `poi` bundle's record now separates the two cases. §2.1 requires the agreement's text to
accompany shared Data, which is an obligation on hosting `poi.db`. The agreement places no
obligation on the model.

GeoNames states its terms twice, and only one statement gives a version. The export readme beside
the files specifies Creative Commons Attribution 4.0, while the about page cites the license without
a version. The record uses 4.0 and says which document it came from, because the conditions differ
across versions of that license.

### The one workspace held for a rights reason had no enforced hold

`packages/osm` is held out of the release pending ODbL counsel sign-off. It is not `private`, and it
declares `publishConfig.access: public`. The hold was membership in `SANCTIONED_RELEASE_ABSENCES` in
`packages/release-kit/lib/release/stage.ts`, a record that `checkReleaseListIdentity` reads so a
missing workspace fails with its name. Nothing on the publish path read it. Running
`mwops release publish-workspace --allow-unplanned` against that directory, or `npm publish` by
hand, would have published it.

**Repaired.** `assertWorkspacePublishable` refuses any workspace the record names, quoting the
recorded reason, and both publish paths call it: `publishWorkspace` before it packs, and
`blessPackages` across every named directory before the first publish. Publishing a held-out
workspace now requires deleting its entry, which a reviewer sees in the diff. The check refuses every
entry, including those held for reasons other than rights. It therefore has no separate
classification of rights-held entries that could drift out of date.

**What this control does not do.** It refuses a workspace by name. It does not decide whether an
artifact's inputs permit publication, and it does not read a provenance record, because no frozen
training manifest exists to read.

### A model upload states its training sources or it does not go out

`mailwoman release hf` in `packages/mailwoman/lib/release-tools/publish-hf.ts` uploads `model.onnx`,
`tokenizer.model`, `model-card.json` and the FST and postcode binaries. It read those files' sizes and
nothing else about them. Uploading is publication, and attribution and share-alike conditions attach
to a source and survive redistribution. The upload is therefore the last point at which to confirm
that a provenance record exists.

**Repaired.** `verifyTrainingProvenance` runs after the artifact checks and refuses a card whose
`training.data_attribution` is absent or empty. The error identifies the card and asks the operator
to record in it the sources the run trained on. Entries without a license are printed with their text
instead of being refused, so the operator sees at publication time which source is unaccounted for.
Missing evidence about a source is a gap to record. A finding against a source is a conclusion that
a person has to reach, and a release control should not make it.

**Correcting a false absence this control first reported.** The first version read
`training.data_attribution` alone and refused `neural-weights-cjk` as recording nothing. That card
records six entries under a top-level `attribution` key instead, naming the Overture CDLA terms, the
National Tax Agency's 利用規約, KOGL Type 1 for the Korean road-name address database, the Korean
permit registry's 이용허락범위 제한 없음, and the Taiwanese Open Government Data License v1.0 together
with the fifteen civil affairs bureaux whose 顯名聲明 that license makes a condition of the grant.

Two spellings exist because the two graph packages were written separately, and the check now reads
both. A control that reports a false absence blocks a release that did not need blocking, and its
report looks identical to a real absence.

Both graph packages pass. `en-us` records ten entries, eight naming a license; the two that do not are
the OpenAddresses PL entry, whose parenthetical reads `public, BDOT-derived`, and the pointer to
`THIRD_PARTY_NOTICES.md`. `cjk` records six, four naming a license; the two that do not state their
terms outside a parenthetical rather than stating none.

## How an operator reads any of this

`mailwoman license attribution` prints the engine's own expression, then per installed package the
sources for the artifacts it ships, the entries it inherits from the package whose graph it decodes
through, and every question that package's record leaves open. `--json` emits the same output for a build
to read. The command states that a commercial agreement covers the code and model artifacts Sister
Software authors and none of the sources below them. It lists any package it did not find instead of
omitting it. It also prints what it does not cover: reference data downloaded separately, and the
fact that a package recording no attribution may still have sources to attribute.

This was verified end to end on this checkout. `npm pack --dry-run` on `neural-weights-en-gb`
includes `LICENSE.md` at 2.1 kB and `PROVENANCE.json` at 5.6 kB, so the records in the next release
will reach consumers. That result applies to this checkout. The next section describes what is on
npm today.

## What the tarballs already on npm carry

The generated rights files were written after `10.0.0` was published, so no published weights package
carries one. Measured 2026-09-21 by unpacking the registry's own tarballs:

| package                                  | `LICENSE.md` | `PROVENANCE.json` |
| ---------------------------------------- | ------------ | ----------------- |
| `@mailwoman/neural-weights-en-gb@10.0.0` | absent       | absent            |
| `@mailwoman/neural-weights-en-us@10.0.0` | absent       | absent            |
| `@mailwoman/neural-weights-cjk@10.0.0`   | absent       | absent            |
| `@mailwoman/neural-weights-ja-jp@10.0.0` | absent       | absent            |

`en-gb@10.0.0` ships eleven files: `README.md`, `model-card.json`, `package.json` and eight data
artifacts. A consumer who installed it holds the model card, which records attribution for `en-us`
rather than for the artifacts in front of them, and nothing that states the terms or the open
questions.

`@mailwoman/core@10.0.0` does ship a `THIRD_PARTY_NOTICES.md`, and its text is the one corrected on
2026-09-21: it attributes the tokenizer, the rule-based classifiers and the solver to Pelias Parser,
where the classifiers and `ExclusiveCartesianSolver` were removed in v7.0.0 and are in no published
package, and it links to the MIT license rather than reproducing the notice MIT requires accompany a
copy.

The next release corrects both, and the existing tarballs stay as they are. A published tarball is
immutable, and none of these has been altered. A consumer holding `10.0.0` can read the record in the
repository at that tag, or install the version that carries the files.

## What the record leaves open

Each published package's `PROVENANCE.json` lists the open questions that apply to it, so the record
ships with the tarball instead of existing only in this document. A package with no recorded training
attribution reads `none-recorded-in-this-package`. An artifact with no recorded digest reads
`unrecorded`.

No package is recorded as cleared. Missing evidence is recorded as missing, and it is neither evidence
of compliance nor evidence of infringement. Which license a given upstream value implies, and which
obligations follow from it, are readings this document does not make.
