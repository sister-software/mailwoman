# Performance: what moves parse throughput

> **In Node, one parse cannot overlap another in the same process. Only worker threads increase
> throughput.**

The two usual ways to speed up a parser are to batch the work or to run it concurrently. Neither one
improves throughput in this system, and the reasons are not visible from the call site. This page
records the measurements, so anyone considering a batch path can read them first.

The measurements were taken on 2026-07-16 against the v6.3.0 model shipped at the time
(`v264-country-softguard`, int8) on a 16-core machine. They still apply to the current 6.5.0. Every
release since then has changed only the weights on the same int8 graph shape, and parse latency
depends on the graph shape alone.

## Where the time goes

The ONNX forward pass takes **93.2% of a parse**. Tokenizing, the anchor/gazetteer/country channel
lookups, Viterbi, and building the tree add up to 0.25 ms, under 7% of the wall clock.

If the forward pass took no time, parsing would be 14.6x faster. Every change below tries to capture
part of that 14.6x, and every one fails for the same reason: the forward pass never sits idle waiting
on anything. ONNX Runtime already uses **8.02 cores on a single batch=1 inference**, so no idle
capacity remains to use.

## Concurrency does nothing

Throughput stays at 1.00x from one worker to sixteen, for both parse and full geocode:

| workers | parse addr/s | scaling |
| ------: | -----------: | ------: |
|       1 |        274.0 |   1.00x |
|       2 |        276.1 |   1.01x |
|       4 |        279.4 |   1.02x |
|       8 |        274.6 |   1.00x |
|      16 |        274.5 |   1.00x |

Two things block the thread, and either one alone is enough to prevent overlap:

- **`onnxruntime-node`'s `session.run()` blocks the JavaScript thread.** It does not hand work to the
  libuv pool. `Promise.all` over N inferences runs them one after another, for any N.
- **`node:sqlite` reads are synchronous** by design, because the resolution ladder is a sync
  interface (see [ARCHITECTURE](./ARCHITECTURE.mdx)). The resolve half of a geocode also blocks.

Scaling stays between 1.00x and 1.02x at every worker count. Contention would produce a declining
curve. A flat line
means that no work overlapped.

For this reason, `MAILWOMAN_BATCH_CONCURRENCY` was removed on 2026-07-16. It defaulted to 8 and was
documented as a tuning knob, but it had never had any effect. Setting it to 1 and to 16 produced the
same throughput to three digits. `POST /v1/batch` is now an explicit sequential loop, which is how it
had always behaved in practice.

The same change works in Python, where `intra_op=1` plus 16 threads gives 1.64x, because Python's ORT
binding releases the GIL during a run. That result does not transfer to Node, because the Node
binding behaves differently.

## Batching does not pay

The obvious counterexample is [deepparse](https://deepparse.org/), which parses at 3.1 ms/addr
batched against 32.5 ms sequential, a 10x improvement. That 10x comes from amortizing per-call Python
and torch overhead. Mailwoman does not have that overhead, so batching has nothing to amortize. Our
sequential path (~300 addr/s) already matches deepparse's batched throughput (320 addr/s) and has
4.7x lower latency than its sequential path.

These results were measured on the shipped int8 graph, re-exported so that it could accept a batch:

| batch | ms/addr | addr/s | scaling |
| ----: | ------: | -----: | ------: |
|     1 |    3.29 |  304.1 |   1.00x |
|     4 |    2.93 |  341.7 |   1.12x |
|     8 |    3.30 |  303.5 |   1.00x |
|    32 |    4.64 |  215.6 |   0.71x |
|    64 |    5.33 |  187.7 |   0.62x |

Throughput peaks at 1.12x and then declines. fp32 behaves the same way (1.24x at B=4). Batching
raises arithmetic intensity, which helps when cores sit idle waiting on memory, and our cores do not.
Above B=8, the working set no longer fits, and throughput drops.

**On CPU, do not build a batching path.** On GPU or WebGPU the arithmetic intensity differs, and
batching could plausibly help, but nobody has measured it. Treat that as an open question.

## A `batch` axis that isn't

`export_onnx.py` requests a dynamic batch dimension on all eight inputs. Until 2026-07-16, the export
silently ignored that request. The graph advertised `['batch', 'sequence']` on every input while its
outputs were fixed at `[1, 'sequence', 33]`, and any batch above 1 failed inside an attention
reshape:

```
Input shape:{64,4,1152}, requested shape:{64,1,3,384}
```

That `1` is the batch dimension, traced in as a literal.

The cause is **`torch.export`'s 0/1 specialization**. `torch.export` always specializes a dimension
of size 0 or 1 to a constant, even when `dynamic_shapes` marks it dynamic. The export traced with
batch=1 example inputs, so it discarded the dynamic request but still labeled the input `'batch'`.
The metadata was therefore wrong. Tracing with batch=2 fixes it:

```
dummy_batch=1  logits_out=[1, 'sequence', 33]        B=4:FAIL
dummy_batch=2  logits_out=['batch', 'sequence', 33]  B=4:OK  B=32:OK
```

The code therefore calls `export_to_onnx(..., dummy_batch=2)`. The parameter defaults to 1, so the
shipped artifact is unchanged, and the batch=2 re-export reproduces it byte-for-byte at 39.4 MB. The
fix is in the tree because an artifact whose metadata advertises a capability it lacks misleads
anyone who trusts that metadata. No batching feature is planned.

Do not try to reproduce the specialization with a small model. A minimal reshape repro exports
correctly at batch=1 on torch 2.13. The failure comes from the transformers attention internals, so
only the real checkpoint shows it.

## What works

Only moving work across a thread boundary increases throughput.

[`geocodeStream`](https://github.com/sister-software/mailwoman/blob/main/mailwoman/geocode-stream.ts)
already does this. It is an async iterator over a `spliterator` worker pool. Each worker builds its
own classifier and lookups, and results are yielded in completion order.

Expect a modest gain. Geocoding is memory- and I/O-bound on a shared multi-gigabyte database. A
measured NPPES sweep peaked at **two workers (~1.4x)** and degraded after that: four workers matched
the baseline, and six gave no gain. Each worker also pays for its own 38 MB session and its own open
database. Measure the worker count on your own data and machine instead of defaulting to
`availableParallelism()`.

Parse-only threading has no database and no contention, so it should scale further than geocoding.
Nobody has measured it. In Python, `intra_op=2` with 8 threads reached 1.57x. That result suggests
the likely shape of the curve, but it is not a figure to quote.

## Before you re-measure

Avoid two mistakes, both of which produced a wrong answer during the original sweep:

- **Warm up, and repeat.** A single cold run showed concurrency at 1.19x on the geocode path and
  nearly led to keeping the concurrency setting. Repeated runs showed no trend, and `c=1` beat `c=8`
  half the time. The spread across identical configs is ~13%, wider than most effects worth
  investigating.
- **Instrument the real runner.** The forward-pass split needs `classifier.cfg.runner`.
  Instrumenting the wrong field reports 0 ms and 0%, which looks like a measurement but means the
  code measured nothing. This is the same class of bug as
  [the meaning of zero](./the-meaning-of-zero.mdx).

The probes live in `scratchpad/` on the branch that produced this page: `batch-export-probe.py`,
`ort-threads-probe.mjs`, `parse-profile.run.ts`, `parse-concurrency.run.ts`, `parse-cpu.run.ts`.

## CLI cold start versus a warm stream

Measure the installed executable directly when profiling Mailwoman, because `npx` adds package-runner startup time
that is not part of `mw` itself. `hyperfine` repeats whole-process launches (process-cold, normally
filesystem-cache-warm):

```bash
hyperfine --warmup 0 --runs 10 \
  './node_modules/.bin/mw geocode "3215 SE Clinton St. Portland OR" >/dev/null'
```

Add `--timing` to break down the wall time. Diagnostics go to stderr, so the result on stdout stays valid JSON:

```bash
./node_modules/.bin/mw geocode --timing \
  "3215 SE Clinton St. Portland OR" >/dev/null
```

The report separates the launcher/CLI import graph, session import, one-time session initialization (weights, resolver,
backends, optional providers, priors), and the warm parse/resolve phases.

The launcher and router import only the selected command. Root and group help list command paths without importing
their implementations, and detailed command help imports only that command and the help renderer. A large CLI-import
time therefore comes from the selected command's own static dependency graph.

To measure persistent sequential throughput, feed one address per line. The command initializes once and emits one
compact JSON object per line:

```bash
/usr/bin/time -v sh -c \
  './node_modules/.bin/mw geocode --stdin < addresses.txt > /dev/null'

pv -l addresses.txt | ./node_modules/.bin/mw geocode --stdin | pv -l >/dev/null
```

To compare the two directly, run both under `hyperfine`. Repeated processes pay the cold start for every address, while
stdin pays it once:

```bash
hyperfine --runs 5 \
  'while IFS= read -r address; do ./node_modules/.bin/mw geocode "$address"; done < addresses.txt >/dev/null' \
  './node_modules/.bin/mw geocode --stdin < addresses.txt >/dev/null'
```

`xargs -P` measures capacity under concurrency, which is a different quantity from warm sequential throughput.
