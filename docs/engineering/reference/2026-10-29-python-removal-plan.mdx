# Python removal plan

This plan implements issue #2874. The issue decides the outcome: the repository ends with zero tracked Python
implementation, test or generator files, without a Python manifest or the `mtf-py` binding, and with a Rust trainer,
Python-free ONNX export and int8 quantization, and a TypeScript launcher. A capability is retired only by an explicit
product decision. A language port keeps every feature in place. Read the issue in full before starting a phase,
with `gh issue view 2874`.

Every claim below is tagged **observed** (read from the tree at `9a2220290`, the head of `origin/main` on
2026-10-29, or from a tool result on that date), **inferred**, **decided** (a choice this plan makes that the
operator may override) or **unknown**. Where the issue corrects the earlier host-local draft, this document records
the correction and the source that confirms it.

### 2.1 Node sampler integration (decided, confirmed by F3)

`packages/mtf/crates/mtf-wasm` builds for `wasm32-unknown-unknown` (**observed** in
`packages/mtf/tools/build-wasm.run.ts` lines 6 and 24) and depends only on `mtf-core`. The browser tokenizer
artifact stays that way, without filesystem or parquet dependencies. The sampler's Node consumers (the
`epoch_mixture` audit, exposure `replayed_draws`, loader profiling) use a native Node binding,
`packages/mtf/crates/mtf-node` built with napi-rs. It is published as an optional platform package only if a consumer
outside the repository needs it. Inside the repository it builds from source with the pinned toolchain the way
`mtf-py` does today. A WASI build is rejected because the `parquet` crate's `zstd` and `tokio` features would need
disabling and the file I/O would still need a host shim (**inferred**). Feasibility check F3 confirmed the decision
on 2026-10-29.

**Observed** (F3, lab host, Node v26.2.0, Rust 1.99.1, napi 3.15): `mtf-node` builds with
`cargo build --profile node --locked -p mtf-node` in 83 s from a clean `node` profile, to a 10.7 MB
`libmtf_node.so`. `packages/mtf/tools/sampler/native.ts` builds the addon on first use and opens it with
`process.dlopen`. Supported platforms are Linux (`.so`) and macOS (`.dylib`); the loader refuses any other host.
Installation needs only the Rust toolchain `rust-toolchain.toml` pins. Each stream (`Sampler`,
`TrainingBatches`, `RawRows`) hands out the chunk the caller asks for, and the observer events are drained per chunk
with `takeEvents()`. `cancel()` ends a stream with the `Cancelled` status.

- Parity: `sampler-parity.run.ts verify` reproduced `c6-train-2k` with 2,000 of 2,000 row identities equal, 16 batch
  sizes equal, and 0 differing rows over all 15 tensors, including `locale_ids` and `address_system_ids`, which
  TypeScript computes. `aug-postcode-move-5k` (4,999 rows), `c6-gold-tokens-5k` (5,000) and `code-unit-train-5k`
  (5,000) also verified with 0 differing rows. `c6-train-2k` took 34.5 s, at a peak RSS of 2,408 MB.
- Memory: the C6 config's train split, seed 43, with the sha256 cache, streamed in 1,024-row chunks. Over 100,000
  requested rows (99,980 yielded after the astral skip), RSS was 1,955 MB at 10,000 rows and 1,988 MB at 90,000 rows,
  and peak RSS was 1,988 MB. Over 1,000,000 rows, RSS went from 1,996 MB at 100,000 rows to 2,096 MB at 900,000 rows,
  and peak RSS was 2,096 MB. The stream takes 28 to 29 s to open, and what it opens holds most of that memory: the source index and
  the 131,072-row shuffle buffer. RSS does not grow with the rows read.
- Browser artifact: `cargo tree -p mtf-wasm --target wasm32-unknown-unknown` lists `mtf-wasm` → `mtf-core` with and
  without `mtf-node` in the workspace. The wasm build gives SHA-256 `6ee2b5b7…` (86,713 bytes) both ways. The
  committed `wasm/mtf.wasm` (`4f3c9bd4…`) is already stale on `origin/main` at `7b69d33ce`, before this change.

### 3.1 Cross-language reference serialization

Reference records use canonical JSON: UTF-8, keys sorted, whitespace limited to what the grammar requires,
integers as JSON integers, floats as the shortest round-trip decimal (`Number.prototype.toString`, Python `repr`,
Rust `ryu`), `null` for a missing field, strings as code points. Offsets are recorded as code-point offsets with an
explicit `offset_unit: "code_point"` field. The serving side converts to UTF-16 in `packages/neural/lib/tokenizer.ts`,
and that conversion is the one place the two units meet. A record stores the source revision, every input path with
its SHA-256 and order, the config, runtime versions, emitted counts, output schema, and either the expected rows or
arrays, so a mismatch report identifies the first differing row, field, tensor or element.

### 3.3 Trainer staged comparison

The issue fixes the order. Each stage passes before the next starts, over this matrix: supervised and MLM, `use_crf`
on and off, each channel on by itself and all channels on, the char path, fp32 and the configured autocast dtype,
and `grad_accum_steps` 1 and 4.

1. Load the reference checkpoint's parameters into both models and assert every tensor equal by bytes.
2. Forward on the saved batches: logits, CRF scores and auxiliary heads within 1e-5 relative in fp32.
3. Loss components (CE, CRF, locale, address-system, MLM) within 1e-5 relative, with identical mask semantics.
4. Gradients per parameter within 1e-4 relative after one backward.
5. One AdamW step with identical hyperparameters and parameter groups: parameters within 1e-6 absolute, and
   schedule values equal at steps 0, 1, 100, warmup end, max.
6. Save and restore a checkpoint in the Rust format, with forward equality after restore and the
   `find_latest_checkpoint` semantics (`training_state.json` marks completeness) preserved.
7. 2,000 deterministic CPU steps from the reference checkpoint with batches from the Rust sampler: the loss column
   of `train_log.csv` within 1e-3 relative at every logged step. Divergence beyond that is investigated and
   classified before acceptance.
8. One approved GPU run of a current recipe, graded by `training-arc` and `eval-model` against the registered
   release requirements in `docs/engineering/CONTRIBUTING_MODEL_WORK.mdx` and the split rules in
   `docs/engineering/HOLDOUT_AND_EVALUATION.mdx`. One successful run is evidence for the trainer. Release
   eligibility is decided by that procedure.

The runtime question is separated from the language question. The repository pins `torch==2.12.0` (**observed**
in `pyproject.toml`), and `tch` 0.26.0 requires libtorch v2.13.0 (**observed** on docs.rs). F1 therefore first
looks for a `tch` release that pins libtorch 2.12 (the 0.25 line, **unknown** until checked). If none exists, Phase 0
adds a Python reference run on torch 2.13 so the comparison in stage 7 is same-runtime, and the 2.12 → 2.13 upgrade
is recorded as its own change with its own export and runtime checks.

### 4.1 F2 result: the Rust exporter and quantizer

Observed on 2026-10-29 on the lab host. The exporter is `packages/trainer/crates/trainer-export` in the new cargo
workspace `packages/trainer`, which has no npm package because no JavaScript module imports it. It reads
`pytorch_model.bin` directly with a zip reader and a pickle machine that records `REDUCE` calls without running
them, so no converter to safetensors was needed. Both checkpoints store bfloat16 tensors, which the reader widens to
float32 exactly, as `load_state_dict` does. It writes the graph with prost types generated from `onnx.proto` of onnx
1.22.0. The quantizer follows onnxruntime 1.30.0's `quantization/` source for `quantize_dynamic(QInt8)` with its
defaults: the `Gemm` to `MatMul` rewrite, `MatMulInteger` with `DynamicQuantizeLinear`, uint8 `Gather` tables, and
the scale and zero point arithmetic in the same float32 and float64 steps.

```bash
cargo run --release --manifest-path packages/trainer/Cargo.toml -- export-onnx --checkpoint <dir> --output fp32.onnx
cargo run --release --manifest-path packages/trainer/Cargo.toml -- quantize --input fp32.onnx --output int8.onnx
node packages/neural/tools/onnx-export-parity.run.ts --weights-overlay <root> --reference <a.onnx> \
  --candidate <b.onnx> --rows <heldout rows.jsonl> --count 1000 --tolerance 1e-3 --out receipt.json
```

The reference is the pinned exporter run on the lab CPU: torch 2.12.0, onnxscript 0.7.2, onnx 1.22.0, onnxruntime
1.30.0, CPython 3.12.3, `export_to_onnx(opset=17, max_length=128)` and then `quantize_dynamic_int8`. For en-us 10.7.0
(`output-v7100-gb-county-s42/checkpoints/step-060000`, read from the volume) the reference fp32 and int8 are byte for
byte the shipped candidate and the quantized artifact. For arm B (`v830-base-c6-90k-mixed-s42` step 90000) the
reference int8 is byte for byte the `model.onnx` beside the checkpoint on the data root.

runtime parses each row and the tool records the feed it builds, with the token ids, mask, five channels and hint.
Every other row is parsed with its own country as `localeHint`, for 500 hinted probes. Arm B's feeds use its c6
tokenizer. Every tenth probe is also run trimmed to its real length, so the `sequence` axis varies.

The shipped en-us int8 measured 43.7 ms p50 and 46.1 ms p95 on the same host in the same session. The SLO suite
has no WebGPU arm, so the WebGPU constraint is untested. The quantizer's unit tests cover the stale `value_info`
case: an annotation that contradicts the graph is dropped and the output is identical to the one without it. The
dynamo graph's 514 annotations pass through the same path.

What does not match, and why:

1. **Graph bytes, node names and initializer names** differ, which §3 permits. The Rust fp32 graph has 105
   initializers and 18 `Reshape` nodes, against 115 and 72.
2. **The fp32 logits differ by up to 4e-5.** onnxruntime's optimizer fuses `input_ln` and `final_ln` into
   `SkipLayerNormalization` in the reference fp32 graph and only `final_ln` in the Rust one (observed in each
   session's optimized graph). That fusion is inferred to cause the difference. The int8 graphs get the same single
   fusion and agree exactly.
3. **Shape annotations change int8 numerics.** Without `value_info`, onnxruntime does not fuse `final_ln`, and the
   int8 `logits` move by up to 2.68e-2 for en-us and 3.49e-2 for arm B. The reference int8 with its `value_info`
   removed gives the same numbers, and the Rust quantizer's output without annotations equals it exactly. So the
   quantizer writes the shapes onnx's inference would write (`trainer-export/src/shape.rs`, including onnx's `unk__`
   symbols), as `quantize_dynamic` saves them. A change to those annotations is a change to int8 output.
4. **Batch size.** Both graphs declare dimension 0 of every output as 1, as torch.export specialized it. The
   reference graph refuses a batch of two (`Attempting to broadcast an axis by a dimension other than 1. 128 by 256`
   at `node_add_440`); the Rust graph computes it. The runtime feeds one row per run, so no served output changes.
5. **Not built yet:** the char path's CharCNN, the span scorer's `span_scores`, the affix and dependent-locality
   heads, and `inject_first_token`. The exporter refuses each by name. The quantizer refuses `Conv`, `Attention`,
   `LSTM`, `EmbedLayerNormalization` and subgraphs, which onnxruntime would quantize.

The Rust export took 0.49 s and 0.57 s with peak RSS 246 MB and 322 MB, and quantization 0.48 s and 0.64 s. The Python
export was not timed. The shipped artifacts and the Python export path are unchanged.

### 4.2 F1 result: `tch` and libtorch on the lab CPU

Observed on 2026-10-29 on the lab host (Ryzen 9 8945HS, AVX-512, `torch.backends.cpu.get_cpu_capability()` =
`AVX512`).

**Version.** No `tch` release links libtorch 2.12: `tch` 0.24.0 pins 2.11.0 and 0.26.0 pins 2.13.0 (`torch-sys`'s
`TORCH_VERSION`, observed in both crates), and there is no 0.25 release on crates.io. **Decided:** the Rust trainer uses
`tch` 0.26.0 with libtorch 2.13.0, and the Python reference for every comparison runs on `torch==2.13.0+cpu` in a
separate environment, so the language comparison is same-runtime. The repository pin stays `torch==2.12.0` until the
upgrade is made as its own change with its own export and runtime checks (§3.3).

**Download and build.** `libtorch-shared-with-deps-2.13.0+cpu.zip` is 126,385,248 bytes (SHA-256
`edbf4cbed78433d803e90a65f1752e57783d164bce66c95c0872b2ab8f5c159e`) and 479 MB unpacked; it downloaded in 63 s. The
build reads it from `LIBTORCH`. A cold release build of `trainer-cli` into an empty target directory (164 crates,
including `torch-sys`'s C++ wrapper and the shim, with the crate sources already downloaded) took 1 min 24 s at
`cargo -j 4` and a host load average of 5.7; the `trainer` binary is 17.6 MB and links the libtorch shared objects at
run time (`LD_LIBRARY_PATH` or an rpath).

**What `tch` does not expose.** `trainer-model/csrc/autocast.cpp` is a C++ shim compiled against the same headers. It
provides per-device autocast (`tch::autocast` switches CUDA only), `torch.is_grad_enabled()` for the
`MultiheadAttention` fast-path choice, `grad = None` for `zero_grad(set_to_none=True)` (AdamW skips a parameter without
a gradient, so a zero gradient would decay it), `linalg_vector_norm` for `clip_grad_norm_`, and a private CPU
generator for the MLM mask.

**Block, optimizer and schedule.** `python -m mailwoman_train.audits.trainer_parity f1` builds one `EncoderBlock`
(384 hidden, 6 heads, 1,536 intermediate) from seed 0, runs it in eval mode with and without gradients (the fast path
`torch._native_multi_head_attention` and the slow path through `scaled_dot_product_attention`), backpropagates a fixed
cotangent, and takes three train-mode AdamW steps (lr 5e-4, weight decay 0.01) with `clip_grad_norm_(1.0)` under the
cosine `LambdaLR` (warmup 2, max 10). `trainer parity f1` repeats it in Rust at the same thread count. Every tensor is
bit-identical: the construction draws, both eval paths, the dropout masks, every gradient, every AdamW update, the
rates and the clip norms (0 difference on every element). `trainer-loop/tests/f1_block.rs` runs the same check in CI
on a 32-hidden fixture under the §3.3 tolerances.

The CUDA image build was not run; it needs the operator's spend approval.
