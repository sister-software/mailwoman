# Component Schema

This document defines the canonical `ComponentTag` union. Where another document disagrees, this one wins.

**Rule:** any change to this file requires:

1. A written rationale in the commit message.
2. A migration plan for existing corpus rows tagged with the old schema.
3. A check that downstream alignment, training, and inference code is updated in the same commit.

## Tag inventory

### Universal (Phase 1, all locales)

| Tag                  | Description                                             | Example                         |
| -------------------- | ------------------------------------------------------- | ------------------------------- |
| `country`            | Sovereign state name or code                            | `USA`, `France`, `FR`           |
| `region`             | First-level admin (state, région)                       | `OR`, `Île-de-France`           |
| `locality`           | City, town, commune                                     | `Portland`, `Paris`             |
| `dependent_locality` | Sub-locality (neighborhood, arrondissement, ward)       | `Brooklyn`, `8e arrondissement` |
| `postcode`           | Postcode                                                | `97215`, `75008`                |
| `subregion`          | Optional county-level admin between region and locality | `Multnomah County`              |

### Street-level (Phase 2)

| Tag                      | Description                                    | Example                            |
| ------------------------ | ---------------------------------------------- | ---------------------------------- |
| `house_number`           | Building number on a street                    | `6220`, `12bis`                    |
| `street`                 | Street name proper, without its type           | `Salmon`, `République`             |
| `street_prefix`          | Directional or descriptive prefix (Anglophone) | `SE`, `North`                      |
| `street_prefix_particle` | Non-English grammatical particle (FR)          | `de la`, `du`, `des`               |
| `street_suffix`          | Street type suffix (Anglophone)                | `Street`, `Boulevard`, `Ave`       |
| `intersection_a`         | First street of an intersection query          | `5th Ave` (in "5th Ave & 42nd St") |
| `intersection_b`         | Second street of an intersection query         | `42nd St` (in "5th Ave & 42nd St") |
| `unit`                   | Apartment, suite, floor                        | `Apt 4B`, `Suite 200`, `5e étage`  |

#### The US street split is canonical — `street_suffix` is its own span

> **The terminal-suffix rule (operator-ratified 2026-08-06).** Apply only the terminal street suffix.
> Earlier suffix-like tokens remain part of the street name unless they are the final suffix element.
> Preserve post-directionals separately. So `Finel Hollow Road` → street `Finel Hollow` + suffix `Road`,
> while `Sutton Hollow` → street `Sutton` + suffix `Hollow` (terminal there) — the arrival of a later
> suffix reverts the earlier ambiguous token to the name. Suffix spans never extend beyond one word;
> a model emitting `Hollow Road` as a suffix is making a suffix-BOUNDARY error rather than a recognition error.

For a **US** address the street type is a SEPARATE span. `6220 SE Salmon St` is four components rather than two: `house_number: "6220"`, `street_prefix: "SE"`, `street: "Salmon"`,
`street_suffix: "St"`. `street` never carries the type.

The split is defined by the USPS Publication 28 Appendix C table in
[`packages/codex/lib/us/street/suffix.ts`](../../../packages/codex/lib/us/street/suffix.ts). `matchTrailingSuffix` is the only
implementation, and no other code copies the table. The table is why the split is canonical rather than
cosmetic. Canonicalization (`Aven` / `Avenu` / `Avnue` all mean `AVENUE`), abbreviation preference
(`AVE` is what the post office prints), and the formatter's conversion between the two forms all
depend on the suffix being its own span. If the suffix is folded into `street`, none of them work.

Two conventions follow from the table, and measurement established both:

- A trailing **post-directional joins the suffix**: `Pennsylvania Avenue NW` is
  `street: "Pennsylvania"`, `street_suffix: "Avenue NW"`. There is no post-directional tag, and this
  is what the corpus adapter emits (`corpus/src/adapters/tiger/street-decompose.ts`).
- A **bare** post-directional with no type before it is not a suffix: `Seymour East` stays folded.
  A directional is not a Pub-28 suffix, and the rows in that class are unit-contaminated
  (`1ST AVE SW BOX E`, where the trailing `E` is a box letter).

This section deliberately leaves the FR convention open. French street typology comes first
(`Rue de la Paix`) and has its own vocabulary. The FR golden labels only 7 of 665 street rows with a
`street_prefix`.

Three components read this convention, and they must agree with each other:

1. **The corpus** splits — TIGER's adapter and the `street-affix` corpus recipe both do.
2. **The golden answer key** splits, from **v0.1.3** onward (`data/eval/golden/v0.1.3`, relabelled
   from v0.1.2 by `mailwoman corpus golden-relabel`). The version's `MANIFEST.json` declares it in
   `convention.street_convention`.
3. **The scorer** reads that declaration. `packages/mailwoman/lib/dev-tools/per-locale-f1.run.ts` folds
   `street_prefix`/`street`/`street_suffix` back into one string only for rows whose country is not
   declared split. A split-convention key is therefore graded on the separate spans.

Golden v0.1.2 and earlier folded the street, and per-locale-f1 joined the model's spans to match. That
mismatch changed a release verdict. The v9.0.0 candidate read `us.street` 87.4 against an 87.8 floor and failed
the eval floor because of a convention disagreement rather than a model regression. On v0.1.3 the same two models read
71.7 (shipped 7.0.0) and 75.2 (candidate), so the sign of the delta flips.

### JP-specific (ACTIVATED — CJK Phase 2, 2026-07-29; the JP sibling model's label set)

| Tag               | Description                     | Example                |
| ----------------- | ------------------------------- | ---------------------- |
| `prefecture`      | JP first-level admin (都道府県) | `東京都`, `Tokyo`      |
| `municipality`    | JP city/ward (市区町村)         | `千代田区`, `Chiyoda`  |
| `district`        | JP district (大字)              | `丸の内`, `Marunouchi` |
| `block`           | JP chōme (丁目)                 | `1丁目`                |
| `sub_block`       | JP banchi (番地)                | `1番地`                |
| `building_number` | JP gō (号)                      | `1号`                  |
| `building_name`   | JP named building (romaji form) | `Tokyo Building`       |

**Activation status (CJK Phase 2, 2026-07-29):** the JP tags are live in the training stack as the `stage3-jp` label set (`corpus-python labels.py`, 47 BIO labels = STAGE3 + these seven). That set is the JP CHAR model's head vocabulary. The Latin model stays on STAGE3 and never emits them. Under the encoder-design D4 rule, compact numbers (`2-3-16`) remain whole-span `house_number`, and `block`/`sub_block`/`building_number` label only the kanji-designator long form (`2丁目3番16号`). The `componentsSupported` field on `LocaleProfile` declares which tags a locale uses. `ja-JP` declares these seven plus `house_number`/`country`/`postcode`.

### CN-specific — organizational units (#2034)

| Tag             | Description                                                                                                | Example                                  |
| --------------- | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| `locality_unit` | The ordinal organizational chain below a named settlement or farm: sub-farm, brigade, team, company, group | `三分场八队`, `一零三团七连`, `民权三组` |

The whole chain is one span, and its generics type each rung. China's rural and state-farm addresses carry a hierarchy that the universal tags cannot represent. Examples include `孟定农场 → 三分场 → 八队` (Mengding Farm → No. 3 sub-farm → No. 8 production team), the XPCC ladder `一四三团十二连` (143rd regiment → 12th company), and the villager group `民权三组`. Five overlapping ladders share the same shape: an ordinal followed by a generic (`分场`, `大队`, `队`, `生产队`, `连`, `团`, `组`, `场部`). A census of the 50,000 CN rows in the coarse-placer data found 328 carrying that vocabulary, and 85 of them were numbered teams without any farm marker (`新合七队`). A tag per rung would grow the schema with every new ladder. The whole ordinal chain is therefore one `locality_unit` span. `@mailwoman/core`'s CN unit reader then reads each generic's rung off the suffix deterministically. The named head unit that the chain belongs to (`孟定农场`, `新合`, `赵光`) is `dependent_locality`. A farm headquarters marker (`场部`) stays inside the chain, because it denotes a point in the unit rather than a further rung. Only the CJK sibling model emits the tag, and the Latin model never sees it. For ancestry, `locality_unit` nests under `dependent_locality`, then `locality`. A `house_number` may attach directly to it (`古北口村南关生产队6号`).

## BIO labeling

For training and inference, each tag `T` becomes two [BIO labels](../../records/site-2026-08/concepts/bio-labels.mdx):

- `B-T` — beginning of a span tagged `T`
- `I-T` — inside (continuation) of a span tagged `T`

Plus one universal label:

- `O` — outside any address component (punctuation, noise, junk)

Example labeling of `"6220 SE Salmon St, Portland OR"`:

```
Token    Label
─────    ─────
6220     B-house_number
SE       B-street_prefix
Salmon   B-street
St       I-street
,        O
Portland B-locality
OR       B-region
```

## Implementation notes

### TypeScript representation

```ts
// packages/core/src/types/component.ts

export const COMPONENT_TAGS = [
	// Universal
	"country",
	"region",
	"locality",
	"dependent_locality",
	"postcode",
	"subregion",
	// Street-level
	"house_number",
	"street",
	"street_prefix",
	"street_prefix_particle",
	"street_suffix",
	"intersection_a",
	"intersection_b",
	"unit",
	// Venue-level
	"venue",
	"attention",
	"po_box",
	// FR-specific
	"cedex",
	// JP-specific (ACTIVATED at CJK Phase 2 — the stage3-jp label set; Latin models never emit these)
	"prefecture",
	"municipality",
	"district",
	"block",
	"sub_block",
	"building_number",
	"building_name",
] as const

export type ComponentTag = (typeof COMPONENT_TAGS)[number]

export const BIO_LABELS = ["O", ...COMPONENT_TAGS.flatMap((t) => [`B-${t}`, `I-${t}`])] as const

export type BioLabel = (typeof BIO_LABELS)[number]
```

The `as const` and derived types are deliberate. They let TypeScript report schema errors at compile time wherever a tag is referenced.

### Validation rule

A `LocaleProfile.componentsSupported` array must be a subset of `COMPONENT_TAGS`. Profile registration checks this at runtime and throws if the check fails.

## Rationale for specific choices

**Why `dependent_locality` and not `neighborhood` or `borough`?** WOF and ISO use `dependent_locality` for the general concept. Names like `borough` are locale-specific. Pick the umbrella term.

**Why split `street_prefix` from `street_prefix_particle`?** English `SE` and French `de la` are grammatically different and synthesis pipelines need to treat them differently. Conflating them produces worse training data.

**Why expose `subregion` if it's optional?** Some US addresses include county (rare in display but common in government data). Modeling it explicitly is better than forcing it into `region` or `locality`.

**Why `cedex` is FR-specific and not subsumed by `postcode`?** A CEDEX designation is a postal routing instruction rather than a postcode. Treating it as one corrupts FR postcode statistics.

**Why were the JP tags listed years-of-phases before activation?** The declarations forced the Phase-0 type design to handle them. As a result, activation at CJK Phase 2 required no changes to core types, as the schema-first principle intended.
