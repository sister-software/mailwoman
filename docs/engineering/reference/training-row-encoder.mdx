# Training-row encoder

The training loader turns each sampled corpus row into the tensors one step reads: piece ids, an attention
mask, label ids, and the soft-feed channels. The channels are the postcode anchor, gazetteer, country,
street type, locality surface and code unit. Since #2870 the encoding runs in Rust, in
`packages/mtf/crates/mtf-channels`, called from Python through the `mailwoman_mtf` extension in
`packages/mtf/crates/mtf-py`. Since #2874 Phase 3 the sampler runs in Rust too, in
`packages/mtf/crates/mtf-sampler`. Every sampling stage draws from one generator, `mtf-sampler/src/pyrandom.rs`,
which reproduces CPython 3.12's `random.Random`, and each stage draws where the Python stage it replaced drew, so a
seed selects the rows the Python sampler selected.

The Rust encoder and the Rust sampler each reproduce the Python code they replaced byte for byte. The encoded tensors
are the model's inputs, so these changes move no model behavior and need no release verdict.

## What runs where

| Stage                                                           | Implementation                                              |
| --------------------------------------------------------------- | ----------------------------------------------------------- |
| Corpus listing, sha256 verification, split attribute, deletions | Rust: `mtf-sampler/src/corpus_files.rs`                     |
| Row-group reads, row filters, country acceptance, coarse filter | Rust: `file_rows.rs` over the `parquet` crate               |
| Source mixture, source restarts, held-out quotas                | Rust: `mixture.rs`                                          |
| Shuffle buffer, astral skip, observer events, `seed + epoch`    | Rust: `sampler.rs`                                          |
| Augmentation and the affix relabel                              | Rust: `augment/`, `relabel.rs`, `emit.rs`                   |
| `source_reps` weights                                           | Rust: `source_reps.rs`                                      |
| Tokenization                                                    | Rust: `mtf-core`, through `mailwoman_mtf.Tokenizer`         |
| Label projection                                                | Rust: `mtf-channels/src/labels.rs`                          |
| Channel painting                                                | Rust: `anchor.rs`, `gazetteer.rs`, `code_units.rs`          |
| Postcode-shape and postcode-syntax finders                      | Rust, the `finders` feature: `finders.rs`                   |
| Packing into arrays                                             | Rust: `encoder.rs`, returned as numpy arrays                |
| The character path (`char_mode != "off"`)                       | Rust: `mtf-sampler/src/char_path.rs`                        |
| `locale_ids`, `address_system_ids`                              | Python, added to the batch in row order                     |
| Tensor conversion                                               | Python: `train/batch.py` wraps each array with `from_numpy` |

The painters and the label projection compile without a regex engine. The serving side can therefore
adopt them later through `mtf-wasm`. That adoption is a separate change, because the serving painters
differ from the training painters in three places:

- `anchoredPostcodeSpans` upper-cases the text before matching, and training matches the raw case;
- `buildSoftFeatures` builds the locality-surface channel only when the street-type channel matched a
  piece, and training always paints it;
- `tokenizer.ts` trims the leading space from a `▁` piece's range, and training keeps it.

Training uses the Rust encoder while serving continues to use the TypeScript painters.

## Interfaces

`mailwoman_mtf.Tokenizer(model_bytes)` loads a SentencePiece unigram model. `encode(raw)` returns
`(id, piece, char_begin, char_end)` per piece in code points. A `▁` piece's range includes the space before
its word. `pad_id`, `unk_id`, `bos_id` and `eos_id` follow SentencePiece. Each is the id of the trainer
spec's piece when that piece has the control type (the unknown type for `unk_id`), and -1 otherwise.
`id_to_piece` and `piece_to_id` match `IdToPiece` and `PieceToId`.

`mailwoman_mtf.RowEncoder(tokenizer, *, max_length, label_to_id, active_tags, ignore_index,
locale_countries, postcode_shapes_path, postcode_syntax_path, ...)` reads each configured lexicon once.
`encode_batch(rows)` returns a dict of C-contiguous arrays:

- `input_ids`, `attention_mask`, `labels`: int64 `[B, L]`;
- per configured channel, `<name>_features` float32 `[B, L, D]` and `<name>_confidence` float32 `[B, L]`.

The arrays own their buffers. `torch.from_numpy` shares that CPU memory, and the arrays stay valid after
later calls. A row with a partial span triple, unsorted, overlapping or out-of-bounds spans, mismatched
token and label counts, or a token absent from its text raises `ValueError` naming the row's batch index
and text. A failed finder match raises `RuntimeError` naming the pattern and the text.
`build_row_encoder` in `corpus-python/src/mailwoman_train/data/loader/encode.py` builds the encoder from a
`DataConfig`.

`mailwoman_mtf.Sampler(config, split, seed, row_limit=None)` opens a split with a generator seeded as
`random.Random(seed)`. `config` is the JSON that `sampler_config` in `encode.py` writes from a `DataConfig`: the
corpus directory, country and source weights, the coarse filter's tags, the augmentation probabilities and exclusions,
the affix lexicon, the postcode layouts, and the data root, volume mount and sha256 cache the corpus listing reads.
Iterating it yields each row as a dict with `raw`, `tokens`, `labels`, `country`, `source` and, for a span-schema file,
`span_starts`, `span_ends` and `span_tags`. `next_rows(n)` returns the next `n` rows, fewer at exhaustion, and an
empty list after. `row_limit` counts rows before the astral skip, as the Python stream counted them. A missing,
unresolvable or unverified file raises `ValueError` naming its path, a corrupt row raises naming the file, the row
group and the text, and `cancel()` stops the stream with `KeyboardInterrupt` at its next row.
`mailwoman_mtf.TrainingBatches(config, batch_size=, seed=, row_limit=, skip_batches=)` yields the train split's
batches without end, reopening the sampler with `seed + epoch` for epochs 1, 2, …, and drops the first
`skip_batches` batches for a resumed run. `mailwoman_mtf.CharEncoder` encodes a batch for the character path:
`char_ids` int64 `[B, S, W]`, and `attention_mask`, `labels` and an all-zero `input_ids` int64 `[B, S]`.

In Rust, `mtf_sampler::Sampler::open(config, split, seed, row_limit)` returns the same stream. `rows()` and
`batches(batch_size)` iterate it, a returned `None` is exhaustion, `open_with` adds a `CancelToken` and an `Observer`
that receives `RowEmitted`, `RowSkipped(reason)`, `SourceRestarted` and `EpochComplete`, and `batch::encode_rows`
encodes a batch through `mtf-channels`.

## Python semantics

The Rust code reproduces the reference interpreter's string semantics rather than Rust's.

- `str.isspace`, `str.isalnum` and `str.isdecimal`, the cased and case-ignorable properties, and the full
  `str.lower` and `str.upper` mappings come from `src/python_text/tables.rs`. The tables are generated
  over every scalar value by `python -m mailwoman_train.text.python_text_tables` (Python 3.12, Unicode
  15.0.0). `test_python_text_tables.py` regenerates them and fails on any difference, so an interpreter
  upgrade that moves a table fails there. Rust's `char::is_alphanumeric` admits marks such as U+0940
  that Python's `isalnum` rejects, and its `is_whitespace` rejects U+001C..U+001F.
- `str.lower` applies CPython's final-sigma rule.
- The finders rewrite `\d`, `\s`, `\w` and `\b` into explicit classes built from those tables before
  `fancy-regex` compiles a pattern, because the Rust engines define `\w` to include marks and connector
  punctuation.
- The code-unit segmenter is written out by hand. It reproduces
  `(?<![A-Za-z0-9])(?=[A-Za-z0-9-]*\d)[A-Za-z0-9]+(?:-(?=\d)[A-Za-z0-9]+)*(?![A-Za-z0-9])`, including the
  lookahead that accepts a non-ASCII digit after the ASCII run.
- Channel values are computed in `f64` and converted to `f32` once, as `torch.tensor(..., float32)`
  converted the Python floats. The anchor posterior is renormalized in the file's key order, with
  serde_json's `float_roundtrip` parsing so every decimal becomes the double Python's `json` produces.

## Parity procedure

`python -m mailwoman_train.audits.encoder_parity capture` draws batches through `iter_batches` and writes a
record under `$MAILWOMAN_DATA_ROOT/audits/encoder-parity/<name>/`:

- `record.json` holds the source revision, the config and its overrides, the SHA-256 of every input
  (tokenizer, each lexicon, the shape and syntax records, the corpus manifest), the runtime versions, the
  requested and emitted row counts, the batch sizes, each row's identity hash, its country, per-channel
  nonzero counts with their denominators, and a SHA-256 per row of every model-input tensor over its
  little-endian bytes;
- `arrays.npz` holds every tensor, so `verify` can report the first differing row, tensor and element with
  both values.

`verify --name <name>` re-draws the sample through the current loader. It fails on a changed emitted count,
row identity, batch boundary, tensor set, dtype or shape before it compares digests. A char-path config
builds no SentencePiece tokenizer: the record hashes its `char_vocab_path` in place of `tokenizer_dir` and
adds `char_ids` to the tensors. The first nine records were captured from the Python encoder at revision
`47495cabf` or `1115bbe3f`, and the six #2874 records from the Python sampler with the Rust encoder at
`553606715`. No record is regenerated from the code it checks. `corpus-python/tests/mailwoman_train/audits/encoder-parity-records.json`
lists every record with its verification against the Rust encoder (`verified`) and the Rust sampler
(`verified_rust_sampler`).

The C6 overrides re-root the lexicons to their host copies. Every CJK char-path corpus on the lab host lists
its files without a sha256, and the loader refuses such a manifest. `char-v8-cjk-regs-5k` therefore reads
`$MAILWOMAN_DATA_ROOT/audits/port-parity/corpora/v8-cjk-regs-2026-09-08-sealed/MANIFEST.json`: the
original manifest's entries, unchanged, with each file's sha256 measured on 2026-10-29.

The grouping records stop short of 5,000 rows because the grouping augmentation raises on C6 rows whose
whitespace tokens do not reach the end of `raw`, in the Python sampler and the Rust sampler alike. At
probability 0.5, seed 43, the stream raises after 250 rows on `insert position 18 is not a token edge
(raw='{114, СНТ «Пчёлка»')`; at 0.05 it raises after 1,994 rows on `'(22 Whampoa East S(338527)'`. No training
config sets `augment_grouping_prob`. The two grouping records were captured by replacing `iter_batch_rows` with
the composition the Python loader ran, `random.Random(seed)` over `stream.iter_rows` with the astral skip, which
reproduced `c6-train-2k`'s row identities and tensor digests exactly before it captured them.

The crate's own tests cover what a sample may miss: `encode_row_reference.rs` against the Python
`encode_row` fixture, `python_reference.rs` against the Python finders and string operations for every
scalar value in 17 templates, and `code_unit_parity.rs` from segmentation through acceptance counts.

Each record verified with 0 differing rows against the Rust encoder (113,920 emitted rows in total). The broad
sample requested 86,864 rows and emitted 81,940: 49,989 of 50,000 train rows after the astral skip, and 31,951
validation rows, where the validation draw exhausts below its 36,864-row limit.

Every record, the nine and the six, verified with 0 differing rows against the Rust sampler on 2026-10-29
(136,158 emitted rows in total): no emitted count, row identity, batch boundary, tensor set, shape or digest
moved. `mtf-sampler`'s tests cover what a sample may miss: `loader_split_reference.rs` replays the Python
loader's recorded fixture in order (train, validation, the char path and source counts), `sampler_stream.rs`
covers row limits, exhaustion, the astral skip, source restarts, held-out quotas, observer events,
cancellation, `seed + epoch` and resume, and the remaining files hold the invariants of the Python data
tests.

### The Rust sampler

Measured on the lab host on 2026-10-29, between 11:52 and 12:06 UTC, with the C6 config, the host lexicon
overrides of the parity records, seed 43, and 40 batches of 128 rows after the first batch. Both arms encode with
the Rust row encoder and convert with `to_tensor_batch`, so they differ only in the sampler: the Python arm runs
`stream.iter_rows` from the parent revision with the astral skip, and the Rust arm runs `mailwoman_mtf.Sampler`.
Both read the sha256 sidecar cache, so neither hashes the 68.7 GB corpus. Each arm ran twice, alternating. The host
was shared with other jobs: the load average was 26 to 30 during the first pair and 18 to 19 during the second, on
16 threads, so the first pair is slower in every column and the second pair is the comparison.

| Run             | Init s | Encoder build s | Sampler init s | Sampling ms | Encoding ms | Conversion ms | Host ms per batch | RSS after init MB | Peak RSS MB |
| --------------- | -----: | --------------: | -------------: | ----------: | ----------: | ------------: | ----------------: | ----------------: | ----------: |
| Python, load 30 |  395.1 |            34.1 |          361.1 |       16.77 |       82.38 |          0.31 |             99.45 |             3,159 |       3,028 |
| Rust, load 26   |   81.2 |            48.4 |           32.9 |        2.37 |       19.28 |          0.20 |             21.85 |             2,920 |       2,785 |
| Python, load 18 |  265.5 |            45.2 |          220.3 |        8.09 |       26.52 |          0.23 |             34.83 |             3,585 |       3,431 |
| Rust, load 19   |   47.5 |            26.5 |           21.0 |        1.75 |       13.12 |          0.17 |             15.03 |             2,918 |       2,783 |

Init is process start to the first converted batch; the sampler's share covers the listing, the sha256 check
against the cache, the source index and the 131,072-row buffer fill. The milliseconds are per batch. RSS after
init is read from `/proc/self/statm`, and peak RSS from `ru_maxrss`. On the second pair the Rust sampler reduced
sampling from 8.09 to 1.75 ms per batch and sampler initialization from 220.3 to 21.0 s. Encoding is the same
Rust code in both arms; its spread follows the host load rather than the sampler.

Parquet reads cannot be separated inside that window, because the 40 batches draw almost every row from row groups
the buffer fill already read. `examples/read_profile.rs` times the read alone: 60 row groups drawn from the C6
corpus's files with seed 7 (2,375,564 rows) over the nine columns the sampler reads, against pyarrow's
`read_row_group` on the same list, alternating, at load 16. pyarrow took 36.12 and 38.97 ms per row group and the
`parquet` crate 23.43 and 26.92 ms. The parity verifies give the end-to-end cost: a 5,000-row train record verifies
in 22 to 33 s at a peak of 2.5 to 3.1 GB, where its Python capture took 225 to 335 s at 4.5 to 5.4 GB, and the
36,864-row validation draw verifies in 131 s. These figures are the lab host's only; the Modal measurement waits
for the next image build, since no Modal job ran for this change. Initialization is dominated by the sampler's stream
setup: building the Rust encoder with the 2,286,339-key anchor table takes 2.04 s, against 5.46 s for the
Python `json.load` of the same table.

A 2,000-step training probe measured the effect on an A100-40GB on 2026-10-29
(`v8.3.0-probe-rust-loader-2k.yaml`, call `fc-01M62R4Y9MDJW0WMAHRR5KVGQ6`). Over steps 300 to 2,000 its median
wall time per 100 steps was 6.50 s (17 windows, range 6.10 to 7.70). The control is the same config's seed 42
run on the Python encoder, `v8.3.0-base-c6-90k-mixed-s42`, over the same steps on the same GPU type: 16.10 s
(17 windows, range 14.10 to 16.90). The Rust path therefore runs 2.48 times as many steps per second
(16.10 / 6.50). The probe differs from the control in three settings that do not run in the compared window:
validation passes, Fisher capture and the run length. Its `source_reps` targets are scaled by 2,000 / 90,000,
so it draws different rows in the same source proportions.

## Builds

The extension builds from source for each interpreter, so the root project keeps `requires-python >=3.11`.
It builds under the workspace's `py` profile (`opt-level = 3`, `panic = "unwind"`). A Rust panic therefore
raises in Python, where the release profile's `panic = "abort"` would end the training process.
`packages/mtf/rust-toolchain.toml` pins the toolchain.

- The lab venv and CI install it through the root `pyproject.toml`'s uv path dependency, which rebuilds on
  any crate source, manifest or lockfile change.
- The Python CI job installs the pinned toolchain and runs `cargo test` for `mtf-channels` with and
  without `finders`. `lib/repo-health/ci-scope.ts` selects that job for a change to the extension's inputs.
- The Modal training image builds the wheel from `packages/mtf` and imports it as its last build step.
  `corpus-python/scripts/verify_toolchain.py` checks that the image's toolchain and maturin pins agree with
  the crate's declarations.
