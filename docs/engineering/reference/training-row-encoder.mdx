# Training-row encoder

The training loader turns each sampled corpus row into the tensors one step reads: piece ids, an attention
mask, label ids, and the soft-feed channels. The channels are the postcode anchor, gazetteer, country,
street type, locality surface and code unit. The encoder is `packages/mtf/crates/mtf-channels` (#2870) and the
sampler `packages/mtf/crates/mtf-sampler` (#2874 Phase 3). The Rust trainer (`packages/trainer/crates/trainer-loop`)
links both crates. The TypeScript tools reach them through the `mtf-node` addon. Every sampling stage
draws from the same generator, `mtf-sampler/src/pyrandom.rs`, which reproduces CPython 3.12's
`random.Random`. Each stage draws at the point where the former Python loader drew. The same seed
therefore selects the same rows, except in a row-limited train epoch that spreads its reads across groups.

The Rust encoder and the Rust sampler each reproduced the tensors of the deleted Python loader byte for byte (see
Parity procedure) until the spread read changed which rows a row-limited train epoch draws. The encoder still does.

The painters and the label projection compile without a regex engine. The serving side can therefore
adopt them later through `mtf-wasm`. For now it keeps its own painters, because the serving painters
differ from the training painters in two places:

- `buildSoftFeatures` builds the locality-surface channel only when the street-type channel matched a
  piece, and training always paints it;
- `tokenizer.ts` trims the leading space from a `▁` piece's range, and training keeps it.

Training uses the Rust encoder while serving continues to use the TypeScript painters.

## Interfaces

`mtf_channels::resources` (the `finders` feature) reads an encoder's files once: `EncoderResources::load` takes the
label schema, the `postal` family's artifact and definition (`packages/postcode/data/artifacts/postal.rca1` and
`packages/postcode/data/definitions/postal.definition.json`), the anchor table and the lexicons a run configures.
`read_processor` loads the tokenizer model. The finder requires an artifact from the `postal` family.
It checks the artifact's schema version and declarations hash against the crate's build and compares
its shapes with the definition. An error for a mismatch or an unreadable or malformed file includes
the file path. The trainer
and the Node addon only convert their options and errors around it. `mtf_channels::Encoder` encodes a batch of rows into an `EncodedBatch`:

- `input_ids`, `attention_mask`, `labels`: int64 `[B, L]`;
- per configured channel, `<name>_features` float32 `[B, L, D]` and `<name>_confidence` float32 `[B, L]`.

A row with a partial span triple, unsorted, overlapping or out-of-bounds spans, mismatched token and label counts, or a
token absent from its text is an error naming the row's batch index and text. A failed finder match is an error naming
the pattern and the text. A `▁` piece's range includes the space before its word.

`mtf_sampler::Sampler::open(config, split, seed, row_limit)` opens a split with a generator seeded as
`random.Random(seed)`. `config` is the sampler document: the corpus directory, country and source weights, the coarse
filter's tags, the augmentation probabilities and exclusions, the affix lexicon, the postcode layouts, and the data
root, volume mount and sha256 cache the corpus listing reads. Each row has `raw`, `tokens`, `labels`, `country`,
`source` and, for a span-schema file, `span_starts`, `span_ends` and `span_tags`. `rows()` and `batches(batch_size)`
iterate it until they return `None`. `row_limit` counts rows before the astral skip. An error for a missing,
unresolvable or unverified file identifies its path. An error for a corrupt row identifies the file, row group
and text. `open_with` adds a `CancelToken` and an `Observer` that receives `RowEmitted`, `RowSkipped(reason)`,
`SourceRestarted` and `EpochComplete`. `batch::encode_rows` encodes a batch through `mtf-channels`. The trainer
reopens the train split with `seed + epoch` for epochs 1, 2, … and skips the batches a resumed run already took. The
character path encodes `char_ids` int64 `[B, S, W]`, and `attention_mask`, `labels` and an all-zero `input_ids` int64
`[B, S]`.

### The spread read of a source an epoch reads in part

On the train split, `row_limit` is also the epoch length that sets each source's expected draws,
`row_limit × weight / total weight`. A source expected to draw at least its row count, and every source of a stream
with no limit, reads its pass file by file and row group by row group, as the Python loader did. A source expected
to draw fewer rows uses `fraction = expected / rows` and shuffles the row groups from all its files
into one order. Each visit takes `⌈fraction × group rows⌉` accepted rows from one group before moving
to the next group. The fraction is first raised to `256 / the source's largest group rows` when it falls below, so every
group, a file's short last group included, gives the same fraction of its rows. A sweep over every group covers the
epoch's expected draws, so every group contributes about its share. Each group's row order comes from a generator seeded by the pass seed and the group's index, so a later
sweep rebuilds the order, continues from the recorded position, and the pass still reads each row once.

The spread read costs decode work and keeps the memory bound: a visit decodes a whole row group, as before, to take a few hundred
rows from it, and one decoded group is held at a time. The 256-row floor caps the decoded rows per drawn row at
about 195 for 50,000-row groups. Where it binds, as for `usgov-nad` (about 3,450 draws an epoch from about 12,000
groups), an epoch visits about 13 random groups. Over the 1,000,000-row epoch of `v8.7.0-base-c6-90k-usgs-structures-s42` the
estimate from the epoch's realized draws is 850 row-group visits per epoch against 180 file-by-file. At the 23 to 27 ms per row
group `examples/read_profile.rs` measured, the 670 extra visits add about 17 s of decoding to an epoch of 7,813 steps. The plan
draws from the epoch's generator (the group order, then one 64-bit pass seed) at the source's first row, so a seed
still fixes every row. A resumed run re-draws skipped batches and reads the same rows. The audits'
`RawRows` plans use the same limit. `openRawRows` defaults that limit to the config's `train_rows_per_epoch`.

`TrainingBatches` places each epoch in its run with an `EpochCursor`: the run seed, the epoch counted from 1, and the
run's `RunPositions` table. Under a cursor, a spread group's row order is seeded by the run seed, the file and the
group, the same order in every epoch. The table counts the rows the run has read from each group's order, and each
epoch starts the order at that count, wrapping at the group's end. The epochs of a run then read each group in turn,
and a run whose draws of a source equal its rows reads nearly every row once. An epoch seeded alone reads a fresh
random part of each group instead, and over `E` such epochs about `(1 − 1/E)^E` of the rows are never read.

The table counts the rows each epoch read. An epoch's row limit counts emitted rows, augmented copies
included, so an epoch draws fewer rows from a source than its weight share of the limit. v8.14.0 and v8.15.0 placed
epoch `e` at `(e − 1) × ⌈fraction × group rows⌉`, the expected draws. Each epoch then left part of its window
unread, and the windows wrapped before the run ended. v8.15.0 drew `wof-admin` 2,815,421 times against 2,780,333 train
rows, and 419,900 rows were never drawn. Of the 429,743 rows drawn twice or more, 407,229 repeated four or more epochs
after their first draw.

`tests/run_coverage.rs` holds both cases. Eight epochs that each expect an eighth of a 24,000-row source read nearly
every row. Ten epochs whose augmented other source emits two rows per draw read 82.2% of the rows under the expected
draws, and read in turn under the table. A resumed run rebuilds the table, because the trainer re-draws the batches it
skips. `Sampler::open`, `RawRows` and the audits open an epoch without a cursor. Their counts per source, country and
label order keep the training stream's distribution, and the rows they read differ from the rows the run trains on.

### A reps target counts emitted rows

`source_reps` derives each target's weight from the run's samples, which count emitted rows. The emit step keeps each
drawn row and adds augmented copies of some, and every emitted row counts toward the epoch's row limit. A source in
`augment_exclude_sources` emits one row per draw and an augmented source more, so in v8.14.0 `wof-admin` emitted 0.82
of the rows its target derived (2,277,277 of 2,780,333) and `usgov-usgs-structures` 1.44. The epoch-mixture audit
measures that ratio per source as `distortion_vs_draw_share`. `data.source_emit_factors` gives it to the derivation,
which reads a target `r` with factor `f` as `r / f` draws per row (`derive_source_weights` in `source_reps.rs`, which
the trainer and, through `mtf-node`, the host audits call). `tools/training/draw/emit-factors.run.ts` writes the block
from an audit and gives a source the audit's epoch emitted fewer than 2,000 rows of no factor. The draw report
compares two configs in emitted rows, both under the current config's factors.

In Node, `packages/mtf/crates/mtf-node` exposes the same streams through napi-rs, and
`packages/mtf/tools/sampler/native.ts` loads it. `Sampler(config, split, seed, { rowLimit, events })` returns rows
`nextRows(n)` at a time, `TrainingBatches` returns the train split's batches, and `RawRows` returns the mixture's rows
before the shuffle buffer, with `nextEmitted(n)` running the emit step on the same generator for the audits. Each call
hands out one chunk, so a consumer holds one chunk at a time. `takeEvents()` drains the observer events of the kinds
listed in `events`, and `cancel()` stops a stream and makes it fail with the `Cancelled` status. `createRowEncoder` and
`createCharEncoder` return the arrays as `BigInt64Array` and `Float32Array`. `packages/mailwoman/tools/training/sampler.ts`
writes the sampler document from a training config resolved by `packages/corpus/lib/training/config/`, and adds each
row's locale and address-system ids to an encoded batch.

## Python semantics

The Rust code reproduces the reference interpreter's string semantics rather than Rust's.

- `str.isspace`, `str.isalnum` and `str.isdecimal`, the cased and case-ignorable properties, and the full
  `str.lower` and `str.upper` mappings come from `src/python_text/tables.rs`. The tables were generated
  over every scalar value by the Python trainer's table script (Python 3.12, Unicode 15.0.0), which was deleted
  with that trainer (#2874), so the committed tables are the record. Rust's `char::is_alphanumeric` admits marks such as U+0940
  that Python's `isalnum` rejects, and its `is_whitespace` rejects U+001C..U+001F.
- `str.lower` applies CPython's final-sigma rule.
- The postcode finders no longer read Python semantics. They read the `postal` family through `recognizer-core`.
  A shape writes `\d` as `[0-9]` and matches either case by Unicode simple case folding. That folding also matches U+212A
  and U+017F, and the family states one case rule for serving and training. The one place the finder tests a
  character itself is the white space after a printed prefix. It reads that character as JavaScript's `\s`, the class the
  family writes.
- The code-unit segmenter is written out by hand. It reproduces
  `(?<![A-Za-z0-9])(?=[A-Za-z0-9-]*\d)[A-Za-z0-9]+(?:-(?=\d)[A-Za-z0-9]+)*(?![A-Za-z0-9])`, including the
  lookahead that accepts a non-ASCII digit after the ASCII run.
- Channel values are computed in `f64` and converted to `f32` once, as `torch.tensor(..., float32)`
  converted the Python floats. The anchor posterior is renormalized in the file's key order, with
  serde_json's `float_roundtrip` parsing so every decimal becomes the double Python's `json` produces.

## Parity procedure

The Python trainer's `audits.encoder_parity capture` drew batches through its loader and wrote each record under
`$MAILWOMAN_DATA_ROOT/audits/encoder-parity/<name>/`:

- `record.json` holds the source revision, the config and its overrides, the SHA-256 of every input
  (tokenizer, each lexicon, the shape and syntax records, the corpus manifest), the runtime versions, the
  requested and emitted row counts, the batch sizes, each row's identity hash, its country, per-channel
  nonzero counts with their denominators, and a SHA-256 per row of every model-input tensor over its
  little-endian bytes;
- `arrays.npz` holds every tensor, so `verify` can report the first differing row, tensor and element with
  both values.

`parity.run.ts verify --name <name>` (below) re-draws the sample through the current sampler and encoder. It fails on a changed emitted count,
row identity, batch boundary, tensor set, dtype or shape before it compares digests. A char-path config
builds no SentencePiece tokenizer: the record hashes its `char_vocab_path` in place of `tokenizer_dir` and
adds `char_ids` to the tensors. The first nine records were captured from the Python encoder at revision
`47495cabf` or `1115bbe3f`, and the six #2874 records from the Python sampler with the Rust encoder at
`553606715`. No record is regenerated from the code it checks. `docs/engineering/reference/encoder-parity-records.json`
lists every record with its verification against the Rust encoder (`verified`) and the Rust sampler
(`verified_rust_sampler`).

## The postal finders

The encoder's two postcode finders read the `postal` family of `@mailwoman/postcode` through `recognizer-core`.
They don't read a regular-expression engine, a shape record or a syntax record. The serving side reads the same artifact.

**What the finders return.** `Finders::postcode_spans` returns the family's embedded candidates in the order they
compete. Each candidate is reduced to its code, so a printed prefix and the white space after it fall outside. The order
is longest first, then earliest start, then form (designated, alphanumeric, numeric) and shape ID, and a range that
several shapes match appears once. A candidate that a connector separates from the rest of a longer one is dropped
(`69152` in `69152-656`).
The anchor painter walks the candidates in that order and keeps the first that the anchor table resolves among those
that overlap, so a longer candidate the table lacks hides no code inside it. A Somali shape matches `VT 05401`, and
that candidate hides no ZIP code.
**The resolution rule.** For each candidate, the encoder reads the countries from every shape in the
definition that matches its range. The candidate resolves only when its anchor-table entry has weight
for at least one of those countries. The resulting posterior includes only weights for those countries.
As with any posterior, the feature vector divides each weight by the total over the locale set. An
entry whose remaining countries all fall outside the locale set paints zeros with its centroid. A
candidate with no accepted country is skipped and hides no other. The table's `111 09` entry holds FR and US only, and
the three-and-two digit shapes belong to other countries, so the house number paints no anchor. A GB unit that fails the
rule falls back to its outward district under the same rule. The serving side applies it in `anchoredPostcodeSpans`
(`restrictEntry`) and the encoder in `AnchorLookup::resolve` and `features`, and the agreement check below compares the
candidates' countries and the keys.
`Finders::code_units` counts the countries whose syntax accepts a unit with the family's whole-input automaton and the
shapes' country lists. The family's one case rule is that every shape matches either case.
`anchor_paint_mode` is `gold` or `postal`. The mode `shaped` is retired. The encoder refuses it with a message that
points to `postal`, and the 186 historical configs that set it don't run on this encoder.

**Files.** The finder reads `packages/postcode/data/artifacts/postal.rca1` and
`packages/postcode/data/definitions/postal.definition.json`. Both are generated files of `@mailwoman/postcode`, and
they replace the two trainer data records that were deleted. The Modal image copies both through `TRAINER_DATA_FILES`
in `launch/image.ts` to `/repo/packages/postcode/data/`, where `DataFiles::in_repository` reads them.

**Agreement.** `postcode-agreement.run.ts` draws the v8.7.0 config's rows through the sampler (corpus
`v0.8.19-retention-overlay`, seed 43). It takes the 50,000 train rows and the validation draw, 22,209 rows, because the
draw exhausts below its 36,864-row limit. For each of the 72,209 rows it compares the encoder's candidates and anchor
keys with those of `findPostcodeSpans` and `anchoredPostcodeSpans`. On 2026-11-16 no row differed. The committed fixture
`test/fixtures/postcode-agreement.json` holds a stratified sample of those rows with serving's candidates, and
`postcode_agreement.rs` and `postal-spans.test.ts` replay it against each side in the fast suites.

**What moved against `shaped`.** The same tool paired each row's anchored spans under the retired table, matched against
the raw text as the trainer matched it, with the postal finder's:

### The Rust sampler

Measured on the lab host on 2026-10-29, between 11:52 and 12:06 UTC, with the C6 config, the host lexicon
overrides of the parity records, seed 43, and 40 batches of 128 rows after the first batch. Both arms encode with
the Rust row encoder and convert with `to_tensor_batch`, so they differ only in the sampler: the Python arm runs
`stream.iter_rows` from the parent revision with the astral skip, and the Rust arm runs `mtf-sampler` through the
Python binding of that revision.
Both read the sha256 sidecar cache, so neither hashes the 68.7 GB corpus. Each arm ran twice, alternating. The host
was shared with other jobs: the load average was 26 to 30 during the first pair and 18 to 19 during the second, on

Init is process start to the first converted batch. The sampler's share covers the listing, the sha256 check
against the cache, the source index and the 131,072-row buffer fill. The milliseconds are per batch. RSS after
init is read from `/proc/self/statm`, and peak RSS from `ru_maxrss`. Each peak reads lower than its after-init
figure, and a peak measured in the same unit cannot be lower. In both Rust rows the ratio is 0.9537, the ratio of
10^6 to 2^20, so the peak column appears to be in MiB and the after-init column in MB. The script that produced
this table isn't committed, so the units are inferred from that ratio. On the second pair the Rust sampler reduced
sampling from 8.09 to 1.75 ms per batch and sampler initialization from 220.3 to 21.0 s. Encoding is the same
Rust code in both arms. Its spread follows the host load rather than the sampler.

Parquet reads cannot be separated inside that window, because the 40 batches draw almost every row from row groups
the buffer fill already read. `examples/read_profile.rs` times only the read: 60 row groups drawn from the C6
corpus's files with seed 7 (2,375,564 rows) over the nine columns the sampler reads, against pyarrow's
`read_row_group` on the same list, alternating, at load 16. pyarrow took 36.12 and 38.97 ms per row group and the
`parquet` crate 23.43 and 26.92 ms. The parity verifies give the end-to-end cost: a 5,000-row train record verifies
in 22 to 33 s at a peak of 2.5 to 3.1 GB, where its Python capture took 225 to 335 s at 4.5 to 5.4 GB, and the
36,864-row validation draw verifies in 131 s. These figures are from the lab host only. No Modal job measured the
Rust sampler. Initialization is dominated by the sampler's stream
setup: building the Rust encoder with the 2,286,339-key anchor table takes 2.04 s, against 5.46 s for the
Python `json.load` of the same table.

## Builds

The root `rust-toolchain.toml` pins the toolchain, and every crate is a member of the root cargo workspace.

- The Rust trainer links the crates directly, and `trainer-cli` builds them with the trainer workspace.
- The Node addon `mtf-node` builds from source on first use, with
  `cargo build --profile node --locked -p mtf-node`. The `node` profile is `opt-level = 3` and
  `panic = "unwind"`, so napi-rs raises a Rust panic as a JavaScript exception. The addon builds on Linux and
  macOS. It is never part of `wasm/mtf.wasm`. That module's dependency tree is only `mtf-wasm` → `mtf-core`. The
  wasm build with the addon in the workspace gives the same SHA-256 as a build without it.
- The CI `rust` job installs the pinned toolchain and runs `cargo fmt --check`, `cargo test` and `cargo clippy` over
  the root workspace. `lib/repo-health/ci/scope.ts` selects that job for a change
  to the crates' inputs.
- The Modal training image builds `trainer-cli`, which links these crates
  (`packages/mailwoman/tools/training/launch/image.ts`).
