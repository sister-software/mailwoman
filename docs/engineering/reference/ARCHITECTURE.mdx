The split between `neural/` (runtime) and `neural-weights-*/` (data) is deliberate, so that users running US-only deployments do not download French weights. Weights packages are versioned independently from the runtime.

## Key abstractions

### `ComponentTag`

`ComponentTag` is the canonical union of address component types. It has a single canonical definition in [`reference/SCHEMA.md`](./SCHEMA.mdx). Adding a tag requires a written rationale.

### `ClassificationProposal`

`ClassificationProposal` is the shape every classifier produces. It replaces the ad-hoc shape that rule classifiers currently use. See `reference/INTERFACES.md`.

```ts
interface ClassificationProposal {
	span: Span
	component: ComponentTag
	confidence: number // 0..1
	source: "rule" | "neural" | "merged"
	source_id: string // 'house_number' for rule, 'neural-v0.3-en-us' for neural
	penalty: number
	metadata?: Record<string, unknown>
}
```

Existing rule classifiers wrap their output in this shape, and the neural classifier emits the same shape. The solver treats proposals from both sources identically.

### `ClassifierPolicy`

`ClassifierPolicy` is per-component configuration that decides which classifier(s) have authority for that component. It controls the gradual, component-by-component replacement of rule classifiers with the neural classifier.

```ts
interface ClassifierPolicy {
	component: ComponentTag
	mode: "rule_only" | "neural_only" | "both" | "neural_preferred" | "rule_preferred"
	confidence_threshold?: number
	locale?: string // policy can vary per locale
}
```

The default policy is `rule_only` for every component until the neural classifier ships. Migration then happens one component at a time, based on golden-set metrics.

### `LocaleProfile`

`LocaleProfile` holds locale-specific behavior: which weights package to load, which rule classifiers apply, and which synthesis rules govern training data generation.

```ts
interface LocaleProfile {
	locale: string // 'en-US', 'fr-FR', 'ja-JP'
	weightsPackage: string // npm package name
	ruleClassifiers: string[] // identifiers of rule classifiers active for this locale
	componentsSupported: ComponentTag[] // not every locale supports every tag (e.g. JP has no `street`)
	policy: ClassifierPolicy[]
}
```

## Locale strategy

Locales are first-class, and the system does not assume English. Every classifier (rule or neural) declares which locales it serves.

- A US-only deployment loads the `en-US` profile, the English rule classifiers, and the US weights.
- A multi-locale deployment loads all configured profiles. A `LocaleDetector` handles per-input locale detection separately (Phase 2 work; v0 can require an explicit locale).
- A new locale needs a new `LocaleProfile`, a new weights package, and optionally new rule classifiers. Core code does not change.

## Model architecture (what the neural classifier IS)

**Family: encoder-only transformer + per-token classification head.** This is the standard NER (named entity recognition) shape. Each token of the input address string gets exactly one BIO label from a fixed set: `O`, plus `B-<tag>` and `I-<tag>` for each tag in the `ComponentTag` union. That is currently 47 labels (1 + 2 × 23 tags).

### Why this family rather than the others

| Family                                                                        | Used for                                                        | Why not us                                                                                                                         |
| ----------------------------------------------------------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **Encoder-only + classification head** (BERT / RoBERTa / DeBERTa + NER heads) | Per-token tagging; same number of output labels as input tokens | **This is us.** Address parsing is a tagging problem rather than a generation problem.                                             |
| Encoder-decoder (T5, BART)                                                    | Seq2seq — translation, summarization                            | The output isn't a different sequence; it's structured tags per input token. Encoder-decoder is overkill and lossy for this shape. |
| Decoder-only (GPT, Llama)                                                     | Autoregressive generation                                       | We annotate, we don't generate. A decoder LLM could approximate via constrained decoding at 1000× the cost.                        |
| Conditional random field (CRF)                                                | Pre-transformer per-token tagging with Markov features          | This is libpostal. We're replacing the CRF with a transformer encoder in front of an effectively-similar tag space.                |

### Concrete config (Phase 2 / issue #10)

- **Backbone**: HuggingFace `BertForTokenClassification` with a small custom config: **6 layers, 256 hidden dim, 4 attention heads, 1024 FF intermediate, max position 128.** The model is trained **from scratch** rather than fine-tuned from a BERT pretrained on English web text, because the address vocabulary is too narrow and too unlike natural language for that pretraining to help.
- **Tokenizer**: SentencePiece (unigram), `vocab_size=16000`, `character_coverage=0.9995`, `byte_fallback=true`. It is trained on the corpus rather than taken off the shelf, and the tokenizer version is locked to the corpus version.
- **Output head**: linear projection → 47 logits per token (the BIO label space derived from `ComponentTag`).
- **Inference**: take the softmax over labels and the argmax per token, decode BIO spans back to character offsets through SentencePiece's offset map, and emit a `ClassificationProposal` per span with the mean per-token softmax probability as its confidence.
- **Size target**: < 30 MB int8-quantized ONNX, < 40 MB including the tokenizer, with a total parameter count in the low millions.
- **Runtime**: `onnxruntime-node` with the CPU execution provider by default. Inference does not use Python.

### The cousin: spaCy's `ja_core_news_trf`

The closest commercial reference point is spaCy's [Japanese transformer pipeline](https://spacy.io/models/ja#ja_core_news_trf):

|                       | spaCy `ja_core_news_trf`                                                                 | mailwoman planned                                                                                |
| --------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Backbone              | `cl-tohoku/bert-base-japanese-char-v2` (BERT-base — 12 layers, 768d)                     | small BERT (6 layers, 256d) — ~10× smaller                                                       |
| Vocab                 | 6,144 char-level (Japanese requires character-level for OOV handling)                    | 16,000 SentencePiece (multilingual; bytes fall back for OOV)                                     |
| Pretrained            | Yes (Tohoku-Univ. Inui Lab BERT)                                                         | No (from scratch on address corpus)                                                              |
| Task heads            | **3** on shared encoder: morphologizer (POS), parser (dependency), NER (22 entity types) | **1** on dedicated encoder: NER for 23 address component types                                   |
| Model size            | 320 MB                                                                                   | < 40 MB int8                                                                                     |
| NER F1 (their domain) | 83.31 ENTS_F on general Japanese NER                                                     | TBD; the rule baseline is > 95% on `country` / `region` for the golden set, so the floor is high |
| Inference runtime     | Python (spaCy)                                                                           | Node (`onnxruntime-node`)                                                                        |
| License               | CC BY-SA 3.0                                                                             | AGPL-3.0                                                                                         |

spaCy supports the choice of model family. The flagship Japanese model of the industry-standard NER toolkit is a BERT encoder with a token-classification head, which is the same shape. Our design differs from theirs in three ways:

- **Smaller** (10× fewer parameters): our task is narrower. General-purpose Japanese NER must handle 22 entity types across all news text, while address parsing handles 23 component types in addresses only. A narrower task can use a smaller model.
- **From scratch rather than fine-tuned**: their cl-tohoku backbone was pretrained on Japanese Wikipedia and news. Our domain is far enough from natural-language text that pretraining transfers poorly. Training from scratch on an address-only corpus should give a smaller, faster, more accurate model.
- **Single head rather than multi-head**: they share one encoder across the morphologizer, parser and NER. We have only one head, so the encoder can specialize fully in component disambiguation. (Multi-head is a future extension, described below.)

### Multi-head extension (Phase 4+)

The spaCy pipeline pattern, one shared encoder with multiple task heads, is worth revisiting later. Candidate heads:

- **Venue vs address-part head**: a binary classifier per token to help compositional disambiguation (in `Buffalo Health Clinic Buffalo NY`, is "Buffalo" a venue token or a locality token?). It would help with the hardest cases in [[project-mailwoman-bitter-lesson]].
- **Locale detection head**: predicts `en-US` vs `fr-FR` vs `ja-JP` for the whole input, so `LocaleDetector` (currently separate) could share the encoder.
- **Completeness head**: predicts whether the input is a complete address, a fragment, or noise, and feeds graceful-failure signaling per [[project-mailwoman-graceful-failure]].
- **Confidence head**: a separate calibration learner trained on held-out data, which replaces the per-token softmax with a calibrated probability.

None of these heads is in scope for Phases 0–3. They are filed for Phase 4 or later. spaCy shows that the pattern works at scale.

### Frameworks + tooling stance — what we use, what we don't, what we steal

**Use**: HuggingFace Transformers + PyTorch for training (Python-only, run once per model, producing the ONNX file). `onnxruntime-node` for inference (TypeScript / Node, the user-facing path). SentencePiece for tokenization in both training and inference. `parquet-wasm` with Apache Arrow for corpus Parquet output. This is the production stack, and anything outside it would be unused or duplicate functionality.

**Don't use**: spaCy as a runtime or training dependency, for these reasons:

- **Runtime**: spaCy is Python-only. The plan's "TypeScript-first" stance is a hard constraint from the epic. Adding Python at inference time would complicate deployment for Node users, and avoiding that is the project's main reason to exist. spaCy's ONNX export path (`spacy-onnx-export`) exists but is rarely production-grade.
- **Training**: spaCy's config-driven training (`spacy.cfg` + `Thinc`) is well designed, but it pays off mostly when pipeline composition matters or the task is novel. Our task, single-head NER on `BertForTokenClassification`, is the most common path in HuggingFace Transformers. spaCy would add an abstraction layer for little convenience. The operator prefers as little Python as possible, which argues against spaCy even for training, where Python is unavoidable.

**Adopt the patterns rather than the tool**:

| What                                                                                                                 | From                                                                                                                                                  | Where to apply                                                                                                           |

| Release notes template (label scheme table + transformer config block + per-component F1 + compatibility matrix)     | spaCy's GitHub release format for models like [ja_core_news_trf-3.7.0](https://github.com/explosion/spacy-models/releases/tag/ja_core_news_trf-3.7.0) | Phase 3 (#11) `@mailwoman/neural-weights-*` package READMEs + model card JSON                                            |

| "Training described entirely by a config file, code is the runner" hygiene                                           | spacy.cfg pattern                                                                                                                                     | `corpus-python/src/mailwoman_train/cli/commands/train.py` config shape — adopt the pattern without taking spaCy as a dep |
| Vintage / language-model-version conventions                                                                         | spaCy's `ja_core_news_trf-3.7.0` naming (`<lang>_<domain>_<size>_<framework>-<version>`)                                                              | Weights package versioning + ONNX file naming                                                                            |

**Optional Phase 3 baseline comparison**: run a fine-tuned `xx_ent_wiki_sm` or `en_core_web_trf` against the same golden set and report the comparison in the model card. Seeing general NER tag `LOC` / `ORG` where we expect `locality` / `venue` shows how the model compares with general NER. A fair baseline run takes ~1 hour of operator time. The comparison is a one-off and stays out of the install dependency tree.

### Casual descriptions (for audiences who don't want the architecture deep-dive)

- **Technical**: "Small encoder-only transformer (BERT-class, from scratch, ~few-million params, less than 40 MB int8 ONNX), with a per-token classification head that emits BIO-tagged address-component spans. It runs in Node via onnxruntime-node and needs no Python at inference."
- **Practitioner**: "Tiny BERT-class NER model specialized for address parsing: a learned replacement for libpostal's CRF, sized to fit in a Node process. It belongs to the same architectural family as spaCy's ja_core_news_trf and is ~10× smaller because the task is narrower."
- **User-facing**: "A small ONNX model that reads an address string and tells you, with per-component confidence, what each piece of it means."
- **For the bitter-lesson audience**: "The contextual-parser half of a contextual-parser-plus-constraint-solver geocoder front-end. The transformer proposes candidates, and the policy registry and solver choose among them."

The model is neither a translator (it has neither a language pair nor autoregressive output) nor a generative model.

## Training cadence vs. plan (2026-05-18 reframing)

The original phase plan (`phases/PHASE_2_training.md`) targeted a **single training run reaching >95% per-component F1** in ~2 weeks. After two iterations, an **iteration cadence** replaced that plan. Each cycle is ~3-7 days of focused work (corpus refinement → train 6-10h GPU → eval → ship), and each cycle produces a shippable artifact even if it misses the >95% bar.

The plan changed for these reasons:

- **>95% F1 in one run was unrealistic.** Address parsing from scratch on a noisy real-world corpus is harder than that target assumed. Ship floors are lower (~0.85 F1 on coarse components is useful in production with proper calibration).
- **Shipping below target follows from the bitter-lesson framing.** Per [[project-mailwoman-graceful-failure]], the success metric is graceful failure rather than maximum F1. A 0.85-F1 model with 0.88 calibration in its conf>0.9 bucket is more useful than a 0.95-F1 model with 0.33 calibration (the v0.1.0 situation).
- **Coexistence with the rule classifiers makes shipping safe.** The neural classifier adds proposals alongside the rule classifiers through the policy registry, so we can start using it before it reaches parity.
- **Iterating beats a single run.** Each cycle produces artifacts: ONNX weights, a model card, an eval report, the npm package shape, and demo updates.

### Why more data doesn't blow up the iteration cost

A training run has a fixed step count rather than a fixed number of epochs. v0.2.0's 50K steps × 128 effective batch = 6.4M examples seen ≈ **2.4% of the 263M-row corpus per pass**. Adding NAD (62M), OA-CA (10M) and state backfills grows the corpus to ~340M rows, and the same 50K steps still finish in ~6.5-10h. The model is far from limited by training data, so a larger corpus adds diversity per example seen without adding wall-clock time.

These steps add time to each iteration:

1. **Vocabulary tier expansion**: adding venue/street/house_number labels requires adapter alignment updates (every adapter's `align.ts` emits the new labels where source data supports them), golden set verification, and a corpus rebuild (~260 min). This is most of the v0.3.0 work.
2. **CRF decoder + label smoothing**: small training-time additions with large calibration and coherence gains. They land in the same retrain.
3. **Per-iteration golden expansion**: already automated through `expand-golden.ts` and `promote-golden.ts` (PR #48 / #49), so each iteration can re-evaluate against the latest golden version.

### Re-framed success metric per iteration

Each iteration succeeds if its artifact is independently shippable and measurably better than the previous one. Reaching 95% F1 is no longer the criterion. The eval ledger at `evals/scores-by-version.json` records this: every shipped run gets a row, and the corpus and eval set are pinned by sha so that deltas compare like with like.

## Why this shape

- **Classifier-as-plugin** preserves Mailwoman's existing extensibility. New rule classifiers, new neural variants, and future learned rankers all conform to the same interface.
- **Per-component policy** allows incremental rollout instead of switching every component at once. A regression in neural `street` parsing does not affect `country` parsing.
- **Locale profiles** keep the architecture from defaulting to English-speaking conventions. If the abstractions cannot express a locale outside those conventions, we fix the abstractions instead of working around the locale.
- **Separate weights packages** keep npm install times reasonable and let users install only the languages they need.
- **Training in Python and inference in TS** uses each ecosystem for its strengths and keeps production code in one language.

## Output shape (Phase 3 concern rather than Phase 2)

The neural model emits per-token BIO labels regardless of how its output is presented. The decoder chooses the format. Three shapes are valid, listed in order of increasing expressivity:

| Shape                                                            | Preserves                                                      | Loses                                         | Round-trip fidelity                                                                                                                       |
| ---------------------------------------------------------------- | -------------------------------------------------------------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **JSON object** `{locality: "Paris", postcode: "75005"}`         | tag → value                                                    | order, repetition, hierarchy, untagged tokens | Country-specific formatter required; reorder errors are silent. Libpostal/Pelias compatible.                                              |
| **Tuple array** `[["locality", "Paris"], ["postcode", "75005"]]` | tag → value + **original order** + repetition                  | hierarchy                                     | Reconstruction is `array.map(([_, v]) => v).join(" ")`; trivially faithful to ordering.                                                   |
| **S-expression** `(locality "Paris" (postcode "75005"))`         | order + **hierarchy** + arbitrary attributes (`:conf`, `:src`) | no material change                            | The most expressive — lets the parsed output say "this postcode is inside this locality." Natural carrier for Phase 4 source annotations. |

**Operator framing (2026-05-18):** address parsing is inherently lossy, because the original formatted address cannot be recovered from the parsed result. The closest approximation comes from applying a formatter to the parsed result. S-expressions may preserve the original shape better because they encode hierarchy, ordering and attributes in one tree.

**Implementation plan (Phase 3, #11):** ship all three decoders behind a `--format json|tuple|sexp` CLI flag. JSON is the default for libpostal compatibility, and S-expr is a power-user mode. A round-trip eval (`parse(format(parse(raw))) == parse(raw)`) shows which shape preserves the most fidelity. If S-expr wins, make it the default.

**The formats require no model retraining.** They are post-processing on the BIO output, and the same neural model serves all three formats.

**Existing isp-nexus formatter** (`isp-nexus/universe/mailwoman/postal/formatting.ts`) converts a flat object into a multi-line string for shipping-label rendering. Port it as the inverse of the JSON decoder, and build a separate `sexp→string` formatter for the S-expr path.

## Source attribution (Phase 4 — #12, deferred)

Source attribution distinguishes Mailwoman from libpostal and Pelias. Libpostal says "this token is a city", and Pelias adds hit/miss provenance against ES indexes. **Mailwoman's goal** (operator framing) is to say "this token is a locality identified by the wof-admin gazetteer with 0.97 confidence."

The corpus already records `source` per row, because every alignment and augmentation step tags provenance. The remaining work is to carry that provenance through to the inference output.

**Decision (operator, 2026-05-18): hybrid Option C, model + Resolver.**

- The model emits BIO labels and per-token confidence (it already does).
- At inference time, the Resolver maps `(span, label) → (source-class, src-conf)` through fast lookups against pre-indexed gazettes (wof, ban, tiger, nppes, hrsa, imls-pls, state-\*).
- Output annotations are stored as S-expression attributes:

```
(locality "Paris" :src wof-admin :conf 0.97
  (postcode "75005" :src wof-postalcode :conf 0.93))
```

### Provenance is already flowing through training

`source_weights` (shipped 2026-05-18 in PR #44) affects what the model emphasizes during training, even though the model itself does not emit source labels. At inference time, the Resolver **makes explicit** the source information that was implicit in training. The data path:

```
corpus row (source-stamped)
   → source_weights filter at data loader
   → training distribution (model internalizes source priors)
   → model emits BIO + confidence (no source field)
   → Resolver looks up labeled spans against gazettes
   → output: BIO + label + confidence + source-class + src-conf
```

### Rejected alternatives

- **Resolver-only at inference, without source-aware training**: the model would have no internal calibration toward gazette-confirmed tokens, which makes this option weaker.
- **Multi-task neural head** emitting `(label, source-class)` per token: this needs ~15 × 8 = 120 sub-classes, makes the model bigger and harder to retrain, and removes the clean separation between span identification (the model's job) and provenance (the Resolver's job).

## Anti-patterns to avoid

- ❌ A `mode: 'auto'` setting in `ClassifierPolicy` that "intelligently" picks rule vs neural. It hides state and is hard to debug. Keep the policy explicit.
- ❌ Hardcoding `'en-US'` as the default in core. The default should be "no locale; classifiers must opt in."
- ❌ Loading all weights at module init. Lazy-load them on the first classification request.
- ❌ Mixing inference and resolution. The parser does not know about coordinates, place IDs, or WOF resolution, which belong to Phase 4.
- ❌ Adding tags to `ComponentTag` without updating the schema doc and the alignment logic in the same commit. Schema drift corrupts the corpus.
