# Spatial-layer interface

Every mailwoman dataset has the **same artifact shape**, whether it is the shipped poi.db, a
user's locally built OSM layer, or a private CRM layer. Each is a sealed, readonly,
provenance-tracked SQLite database ("a layer") keyed on a shared spatial spine. The shared
shape lets shipped, build-local, and private layers use one query surface (`@mailwoman/spatial`
primitives, the `mailwoman_layer_manifest` MCP tool, the planned `layer_query`), and the
consumer doesn't need to know where the data came from.

This page describes the interface in prose for layer authors. The code lives in
[`packages/core/lib/layers/`](https://github.com/sister-software/mailwoman/tree/main/packages/core/lib/layers)
(`schema.ts` defines the tables, and `manifest.ts` handles read/write IO). The design
rationale was the 2026-07-18 spatial-layers and POI design spec, which commit `0d8b2847a` deleted.
Read it with
`git show 0d8b2847a^:docs/superpowers/specs/2026-07-18-spatial-layers-and-poi-design.md`. If you're
building a specific layer,
read the worked example first. The [POI layer runbook](./poi-layer-runbook.mdx) records the
problems found during the first four poi.db builds.

## What a layer is

A layer applies the gazetteer conventions (sealed 0444 artifacts, Kysely schema modules,
build-then-swap) to analysis data as well as reference data. A layer database:

- Embeds the **two interface tables** below (`layer_manifest`, `layer_coverage`) regardless of
  tier, plus whatever domain tables the layer needs.
- Is **sealed 0444** on completion (`sealDatabase` from `@mailwoman/sqlite/sealed/db`). It is a
  readonly artifact and is never reopened read-write. Updates are full rebuilds that are swapped
  into place: build to a temp path, move the old file aside, and move the new one in. The live
  artifact therefore stays consistent even if a build fails halfway. `buildSealedArtifact` in
  `packages/sqlite/lib/sealed/build.ts` does this for the flood, coastal, zoning and soil builders.
  The POI builder is the exception: it removes the previous `poi.db` and writes the output path
  directly (see the [runbook](./poi-layer-runbook.mdx)). The installer that puts an acquired or
  recipe-built artifact into a data root is a separate step, described in
  [Layer installation](./layer-installation.mdx): the artifact moves into an immutable
  `db/<role>/<sha256>/` directory and `active.json` selects it.
- Addresses every domain row by **at least one spine key**, so cross-layer joins and spatial
  primitives share a common key.

## The spine

Every layer row is addressable by at least one of four shared keys. Other id spaces remain
nullable metadata (the GERS rule). Store the id spaces your source provides, and declare them in
the manifest's `spine_keys`.

| spine key    | column        | meaning                                                                                                     |
| ------------ | ------------- | ----------------------------------------------------------------------------------------------------------- |
| `h3`         | author-chosen | H3 cell, stored as a **48-bit short cell** (`shortenH3Cell`/`expandH3Cell`). Resolution declared per table. |
| `wof_id`     | author-chosen | WOF ancestry anchor — the resolver's existing id space (Who's On First).                                    |
| `address_id` | author-chosen | The `@mailwoman/address-id` key, where rows are address-grained.                                            |
| `street`     | author-chosen | Normalized street column used to join address-point or street-segment layers.                               |

The manifest declares column names and the H3 resolution in its `spine_keys` field (a
`SpineKeys` record, JSON-encoded in the table). At least one key is **required**.
`writeLayerManifest` throws at build time, and `readLayerManifest` throws at open time, if a
manifest declares none.

### `spine_keys.h3` for polygon layers

Every overlay of this shape follows the rule below. It was first set for the EA flood-zone layer. A polygon spans multiple cells, so no single cell addresses it. A two-tier polygon
layer therefore stores the authority's unsimplified rings as the truth table and an H3 cell table
above them as the summary. The question is which of the two tables `spine_keys.h3` refers to.

**`spine_keys.h3` points at the index, and its `column` value is qualified with the table:**
`{ "h3": { "column": "flood_zone_cell.h3_cell", "resolution": 9 } }`. Three reasons support this,
in order of importance.

1. **It is accurate.** The layer is addressable by cell, and the geometry table isn't. A manifest
   that points at a column that doesn't exist, such as `flood_zone_area.h3_cell`, is worse than
   either option, because a consumer joins on the field the manifest declares.
2. **The qualified column name resolves the objection.** The objection to declaring `h3` was that
   it points a consumer at the index rather than at the domain table. The qualified column name
   `flood_zone_cell.h3_cell` instead of a bare `h3_cell` states that in the field a consumer
   already reads. It incurs no cost, because `SpineKeys.h3.column` has always been free text the
   author chooses.
3. **Another spine-key kind would add no value.** `street` was added because the situs
   `address_point` and `street_segment` tables lack a cell, a WOF id and an address-id. That absence was
   measured. A polygon layer has a cell key. It also has a second tier, and a tier isn't
   an addressing scheme.

**When a layer also has a reduction table, the key points at the reduction instead of the
index.** This case came from `@mailwoman/soil`, which has three cell-facing tables: the
unsimplified rings, a `(cell, feature)` containment index above them, and a table with one row per
cell that reduces the index into the summary both of its consumers read. The rule above still
applies, because the key identifies the table a consumer joins on. Here that table is
`soil_capability_cell.h3_cell`. It has a single resolution and one row per cell, and it is the only
one of the three tables a bulk reader can key against. The containment index is keyed
`(h3_cell, area_id)` and has mixed resolutions by construction, so it is a tier that the layer's own
reader walks, and consumers do not join on it. A layer without a reduction, such as the flood
zones, points at its index because that's its only cell-keyed table.

A consumer must account for two consequences.

**The declared `resolution` is the index's target, and each stored row records its own
resolution.** The whole tier is compacted toward parent cells (`compactCells`). A polygon whose
bounding box would overrun h3's allocator at the target resolution is indexed at a coarser one. As
a result, `flood_zone_cell.resolution` is stored per row, and a probe walks its own `cellToParent`
chain over every resolution in the table. A reader that probed only the manifest's resolution would
treat every row at another resolution as absent. This interface is designed to prevent that false
negative.

**`layer_coverage` has a single resolution, and that resolution is a third, separate value.**
`recoverShortCellResolution` in `@mailwoman/spatial` recovers one resolution from the stored coverage
cells and throws on a table that mixes resolutions, so the coverage tier is never compacted. Three
resolutions therefore coexist in one artifact: the manifest's index target, the per-row cell
resolutions, and the coverage resolution. Read each one from where it is stored, and never infer
one from another.

### h3 allocator exhaustion in polygon builders

The failure is in h3 and not in the EA flood layer it was measured on, so every polygon builder can
hit it.

**h3's WASM heap cannot be reset from JavaScript, and when it is exhausted, it returns a null pointer.**
`polygonToCellsExperimental` sizes its output buffer with `_calloc`. A failing `_calloc` returns
a null pointer (address zero), and in WASM, address zero is ordinary writable memory. The call therefore reports
success, and the reader returns an array of zeros. An exhausted allocator answers "no cells"
instead of raising an error. h3-js frees every buffer it allocates, so the problem that builds up
over millions of calls is heap fragmentation.

That mechanism was measured with h3-js 4.5.0. The two requirements below apply to every polygon
builder, including one built on `@sister.software/h3`:

1. **Refuse an empty answer for any part.** A part with a non-degenerate bounding box touches at
   least one cell, so zero cells is impossible for it. Run the check on each part. A
   per-feature check passes any multi-part feature whose other parts returned cells, and it indexes
   the feature incompletely without any error. That would reproduce, through the index, the silent
   absence the coverage rule is designed to refuse in the data.
2. **Bound the classification by construction.** Run it in child processes over ranges of the
   source's own stable ids, so each process starts with an empty heap. A lower call count, for
   example by skipping the polyfill where the geometry by itself determines the answer, helps speed but doesn't
   guarantee correctness. A build that completes only when fragmentation happens to stay low isn't
   reproducible.

Worked example, with the numbers: in `packages/flood`, three runs failed at one 164 m² feature
after ~510,000 others, and a fourth failed at another feature after ~798,000. Each of those features
classifies in milliseconds in a fresh process.

### Ring orientation through GDAL

The measurements below come from `packages/zoning`. GDAL causes the failure, so it affects every
polygon builder whose source encodes anything in ring orientation.

**GDAL's GeoJSON writer always enforces the RFC 7946 winding.** `-lco RFC7946=NO` isn't a
GeoJSONSeq layer-creation option, and `--config OGR_ORGANIZE_POLYGONS SKIP` has no effect. A source
that marks holes by winding them opposite to their exterior therefore comes out of a reprojection
with every ring wound as an exterior. Ireland's largest zoning feature shows this. Meath County
Council's `RA - Rural Area` is published as 107 single-ring parts, 5 clockwise and 102
counter-clockwise. Through `-f GeoJSONSeq`, it arrives as 107 counter-clockwise exteriors totaling
2,371.9 km², against the publisher's own 2,232.1 km². The same conversion written as
`-f CSV -lco GEOMETRY=AS_WKT` keeps the source's clockwise/counter-clockwise split intact.

Two requirements follow, and the second makes the first checkable.

1. **Choose a transport that preserves what the source encoded**, and state in the ingest code
   which property it preserves. A reprojection can change the meaning of a geometry whose meaning
   depends on its winding.
2. **Compare the built area against the publisher's own figure rather than against the archive's.**
   Ireland publishes `Shape__Area` on the service and omits it from the bulk export, so the
   comparison uses an independent source rather than a file compared with itself. Read with their
   holes, the rings total 5,444.5 km², and the publisher's column sums to 5,444.5 km². Read without
   the holes, they total 5,666.6 km². The 4.1% area error matters less than what the
   ray cast does: it answers "inside" for every location the plan excluded.

### Authority designations

This rule is also recorded here, because it belongs to the interface rather than to one layer.

A layer reports what an authority designates at a resolved coordinate through a
`QueryIntentMarker`. The marker has `code: "authority_designation"`, a `mechanism` in the
`family:rule` form with `layer` as the family and the layer as the rule (`layer:flood_zone`), and
`evidence` carrying the code, the authority's own definition of it, the containment path, the
coverage row and the layer's manifest identity.

**The marker reports the verdict's own top kind.** By convention, `QueryIntentMarker.kind` is a kind
the verdict contains. A designation isn't raised by query intent, because no address component
asks for a flood zone, so it has no kind of its own. The interface is satisfied by reporting the top kind
literally. `declared_ambiguity` is also a marker raised at resolve time rather than by the classifier.
This marker differs from it in having no kind of its own. The project chose this over the
alternative of widening the carrier with an optional-kind marker variant. That variant would create a
second advisory shape without any benefit a reader can use.

**The layer raises no advisory where the authority made no determination.** Outside the authority's
footprint there's no coverage row, and an advisory there would report a determination that the authority
never made. `supportsExclusion` applies the same asymmetry: positive evidence needs no coverage row, and
a claim of absence does.

### Coverage basis per source

A coverage rule that fits one authority's product can be wrong for the next one. When it is wrong,
it produces a confident answer instead of a missing one. The first two layers below were built on
the same platform three months apart, and they show both directions:

- **`packages/flood`.** The Environment Agency states that its Flood Zone mapping "covers all of
  England", and the Planning Practice Guidance defines Zone 1 as "all land outside Zones 2, 3a and
  3b". A location inside the footprint without a polygon therefore has a designation. It is stored as
  a `layer_coverage` row with `basis = designated, completeness = 1.0`, and the reader reports it as
  `designated_absence`.
- **`packages/coastal`.** The same authority publishes coastal-erosion zones and **no coverage
  statement**. A location in England without an erosion polygon may be inland. Inland covers most of
  the country, and the product makes no statement about it. The location may also be on the coast and outside the
  mapped risk area. That second case is the designation a caller wants. The published layers cannot distinguish
  these cases. Every coverage row therefore has `basis = source_present`, the layer has no absence
  reading, and the observation reports no entry where no polygon contains the point.
- **`packages/zoning`.** A location without a zoning polygon can mean at least four
  different things: it is outside any adopted plan area, it is inside one on land the plan doesn't
  zone, its jurisdiction has never adopted zoning, or its jurisdiction's records are unpublished.
  No product distinguishes them. This is the hardest of the three, and it shows that the rule
  depends on the source and not on the subject. **The source itself shows the asymmetry**: it states
  `UNZ - Unzoned` as a positive value on 4 of its 85,330 rows. Where the authority means unzoned, it
  states so on a row, and every other absence is a missing row. This layer also uses
  `source_present` and refuses exclusions at both ends.

A builder that had applied the flood rule to either of the other layers would have written "no
erosion risk" over all of England, or "no restriction applies" over most of a country's land. The
artifact would have been well formed and would have passed every structural check.

**The basis is therefore checked in code at both ends.** A layer whose source publishes no
footprint refuses to write a coverage row that would support an exclusion, and it refuses to open an
artifact that contains one. The constructor calls `supportsExclusion` over the distinct bases, and a
stronger basis throws an error that explains why. A move to a stronger basis takes a deliberate edit
to a guard whose message states the reason, so it can't arrive as an unnoticed coverage row.

**The footprint question is recorded where a reader will look for it, and it depends on the
source.** For the coastal layer as built, the project hasn't chosen a mapped-footprint source, so
the basis is `source_present`. Two unverified candidates exist. The first is the Environment Agency's
Shoreline Management Plan Mapping record: NCERM's own lineage states it is derived from the Shoreline
Management Plans, and every erosion feature has `smp_no`, `smp_name` and `smp_pu`. The second
is the frontage geometry behind `frontageid`, which may not be published. A change from
`source_present` to `designated` requires a published statement of the area the authority mapped,
plus its geometry. A footprint derived from the union of the hazard polygons isn't accepted, for
the same reason the flood layer doesn't accept one. The union of "at risk" areas differs from the mapped
area, and that difference is exactly what a negative answer reports.

## The manifest — `layer_manifest`

`layer_manifest` is a single-row table that holds the layer's identity, provenance, and licensing.
The `name` column is the primary key, and the writer inserts exactly one row.
`readLayerManifest` refuses a table that's empty or has multiple rows, so a layer with no identity,
or with two, fails immediately instead of causing errors downstream.

| field                                                | meaning                                                                                                    |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `name`, `version`, `schema_version`                  | identity                                                                                                   |
| `tier`                                               | `shipped` \| `build-local` \| `private` (see below)                                                        |
| `license`, `attribution`                             | SPDX expression the build admits (see below), e.g. `CDLA-Permissive-2.0`, `ODbL-1.0`; attribution nullable |
| `source`, `source_vintage`, `build_cmd`, `build_sha` | provenance — pin baselines by SHA + the command that produced them                                         |
| `freshness_policy`                                   | `sealed` (rebuild-only) \| `versioned-refresh` (re-issued under the same name)                             |
| `spine_keys`                                         | which spine columns this layer stores, and the H3 resolution (JSON-encoded)                                |
| `created_at`                                         | ISO-8601, supplied by the build script — never generated in-library                                        |
| `source_records`                                     | JSON object of input record counts per publisher, or NULL when the build recorded none                     |
| `source_url`, `source_sha256`                        | the input file's download URL and SHA-256, or NULL when the build recorded neither                         |

`created_at` is deliberately supplied by the caller. The library never stamps a timestamp, so a
rebuild from the same inputs is reproducible instead of recording a new "now" on every run.

### Tiers

The tier sets how the artifact is distributed. It decides whether _we_ publish the artifact or
ship only the builder.

- **`shipped`**: permissive sources only (Overture Places CDLA-P, Census/TIGER public domain,
  Wikidata CC0, Foursquare labels Apache-2.0). We build these layers and publish them to R2/npm
  like the gazetteer.
- **`build-local`**: share-alike sources (ODbL: OSM POIs, Overture's _base_ theme). We ship the
  **builder CLI**, the user builds the layer on their own disk, and we distribute no data under
  ODbL. `@mailwoman/osm` follows the same model: npm holds its code, and its manifests record the
  Geofabrik URL and SHA-256 of the extract in `source_url` and `source_sha256`. When a build-local layer is
  absent, the answer is "requires the locally-built layer," never a degraded or invented result.
- **`private`**: the user's own data (CRM, survey notes, parcel relationships), conforming to the
  same schema, loaded from `$MAILWOMAN_DATA_ROOT`, and never leaving their machine. This tier lets
  internal geographic data use the same query surface as public layers.

### Freshness policy

- **`sealed`**: immutable, and updated only by full rebuilds (the gazetteer convention). This is
  the default.
- **`versioned-refresh`**: periodically re-issued under the same name (e.g. a registry of people
  or programs that changes over time). Each issue is still sealed. The policy only records that a
  newer issue under the same name is expected.

## Coverage — `layer_coverage` and the meaning-of-zero rule

A layer derived from an incomplete survey (OSM above all) **must** include a `layer_coverage`
table. It records survey completeness per H3 cell at a coarse resolution, so a consumer can
distinguish "mapped and absent" from "unmapped."

| column          | meaning                                                                        |
| --------------- | ------------------------------------------------------------------------------ |
| `h3_cell`       | 48-bit short H3 cell at the coverage resolution, one per table                 |
| `completeness`  | estimated completeness of the source survey in the cell, 0..1                  |
| `basis`         | what that `completeness` rests on — `designated`, `surveyed`, `source_present` |
| `observed_rows` | rows this layer holds in the cell                                              |

**Never read `completeness` without reading `basis`.** A
cell recorded at `1.0` because an authority designates the set complete and a cell recorded at
`1.0` because the source happened to return rows there support entirely different conclusions. Only
`designated` (an authority declares the set complete) and `surveyed` (we measured completeness
against an independent reference) can support an **exclusion**. An exclusion is a claim that the thing
asked for is absent. `source_present` supports presence and no exclusion. It shows that the source
was checked for the cell, and the source may still have missed rows there. A caller building negative evidence
calls `supportsExclusion(cell)` first and stops when it returns false. Without `basis`, the
exclusion would fire the same way on a cell measured as empty and on a cell that was never surveyed. A NULL `basis` comes from an artifact built before the column
existed, and it reads back as `source_present`. That's the weakest reading, and it matches what
those builders recorded.

`writeLayerCoverage` and `readLayerCoverage` both refuse a malformed cell: a `completeness` outside
`[0, 1]`, an unknown `basis`, or a negative or fractional `observed_rows`. Callers treat these
values as statements about what's known, so a well-formed wrong value is worse than an error.

The worked example of a `surveyed` basis covers one class and one region, with the arithmetic and
the limits of what it establishes. It is
[`docs/superpowers/specs/2026-08-27-exclusion-grade-coverage-pilot.md`](https://github.com/sister-software/mailwoman/blob/main/docs/superpowers/specs/2026-08-27-exclusion-grade-coverage-pilot.md),
built by `mw gazetteer build poi-coverage`.

**The meaning-of-zero rule.** A _missing_ `layer_coverage` row means **unknown (unmapped)**,
never "surveyed and found empty." `readLayerCoverage` returns `undefined` for an unsurveyed cell,
and callers mustn't treat that as `{ completeness: 0 }`. A missing row is never evidence by
itself. For this reason, the table is **required by the interface from the start**, even for
layers that happen to be complete today. A later addition of coverage information to sealed artifacts
would mean rebuilding every one of them. See [the meaning of zero](./the-meaning-of-zero.mdx) for
the general principle: a value never records its own absence, so store presence separately from
the value.

Scorers built on layers follow the same rule. They emit `{ claim, evidence_found,
coverage_confidence }` and never a bare score. A cell with sparse coverage moves a score toward
"insufficient survey data," which is a legitimate output in its own right and is distinct from a
silent zero.

## The TypeScript API

`@mailwoman/core/layers` is the single module boundary. A layer's build script and its readers both
use it, and each layer defines its own domain tables.

```ts
import {
	type layerschemadatabase,
	createLayerManifestTable,
	createLayerCoverageTable,
	writeLayerManifest,
	readLayerManifest,
	probeLayerManifest,
	writeLayerCoverage,
	readLayerCoverage,
	COVERAGE_INSERT_BATCH,
} from "@mailwoman/core/layers"
```

- **DDL**: `createLayerManifestTable(db)` and `createLayerCoverageTable(db)` build the two
  tables through Kysely's schema-builder. The coverage table is `WITHOUT ROWID`, which suits small
  fixed-width rows probed by PK. Intersect `layerschemadatabase` into your layer's own schema
  interface, so that a column added to one side causes a compile error against the other.
- **Write (build-time, cold path)**: `writeLayerManifest(db, manifest)` inserts the single
  identity row and validates invariants (known tier, known freshness policy, at least one spine
  key) before it writes. `writeLayerCoverage(db, cells)` bulk-inserts coverage in chunks of
  `COVERAGE_INSERT_BATCH` (5,000 rows/statement) to stay under SQLite's limit of 32,766 bound
  variables. A continental-scale res-6 cell count exceeds that limit in one `.values()` call.
- **Read**: `readLayerManifest(db)` returns the parsed, camelCase `LayerManifest`, and throws on
  a missing, empty, multi-row, or invalid table. `probeLayerManifest(db)` reads the same row but
  returns `{ state: "absent", reason }` when the database has no `layer_manifest` table, the state of an
  artifact built before the layer interface. A reader that serves several layers uses it to report
  that file and keep serving the others. An empty or invalid table still throws, because the build
  that created the table never wrote its row. `readLayerCoverage(db, h3Cell)` returns a `CoverageCell`
  or `undefined`. Apply the meaning-of-zero rule to `undefined`.

Validation runs at both ends, so a hand-built or corrupted layer fails when it is
opened instead of three joins downstream.

## Checklist for authors

A new layer must meet these interface requirements, in order:

1. Define your domain schema as a Kysely schema module (`createXTable` next to the typed
   interface), following the project's DB conventions: raw positional INSERTs for the hot bulk
   load, `WITHOUT ROWID` only for small PK-probed tables, and FTS5 as raw DDL where needed.
2. Intersect `layerschemadatabase` into your schema and call `createLayerManifestTable` and
   `createLayerCoverageTable`.
3. Choose a spine: store every id space your source provides, declare them in `spine_keys`, and
   key every domain row by at least one of them.
4. Populate `layer_coverage` from your source's actual survey extent: one row per surveyed cell,
   with an accurate `completeness`, and unsurveyed cells left absent rather than zero-filled.
   Declare a `basis`. Use `source_present` unless you can identify the data the completeness was
   measured against. Use a stronger basis only when you have that evidence.
5. Write the manifest with real provenance: `source`, `source_vintage`, `build_cmd` and
   `build_sha`, the correct `tier` and `license`, and a caller-supplied `created_at`.
6. Build to a temp path, verify, then swap the file into place under `$MAILWOMAN_DATA_ROOT` and
   seal it 0444. Never modify a shipped or live layer. Rebuild it instead.

## Admissible license expressions

`writeLayerManifest` accepts a `license` only if each of its identifiers is one of the following: an identifier in
the obligations table (`packages/core/lib/license/obligations.ts`, which `mailwoman doctor` also summarizes), a
`LicenseRef-` this repository defines, or `NOASSERTION` when the publisher states no license. A manifest is sealed
data. Without this check, a vendor-suffixed identifier such as `PDDL-1.0-USGov-NRCS` would ship and read as
unrecognized on every machine that opens it.

| `LicenseRef`                         | Meaning                                                                                                                                                                                      | Obligations |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| `LicenseRef-Commercial`              | mailwoman's commercial agreement (`COMMERCIAL-LICENSE.md`)                                                                                                                                   | attribution |
| `LicenseRef-USGov-Public-Domain`     | a work of the United States Government, 17 U.S.C. § 105 — SSURGO, the FCC BDC filings. SPDX has no identifier for it                                                                         | none        |
| `LicenseRef-WhosOnFirst-Mixed`       | the Who's On First records, subject to the terms of the sources the WOF source list names. Its own text grants CC0 over "the format and structure", in those words, and requires a link back | attribution |
| `LicenseRef-US-Mixed`                | the US address layer: NAD, OpenAddresses runs and Overture's OpenAddresses rows, each under its publisher's own terms. No one document states them                                           | unknown     |
| `LicenseRef-Undeclared-Input`        | a fold whose own database declared no terms this build could read. `candidateLayerManifest` adds it rather than leaving the fold out of the expression                                       | unknown     |
| `LicenseRef-INEGI-Terms`             | Mexico's `Términos de Libre Uso de la Información del INEGI`, a text that cites no Creative Commons license and states no version. Retrieved 2026-09-27                                      | attribution |
| `LicenseRef-GEBCO-Operator-Election` | the IHO-IOC GEBCO Gazetteer of Undersea Feature Names, used under the operator's own election of 2026-11-02 (#2896)                                                                          | attribution |

`LicenseRef-GEBCO-Operator-Election` records an election made without a written grant. GEBCO and NOAA NCEI
publish the gazetteer with a citation request and state no restriction. GEBCO's disclaimer excludes only
use for navigation or for safety at sea. The records are names, generic terms and coordinates, and the
undersea layer uses them as map labels and search names. The layer credits "IHO-IOC GEBCO Gazetteer of
Undersea Feature Names, www.gebco.net". A request for written confirmation has gone to GEBCO. If GEBCO's reply
restricts reuse, the layer moves to GeoNames class `U` under CC BY 4.0.

`LicenseRef-Undeclared-Input` is deliberately absent from the obligations table, so `summarizeLicense`
reports it as unrecognized and `refusalsForPublication` refuses a layer that includes it. A grant no one has
read imposes unknown obligations rather than none, and an expression that omitted the fold would read as a
complete list of the artifact's terms.

### Who's On First's obligations

`LicenseRef-WhosOnFirst-Mixed` records attribution only (#3163). The reading rests on four texts and
two counts.

Each WOF repository's `LICENSE.md` states: "Crediting Who's On First is recommended and linking back to this
License is required." It continues: "The Who's On First dataset is both original work and a modification of
existing open data. Some of those open data projects **do** require attribution." The attribution notice holds
the link back, and the OGC server's `license` link for this identifier points to that text.

The [WOF source list](https://github.com/whosonfirst/whosonfirst-sources/blob/master/data/sources-spec-latest.json)
(182 entries, retrieved 2026-11-21), types 16 entries as restricted or non-commercial: 14 `Restricted`, `eg` as `Restricted Use License
(non-commercial)` and `wmo` as `CC BY-NC-ND 4.0`. Each has `usage_geometry: 0`. All but `iso` and `itu` also have
`usage_property: 0`. `wikipedia` is `CC BY-SA 3.0` with `usage_geometry: 1` and `usage_property: 1`.

`LICENSE.md` describes Quattroshapes geometry with `qs_source:EuroGlobalMap` and asks for credit to the European
national mapping agencies it lists. The non-commercial `eg` entry isn't that data. Its description reads:
"EuroGeographics restricts this usage to non-commercial, so this source is used for concordance values only.
EuroGeographics also offers other commercial data products, and some open data with a coarser resolution
1:1,000,000 scale in their EuroGlobalMap project (which is aggregated by both Quattroshapes and Mesoshapes)." The
source list types `quattroshapes` as `CC BY 2.0`.

Measured 2026-11-21 over the 271 clones under the WOF repositories root, parsing every record file
(8,787,297 records, the count the record store holds, plus 685,831 alternate-geometry files). One alternate file
in `whosonfirst-data-admin-alt` is a Git LFS pointer and doesn't parse.

| What a record holds                                                                          | Records                   | In `admin-global-priority.db` `spr` | In `candidate.db` |
| -------------------------------------------------------------------------------------------- | ------------------------- | ----------------------------------- | ----------------- |
| a `src:*` value (`src:geom`, `src:geom_alt`, `src:population`, …) naming a restricted source | 0                         | 0                                   | 0                 |
| `qs:source` naming EuroGlobalMap                                                             | 74,359                    | 74,276                              | 74,230            |
| of those, `src:geom` = `quattroshapes`                                                       | 28,558                    | 28,477                              | 28,431            |
| `iso:country`, `iso:subdivision`, `iso:parent`, `itu:country_code`, `itu:region`             | 8,784,819 property values | none stored                         | none stored       |

The EuroGlobalMap records are in 52 countries, FR 19,043, DE 9,864, IT 8,674 and UA 6,198 the largest. They're
Quattroshapes data under CC BY 2.0, and the attribution obligation covers the agencies' credit. The
`iso:` and `itu:` properties never reach a layer, because the WOF record store keeps only `wof:` and `name:`
properties and a short list of `geom:`, `lbl:`, `gn:`, `mz:` and `edtf:` ones (`isStoredProperty`).

Restricted sources reach the admin build as identifiers only, in the `concordances` table: `fct:id` 78,938,
`eg:gisco_id` 74,066, `iso:code` 4,506, `iso:id` 3,850, and under 1,000 each for `nyt`, `digitalenvoy`, `m49`,
`itu`, `ioc`, `uncrt`, `icao`, `wmo` and `latimes`. That's the concordance usage the source list records for
each of them.

Wikipedia is the `src:geom` of 14 records and the `src:population` of 2,338 (`wikipedia` or its prefix `wk`).
Of those 2,352 records, 2,331 are in the admin build's `spr` table, 2,330 in its `place_population` table and
2,330 in `candidate.db`, where they supply centroids, boxes and populations.

Those values carry no share-alike term. The
[CC BY-SA 3.0 legal code](https://creativecommons.org/licenses/by-sa/3.0/legalcode) defines the Work as "the
literary and/or artistic work offered under the terms of this License". Its Section 2, "Fair Dealing Rights", opens by stating that no part of the License is
"intended to reduce, limit, or restrict any uses free from copyright". A population figure and a coordinate are facts rather than literary or artistic work. The license grants no
right over them and imposes no condition on them, share-alike included. The 14 geometries are each a single `Point` with a `geom:area` of 0, read on 2026-11-21 from the
WOF record store's located GeoJSON for the issue's record-ID list. They're airport and airfield `campus` records,
such as Innsbruck Airport (`102556255`) and Istanbul Airport (`1779770747`). None is a drawn polygon, which
would be the one Wikipedia contribution that could carry authorship. The table therefore records attribution
alone.

Issue #3163 records the scan's per-country and per-property tables.

### The US address layer's obligations

`LicenseRef-US-Mixed` records unknown obligations, so it stays out of the obligations table. The sources whose
terms were read owe attribution at most. The publishers of 30% of the layer's records have terms no reader has
recorded, and 13 publishers whose terms the register refuses have files in the layer. The OGC server's `license`
link for this identifier points to this section. Each region's `ATTRIBUTION.json` lists that region's sources
with the terms OpenAddresses records for each.

Three outputs publish the per-source reading, all from one join in `packages/mailwoman/lib/data/mixed-layer.ts`
of the regions' `ATTRIBUTION.json` ledgers to the register through `us-situs-sources.json`:

- The data bill of materials (`mailwoman data bom`) nests one component per source under the layer's component.
  Each states the publisher, the register decision, the basis (`open-license`, `publisher-grant`,
  `no-restricting-terms`, `refused`, `unread` or `unregistered`), what the terms page held (`terms`, an empty
  statement as `no-statement`, or site-wide terms the decision didn't read as the dataset's as
  `site-terms-not-applied`), the terms URL, the attribution and share-alike states and the record count. A source with no register
  row reads `unregistered` with unknown obligations.
- `mailwoman doctor` prints the count of sources in each obligation class for the attached layer and points to
  the other two.
- `mailwoman situs attribution-manifest --layer-version <version>` writes `NOTICE.txt` beside the version's
  `manifest.json`, the credits a customer ships with the layer, and `mailwoman situs publish` uploads it.

An aggregator's row, such as Overture's, sets no obligation of its own: OpenAddresses and Overture grant no
license over address rows, so the publishing body's row decides unless the aggregator's row blocks.

The US layer build (`packages/corpus/lib/us/address-records/layer.ts`) combines three sources per state:
NAD release 24, the Overture addresses rows from the datasets other than NAD, and the OpenAddresses runs of
the plan. Since #3241 the build admits each source by its register decisions. `packages/corpus/data/us-situs-sources.json`
maps each source id to the register rows its data comes from. `admitUSStateSources` fully admits a source when
every row holds an elected decision permitting `fetch`, `extract` and `redistribute-data`, the rule the corpus
build applies to `transform` and `train`. A refused source is always excluded. A source with unread terms or no
row is excluded while `EXCLUDE_UNREAD_SOURCES` in `packages/corpus/lib/us/address-records/rights.ts` holds, its
default, or the build runs with `--exclude-unread-sources`; `--no-exclude-unread-sources` admits it. Each region's
`build.json` lists the excluded sources and the admitted unread ones with their reasons, and
`mailwoman situs layer` prints both. Before #3241 the build read only the terms an OpenAddresses source definition records, and the
measurement below describes a layer built that way.

The source texts, retrieved 2026-11-21:

- USDOT's
  [NAD disclaimer](https://www.transportation.gov/mission/open/gis/national-address-database/national-address-database-nad-disclaimer)
  states that the NAD is a federal work outside copyright under 17 U.S.C. § 105 and is "available for re-use
  without limitation or restriction." It also states that the NAD isn't intended as a mailing list and "is
  subject to individual state statutes that prohibit it's use as a mailing list." That limit comes from state law rather than from a license term, so no
  obligation class records it.
- The [OpenAddresses README](https://github.com/openaddresses/openaddresses#license) states that the
  pipeline's data keeps the original sources' licenses: "Individual sources will have their own licenses. The
  OpenAddresses team does its best to summarize the source licenses in the source
  JSON for each source." A definition's recorded license is OpenAddresses' summary of the publisher's terms.
  A definition with no license field means no summary was written. It doesn't mean the publisher states no terms.
- Overture's [attribution page](https://docs.overturemaps.org/attribution/) states that the addresses data "comes
  from a variety of sources. All carry permissive open licenses. Some have special terms or require
  attribution." It lists, for example, El Dorado County as "Public domain by judicial interpretation of the
  Public Records Act". The register refuses El Dorado County after reading the county's own page, so Overture's
  labels are a third party's claim.

The US position in `packages/corpus/lib/us/AGENTS.md` elects a public body's file published without restricting
terms. A register decision records that reading of the publisher's page. Measured 2026-11-21 over the 52 regions
of the served manifest, `addresses/us/2026-11-13/manifest.json`, by reading each region's `ATTRIBUTION.json` and
joining each source to its row in `address-source-register.json`. An Overture dataset joins through
`us-situs-sources.json`, and an OpenAddresses run through the row whose `access` names the run.

Of the 179 elected, 177 are elected under the US factual-data reading, the City of Berkeley under its portal's
reuse statement, and `us/dc/statewide` under CC BY 4.0, which brings in the attribution term.

The 22 refused source ids are 13 publishers' files, 12 OpenAddresses runs with 1,317,791 records and 10 Overture
datasets with 28,852: the counties of San Luis Obispo, El Dorado, Madera, Tehama, Mono and Mariposa in California, Brevard and

County file in Idaho. Each decision states the restriction, such as Cook County's clause withholding

The 7 unchecked source ids are SanGIS, Placer, Stanislaus and Santa Cruz in California and Lee and Sumter in
Florida. Of the 1,988 runs without a register row, 1,691 record no terms (39,746,932 records), 210 record an

Every one of those runs now has a register row from the 2026-11-21 terms reading (#3260), and the register
decides each through `createSourceAdmitter` in `packages/corpus/lib/us/address-records/rights.ts`, which the
layer build, `situs address-points` and the county address-point builder share.

The register's own reviews show why a definition that records no terms doesn't settle the reading. The layer
holds 88 OpenAddresses runs that record no terms and have a register row. Readers elected 76 of them and found
restricting terms on 11, and one is unread.

`LicenseRef-INEGI-Terms` is in the table, because its terms were read. They permit copying, publishing,
adapting, extracting and commercial use, require the credit `Fuente: INEGI, <product name>`, and state no
share-alike term. The retained bytes are
`internal/strategy/rights-receipts/mx-gb-2026-09-27/mx-inegi-terminos.html`.

Measured 2026-09-27: 28 of the 28 postcode and locality databases under `db/wof/` have no
`layer_manifest`. Two record their terms in a `meta` key/value table instead, as prose —
`postalcode-gb-codepoint.db` reads `Open Government Licence v3.0` and `postalcode-ni-osm.db` reads

The remaining 26 state terms nowhere. `LicenseRef-Undeclared-Input` exists for them.

`mailwoman data inventory` reports this for a whole data root. It reads each database's manifest with
`probeLayerManifest`, and its layer report states one of four outcomes per database: read, absent (no
`layer_manifest` table), invalid (the table exists and `probeLayerManifest` refuses its contents) or
unopenable. For a read manifest it states the license, the obligations `summarizeLicense` gives it, and each
source with the location its owning package records. The owners' tables are joined in
`packages/mailwoman/lib/data/source-locations.ts`, and `resolveLayerTerms` in `@mailwoman/core/layers/provenance`
turns manifests into license and source links for both the report and the OGC adapter.
