# How much independent address data each measured locale has

A row count doesn't say how much independent address data a locale-isolated graph has. The sampler
restarts an exhausted source with a fresh shuffled pass, so a small source is presented once per
pass and its row count reads as supply it doesn't have. A corpus can also hold one street rendered a
hundred ways, and those hundred rows count one street.

`locale_supply_census` counts four things a row count cannot give, over a full scan rather than a
sample, because a distinct count cannot be extrapolated from a sample. This page records
the census results.

Measured on `v0.32.0-locality-shape`, all 718 train files, unless a row states otherwise. Receipts are stored
on the `mailwoman-training` volume as `audits/locale-supply-<iso2>.json`.

## `synth-` source ids and their current spellings

Read this before the table. A source id beginning `synth-` is a **locale recipe**, and every one of
them renders real published address tuples through a template. Readers took the prefix to mean the
rows were fabricated. A recipe-output source is now spelled `<operation>-<tail>` with the tail
unchanged, and the prefix states what the recipe did to attested data: `rendered-de`, `fragment-fr`,
`spliced-unit-v30`, `invented-po-box-cedex`, `codex-bare-postcode`, `reviewed-postcode-tail`. The
prefix never restates `surface` or the register.
`packages/corpus/lib/recipes/sources.ts` records every source under both spellings, with the file
that writes it. `v0.7.0-de-holdout` is the first corpus whose rows store the current spelling. Every
corpus assembled before it, and every training config that targets one, keeps the `synth-` spelling,
because a source id is the string stored on every row of a built corpus and a config keys on what its
corpus stores. The left column below uses the spelling the measured corpus,
`v0.32.0-locality-shape`, stores, and the middle column gives the spelling a corpus assembled from
`v0.7.0-de-holdout` on stores:

| source     | stored now    | reads                                                        |
| ---------- | ------------- | ------------------------------------------------------------ |
| `synth-gb` | `rendered-gb` | HM Land Registry Price Paid Data, `ppd/<date>/gb-tuples.csv` |
| `synth-nl` | `rendered-nl` | OpenAddresses NL `countrywide.csv`                           |
| `synth-pt` | `rendered-pt` | OpenAddresses PT `countrywide.csv`                           |
| `synth-ch` | `rendered-ch` | OpenAddresses CH `countrywide.csv`                           |
| `synth-hr` | `rendered-hr` | OpenAddresses HR `countrywide.csv`                           |
| `synth-sk` | `rendered-sk` | OpenAddresses SK `countrywide.csv`                           |
| `synth-lu` | `rendered-lu` | OpenAddresses LU `countrywide.csv`                           |
| `synth-it` | `rendered-it` | OpenAddresses IT `countrywide.csv`                           |
| `synth-es` | `rendered-es` | the CNIG export, read raw for the pedanía variant            |
| `synth-nz` | `rendered-nz` | a LINZ-derived OpenAddresses extract                         |

Three columns record this, each answering one question. `source` names the code that produced the
row, `register` names the publication its record came from, and `surface` states how the text was
built: `attested` is the publisher's own string, `composed` is a template over one real record's
fields, and `invented` names no published record. A fourth, `augmentation`, names the transform that
derived a row from the base row `base_source_id` names, such as `case-lower`, and is null on every
other row. A corpus written before #2741 holds that value, or the producer's name, in a `recipe`
column; `corpusRowFromParquet` in `@mailwoman/corpus/parquet/schema` reads it as an augmentation only
where `base_source_id` is set.

So `rendered-gb-os-open` writes `register: gb-os-opendata`, `surface: composed` — an OS OpenData
record in the recipe's order. `invented-po-box` writes `register: null`,
`surface: invented`, because no register asserts that box exists. `fragment-assay`,
`spliced-sub-venue` and the other shape recipes divide the same way.

With `register` and `surface` in separate columns, a composed rendering of a Land Registry record
reads as a real record written in the recipe's order.

## GB train supply by source

Every GB row with a street comes from one source, and that source isn't a gazetteer:

| source            |       rows | has a street |
| ----------------- | ---------: | ------------ |
| `wof-postalcode`  | 13,548,202 | no           |
| `wof-admin`       |  1,263,798 | no           |
| `synth-gb`        |    800,000 | yes          |
| `synth-sub-venue` |     31,800 | shape recipe |
| `synth-fragment`  |        907 | shape recipe |

`street_rows` is 825,083 against 832,707 rows from the three recipe sources. Scanned locally on
`v0.5.0`, GB's two `wof-*` sources hold 14,812,000 rows and **0** have a `street` or `house_number`
tag, so every GB street row the model sees is a `synth-gb` rendering of a Price Paid row.

Price Paid holds 25,674,049 rows and the recipe emits 800,000 of them (3.1%). The recipe reads
them through Algorithm-R reservoir sampling with a reservoir of `RESERVOIR_CAP`, 1,200,000 per
part, so memory stays bounded on a 1.5 GB input.

Two further readings of the same receipt. 13,548,202 of GB's 15,644,707 rows — 86.6% — sit in two
component sequences, `locality|postcode` and `postcode`. The largest sequence that includes a street,
`house_number|street|locality|postcode`, holds 268,173 rows, or 1.7%.

**Price Paid covers England and Wales.** Scotland and Northern Ireland register land separately, so
a GB postcode-area census over these rows finds ZE, HS, KW, IV, DG, PA, PH and AB at zero. That's a
property of the register rather than of GB addressing, and it is why `defaultHoldouts()` couldn't
pick a Scottish area.

## GB source data on disk that no corpus adapter reads

The corpus has 23 adapters and none of them is GB. These sit in the data root, fetched and recorded,
with no path to a `CanonicalRow`:

| path                | size   | what it is                                  |
| ------------------- | ------ | ------------------------------------------- |
| `epc/<date>`        | 26 GB  | UK Energy Performance Certificates, 15 CSVs |
| `osopenuprn/<date>` | 2.7 GB | OS Open UPRN                                |
| `codepoint/<date>`  | 184 MB | Code-Point Open                             |

EPC records `address1`, `address2`, `address3`, `postcode` and `posttown` per certificate. UPRN and
Code-Point are read by `gazetteer-pipeline` for the retrieval artifacts — `pair-index-gb.bin`,
`postcode-gb.bin` — rather than for training rows.

GB's street supply is therefore one 3.1% sample of one register. None of the three sources above is
read for training rows.

## Source pools for PT, CH, HR, SK and LU

These five locales were added on 2026-09-22.

Read by `COUNTRY_SOURCES` in `packages/corpus/lib/international/recipes/locale.ts` for the first
time. These are pool sizes reported by the recipe's own reader on the run that generated each
output, rather than corpus row counts. No corpus contains these rows yet.

| locale | rows in the source CSV | reservoir drew | city-noise drops | rows emitted | skipped |
| ------ | ---------------------: | -------------: | ---------------: | -----------: | ------: |
| PT     |              5,667,574 |      1,200,000 |                0 |      800,000 |     332 |
| CH     |              2,759,181 |      1,200,000 |                0 |      800,000 |      12 |
| HR     |              1,679,500 |      1,200,000 |            1,003 |      800,000 |      63 |
| SK     |                219,728 |        219,728 |                0 |      200,000 |       0 |
| LU     |                164,415 |        164,415 |                0 |      150,000 |       0 |

SK and LU drew their whole source because it is smaller than `RESERVOIR_CAP`'s 1,200,000. Their
emitted counts are set below the pool so no row is drawn twice.

Three countries with an extract on disk are deliberately absent, each for a reason recorded at the
`COUNTRY_SOURCES` call site: Saudi Arabia is Arabic script and this repository ships no Arabic
graph. Iceland has a locality on 19 of 125,681 rows. Estonia is blocked by `cleanCityNoise`
rather than by supply, because its `CITY` is two admin levels joined by a comma and rule 1 drops any
city containing one.

## What this doesn't establish

- Whether a templated surface teaches as well as an attested one. The addresses are real, but the
  rendering is the recipe's, and no measurement here isolates the difference.
- Whether GB is worse supplied than the alternatives. Five locales have a receipt, and the funnel's
  opportunity view lists 28 candidate jurisdictions with no corpus rows at all.
- What a GB sample above 3.1%, or an EPC adapter, would change. Both could be measured, and neither
  has been.

## Compare a locale metric with this page

A validation metric for a locale is bounded by what that locale's split contains. That's a
different measurement: `audit_validation_coverage`, and the per-locale floor in
[Contributing model work](../CONTRIBUTING_MODEL_WORK.mdx). This page measures supply: what a split
could hold out. `audit_validation_coverage` measures what a split did hold out.
