# Capacity planning

This page answers two deployer questions: **"how much space will I need to run a
whole-world mailwoman installation?"** and **"how much memory will that take?"** Every number
here is either measured on our artifacts (dated, with the artifact identified) or an extrapolation
whose per-unit cost is measured. When an artifact changes materially, re-measure and update the
table. Every number in this file needs a citation.

## Disk and memory model

Rooftop fidelity is a property of the data. The parser is a 38 MB int8 ONNX
model shared world-wide (the locale overlay packages don't ship a copy of it); adding a country never
grows it. Fidelity grows by adding **layers** — sealed, read-only, memory-mapped SQLite
artifacts probed by parse-derived keys (see
[the layer interface](./layer-interface.mdx)). Because retrieval is a keyed probe — house
number + street within an already-resolved locality — rather than fuzzy full-text recall,
there's no query-time index that must be resident in RAM. Disk holds the data. The page
cache holds whatever the query traffic touches.

## Measured unit costs (2026-08-07)

| Artifact                                                        | Measured size | Unit cost                    |
| --------------------------------------------------------------- | ------------- | ---------------------------- |
| Parser model, int8 ONNX (model 9.0.0)                           | 38 MB         | one model, world-wide        |
| Full en-us weights bundle (model + tokenizer + FST + lexicons)  | 72 MB         | overlays add ~2–20 MB each   |
| US rooftop address points, all states (124.9M points)           | 29 GB         | **~230 B/point** incl. index |
| WOF admin hierarchy, whole world (`admin-global-priority.db`)   | 5.0 GB        | —                            |
| Candidate gazetteer, global                                     | 0.9–1.6 GB    | —                            |
| GB postcodes, SQLite (`postalcode-gb-codepoint.db`, 1.75M keys) | 836 MB        | ~480 B/key                   |
| GB postcodes, packed (`postcode-gb.bin`, same 1.75M keys)       | 21 MB         | **~12 B/key**                |
| NL PC6 postcode DB                                              | 193 MB        | —                            |
| International postcode DB                                       | 144 MB        | —                            |
| poi.db (13.68M Overture rows)                                   | 3.7 GB        | ~270 B/row                   |

The GB postcode pair shows that **the same dataset costs 40× less
when packed for its one probe shape** than in general-purpose SQLite form. See the
cost-reduction roadmap below.

## Whole-world estimate

The world's acquirable rooftop set (OpenAddresses global + OSM address nodes + national
registers: BAN, GNAF, LINZ, …) is roughly 500–800M points. At the measured 230 B/point:

| Component                             | Estimate       |
| ------------------------------------- | -------------- |
| Address-point spine (500–800M points) | 115–185 GB     |
| Admin + candidate + polygons          | ~8 GB          |
| Postcodes, all countries              | 4–6 GB         |
| Global POI (~60M Overture places)     | 16–20 GB       |
| **Total disk**                        | **150–220 GB** |

**Memory: ~1–2 GB floor.** The fixed cost is the ORT session + tokenizer + FST + lexicons
(~300–500 MB resident). Every layer is memory-mapped and probed by key, so the rest is page
cache: more RAM lowers latency and doesn't change results, and no heap has to hold an index.

For context, here are the incumbents this trades against, from their public deployment guidance for
full-planet installs (approximate). A planet Pelias is on the order of 600 GB of
Elasticsearch that needs to be hot across a cluster. A planet Nominatim is on the order of
1 TB of Postgres plus an 80 GB flatnode file. Both keep a large index resident at query time.
Mailwoman spends that cost at build time and keeps the result in sealed artifacts.

## The per-locale template

A locale is a fixed kit. The kit doesn't change the model:

| Kit piece           | What it is                                                | Typical size   |
| ------------------- | --------------------------------------------------------- | -------------- |
| Weights overlay     | data-only npm package (`@mailwoman/neural-weights-<loc>`) | 2–20 MB        |
| Codex module        | postal reference + branded types (`@mailwoman/codex`)     | in-package, ~0 |
| Postcode DB / bin   | centroid or full-fidelity lookup                          | 2 MB–836 MB    |
| Address-point layer | rooftop register as a sealed layer                        | ~230 B/point   |
| FST gazetteer       | per-locale name matcher                                   | 4–21 MB        |

Worked examples: en-us (all pieces), fr-fr (overlay + BAN points), en-gb (overlay +
Code-Point postcodes, with the rooftop layer as the open acquisition). Coverage status per country
belongs to the coverage register rather than this file.

## Cost-reduction roadmap

Three changes wait on the five-arm benchmark's per-query-class latency and fidelity data,
because a layout chosen before that measurement would rest on reasoning rather than measurement.

1. **Packed address-point spine** ([#1547](https://github.com/sister-software/mailwoman/issues/1547)) —
   parent-relative encoding: per-locality street dictionaries, delta-encoded number
   sequences, coordinates as 16-bit offsets from the parent H3 res-9 cell. The 40× GB
   postcode comparison above is the evidence for this estimate. The landing estimate is 40–60 B/point, taking the
   world spine from ~150 GB to ~30–50 GB. Decode must stay fixed-stride trivial. The
   resolver ladder runs synchronously on every keystroke.
2. **Admin-keyed distribution by country file** ([#1548](https://github.com/sister-software/mailwoman/issues/1548)) —
   deployment scope becomes a fetch list of per-country files, each carrying its own coverage
   manifest ([the meaning of zero](./the-meaning-of-zero.mdx)). Differential updates: a register rev re-fetches one
   country file. The candidate gazetteer stays global and monolithic, because namesake resolution is
   inherently global (#1546 is what candidate-set gaps do).
3. **Targeted precompute** ([#1549](https://github.com/sister-software/mailwoman/issues/1549)) —
   build-time artifacts that make hot, stable queries single lookups (H3-ring KNN lists,
   interpolation-ready per-street tables). The candidate table and postcode bins already follow
   this pattern, and the 40× comparison shows probe-shaped precompute costs less than the
   general form it replaces. Only stable + hot queries warrant an artifact, because precompute freezes a
   query distribution.

Changes 1 and 3 overlap: a layout specialized to the probe shape both compresses the data and
precomputes the lookup. All three come from the same build passes, and the existing practice of
rebuilding rather than patching keeps them consistent.
