# Page briefs for the new public site

These briefs define proposed reader results and their acceptance checks. IDs and routes come from `information-architecture.md`. The writer must confirm every current command, package, output shape, footprint, supported locale, and numerical claim against the release being documented. Old article text is source material with an unverified factual status. Each page has one primary reader result, a role, source leads, and a check that can fail.

D15 implementation status: Published `@mailwoman/mcp@11.0.0` advertises `mailwoman-mcp` as its stdio executable and depends on `@modelcontextprotocol/sdk` `^1.32.2`. Its `mailwoman_parse` tool calls `loadCore()` before parsing. That function requires a candidate database or suitable Who's On First extracts. A disposable client using SDK 1.32.2 connected, listed the nine tools, and called `mailwoman_parse` with `1600 Pennsylvania Avenue NW, Washington, DC 20500`. The call returned `isError: true` with `✗ no gazetteer data found — the endpoint needs a resolver database to answer queries.` The process itself exited 0. The only repository `candidate.db` found was an 83-byte UTF-8 test fixture. SQLite rejected it with `file is not a database`. No supported small database was found for a successful parse call. Keep D15 unpublished until a valid database is available and the complete client call can be run. Do not infer parse-only operation from the tool name.

D22 implementation status: Published `mailwoman`, `@mailwoman/neural`, and `@mailwoman/neural-weights-en-us` 11.0.0 parsed `Empire State Building` with kind `landmark` and one `venue` node spanning `[0, 21)`. The same packages parsed `Behind the gas station` with kind `landmark` and one `venue` node spanning `[0, 22)`. Both parses returned `poiIntent: null` and no stage faults. These parse results do not identify a place candidate or coordinate. The older 8.7.0 guide describes `Empire State Building` as a `locality` node. The observed 11.0.0 node is `venue`. The worktree has no valid candidate, POI, or landmark database and no data-root override. Published `geocode/session.ts` can open a configured POI database and an optional `landmarks.db` beside it. D22 needs an installed, versioned geographic data setup and executed place-candidate responses before a reader can follow a place-selection procedure. Keep `/docs/guides/handle-landmark-queries` unpublished until those responses can be checked.

## Draft and review sequence

1. Confirm the reader question and the page role. The proposed role can change if a task exercise reveals a different need.
2. Check `source-to-target.md` for old sections and old URLs. Extract facts into a claim list before writing new prose.
3. Check each command against the owning code or released artifact. Check each measurement against its dated data source or executed example. Mark unsupported claims for omission or a labeled open question.
4. Draft from a role template in `docs/engineering/page-templates/`. Use Good Docs prompts only where they serve the reader's task. Define terms on first use and follow `docs/engineering/writing-system.md`.
5. Run the page's commands, inspect rendered output and links, and ask a reader in the target group to attempt the result. Record version, platform, data, and date.
6. Publish the replacement route and its redirects together. Check inbound old links and the old section anchors before retiring the source page.
