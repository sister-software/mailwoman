## 3. Orphan pages

**Method:** every file under an autogenerated-sidebar directory (`understanding`, `concepts`,
`recipes`, `plan`, `evals`, `retrospectives`, `licensing`) is automatically pulled into that
sidebar's tree by Docusaurus, and this config has no per-file opt-out. Only one file in `articles/`
sets `draft: true`, `unlisted: true`, or `sidebar: false`, and that file is also excluded from the
build (see below). Orphans can therefore exist only among files at the `articles/` root that are
missing from the explicit `startHere` array, or in a directory that no sidebar includes.

**`articles/` root inventory** (non-asset files): `api.mdx`, `contributing.md`,
`getting-started.mdx`, `releases.mdx`, `sotm-2026-talk-proposal.mdx`, `status.mdx`.
`startHere: ["status", "releases", "getting-started", "api"]` accounts for 4 of these 6.

### Orphans found: 2

1. **`docs/articles/contributing.md`** builds to `/docs/contributing/` (confirmed present in
   `docs/build/docs/contributing/index.html`). Its frontmatter sets `sidebar_position: 5`, which has
   no effect because `startHere` is an explicit array and is not autogenerated. The page therefore
   appears in no sidebar. The `5` suggests the page was meant to follow `api` (implicitly position 4)
   in the Start Here nav and was dropped by accident when the array became explicit.
2. **`docs/articles/sotm-2026-talk-proposal.mdx`** builds to `/docs/sotm-2026-talk-proposal/`
   (confirmed present in the build output). This orphan **is** intentional. A comment in
   `sidebars.ts` mentions it by name: _"these live at the articles/ root alongside orphans like
   sotm-2026-talk-proposal that should stay out of the nav."_

### Adjacent but out of scope for "orphan" (excluded from the build outright rather than merely un-navved)

These files are **not reachable by URL at all**. Docusaurus's `exclude` glob removes them from the
docs plugin's content before routes are generated, so their URLs return a 404 and they do not
exist as unlisted pages:

- `docs/articles/reviews/`: 15 files, entirely excluded (`reviews/**`).
- 38 `evals/**/*postmortem*` files + 1 `evals/**/*night-shift-session-report*` file: 39 files,
  all under `evals/night-shifts/` and `evals/retrospectives/`.

Total excluded from the build: 54 files. One of the 38 postmortems,
`evals/night-shifts/2026-06-18-night-postmortem.md`, is also the one file in the repo with
`draft: true` frontmatter. That setting is redundant, because the glob exclude already removes it.

**Commands run:**

```bash

find docs/build/docs -maxdepth 1 -iname "*contributing*" -o -maxdepth 1 -iname "*sotm*"

## 4. Duplicate / near-duplicate titles

**Scope:** frontmatter `title:` field, swept across all of `docs/articles/` **excluding only**
`reviews/`, which is never published. Per the task, this sweep **includes** `evals/` and
`retrospectives/`, including the 39 postmortem and session-report files that are excluded from the
live build. A match involving one of those files is flagged below, because a title collision there
affects only repository hygiene and cannot appear in live search.

**Result:** of 370 `.md`/`.mdx` files scanned, only **179 have a `title:` frontmatter field**;
**191 do not** (they rely on Docusaurus's fallback to the first H1 heading). This is itself a
finding: roughly half the corpus's page titles are undeclared and this sweep can't see them. The
191 no-title files cluster heavily in `evals/` (calibration, competitive-parity,
model-versions, night-shifts, resolver-geo) — dated report-style docs that were never given
explicit frontmatter titles.

### Exact duplicates: 1 pair

| Title            | Files                                                                                        |
| ---------------- | -------------------------------------------------------------------------------------------- |
| `Retrospectives` | `docs/articles/evals/retrospectives/index.mdx` and `docs/articles/retrospectives/README.mdx` |

Both are live, because neither matches an exclude glob, so this is a real site-wide title collision.
Two different sidebar sections (`Eval reports` and `Retrospectives`) each have a landing page titled
exactly "Retrospectives".

### Also a collision, but missed by a title-only sweep (worth flagging anyway)

- **`docs/articles/understanding/README.mdx`** has `title: Start here`. This is the landing page of
  the **`Understanding Mailwoman`** switcher section. "Start here" is also the exact label of the
  **`startHere`** switcher section, an unrelated section containing Status/Releases/Getting
  started/API. A reader told to "start here" inside Understanding Mailwoman
  and a reader clicking the "Start here" section tab land on two different pages with the same name.

### Near-duplicates

1. **Likely duplicated content, beyond a naming overlap.** `Record-matcher data catalog`
   (`docs/articles/concepts/record-matcher-data-catalog.md`) vs `Record-matcher source-data catalog`
   (`docs/articles/plan/reference/record-matcher-sources.md`). Both cover the same subject (the
   public datasets the record-matcher joins), use the same data root path
   (`$MAILWOMAN_DATA_ROOT/record-matcher/sources/`), and have overlapping prose ("no shared key across
   publishers" / "no shared entity key across them"). One lives under Concepts and the other under
   Implementation Plan → reference, and neither opening section links to the other.
2. **Same-day near-identical pair, both created today (2026-07-14).**
   `Failure report — shipped · v257 · v261` (`evals/competitive-parity/2026-07-14-failure-report-golden.mdx`)
   vs `Failure report — shipped · v257 · v261 · v280`
   (`evals/competitive-parity/2026-07-14-failure-report.mdx`). The titles differ only by a trailing
   `· v280`. A human should check whether the non-`-golden` report supersedes the other or whether
   both are meant to coexist.
3. **`Postcode-only diagnostic (v0.6.0)`** (`evals/model-versions/2026-05-29-postcode-diagnostic.mdx`)
   vs **`Postcode-only geocoding`** (`understanding/alternatives/simple-postcode-only.mdx`). They
   share a prefix but are different documents in different sections (an eval report and a "simple
   alternatives" critique page), so the confusion risk is low.
4. **Themed clusters.** The same construction repeats across several titles. Each has low confusion
   risk, but together they are visually noisy in a flat list or search results:
   - "Falsehoods about …" × 8 (addresses, format, shapes/dimensions, admin hierarchy, geocoded
     precision, numbers, postcodes, street names) — all `understanding/why-its-hard/falsehoods-*.mdx`,
     intentional parallel series.
   - `How it {used to work, will work, works now}` — 3 titles,
     `understanding/our-approach/how-it-*.mdx`, intentional parallel series, differ only by tense.
   - `Switching from {libpostal, Nominatim, OpenCage, Pelias, Photon}` — 5 titles,
     `concepts/switching-from-*.mdx`, intentional and well-differentiated (product names carry the
     distinction), lowest concern of the clusters.
   - `Night {shift, Shift, N postmortem}` naming — roughly a dozen titles under
     `evals/night-shifts/`, inconsistent even in capitalization (`Night shift 2026-06-18 — …` vs
     `Night Shift 2026-07-01 — Issue Cleanup`, capital vs lowercase "Shift"). Most of the raw
     postmortem files have no `title:` (H1 only), so this list is shorter than the file count
     suggests. The inconsistent capitalization on the titled ones is a small, fixable problem.

**Commands / method:** an uncommitted Python script read each file, extracted the first YAML
frontmatter block if present, pulled the `title:` line, stripped surrounding quotes, and grouped
titles by exact string match. Near-duplicates were then found by reading the sorted unique-title
list (178 unique strings for 179 titled files). That step is manual and could miss subtler
rewordings, so treat the near-duplicate list as representative and not exhaustive.

## 5. Click paths for the four goal questions

These paths were traced from the docs entry points (homepage `/` and the top navbar) through the
**current** nav. The DocsSubHeader switcher is server-rendered (it is present in the static HTML
rather than rendered only on the client), so the link targets below are exact and were read directly from
`docs/build/docs/status/index.html` and `docs/build/docs/plan/SCOPE/index.html`.

**Correction to the run-docs SKILL.md runbook:** its Gotchas section says _"The nav link labeled
'Docs' points there [`/docs/understanding/`]."_ That statement is stale. The built navbar currently
emits `<a href=/docs/status>Docs</a>`, which is the `startHere` sidebar's first doc. The SKILL doc
likely predates the current `startHere` array (`["status", "releases", "getting-started", "api"]`).
That skill file needs a separate follow-up fix.

### (a) What does Mailwoman do and when should I use it?

The homepage (`/`) answers this without any clicks. The hero tagline, subtitle, and the
Parse/Geocode/Match "Gallery" cards give a good short answer. **The problem is the navbar "Docs"
link**, which goes to `/docs/status`. That page is a dense, changelog-style page ("Verified as of
2026-07-02 — release 5.0.0", per-tag score callouts, a link to the parity scorecard) and does not
introduce the project. The "what and why" narrative (`concepts/what-mailwoman-is.mdx`,
`understanding/README.mdx`) requires switching the DocsSubHeader to "Understanding Mailwoman" or
"Concept deep dives" from there, and a first-time visitor on a status page has no particular reason
to do that. **Verdict: the homepage answers the question well, and the "Docs" nav entry point does
not. The path is adequate only if the visitor stays on the homepage.**

### (b) How do I parse, geocode, or integrate it?

Two good paths lead here. The homepage's "Read the docs" button goes directly to
`/docs/getting-started` (1 click), which has install and first-parse code for both Node and CLI.
The navbar path "Docs" → `/docs/status` → "Getting started" in the `startHere` sidebar (2 clicks)
reaches the same page. Task-specific integration content (batch geocoding, multi-service geocoding,
map display, CSV ingest, timezone/UN-LOCODE lookups) lives in the `Recipes` switcher section, one
more switcher click from any `startHere` page. **Verdict: adequate, and the best-served of the four.
The paths are short and code-forward, and both entry points lead to the same page.**

### (c) How does the system work at a useful technical level?

Good content exists for this (`concepts/staged-pipeline-interface.mdx`,
`understanding/our-approach/the-staged-pipeline.mdx`, and the whole Concepts and Understanding
tracks). No link on the homepage or in the top navbar points to it directly. A reader reaches it only
by landing somewhere in `/docs/` and then using the DocsSubHeader switcher, which is not visible
before the reader reaches a docs page. From navbar "Docs": `/docs/status` → switch to
"Understanding Mailwoman" or "Concept deep dives" (2 clicks, plus discovering the switcher).
**Verdict: content is adequate once found; the path to it is not obvious from either of the two
site entry points (homepage, navbar).**

### (d) What is the authoritative interface or operational procedure?

This is the hardest path of the four. `plan/reference/SCHEMA.mdx` (the authoritative record for the
`ComponentTag` union, per `AGENTS.md`) and `plan/reference/OPERATIONS.mdx` (the ops playbook) live
inside the **`Implementation plan 🧪`** switcher section. Its test-tube emoji reads as
"experimental / in-progress," which undersells content that `AGENTS.md` calls authoritative.
From navbar "Docs", the path is: `/docs/status` → switch to "Implementation plan 🧪" (lands on
`/docs/plan/SCOPE`, a good orientation doc at sidebar_position 1) → scroll the sidebar to find a
**collapsed, lowercase, auto-labeled** category named `reference` (without a `_category_.json` to
give it a friendlier label) → expand it → click the specific doc. That is **3 clicks past the
navbar plus a manual expand**. Clicking the `reference` category header itself (instead of the
caret) navigates to `/docs/plan/reference/tokenizer-a0-baseline`, an unrelated tokenizer report,
because Docusaurus routes a category click to its first child by file order. `SCHEMA.mdx` itself
has **zero frontmatter** (neither `title:` nor `sidebar_label:`), so Docusaurus derives its sidebar
entry from the filename. **Verdict: inadequate. The content that most needs to read as authoritative
is the hardest of the four to reach, sits behind a label that suggests it is experimental, and its
landing doc has no title of its own.**

sed -n '1,10p' docs/articles/plan/reference/SCHEMA.mdx        # confirms no frontmatter
```
