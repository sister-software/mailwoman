# Filer Spine Phase 3b Implementation Plan — corporate families + the record-linkage eval

> **For agentic workers:** required sub-skill: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Distinguish **corporate families** from entity clusters. Families are typed, provenanced and time-scoped, and they come from Form 499's holding/management fields and SEC EDGAR Exhibit 21. The phase also publishes the held-out record-linkage eval as a scorecard.

**Architecture:** The work starts with a schema boundary: relationship kinds and a family rollup that cannot be confused with an entity cluster. Family edges from data already in hand come next, then the eval, then EDGAR as additive enrichment. This order lets tasks 1-4 ship real value even if the EDGAR chain proves intractable.

**Tech Stack:** the same as 3a. All Global Constraints from `2026-07-30-bdc-2a-plan.md` apply verbatim.

**Spec:** `docs/superpowers/specs/2026-07-31-filer-spine-design.md` §4.1, §5, §6-3b, §10 (3a carry-forwards), §11-12 (CORES unavailable, ASR/ULS located). Recon on 2026-07-31 found six conflicts with the spec, and the decisions below resolve them.

## Verification ladder (every task)

`yarn vitest run filer bdc registry match mcp` · full untargeted `yarn tsc -b` · **`yarn typecheck:tests`**. The third command is mandatory, because the other two do not check `satisfies` pins.

## Pre-registered decisions (cite in commits)

1. **`filer_edge` gains a `relationship` column.** Today the target node's `identifier_type` implies family semantics, and `assertion` is a closed two-value const (`authoritative`/`inferred`) that describes _evidence strength_ rather than _relationship kind_. The two properties are independent, and one column must not carry both. New const: `FilerRelationship = { SameEntity, HoldingCompany, ManagementCompany, ParentCompany, Subsidiary }`. Existing 3a edges migrate to `SameEntity` except holding/management, which take their named kinds.
2. **Corporate family is a separate rollup from entity cluster, with its own table.** Spec §4.1 defines two rollups, and `filer_cluster` currently has no column to tell them apart, since its `assertion` column reuses `FilerEdgeAssertion`. Add `filer_family` (`node_id`, `family_id`, `relationship`, `source`, `valid_from`, `valid_to`). A family membership must never be readable as an entity-cluster membership, and the reverse must also hold. This is an acceptance check and follows the same rule as 3a's decision 5.
3. **The eval does not go in `evals/scores-by-version.json`.** That ledger is designed for parser evals. It sets `additionalProperties: false` and requires `model_version` (a `neural-weights-*` semver), `corpus_sha256`, `training_steps`, `training_wall_clock_seconds`, and `metrics.per_component` keyed by `ComponentTag`. A record-linkage scorecard fits none of these fields, and `ledgerAppend` also demands a promotion-check `verdict.json` and a `model-card.json`. Publish the scorecard as a markdown report in `docs/articles/evals/`, generated by a tools module. The closest in-repo precedent is `registry/tools/learned-scorer-eval.ts` with `mailwoman/commands/registry/scorer-eval.tsx`.
4. **The eval must not leak the answer, and a test must show it.** The authoritative FRN↔holdingCompany link is the ground truth, so the eval run must _exclude it from the matcher's inputs_. A run that feeds the answer in and reports high F1 is worse than having no eval. Assert the exclusion structurally: the eval builds its input records from a filtered projection, and a test confirms that the truth field is absent. The scorecard reports the input record shape.
5. **The SEC client is the repo's first throttled fetcher, so design it carefully.** `bdc/sdk/client.ts` has no rate limiting, caching or retry, and `filer/sdk` shipped without a fetcher. SEC's fair-access policy requires a descriptive User-Agent with a contact address and at most 10 requests per second. Implement a UA read from `$private.SEC_EDGAR_USER_AGENT` that fails fast if unset, a token-bucket limiter, an on-disk cache keyed by URL, and bounded retry with backoff on 429/5xx. Tests use a stub `fetchImpl`, and **the suite makes no live network calls**.
6. **Exhibit 21 parsing abstains rather than guesses.** Exhibit 21 is free-form. Filers use HTML tables, nested lists or plain text, and the formats vary widely. A subsidiary row that cannot be extracted with confidence is **counted and dropped, never inferred**. The result reports `parsed` and `unparseable` counts. A filing whose exhibit yields no extractable content is a normal outcome rather than an error. The parser emits positive evidence only, as the BDC vertical does.
7. **Transfer-of-control edges are out of scope for 3b.** The transaction layer (`2026-07-31-transaction-layer-and-portability.md` §2) needs FCC assignment/transfer applications. Those live in the **ULS bulk tree that 3c already ingests** (`data.fcc.gov/download/pub/uls/complete/`, verified reachable). In 3c the work costs one extra table on a download that is already parsed. Doing it here would mean building ULS ingestion twice. 3a's snapshot semantics also require historic-dated edges to arrive in the same build or in a post-build pass.
8. **`filer.db` stays outside the layer interface** (3a decision 2 unchanged). It has no coordinates until 3c.

## Acceptance checks (§7-3b, pre-registered — Task 3 and Task 8 discharge them)

1. **Family and entity cluster are never conflated (required).** The separation is structural. A family membership cannot be returned as an entity-cluster member, and the reader returns the two as distinct fields with distinct types. Mutation-test it: make the rollup fold families into clusters, and confirm that the check fails.
2. **Every family edge requires a relationship kind and provenance.** A family edge cannot exist without `relationship`, `source`, `source_vintage` and `valid_from`. Pin this structurally with `satisfies Record<keyof FilerFamilyInsert, true>`, and reject empty and whitespace-only values at runtime, because SQLite `NOT NULL` accepts `""` (learned in 3a).
3. **Exhibit 21 abstention.** A fixture with a mangled or unparseable exhibit yields zero subsidiary edges and a non-zero `unparseable` count without throwing. A clean fixture yields exactly the expected subsidiaries. The parser never guesses names.
4. **Eval integrity.** A test asserts that the held-out truth field is absent from the matcher's input records. The scorecard reports precision, recall, F1, the input record shape, and the SHA of its inputs. Re-running with the same inputs reproduces the same numbers.

### Task 1: Schema boundary — relationship kinds + `filer_family`

**Files:** Modify `filer/schema.ts`. Create `filer/sdk/guards.ts` and move `assertISODate` there from `build-filer.ts`. `cluster-filers.ts:150` already imports it from the builder, and each new writer would add another such import. Update the importers. Test: `filer/schema.test.ts`.

**Produces:**

```ts
export const FilerRelationship = {
	SameEntity: "same_entity",
	HoldingCompany: "holding_company",
	ManagementCompany: "management_company",
	ParentCompany: "parent_company",
	Subsidiary: "subsidiary",
} as const
export type FilerRelationship = (typeof FilerRelationship)[keyof typeof FilerRelationship]
// filer_edge gains: relationship: string   (NOT NULL)
export interface FilerFamilyTable {
	node_id: string
	family_id: string
	relationship: string
	source: string
	source_vintage: string
	valid_from: string
	valid_to: string | null
}
export async function createFilerFamilyTable(db): Promise<void>
export async function createFilerFamilyIndex(db): Promise<void>
```

Bump `schema_version` in the manifest. `filer_edge`'s PK stays `(from_node_id, to_node_id, source, valid_from)`. Adding `relationship` to the PK would let one source assert two different kinds for the same pair at the same instant. That is a contradiction, and the database should reject it rather than store it.

- [x] TDD: all tables are created, a family row round-trips, `relationship` rejects empty and whitespace-only values, and the edge PK still rejects a literal duplicate. Commit `feat(filer): relationship kinds + filer_family table (3b task 1, decisions 1,2)`.

### Task 2: Family edges from Form 499

**Files:** Modify `filer/sdk/build-filer.ts` so every edge carries `relationship`. Holding and management edges take their named kinds, and all others take `SameEntity`. Add family-membership emission, with tests alongside.

Holding and management edges already exist from 3a. This task types them and derives family membership. A `holding_company_name` node with N distinct FRNs pointing at it is a family of N members. ### Task 8: EDGAR family edges + rollup integration

**Files:** Modify `filer/sdk/build-filer.ts` (optional `edgarRows` option), `family-rollup.ts`. Tests extend checks 1-2 to EDGAR-sourced families.

Parent CIK → subsidiary name becomes a `Subsidiary` family edge with `source: "edgar-exhibit-21"`, and both `source_vintage` and `valid_from` set to the filing date. Subsidiary names are name nodes. Joining them to FRNs is **inference rather than authority**. If a subsidiary name matches a filer's canonical name, emit an `inferred` edge with a score, never an authoritative one.

**A `filer_edge` row alone is not enough, so write the `filer_family` rows too.** This was measured, and a regression test pins it (`filer/tools/linkage-eval.test.ts`, "does not move when the same ownership fact arrives only as filer_edge rows (the Task 8 precondition)"). Wiring EDGAR in exactly as the paragraph above describes produces inferred `Subsidiary` **edges** with `match_score 0.92` that tie three same-family FRNs to one `cik:` node. With those edges, the linkage eval's recall stays at **0.000**, the same as with no EDGAR data at all. Writing the same facts as `filer_family` **rows** raises recall to 0.500.

The cause is structural and predates this task:

- `cluster-filers.ts`'s `readAuthoritativeGroups` filters on `assertion=authoritative AND relationship=same_entity`.
- `buildInferredRecords` reads only `filer_attribute.legal_name` and the identifier code sets.
- Every corporate-family reader on the product surface (`familyRollup`, `filerLookup.families`) answers membership questions from `filer_family` alone. These readers do read `filer_edge`, but only through `readFamilyDisplayNames`, to recover the raw company name behind a `family_id`.

An EDGAR edge without a matching family row is therefore invisible to every consumer that asks a family question. The data would be in the artifact and absent from every answer.

This task must extend `insertFamilyMembership` (or an EDGAR equivalent) so that each inferred subsidiary relationship is written as both an edge and a family membership row, carrying `naming_node_id` like every other family row. Task 4's `docs/articles/evals/2026-07-31-filer-linkage.md` is the published before-measurement. Re-running `mailwoman filer linkage-eval` after this task shows whether the corroboration channel works, and it will report 0.000 again if only edges are written.

- [x] TDD. Commit `feat(filer): EDGAR Exhibit 21 family edges (3b task 8)`.
