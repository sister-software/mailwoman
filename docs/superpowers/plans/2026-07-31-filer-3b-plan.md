# Filer Spine Phase 3b Implementation Plan — corporate families + the record-linkage eval

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Distinguish **corporate families** from entity clusters — typed, provenanced, time-scoped — sourced from Form 499's holding/management fields and SEC EDGAR Exhibit 21, plus the held-out record-linkage eval published as a scorecard.

**Architecture:** A schema seam first (relationship kinds + a family rollup that cannot be confused with an entity cluster), then family edges from data already in hand, then the eval, then EDGAR as additive enrichment. Ordered so tasks 1-4 ship real value even if the EDGAR chain proves intractable.

**Tech Stack:** as 3a. All Global Constraints from `2026-07-30-bdc-2a-plan.md` bind verbatim.

**Spec:** `docs/superpowers/specs/2026-07-31-filer-spine-design.md` §4.1, §5, §6-3b, §10 (3a carry-forwards), §11-12 (CORES dead; ASR/ULS located). Recon 2026-07-31 found six frictions; decisions below resolve them.

## Pre-registered decisions (cite in commits)

1. **`filer_edge` gains a `relationship` column.** Today family semantics live implicitly in the target node's `identifier_type`, and `assertion` is a closed two-value const (`authoritative`/`inferred`) describing _evidence strength_, not _relationship kind_. These are orthogonal and must not be overloaded. New const: `FilerRelationship = { SameEntity, HoldingCompany, ManagementCompany, ParentCompany, Subsidiary }`. Existing 3a edges migrate to `SameEntity` except holding/management, which take their named kinds.
2. **Corporate family is a SEPARATE rollup from entity cluster, with its own table.** Spec §4.1 defines two rollups; `filer_cluster` currently has no seam to tell them apart (its `assertion` column reuses `FilerEdgeAssertion`). Add `filer_family` (`node_id`, `family_id`, `relationship`, `source`, `valid_from`, `valid_to`). A family membership must never be readable as an entity-cluster membership or vice versa — this is a gate, and it is the same doctrine as 3a's decision 5.
3. **The eval does NOT go in `evals/scores-by-version.json`.** That ledger is parser-shaped: `additionalProperties: false`, requiring `model_version` (a `neural-weights-*` semver), `corpus_sha256`, `training_steps`, `training_wall_clock_seconds`, and `metrics.per_component` keyed by `ComponentTag`. A record-linkage scorecard fits none of it, and `ledgerAppend` additionally demands a promotion-gate `verdict.json` plus a `model-card.json`. Publish instead as a markdown report in `docs/articles/evals/`, generated by a tools module — following `registry/tools/learned-scorer-eval.ts` + `mailwoman/commands/registry/scorer-eval.tsx` (the closest in-repo precedent).
4. **No leakage in the eval, and prove it.** The authoritative FRN↔holdingCompany link is the ground truth; it must be _excluded from the matcher's inputs_ for the eval run. A run that feeds the answer in and reports high F1 is worse than no eval. Assert the exclusion structurally (the eval builds its input records from a filtered projection, and a test confirms the truth field is absent), and report the input record shape in the scorecard.
5. **The SEC client is the repo's first throttled fetcher — build it deliberately.** `bdc/sdk/client.ts` has no rate limiting, caching, or retry, and `filer/sdk` shipped no fetcher at all. SEC's fair-access policy requires a descriptive User-Agent with a contact address and ≤10 requests/second. Implement: UA from `$private.SEC_EDGAR_USER_AGENT` (fail fast if unset), a token-bucket limiter, an on-disk cache keyed by URL, and bounded retry with backoff on 429/5xx. Tests use a stub `fetchImpl`; **no live network in the suite**.
6. **Exhibit 21 parsing abstains rather than guesses.** Exhibit 21 is free-form — HTML tables, nested lists, plain text, wildly inconsistent across filers. A subsidiary row that cannot be confidently extracted is **counted and dropped, never inferred**. The result reports `parsed` and `unparseable` counts; a filing whose exhibit yields nothing is a normal outcome, not an error. Positive evidence only, exactly as the BDC vertical does it.
7. **Transfer-of-control edges are OUT of 3b.** The transaction layer (`2026-07-31-transaction-layer-and-portability.md` §2) needs FCC assignment/transfer applications, which live in the **ULS bulk tree 3c is already ingesting** (`data.fcc.gov/download/pub/uls/complete/`, verified reachable). Doing it in 3c costs one extra table on a download already being parsed; doing it here means standing up ULS ingestion twice. Note also that 3a's snapshot semantics mean historic-dated edges must arrive in the same build or a post-build pass.
8. **`filer.db` stays outside the layer contract** (3a decision 2 unchanged) — still no coordinates until 3c.

## Acceptance gates (§7-3b, pre-registered — Task 3 and Task 8 discharge them)

1. **Family and entity cluster are never conflated (load-bearing).** Structural: a family membership cannot be returned as an entity-cluster member, and the reader surfaces them as distinct fields with distinct types. Mutation-test it: make the rollup fold families into clusters, confirm the gate dies.
2. **Relationship kind + provenance mandatory on every family edge.** No family edge without `relationship`, `source`, `source_vintage`, `valid_from`. Pin structurally with `satisfies Record<keyof FilerFamilyInsert, true>`; reject empty and whitespace-only at runtime (SQLite `NOT NULL` accepts `""` — the 3a lesson).
3. **Exhibit 21 abstention.** A fixture with a mangled/unparseable exhibit yields zero subsidiary edges, a non-zero `unparseable` count, and no thrown error; a clean fixture yields exactly the expected subsidiaries. No guessed names.
4. **Eval integrity.** The held-out truth field is absent from the matcher's input records (asserted); the scorecard reports precision, recall, F1, the input record shape, and the SHA of its inputs; re-running with the same inputs reproduces the same numbers.

### Task 1: Schema seam — relationship kinds + `filer_family`

**Files:** Modify `filer/schema.ts`; create `filer/sdk/guards.ts` (extract `assertISODate` out of `build-filer.ts`, which `cluster-filers.ts:150` already reaches into — the coupling worsens with every new writer); update importers. Test: `filer/schema.test.ts`.

**Produces:**

```ts
export const FilerRelationship = {
	SameEntity: "same_entity",
	HoldingCompany: "holding_company",
	ManagementCompany: "management_company",
	ParentCompany: "parent_company",
	Subsidiary: "subsidiary",
} as const
export type FilerRelationship = (typeof FilerRelationship)[keyof typeof FilerRelationship]
// filer_edge gains: relationship: string   (NOT NULL)
export interface FilerFamilyTable {
	node_id: string
	family_id: string
	relationship: string
	source: string
	source_vintage: string
	valid_from: string
	valid_to: string | null
}
export async function createFilerFamilyTable(db): Promise<void>
export async function createFilerFamilyIndex(db): Promise<void>
```

Bump `schema_version` in the manifest. `filer_edge`'s PK stays `(from_node_id, to_node_id, source, valid_from)` — adding `relationship` to the PK would let one source assert two different kinds for the same pair at the same instant, which is a contradiction we want rejected, not stored.

- [ ] TDD: all tables create; a family row round-trips; `relationship` rejects empty/whitespace; the edge PK still rejects a literal duplicate. Commit `feat(filer): relationship kinds + filer_family table (3b task 1, decisions 1,2)`.
