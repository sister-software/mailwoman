> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land the telecom-infrastructure build-local POI layer, the `plausibility_check` scorer composing filing + physical evidence into `{ claim, evidence_found, coverage_confidence }` bundles, and the `mailwoman_plausibility_check` MCP tool, passing the four §7-2b gates — the positive-evidence-only invariant being load-bearing.

**Tech Stack:** as 2a (TS, Kysely/node:sqlite, zod, vitest). House patterns identical to `docs/superpowers/plans/2026-07-30-bdc-2a-plan.md` Global Constraints — they all bind here too (no enum, no raw process.env, oxfmt-before-commit, sealed artifacts, salvage rules, Fabric boundary, BDC casing).

**Spec:** `docs/superpowers/specs/2026-07-20-bdc-plausibility-design.md` §2.3, §3.2, §4, §7-2b. Recon (2026-07-30, this session) contradicts it in six places; decisions below resolve them.

## Pre-registered decisions (cite in commits)

1. **Taxonomy already half-done:** `telecom_cabinet` + `data_center` exist in `poi-taxonomy/data/curated-overlay.json` with synonyms; only `telecom_exchange` and `tower_comms` are new. Category ids stay `hierarchy: ["infrastructure", <id>]`, `source: "mailwoman-infra"` (which makes `requiresBuildLocalLayer` true for free — `poi-taxonomy/lookup-core.ts:141`).
2. **Tag disjunctions/conjunctions live in the extractor, not the taxonomy.** `CategoryRecord.osmTag` is a single scalar consumed by the Overpass emitter (`poi-taxonomy/overpass.ts:78` hard-splits on one `=`). The OSM POI extractor owns a tag-matcher table expressing OR (`man_made=telephone_exchange` | `telecom=exchange`) and AND (`man_made=mast` + `tower:type=communication`; `man_made=street_cabinet` + `street_cabinet=telecom`). Taxonomy carries only the primary scalar tag per category. Follow-up (not 2b): richer `osmTags` if Overpass export of infra categories is ever wanted.
3. **`poi build --source osm` must be BUILT, not extended** — no OSM POI ingest exists (`osm/sdk` is address-only). New extractor `osm/sdk/extract-poi.ts` (OGRSQL over `points` + `multipolygons` with telecom predicates, same ogr2ogr machinery as `osm/sdk/extract.ts`) yields `POISourceRow`s into the existing `BuildPOIOptions.rows` seam (`build-poi.ts:341`) — DuckDB bypassed.
4. **Point→block GEOID does not exist; 2b pins the h3-cell approximation and flags it.** `geocodeAddress` returns lat/lon only; `tabblock20` has no spatial index. The scorer's filing-evidence step uses point → `latLngToCell(·, 9)` → `shortCellToInt` → `filingLandscape({h3Cells})`. This is UNSOUND when an address's res-9 cell differs from its block-centroid's cell: the bundle carries `block_resolution: "h3_cell_approximation"` on every per-address answer (this doubles as the spec's block-grain-inference flag, gate 4). Fidelity upgrade (PIP over tabblock20 + r-tree) is ticketed, not built.
5. **OSM infra coverage = extract-region res-6 cells** (h3-js `polygonToCells` over the extract bbox, `completeness: 1`, `observed_rows` = infra-POI count in cell, zero permitted). This gives "well-surveyed cell, no plant found" its §4 meaning without pretending OSM sparsity is survey completeness. Requires parameterizing `build-poi.ts`'s coverage step (currently hardcoded rows-present ⇒ 1) and manifest fields (source/tier/freshness) for the OSM branch.
6. **Missing layers follow the poi-executor abstain precedent** (`poi-executor.ts:88`: typed `{type: "abstain", reason: "requires_build_local_layer"}`), NOT 2a's raw sqlite throw. `plausibility_check` names the missing layer in the bundle; it never fabricates a distance. In passing, the 2a `mailwoman_bdc_filing_landscape` deps impl gets the same guard (friendly error naming the layer when bdc.db is absent).
7. **`nearestInfrastructure` wraps `POILookup.search`** (`resolver-wof-sqlite/poi-lookup.ts:198` — already category-filtered k-nearest with `distanceM`) with `maxRings` default raised to 32 (≈10.8 km; telecom plant is sparse — 2a default 16 ≈ 5.4 km is too tight) and each hit paired with `readLayerCoverage(res9ShortCellToRes6Parent(hit cell))`.
8. **Reuse, never re-derive:** speed comparison uses `speedBucketForDownloadSpeed` + threshold consts from `bdc/sdk/filing-landscape.ts`; res-6 parents via `res9ShortCellToRes6Parent`; the `asContractDB` cast idiom copies from `filing-landscape.ts:150`.

### Task 5: `plausibility.ts` — the scorer

**Files:** Create `bdc/sdk/plausibility.ts` + test; export from barrel. This is the heart; the four §7-2b gates land in Task 6 but design for them now.

**Produces:**

```ts
export interface PlausibilityClaim { address?: string; point?: PointLiteral; geoid?: string; technologyCode: number; claimedDownloadMbps: number }
export type PlausibilityEvidence =
	| { type: "filing"; filing: ProviderFilingSummary; vintage: string; corroborates: boolean }
	| { type: "physical_plant"; hit: InfrastructureHit }
	| { type: "abstain"; reason: "requires_build_local_layer" | "requires_bdc_layer" | "insufficient_survey_data"; layer?: string }
export interface PlausibilityBundle {
	claim: PlausibilityClaim
	evidence_found: PlausibilityEvidence[]
	coverage_confidence: "high" | "low" | "insufficient_survey_data"
	block_resolution: "geoid" | "h3_cell_approximation" // decision 4 — ALWAYS present on per-address/point answers
	vintage: string | null // null only when the bdc layer itself abstained
}
export interface PlausibilityDeps { bdcDB?: DatabaseClient<BDCDatabase>; poi?: /* per Task 4 */; geocode?: (address: string) => Promise<GeocodeResult> }
export async function plausibilityCheck(claim: PlausibilityClaim, deps: PlausibilityDeps): Promise<PlausibilityBundle>
```

Composition rules (spec §4, verbatim doctrine): claim → resolve to point (geocode when address; `deriveGeocodeRegister`/formatted register is the geocode dep's concern, wired at the CLI/MCP layer) → filing evidence via `filingLandscape({h3Cells:[cell]})` (`corroborates` = same tech at ≥ claimed speed using the exported bucket helpers; a lesser filing is evidence with `corroborates: false`, never disproof) → physical evidence via `nearestInfrastructure` with the tech-implied categories (fiber → exchange/cabinet/data_center; wireless codes → tower_comms; mapping table exported) → coverage_confidence from the pair of layer coverages (both covered = high; either UNKNOWN = degrade; both absent/unknown = insufficient) → NEVER any output stronger than "no supporting evidence found, and coverage is good enough that this is informative"; absence NEVER lowers below unknown. Missing bdcDB/poi dep → the corresponding typed abstain (decision 6).
