# BDC Phase 2b Implementation Plan — infra layer + `plausibility_check` + MCP tool

> **For agentic workers:** required sub-skill: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land three pieces that pass the four §7-2b checks. The first is the telecom-infrastructure build-local POI layer. The second is the `plausibility_check` scorer, which composes filing and physical evidence into `{ claim, evidence_found, coverage_confidence }` bundles. The third is the `mailwoman_plausibility_check` MCP tool. The positive-evidence-only invariant is a required check.

**Architecture:** Extend the existing poi.db implementation with an OSM source branch: an extractor in `osm/sdk`, `--source osm` on the build CLI, the build-local tier, and bbox-derived coverage. Reuse `POILookup.search` as the nearest-infrastructure primitive. `plausibility.ts` in `@mailwoman/bdc` is a thin composition over `filingLandscape` and the nearest wrapper. It handles missing layers the way the poi-executor does, by abstaining.

**Tech Stack:** the same as 2a (TS, Kysely/node:sqlite, zod, vitest). The Global Constraints in `docs/superpowers/plans/2026-07-30-bdc-2a-plan.md` all apply here too: avoid enum and raw process.env, run oxfmt before commit, and respect sealed artifacts, salvage rules, the Fabric boundary, and BDC casing.

**Spec:** `docs/superpowers/specs/2026-07-20-bdc-plausibility-design.md` §2.3, §3.2, §4, §7-2b. Recon in this session (2026-07-30) contradicts the spec in six places. The decisions below resolve them.

## Pre-registered decisions (cite in commits)

1. **The taxonomy is already half done.** `telecom_cabinet` and `data_center` exist in `poi-taxonomy/data/curated-overlay.json` with synonyms. Only `telecom_exchange` and `tower_comms` are new. Category ids keep `hierarchy: ["infrastructure", <id>]` and `source: "mailwoman-infra"`, which makes `requiresBuildLocalLayer` true without further work (`poi-taxonomy/lookup-core.ts:141`).
2. **Tag disjunctions and conjunctions live in the extractor rather than the taxonomy.** `CategoryRecord.osmTag` is a single scalar that the Overpass emitter consumes, and `poi-taxonomy/overpass.ts:78` splits it on one `=`. The OSM POI extractor owns a tag-matcher table that expresses disjunctions (`man_made=telephone_exchange` | `telecom=exchange`) and conjunctions (`man_made=mast` + `tower:type=communication`, and `man_made=street_cabinet` + `street_cabinet=telecom`). The taxonomy carries only the primary scalar tag per category. A follow-up outside 2b could add richer `osmTags` if Overpass export of infra categories is ever wanted.
3. **`poi build --source osm` must be built from scratch.** No OSM POI ingest exists, since `osm/sdk` handles addresses only. The new extractor `osm/sdk/extract-poi.ts` runs OGRSQL over `points` and `multipolygons` with telecom predicates, using the same ogr2ogr implementation as `osm/sdk/extract.ts`. It yields `POISourceRow`s into the existing `BuildPOIOptions.rows` boundary (`build-poi.ts:341`) and bypasses DuckDB.
4. **No point→block GEOID lookup exists, so 2b pins the h3-cell approximation and flags it.** `geocodeAddress` returns only lat/lon, and `tabblock20` has no spatial index. The scorer's filing-evidence step uses point → `latLngToCell(·, 9)` → `shortCellToInt` → `filingLandscape({h3Cells})`. The approximation is wrong when an address's res-9 cell differs from the cell of its block centroid. Every per-address answer therefore carries `block_resolution: "h3_cell_approximation"`, which also serves as the spec's block-grain-inference flag (check 4). The fidelity upgrade (PIP over tabblock20 with an r-tree) is ticketed rather than built.
5. **OSM infra coverage uses the extract region's res-6 cells.** The build runs h3-js `polygonToCells` over the extract bbox with `completeness: 1`, and `observed_rows` is the infra-POI count in the cell, which may be zero. This gives "well-surveyed cell without a plant" its §4 meaning without treating OSM sparsity as survey completeness. The OSM branch requires parameterizing `build-poi.ts`'s coverage step (currently hardcoded to 1 when rows are present) and its manifest fields (source, tier, freshness).
6. **Missing layers produce an abstain, as in the poi-executor** (`poi-executor.ts:88` returns a typed `{type: "abstain", reason: "requires_build_local_layer"}`), rather than 2a's raw sqlite throw. `plausibility_check` records the missing layer in the bundle and never fabricates a distance. The 2a `mailwoman_bdc_filing_landscape` deps implementation gets the same guard, which returns a friendly error identifying the layer when bdc.db is absent.
7. **`nearestInfrastructure` wraps `POILookup.search`** (`resolver-wof-sqlite/poi-lookup.ts:198`), which already does category-filtered k-nearest search with `distanceM`. The wrapper raises the `maxRings` default to 32 (≈10.8 km). Telecom plant is sparse, so 2a's default of 16 (≈5.4 km) is too tight. Each hit is paired with `readLayerCoverage(res9ShortCellToRes6Parent(hit cell))`.
8. **Reuse existing helpers instead of re-deriving them.** Speed comparison uses `speedBucketForDownloadSpeed` and the threshold constants from `bdc/sdk/filing-landscape.ts`. Res-6 parents come from `res9ShortCellToRes6Parent`. The `asschemadb` cast idiom is copied from `filing-landscape.ts:150`.

### Task 5: `plausibility.ts` — the scorer

**Files:** Create `bdc/sdk/plausibility.ts` and a test, and export it from the barrel. This is the core task. The four §7-2b checks land in Task 6, but the design must account for them now.

**Produces:**

```ts
export interface PlausibilityClaim { address?: string; point?: PointLiteral; geoid?: string; technologyCode: number; claimedDownloadMbps: number }
export type PlausibilityEvidence =
	| { type: "filing"; filing: ProviderFilingSummary; vintage: string; corroborates: boolean }
	| { type: "physical_plant"; hit: InfrastructureHit }
	| { type: "abstain"; reason: "requires_build_local_layer" | "requires_bdc_layer" | "insufficient_survey_data"; layer?: string }
export interface PlausibilityBundle {
	claim: PlausibilityClaim
	evidence_found: PlausibilityEvidence[]
	coverage_confidence: "high" | "low" | "insufficient_survey_data"
	block_resolution: "geoid" | "h3_cell_approximation" // decision 4 — ALWAYS present on per-address/point answers
	vintage: string | null // null only when the bdc layer itself abstained
}
export interface PlausibilityDeps { bdcDB?: DatabaseClient<BDCDatabase>; poi?: /* per Task 4 */; geocode?: (address: string) => Promise<GeocodeResult> }
export async function plausibilityCheck(claim: PlausibilityClaim, deps: PlausibilityDeps): Promise<PlausibilityBundle>
```

Composition rules (spec §4, verbatim doctrine):

1. Resolve the claim to a point. Geocode it when it is an address. The geocode dependency handles `deriveGeocodeRegister` and the formatted register, and it is wired at the CLI/MCP layer.
2. Gather filing evidence with `filingLandscape({h3Cells:[cell]})`. `corroborates` means the same technology at or above the claimed speed, compared with the exported bucket helpers. A lesser filing is evidence with `corroborates: false` and is never treated as disproof.
3. Gather physical evidence with `nearestInfrastructure` over the categories the technology implies: fiber maps to exchange, cabinet and data_center, and wireless codes map to tower_comms. Export the mapping table.
4. Derive `coverage_confidence` from the two layer coverages. Both covered gives high. Either one unknown degrades the result. Both absent or unknown gives insufficient.
5. The strongest permitted output is "no supporting evidence found, and coverage is good enough that this is informative". Absence never lowers the result below unknown.

A missing bdcDB or poi dependency produces the corresponding typed abstain (decision 6).

- [x] Steps per TDD; commit `feat(bdc): plausibility scorer — evidence bundles, positive-evidence-only (2b task 5, decisions 4,6,8)`.
