# AGENTS.md

Mailwoman is a postal-address parser shipped as the unscoped entry package `mailwoman` (CLI + library) plus **74 scoped `@mailwoman/*` workspaces** — **75 workspaces once the root `workspaces` field (`docs` plus the `packages/*` glob) is expanded**, which `readWorkspaceDirectories` in `@mailwoman/core/workspaces` does for every reader, and which is the list to trust. The repo root is the private orchestration package `@mailwoman/universe` (not published).

**60 of the 75 publish to npm.** The publish set is `.release-it.json`'s `@release-it-plugins/workspaces` list, and it is not derivable from the `private` flag alone: fourteen workspaces are `private: true` and can never publish (`docs`, `tile-worker`, `license-worker`, `geocode-oracle`, `neural-weights-base-latn`, `dev-mcp`, `release-kit`, `repo-health`, `ops-cli`, `release-mcp`, `astrogeology`, `planetary`, and the two app-side workspaces `earth` and `site-kit`), and **`osm` is public but deliberately held OUT of the release list** — ODbL counsel sign-off pending (`packages/osm/README.md`). That is fifteen, and 75 − 60 = **fifteen**, so every absence currently has a reason someone can state. Trust the subtraction over the story: run the check in `packages/release-kit/AGENTS.md` whenever you add or move a workspace, and when the number stops matching the workspaces you can name a reason for, one has fallen out of the release.

Every workspace, its npm package and what it holds, grouped by role, is catalogued in [`docs/engineering/reference/workspaces.mdx`](./docs/engineering/reference/workspaces.mdx).

Source lives under `lib/` in every `packages/*` workspace (the workspace-conventions section below has the build consequences); **`docs/` keeps Docusaurus's `src/`**. Every workspace lives under `packages/` except `docs/`, which stays at the repository root.

Beyond the 75 workspaces the repo root holds workspace config and five directories that are **not** workspaces — do not go looking for them in the table:

- `corpus-python/` — the Python training code, including the Modal launcher
- `hf-publish/` — four Hugging Face model/dataset card READMEs (en-us, cjk, the tokenizer, the WOF gazetteer), nothing else
- `data/` — checked-in reference inputs (e.g. `data/gazetteer/anchor-lexicon-v1.json`, the copy `mailwoman eval promote` runs against)
- `evals/` — the per-model score ledger (`evals/scores-by-version.json`)
- `docker/` — the private `mailwoman-docker` dependency manifest for the ghcr image. It has a `package.json`, which makes it look like a workspace; it is not in the `workspaces` array, and it installs the published `@mailwoman/*` packages rather than the local ones

### Four words are banned from prose

`config/vale/styles/AmbiguousShorthand.yml` refuses four nouns that each stand for four or five different things here, so a reader cannot tell which one a sentence means. This file does not list them, so that the words never enter an agent's context through the instructions; read the rule file when a finding names one. Because the rule lives in the shared Vale style it applies to published pages, this file, every package README, the engineering docs — and to agent replies through `.vale-chat.ini`. Name the concrete thing instead: the check by its name (the promotion eval, the verify step, the D-rule, the required `test` CI context) or a plain verb (blocks, requires, refuses); the artifact by its filename; the boundary by its interface; and for a release, publish it.

A second rule in the same style, `config/vale/styles/ShellNoun.yml`, refuses a hypothesis or result that has been compressed into a definite noun and then reported on as if it were an experimental object. The action is the proposition in full, with its metric and its number: what was measured, the value it took, and what that rules in or out. It runs over the same surfaces as the four-word ban, plus the training configs under `corpus-python/`, whose comment block is where the shape had settled. A third, `config/vale/styles/EmphasisCapitals.yml`, refuses an ordinary English word set in capitals for emphasis or as a telegraph predicate on those same surfaces: write the word in lowercase, or write the clause the capitals stood in for. Acronyms, tag names and identifiers keep their capitals.

Names tied to a interface keep their spelling. `@mailwoman/locale-hint`, `mailwoman eval promote`, `mwdev_promotion_eval`, `promotion-eval.ts`, `packages/corpus/lib/recipes/` and `RegionDatabaseProvider` are unchanged — Vale skips inline code, so backticking an identifier in running prose is both the action and correct markdown. Renaming one of them is a separate, operator-approved change (#1937) — which is what happened to the family of names for a corpus recipe output, a WOF extract and a region database: that word is now removed outright, at **zero occurrences**, enforced by `repo-health`'s `bannedVocabulary` counter. The renames are recorded in the #1937 receipt. Do not reintroduce it, in prose or in comments; the four concepts it used to cover are a corpus recipe, a corpus recipe OUTPUT, a WOF extract, and a region database. Two more words joined the same list on the same reasoning and by the same method — each site given the name of the thing it meant, never a substitution — so the concrete vocabulary above is now the whole vocabulary: a parquet file of a corpus split is a parquet file, a key of `source_weights` is a source, the generated artifact is a recipe output, the generator is a recipe, a country builder's whole output is a corpus, and reps per row over a run are reps per row. Three configs run the rule: `.vale.ini` over the published corpus, `.vale-vocab.ini` over the root markdown + `docs/engineering` + package READMEs (`yarn lint:prose`, part of `yarn lint`), and `.vale-chat.ini` over replies. Dated point-in-time records are out of scope, the same exemption the acronym-casing convention gives them.

## Workspace + test conventions

- **Source runs directly under `node`** (type stripping, no flags): relative imports use explicit `.ts` extensions, and each workspace tsconfig sets `rewriteRelativeImportExtensions: true` so `tsc` emits `.js` specifiers into `out/`. `erasableSyntaxOnly: true` is enforced everywhere — no `enum` (use `const X = {…} as const` + `type X = (typeof X)[keyof typeof X]`), no constructor parameter properties, no runtime namespaces. tsc rewrites dynamic `import()` string literals too, comments (`/* webpackIgnore: true */`) included.
- Each workspace has its own `tsconfig.json` + (for `packages/core/` and `packages/neural/`) a `vitest.config.ts` that aliases sibling `@mailwoman/*` subpath imports to source. This lets `yarn test` run without a precompile step. The cross-package aliases are fiddly — see the file headers for the resolution rules.
- **A package never re-exports another workspace package's names.** `export { Resolver } from "@mailwoman/core/resolver"` inside `@mailwoman/resolver`, or `export * from "@mailwoman/core"` inside `mailwoman`, gives one declaration two public homes, and a reader can no longer tell from an import which package owns a type. The declaring package is the only public home: a consumer imports `Resolver` from `@mailwoman/core/resolver` and `LocaleHint` from `@mailwoman/core/pipeline`, never through a neighbour. `mailwoman/no-cross-package-reexport` (`oxlint.plugin.ts`) refuses `export … from` a `@mailwoman/*` or `mailwoman` specifier in every workspace, with no exemptions: the last one, the deprecated `@mailwoman/neural-web` shim over `@mailwoman/neural`'s browser runtime, was deleted rather than kept as the one file that could. `node:*` re-exports inside `@mailwoman/core/fs` are out of the rule's scope on purpose: they are the funnel that keeps the builtin out of every other package. A package's own `#` map is not a foreign name and stays legal.
- **A test file imports the package under test through its public exports** (`@mailwoman/<pkg>/<subpath>`, `mailwoman/<subpath>`); a relative path names a test helper under `test/` and nothing else. The `#` subpath-imports map is the package's private naming and stays inside `lib/`: a test that reaches through it never exercises the surface a consumer gets, and `vi.mock("#x")` binds to a module the public specifier may not name. A module a test needs and no export names gets an `exports` entry, which is the decision made visible. Two checks hold the line: `mailwoman/no-private-import-in-test` (`oxlint.plugin.ts`) refuses a `#` specifier in any import, re-export, `import()`, `typeof import()` or `vi.mock`-family call under `packages/*/test/**` and `docs/test/**`, and `repo-health`'s `test-interface` refuses a relative import that leaves `test/`.
- **Source lives under `lib/`; tests live under `test/`.** Every `packages/*` workspace puts its TypeScript in `lib/`, and each `tsconfig.json` sets `"rootDir": "./lib"` with `"include": ["./lib/**/*"]`. `rootDir` STRIPS that segment from the emit, so `lib/utils/index.ts` compiles to `out/utils/index.js` and the published layout is unchanged — which is why only the dev-only `node` condition in `imports`/`exports` names `./lib/…` while `default`/`types` still name `./out/…`. Two consequences worth knowing before you edit build config: a workspace's `tsconfig.test.json` re-widens `rootDir` to `${configDir}` (via `tsconfig.test-base.json`) because `test/` sits outside `lib/` and TS6059 fires even under `noEmit`; and the ten data-only `neural-weights-*` packages plus `sentencepiece-wasm` have no `lib/` at all, because they have no `tsconfig.json` and compile nothing. `docs/` keeps Docusaurus's `src/`.
- `packages/core/lib/utils/repo.ts` computes the repo root and the `@mailwoman/core` package root by counting `..` up from `import.meta.url`. It has no source-vs-compiled branch, and that is deliberate rather than incidental: `lib/` and `out/` are siblings, so this file sits at the same depth in both trees and one constant serves both. It used to carry an `__isCompiledTree` flag, and that flag was wrong in production once (#481 — it overshot `out/` and sent dictionary reads to a nonexistent `core/out/data`). If a layout change ever breaks the equal-depth requirement, restore the equality rather than reintroducing the flag.
- **`sdk/` submodules mean data acquisition** (fetch/extract plus a `RegionDatabaseProvider` implementation — see `packages/ban/lib/sdk`, `packages/osm/lib/sdk`, `packages/tiger/lib/sdk`). CLI helpers live in `packages/mailwoman/lib/cli/kit/` (`useCommandTask`, `CheckList`, the command component types), the parser test harness in `packages/mailwoman/lib/test-kit/` — do not grow a new `sdk/cli`. **`@mailwoman/spatial` has no `sdk/`**: it held a pure WKT/WKB codec (now `spatial/lib/well-known-text.ts`, exported as `./well-known-text`) and an `ogrinfo` shell-out (now `spatial/lib/tools/ogr.ts`, exported as `./tools/ogr`), and acquired nothing. Those `./sdk*` subpaths were REMOVED rather than shimmed — see CHANGELOG "Unreleased".
- **This bullet has been written twice, so the third time is an edge check rather than a sentence.** The 2026-07-09 regroup moved `mailwoman/sdk/{cli,test}` out and declared the meaning restored; by 2026-09-01 `filer/lib/sdk/` and `bdc/lib/sdk/` held domain analysis again. A directory name cannot enforce itself, so `dependency-cruiser.config.mjs`'s `no-serve-package-to-build-tooling` enforces the part that matters: the browser and request-path packages (`react`, `tile-worker`, `api`, `fastify`, `mcp`, `earth`) may not reach `lib/tools/` or `lib/sdk/` in any workspace. It is scoped by PACKAGE rather than by folder name, because **`tools/` carries at least four senses here** — build tooling (`core`, `codex`, `corpus`), MCP tool definitions (`dev-mcp`), a CLI command's library half (`filer`, `mailwoman`), and product analysis (`registry`). The folder-name version of this rule was written first and produced 38 violations, every one of them correct behaviour.
- **HTTP clients extend or instantiate `APIClient`** (`@mailwoman/core/api`) rather than raw `fetch`. It carries what every fetcher otherwise re-derives: strict minimum-interval pacing (`minRequestIntervalMs`) or a `requestsPerMinute` budget, both applied downstream of the cache so a hit costs nothing; bounded retry honouring `Retry-After` (**off unless you set `retry`**); response caching (`@mailwoman/core/api/disk-storage` for an on-disk one); and error mapping to `ResourceError`, so callers branch on `error.status` / `isTransientResourceError(error)` rather than message prose. Inject `clock` and drive it with `@mailwoman/core/api/test-clocks` so timing tests never sleep. `packages/filer/lib/sdk/sec-client.ts` is the worked example; `packages/bdc/lib/sdk/client.ts` is the second, and covers what SEC didn't — a binary path (`responseType: "arraybuffer"` plus a per-request `cache: false`, which is how you turn caching off without touching `packages/core/lib/api`) and a per-minute budget. **`requestsPerMinute` does not deliver N requests per minute**: its cooldown is `60000/N` minus the gap since the last dispatch, so N alone dispatches N requests every `60/N` seconds — measured at 100/min for `requestsPerMinute: 10`. Set `minRequestIntervalMs` too (`60000/N`); that is the setting that holds the rate. **This rule binds API REQUESTS.** **API requests** — small bodies, repeated calls, rate-limited hosts — are the sites `APIClient`'s pacing, bounded retry, response caching and `ResourceError` mapping exist for; `packages/release-kit/lib/release/check-parity.ts` is the worked example of the migration, verified to produce a byte-identical verdict. **File transfers** are not: `packages/osm/lib/sdk/fetch.ts` and `packages/tiger/lib/sdk/download.ts` stream multi-gigabyte archives straight to disk, where response caching is nonsense, there is nothing to pace, and axios buffers any non-stream response type in memory. Those keep raw `fetch` and say so in place. Do not "finish the job" on them.
- **Filesystem work goes through `@mailwoman/core/fs`.** It is the one place in the tree that reaches `node:fs`; `oxlint.config.ts` refuses every `node:*` import outside `@mailwoman/core` and names the core home for each builtin in its message. Four modules: **`/readers` + `/writers`** answer promises — every reader and writer does, because no executable repository code makes a blocking filesystem call; **`/streams`** holds `openReadStream`/`openWriteStream`, which are neither, because a stream returns immediately and the work happens as the consumer pulls; **`/temporary`** owns a scratch directory (see the `mkdtemp` pitfall below). Every helper takes a `PathBuilderLike`, and where two helpers differ only in what they forgive, the name is what says which is which: `statPath` raises ENOENT where `tryStat` answers null, `removePath` raises where `removePathIfPresent` forgives, `makeDirectories` is recursive and idempotent where `makeDirectoryExclusive` raises EEXIST — and bare `mkdir` being an atomic test-and-set is how both of this repository's inter-process locks are held, so swapping one for the other would let every waiter take the lock at once. `pathExists` is the one deliberate NARROWING of a builtin: `existsSync` answers `false` for a path it could not read, and EACCES on a parent directory is not the same answer as "there is nothing here". Two ceremonies are encoded rather than repeated: every file writer creates the parent directory, and `copyFileTo`/`createSymbolicLink` clear the destination first, because `copyFile` onto a symlink writes THROUGH it (the defect that put symlinks in a publish tarball and made npm answer HTTP 415). File-DESCRIPTOR work — a partial read at an offset, a `FileHandle` held across calls — goes through `readFileRange` and `open` from `/readers`, so no file reaches past the idiom for it. `packages/repo-health/lib/checks/debt.ts`'s `synchronousFilesystemCalls` baseline is ZERO: the counter walks every tracked `.ts`/`.tsx` minus `packages/core/lib/fs/` for a builtin sync call or an import of a sync helper module, and one anywhere fails the check. One site reaches `node:fs/promises` for a reason the rule cannot see: `@mailwoman/neural`'s `tokenizer.ts` loads `readFile` through a dynamic `import(/* webpackIgnore: true */ "node:fs/promises")` so the browser bundle never meets it, and flattening that to a static `@mailwoman/core/fs/readers` pulls `#objects` and the rest of core into the client graph — which `browser-slo.test.ts` catches as an esbuild failure to resolve `fs`, and nothing else catches at all. `mailwoman/no-sync-fs-in-async` catches the regression that started all this: a synchronous call inside a function that is already `async`, which is a blocked event loop with an `await` legal on the same line. Paths themselves go through `path-ts` (`join`, `resolvePath`/`resolvePathBuilder`, `dirname`, `basename`, `extname`, `relative`, `normalize`, `isAbsolute`, `sep`), and a module's own location is `import.meta.dirname`/`import.meta.filename`; a `file:` URL that names something else converts through `@mailwoman/core/module/file-url`, and a package directory is located with `@mailwoman/core/module/resolvers`.
- **Data-root paths go through `@mailwoman/core/data-root`** — `dataRootPath("wof", "x.db")` / `mailwomanDataRoot()` (`packages/core/lib/data-root.ts`, using `path-ts` over the typed `$public` environment). `env-paths` supplies the platform default; lab checkouts provide `MAILWOMAN_DATA_ROOT` through private configuration. Never hard-code the lab path in shipped code or scripts. In docs/comments/help text reference `$MAILWOMAN_DATA_ROOT` rather than the literal. Repo/package root paths are the sibling home `@mailwoman/core/paths`; both were extracted from `core/utils` in 2026-09 when it stopped being a home and became a shelf.
- **Never hand-assemble a path into another package's install directory.** `resolve(root, "node_modules/@mailwoman/neural-weights-en-us/model.onnx")` encodes a layout its owner never agreed to: it survives a hoist, a scope rename, a `files` change and a package move by silently pointing at nothing, and the caller reads that as "the artifact is missing" rather than "I looked in the wrong place". Three blessed mechanisms replace it — `resolveModulePath("pkg/file")` / `resolvePackageDirectory("pkg")` from `@mailwoman/core/module/resolvers` (or `createRequire(import.meta.url).resolve` where `import.meta` may not exist, e.g. under the Docusaurus config loader — `docs/plugins/demo-assets/resolve.ts` explains that case in place), a real `exports` subpath on the workspace, or `dataRootPath`/path-ts `resolvePath` when what you wanted was a data-root artifact. A package's own file — a data sibling `tsc` does not emit, a script to spawn, a test fixture — is `resolvePackagePath("<package>", …)`, anchored at the package root so it names the same file from the source tree, `out/`, and a published tarball; a repository file is `repoRootPath(…)`; a module's own directory is `import.meta.dirname`, and counting `..` up from it is refused by `mailwoman/no-import-meta-dirname-walk`. Every static or dynamic import of a sibling goes through the package's `imports` map (`#eval-harness/baseline-assert` — every workspace carries `"#*"`, so the path from the package root IS the specifier, with no extension), never `import("../…")` — `mailwoman/no-import-meta-resolve` and `mailwoman/no-relative-dynamic-import` hold those lines. One trap: importing `package.json` as a JSON module makes `tsc` copy it into `out/`, where it becomes Node's package scope for the compiled tree and sends every `#` import to `out/*.ts`; read the manifest with `readLocalJSONFile(resolvePackagePath(name, "package.json"))` instead. `packages/repo-health/lib/checks/node-modules-reacharound.ts` holds the line: it walks the TypeScript AST for a `node_modules` segment inside a `join`/`resolve`/`resolvePath` argument and carries a three-entry allowlist, each with its reason.

  **The rule is not "don't use `node:path`."** Most `join`/`resolve` call sites are legitimate — scratch directories, test fixtures, a CLI `--out` flag, walking a user-supplied tree, composing under a root a caller threaded in — and banning the import would flag all of them to catch a handful. Two shapes that look like violations and are not: a LOCAL root alias derived once from `mailwomanDataRoot()` and composed from thereafter (`packages/release-kit/lib/weights/copy-weights.ts` — the concern is re-deriving the root rather than composing from it), and a probe that reads a FOREIGN project's install layout on purpose (`packages/release-kit/lib/release/smoke/clean-install.ts` — `resolveModulePath` would answer from the monorepo's graph, which is the exact thing a clean-install smoke must not consult).

- **Before writing a small utility, check whether it already has a home.** Most duplication here is not "nobody wrote it" but "the call site could not find it, or could not use it as shaped". The homes, beyond `APIClient` and `dataRootPath` above: The enforced half of this list is `HELPER_HOMES` in `oxlint.plugin.ts` (`mailwoman/prefer-home`): each row is a shape a re-typed copy cannot avoid (`toISOString().slice(0, 10)`, the literal `6371`, a generator's multiplier) with the import that replaces it, and the pre-commit hook reports a copy at commit time. When a review finds a helper typed twice, add the row; that is the durable half of the review. The detector for the shape nobody has tabled yet is `repo-health`'s `private-name-shadows-export` check: a module-private function sharing its name with a function another module exports is a copy or a collision, and a copy that stays says why behind `// repo-health-ignore private-name-shadows-export -- <reason>`.
  - `packages/core/lib/random.ts` (`@mailwoman/core/random`) — `mulberry32(seed)` and `makeLcg(seed)` as `() => number` thunks, plus the `SeededRandom` class. Sixteen files had re-typed one of these. Prefer `mulberry32` for new code; `makeLcg` exists only because its exact stream is baked into shipped corpus rows and eval splits.
  - `packages/core/lib/utils/sealed-db.ts` — `swapDatabaseIntoPlace(tmp, final)`, the atomic publish step this file specifies in prose, next to `sealDatabase` / `openBuiltDatabase`.
  - `packages/core/lib/stats.ts` (`@mailwoman/core/stats`) — `percentile` (nearest-rank, `p` in **[0, 100]**), `median`, `formatPercent`. Watch the unit: local copies elsewhere took a fraction, so a careless swap silently changes a promotion threshold.
  - `packages/core/lib/hash.ts` (`@mailwoman/core/hash`) — `sha256File` / `sha256Hex` / `md5File`. **There is no `core/utils/jsonl.ts`**, and this list named one until 2026-09-01: the module was deleted when `spliterator` replaced it, but its `./utils/jsonl` `exports` subpath outlived it by several releases, so `@mailwoman/core/utils/jsonl` was a published path that resolved to nothing (#2052). Import them from here and nowhere else: several of them were defined in `resolver-wof-sqlite/geo.ts` despite having no SQLite dependency, which is how a gazetteer BUILD step ended up taking point-in-polygon from a query backend. That coupling is gone, along with the package's `./geo` subpath.
  - `packages/match/lib/comparators.ts` — `jaro`, `jaroWinkler`, `levenshteinSimilarity`, `nameSimilarity`, `jaccard`.
  - `packages/core/lib/utils/time.ts` — `isoDate(now?)` (`YYYY-MM-DD`), `isoSeconds` (`Z` suffix, second precision) and `isoSecondsUTC` (`+00:00`, the Python manifest shape). Twenty sites had re-typed `toISOString().slice(0, 10)` before `prefer-home` reported the shape; the same rule reports an Earth radius typed outside `@mailwoman/spatial`.
  - `packages/core/lib/git.ts` (`@mailwoman/core/git`) — `gitHead`, `currentBranch`, `dirtyTrackedFiles`, `trackedFiles`: the working tree's own git state, one `runFile("git", …)` each. Seven sites had spelled `git rev-parse HEAD` through their own wrapper; the `git-state` row in `HELPER_HOMES` reports the next one.
  - `packages/core/lib/fs/writers.ts` — `changeMode` for a chmod, `writePrivateTextFile` for a secret that must be created `0600`.
  - `packages/mailwoman/lib/cli/kit/metadata.ts` — `readMailwomanManifest()`, the one read of mailwoman's own `package.json` (version, engines floor, license).
  - `@mailwoman/core/release-config` — the typed reader of `release.config.json` and `repoCommittedSoftFeedSources`; `packages/release-kit/lib/weights/weights-recipe.ts` re-exports it. A reader that lives outside a package is unreachable from one, which is how a package comes to hardcode what the config names.
  - `@mailwoman/core/data-root` — `configRootPath` beside `dataRootPath`, for anything under `$MAILWOMAN_CONFIG_ROOT`.
  - `packages/corpus/lib/adapter.ts` — `HOUSE_NUMBER_PREFIX` + `splitStreetLine(line)`, the house-number/street split every US CSV adapter uses.

  Two leaf packages deliberately keep local copies rather than take a dependency: `nuts-lookup` and `timezone-lookup` re-implement the ray cast because reaching `@mailwoman/spatial` would pull `@mailwoman/core`'s ~11 MB of shipped data behind it, and `packages/match/gbt.test.ts` keeps an LCG for the same reason. Each says so in place. When you find a duplicate, price the dependency before moving it — the answer is sometimes "leave it, and write down why".

  **When two copies must agree, share the FUNCTION — sharing the constants proves nothing.** Matched literals and a "keep in lockstep" comment hold only the part of a interface a constant can express; the code diverges at the points it cannot — which field a term reads, whether a result is written back — and a reviewer comparing the constants finds them identical every time. Extract the function into a platform-free module and have both sides call it; `primary-preference.ts` and `proximity-rerank.ts` are the two that do.

  **A duplicate can indicate a bug in the shared tool.** When you meet one, the useful question is not "why didn't they know" — it is **"what was wrong with the shared thing?"** Sometimes nothing. Common causes include being too slow, async against a sync caller, or shaped for a different call site. Fix that and the duplicates collapse on their own; delete them without fixing it and they grow back.

- **A test that matches rendered output strips ANSI first.** `stripAnsi` from `mailwoman/cli-kit` is the one place that does it. chalk's level follows `FORCE_COLOR`, which several terminals and `tmux`/`direnv` setups set and nothing in this repository clears. Therefore, a raw capture has two possible contents and a test that matches one of them passes or fails by the environment it ran in. `\s+` is the tell: chalk emits a dim/reset pair around a label, so `/system\s+us/` cannot span the reset between the label and its value, and `FORCE_COLOR=3 yarn vitest run …/static.test.ts` failed while CI stayed green. A NEGATIVE assertion is the worse case — `expect(stdout).not.toMatch(/\s+at\s/)` passes because an escape broke the pattern rather than because the stack is absent.
- **A pty test must force Ink interactive.** `render()` resolves `interactive` from `is-in-ci` and `stdout.isTTY` (`resolveInteractiveOption`), and CI detection wins over a real TTY — so under GitHub Actions a probe driven through `script` renders NON-interactively, and a non-interactive Ink writes only the final frame at unmount. A test that reads a component's edit history out of the pty capture then finds exactly one frame: the last one, with the correct value. Pass `render(node, { interactive: true })` in the probe — `packages/mailwoman/lib/debug-view/test/input-probe.ts` is the worked example. The suppression costs wall-clock too: with nothing written before unmount, a `READY` wait burns its whole timeout on every case (`input.pty.test.ts`, 42s → 2.8s once forced).

- The **bare-import + subpath-import cycle** is a fragility surface. When a test file imports `@mailwoman/core` bare and a subpath, Vite can leave the bare re-exports unbound while the two module graphs interleave — base classes at the far side of the barrel evaluate as `undefined`. (`packages/core/lib/resources/libpostal.ts` had a top-level `await readdir` that contributed until #481 made it a lazy `getAvailableLanguages()` getter; the cycle turned out to be **structural** — Vite's bare/subpath interleaving — not TLA-driven, so it persists after the TLA removal.) Workaround: a side-effect `import "@mailwoman/core"` at the top of the affected test file forces full init first. Full fix = import-graph hygiene (tracked on #481).

### Moving a workspace

`tsc -b`, `yarn lint` and `yarn typecheck:tests` all pass over a half-moved tree. The paths that break are STRINGS the compiler never reads, each read at runtime by something that treats absence as a NEGATIVE ANSWER rather than an error: a `.husky/` regex that stops matching, a `run:` block, a CLI flag default, a test skip-guard. So after a move, sweep for QUOTED literals whose first path segment is a workspace name — not for imports, which the compiler already checks. Two shapes look stale and are not: a data-root-relative path (`data-bundles.ts`'s `localPath`, paired with a `remotePath`), and a package specifier — `import("mailwoman/gazetteer-pipeline")` is the `mailwoman` package's subpath export rather than a directory, and prefixing it with `packages/` breaks it. CodeQL re-raises every existing alert at its new path and dismissals do not follow the file; re-dismiss after merge, and do not let the count block the merge — the ruleset requires the `test` context. The regroup that established this is in [`docs/records/retrospectives/agents-md-receipts.mdx`](./docs/records/retrospectives/agents-md-receipts.mdx).

## Database / inline SQL

A database is a readonly artifact: build it, move the previous version to a temp directory, then move the new one into place, so the file on disk stays consistent even when the build fails halfway. Kysely over `node:sqlite` is the only supported connector, and table DDL goes through its schema-builder rather than raw `db.exec("CREATE TABLE …")`. The full idiom, and the inline SQL that stays raw on purpose, live in [`packages/sqlite/AGENTS.md`](./packages/sqlite/AGENTS.md).

## When in doubt

Read the workspace-local docstrings before changing infrastructure files. The headers in `packages/release-kit/lib/**`, `packages/repo-health/lib/**`, `.release-it.json`, and `.github/workflows/*.yml` explain why each piece exists. There is no root `scripts/` directory: an executable enters through a registry (`@mailwoman/release-kit`, `@mailwoman/repo-health`), a `mailwoman` command, or a `packages/mailwoman/lib/dev-tools/*.run.ts` measurement, and the `no-root-scripts` health check refuses a path that names one. If a file's purpose isn't documented inline and you're about to touch it, add the docstring as part of your change — future-you (or future-claude) will thank you.

**A reader that can return a PARTIAL result must say what it got, or throw.** Every failure of this shape returns a well-formed wrong answer that is indistinguishable from a real absence — and absence is the result the question seeks, so the wrong answer arrives looking like a discovery. Three rules follow. Prefer a reader that ERRORS on a requested-but-missing column over one that omits it. When a projection drops a field, the consumer that needed it gets `unchanged` rather than a type error, so carry the whole payload or name what you dropped. And `?? 0`, optional chaining and a bare `.filter()` all convert _"I could not read this"_ into _"there is none of it"_ — at a measurement boundary that is a lie, and the cheap insurance is to re-measure a surprising ABSENCE by a second path before reporting it. The seven shipped instances that produced these rules are in [`docs/records/retrospectives/agents-md-receipts.mdx`](./docs/records/retrospectives/agents-md-receipts.mdx).

**The defects that survive review live in the input tail.** Reading code tells you what it does on the inputs you are imagining, which is exactly the set that already works: a ReDoS that needs tab characters, a leading zero dropped only for base cells 0–7, a quote-blind CSV splitter against sources that happen to carry no embedded newline, a quadratic scan whose every existing caller happened to be chunk-bounded. So when a change rests on a claim about data or scale — _this source has no quoted newlines_, _this path is fast enough now_, _this artifact is stale_ — spend the one command that determines the result, and put the number in the docstring afterwards: `27,405 ms → 175 ms on 8 MB` tells the next reader whether the constraint still binds; "this is slow" does not.

Corollary for the docstring you write afterwards: if a measurement produced the conclusion, put the number in. `27,405 ms → 175 ms on 8 MB` tells the next reader whether the constraint still binds. "This is slow" does not.

That corollary covers a MEASUREMENT THAT STILL BINDS, and nothing else. A comment states the invariant, the non-obvious constraint, or the reason an obvious implementation is unsafe; the incident that produced it goes in the commit message, the PR, or the runbook page. **A date, a version number, or a list of affected packages inside a comment is the tell** — strike it and see whether the sentence still stands; if it does not, the sentence was history.

**A threshold fitted to a failing population measures the defect producing the failures rather than the quantity it names.** A separation drawn over the rows that are currently wrong is evidence about their shared cause, and where that cause is the defect you are already fixing, the threshold measures your own bug rather than the quantity it names. No rate is claimed here — check it per case, which is what the three steps below are for. So before registering a rule: fix the cheapest candidate cause and re-measure; ask whether the separating quantity is CAUSED by that cause; and read the rows the rule would newly refuse, which is where a fitted threshold shows its real precision. The same reflex catches two neighbours — a finding that names three countries is a hypothesis about a global distribution until the statistic is computed for all of them, and a negative control built by REMOVING the right answer is complete only under the identity relation the data has rather than the one the join used. The receipts are in [`docs/records/retrospectives/agents-md-receipts.mdx`](./docs/records/retrospectives/agents-md-receipts.mdx).

### Acronym casing in identifiers

Acronyms are capitalized as whole camelCase components: `createWOFResolver`, `parseJSON`, `readID`, `fetchOSM`, `WOFSQLitePlaceLookup`, `modelURL`. Not `createWofResolver` / `parseJson` / `readId`. This applies to TS/TSX identifiers (functions, classes, types, interfaces, object properties) and the code examples in living reference docs. It does **not** touch:

- **`snake_case`** — DB columns and wire keys (`parent_id`, `place_id`, `name_key`) stay as-is; they're string interfaces, and the convention is camelCase-only by construction.
- **External library names** — match the dependency's own casing (`HttpStatusCode` from axios, `createQueryId`/`createWithSql` from kysely, `sqlite-wasm`).
- **CLI flag props** — the schema adapter binds a kebab flag to a lowercase-acronym prop (`--resolve-db` → `resolveDB`), so those specific schema keys must match its derivation. Result-read fields and domain properties (`result.placeID`) still follow the convention.
- **Dated historical records** — `docs/records/evals/`, `reviews/`, postmortems, and phase docs are point-in-time; don't rewrite their acronyms.

`yarn lint` enforces this via `sister-software/no-title-case-acronym` from `@sister.software/oxlint-config`. It reads the AST, so it sees exported declarations, the MEMBERS of exported interfaces/classes/enums, and the exported half of a re-export — the standalone script it replaced matched `^export <keyword> <name>` and missed every member. Configure it in `oxlint.config.ts`: `extraAcronyms` layers this project's vocabulary onto the shipped list, `ignoreNames` exempts names whose casing is not ours. Prefer a scoped `// oxlint-disable-next-line sister-software/no-title-case-acronym -- <reason>` at the one site that needs it; a config entry silently covers every future declaration of that name. When adding an acronym, cap the whole component.
